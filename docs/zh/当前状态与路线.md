## 1.1 Claude Code 学习后的执行主线

本轮已把本地 `claude_code/` 源码学习结果收敛为 [Claude Code 学习落地计划.md](./Claude%20Code%20学习落地计划.md)。后续执行主线如下：

- **PromptEnvelope 产品化**：系统级提示词按 section 组装、缓存、落盘和审计，不再是不可追踪的大字符串。
- **CapabilityManifest 分层**：direct tools、deferred tools、MCP、skills、subagents、modes、verification 都要以模型可理解、runtime 可强制的形式进入上下文。
- **ToolObservation 统一**：每次工具调用同时产出模型 observation、user_progress 和 raw evidence，失败进入 repair/replan/ask/stop 循环。
- **DelegationContract 强化**：子 worker brief 必须包含目标、背景、已知事实、作用域、权限、期望输出和验证预期；不能把理解外包给子 worker。
- **独立验证契约**：非平凡实现不能由实现者自封 PASS，ReviewAgent/MergeGate/Runtime OS gate 必须消费独立验证证据。
- **ContextSnapshot 升级**：压缩和 resume 必须保留目标、决策、文件触点、验证结果、失败证据、风险和下一步，而不是只保存自然语言摘要。
- **AgentRoleContract 路由化**：借鉴 opencode 一类多角色运行时的方向，但不只按命令硬切。Asteria 将模型路由与 deadline 绑定到 GoalSpecAgent、PlannerAgent、CoderAgent、DebugAgent、ReviewAgent、ResearchAgent、ChatAgent 等角色契约，再叠加任务类型、风险、capability feedback 和 provider_route_strategy。这样既保留模型主导循环，也让 Runtime 能审计每次调用为什么用这个 tier、deadline 和 fallback 策略。
- **文档收敛**：当前事实看本文件，学习落地看 Claude Code 学习落地计划，长期设计看模型主导运行时设计；已吸收的调研/复盘进入 archive。

这些改动必须保留 Asteria 原有优势：Runtime OS evidence-first、candidate workspace isolation、promotion gate、多模型 profile、JSON/JSONL MVP、user_progress 主线和 hard-stop DecisionPoint。

## 1.2 2026-05-24 Studio product route correction

Studio's next phase changes from "one interface that mixes user chat and backend observability" to:

```text
Product Workspace + Ops / Debug Console
```

Normal product users should not perceive backend objects such as `run/status/evidence/model_route/goal_policy`. Users need their goals understood, tasks advanced, results delivered, and approvals requested only when necessary. Backend state, evidence chains, model routes, and failure diagnosis belong in a dedicated Ops Console explained by an AI Debug Agent.

Upcoming Studio development:

1. Product Workspace defaults to Auto input and shows only natural answers, user-level progress, permission confirmations, and final deliverables.
2. Backend observability moves out of the main thread into Ops Console: Inspector, Evidence Explorer, run detail, route timeline, goal_policy, and DecisionPoint.
3. Add an AI Debug Agent dedicated to backend/debug questions.
4. If a normal user asks "how is it going", answer in terms of the user's goal progress.
5. Add regression tests to prevent backend fields from leaking into the normal user thread.

## 2. 当前阶段

当前项目处于：

```text
编排式 Asteria Runtime OS 阶段
```

产品能力描述是：

```text
长任务自主开发 Runtime
```

也就是说，当前重点不是继续堆聊天能力或 dashboard，而是把系统打造成一个可编排、可隔离、可恢复、可审计、可控成本的本地优先自主开发运行时。

## 4. 当前主要差距

现在最大差距不再是“有没有命令”，而是 Runtime OS 的可靠性和可解释性：

- TaskGraph 仍在从线性 task board 过渡到更明确的 DAG 执行模型。
- WorkerInvocation 与 Coordinator 边界已完成主要下沉；后续重点从“继续拆 ExecuteCommand”转为“防止执行细节回流命令层，并把候选工作区、上下文裁剪和报告证据继续做厚”。
- 候选工作区已有隔离能力和 merge gate，但 Git worktree/candidate branch 形态仍需增强。
- promotion queue 已有 list/approve/reject/retry/discard 控制面，并会把 pending/blocked/failed/discarded 状态持久化给报告和 session context 消费；剩余工作是让人工审批默认策略和 release 风险阈值更产品化。
- promotion release risk 已有 policy 化阈值：`promotion.release_blocking_statuses`、`max_pending_release_promotions`、`max_blocked_release_promotions` 会进入 `gate-status --json`，默认 unresolved promotion 不允许 release-ready。
- ContextPackage 已明确区分 read scope、write scope、证据 refs 与最近失败；后续继续把这些分层信号用于 Planner 和模型路由，避免 worker 默认吃全量历史。
- capability profile 已能吸收模型调用、worker、runtime request、validation pass rate 与 merge gate block 信号；`ContextLoader` 已把 actionable capability feedback 注入 Planner runtime context，Planner 会在 task notes 中保留“收窄 scope / 复核 route / 加强验证”等提示；RuntimeProfile route selection 已开始消费 route guidance，对弱 medium/cheap 路线升级到 stronger tier，并把相关 guidance 放入 worker runtime context。下一步需要扩大实战数据量，观察这些信号对成本和成功率的真实影响。
- acceptance gate 已经覆盖 Runtime OS 证据，当前已有 release-ready 基线；`gate-status --json` 已增加按 git 变更规模生成的 `validation_recommendation`，用于提示 targeted、core subset 或 full gray/core 验证路线；后续仍要保持 core gate 复跑，避免单次通过被误当成长期稳定性证明。
- `gate-status --json` 现在也输出 `promotion_release_risks`，如果 candidate promotion queue 仍有 `queued`、`pending_manual_approval`、`approved`、`blocked` 或 `promotion_failed` 状态，会降为 blocked，避免在未解决候选合并风险时扩大灰度。
- 文档/文本只写任务的 verification 生成已收敛；实现类小任务已补 artifact id 并发分配、DebugAgent 常见包裹 JSON 解析、Planner 既有 artifact scope 收敛和单引号 planned verification 抽取护栏。最新 7 个灰度场景批次已全部通过（文件产出、多文件工具、测试修复、文档只写、小 CLI 工具、受控重构、runtime request resume），平均 1.0 repair/field场景，所有场景 within_budget、review 0.9。剩余重点是继续扩大批次数和复杂度范围，观察高复杂度任务的 repair 次数是否稳定收敛。
- 系统已有本地 wheel 与灰度 runbook 基线；后续仍需在真实小任务批次中验证用户能否按 runbook 独立定位失败。
- 文档刚完成主线收敛，后续新增能力必须先更新当前状态和验收入口，避免再次变成开发日志堆叠。

## 5. 近期研发优先级

P0：模型主导 Agent Harness。

- 下一阶段从“状态机严格驱动模型”调整为“模型主导工作循环，Runtime 提供能力环境和护栏”。详细设计见 [Asteria 模型主导运行时设计.md](./Asteria%20模型主导运行时设计.md)。
- 角色化路由是模型主导 Harness 的前置契约：模型可以选择下一步模式和工具，但每次调用必须挂在角色职责、deadline、budget、权限和 evidence 上。不要只靠代码 if/else，也不要只按 CLI 命令切分；命令是用户入口，角色契约才是运行时调度单位。
- PromptEnvelope / CapabilityManifest 已进入 plan、execute、debug、review 和 Runtime OS gate；真实模型 prompt 会直接接收 PromptEnvelope section 摘要、CapabilityManifest 和最近 ToolObservation。ToolObservation 已开始统一 raw evidence、模型 observation 和 user_progress 三线。
- `goal_spec`、`task_plan`、`task_plan_eval` 和 `final_answer` 继续作为可审计产物保留，但不能把格式不完美当成用户目标失败；优先走补全、提取、最小摘要 fallback 或 repair。
- Runtime 的主职责是构建 prompt envelope、能力 manifest、权限/沙箱/预算边界、工具 observation 和 user_progress，而不是替模型写死完整执行路线。
- 模型应在 mode、tool、MCP、skill、subagent 和验证能力之间自主选择下一步；每次工具结果都回灌模型形成下一轮判断。
- DelegationContract 下一步重点是把 blocking policy 从 execute worker 扩展到 review/debug 替换路径和后续 subagent 调度，并把阻断口径纳入 Runtime OS release gate。
- Studio 和 benchmark 的验收重点改为“是否呈现完整 agent 工作过程和自然语言结论”，而不是只检查后台 JSON/channel 是否齐全。

### 5.0 90% 完成度门槛

在开启打包部署测试前，项目应达到约 90% 的 Runtime OS alpha 完成度。判定标准：

- release gate 不只检查 acceptance report，还必须阻断 unresolved candidate promotion：`pending_manual_approval`、`approved`、`blocked`、`promotion_failed` 都不能进入 release-ready。
- `gate-status --json` 必须同时反映 route environment、route guidance、gray/core gate 和按变更规模推荐的验证路线；如果 capability profile 标记 route blocked，不能继续扩大真实灰度。
- capability profile 的反馈必须至少进入 Planner 和控制面；自动切换模型可以后置，但路线风险不能只停留在报告文本里。
- long-run plan 必须优先处理 pending decision、unresolved candidate promotion、blocked route guidance 和 failed acceptance，不能在这些风险存在时继续扩大执行预算。
- ContextPackage 必须持续保持 read scope、write scope、evidence scope、recent failures 分层，避免复杂任务默认吃全量历史。
- candidate workspace 必须证明失败候选、promotion failure、discard 不污染主工作区。
- full `pytest`、`ruff`、`mypy`、`package-check`、core acceptance gate 必须稳定通过；进入部署测试前再跑真实 `real-model-gate` 和完整 gray suite。
- 灰度 runbook 必须覆盖安装、配置、升级、回滚、自检、失败收集和暂停/恢复。

P0：Runtime OS 发布门槛继续硬化。

- 继续扩展 TaskGraph、WorkerInvocation、MergeGate、ContextMount 的真实 core release evidence。
- 确保 capability report、weekly report 和 acceptance gate 的 Runtime OS 判断保持一致。
- Runtime OS gate 的证据口径必须覆盖 ContextPackage 切片、sandbox backend、runtime request resume、merge gate block、worker validation 结果、DelegationContract 阻断/例外和 ToolObservation failure next_hint 消费。
- Runtime OS gate / acceptance gate 已开始检查 candidate promotion release risks；后续继续把 release 风险阈值产品化。
- 保持 full core acceptance 作为发布门槛，开发期优先跑场景子集和 failed-only。

P0：产品化灰度前置条件。

- 维持真实 `core` suite 与 `acceptance-gate` 的 release-ready 基线；gray suite 只能作为进入 core 的候选门槛，不能替代发布门槛。
- 把 `gate-status --json` 作为灰度入口的单一状态判断，明确 blocked / conditional / release_ready 的用户可见含义。
- 固化可重复安装包：本地 wheel、版本号、默认配置模板、示例 `.asteria/` 初始化结果、安装后 `version/package-check/doctor/gate-status` 自检和卸载说明。
- 在干净目录或新虚拟环境中执行首轮安装后自检样例，并保存 `version/package-check/doctor/gate-status/model-check` 输出作为灰度证据。
- 成本优先灰度阶段 strong route 先用 `glm-4.7` 消耗免费 token 额度；额度耗尽、质量不足或发布门槛复验时切到 `glm-5.1`。
- 明确灰度运行边界：默认只允许本地文件系统 + JSON/JSONL 状态；不启用破坏性 shell；不读取 protected paths；真实 API key 只从环境变量或 secret 注入。
- 建立灰度 runbook：安装、配置 GLM/MiniMax 路由、运行 gate、运行 gray/core acceptance、查看报告、暂停/恢复、故障收集和回滚。
- 将首轮灰度限定为少量真实开发任务：文件产出、多文件小工具、测试修复、文档更新和受控重构；暂不开放长时间无限制自动推进。
- 首轮小真实任务批次维护在 [小真实任务灰度批次.md](./小真实任务灰度批次.md)，默认 12 个任务；`gray-run` 统一使用 `--max-iterations 3 --max-tasks-per-iteration 1` 并内部关闭 research，批次后再决定是否翻转人工审批默认策略。
- 继续收敛实现类小任务：扩大真实小任务批次数，重点观察 action 生成、跨 run 依赖、验收范围扩张和 repair/replan 稳定性。

P0：真实 provider 流式体验与 deadline 产品化。

- timeout 不能只靠外层 subprocess 兜底，必须产品化为 suite -> scenario -> run/review/recovery -> provider call 的统一 deadline budget。
- 灰度默认先收紧最坏路径：真实 acceptance 默认 1 次 run attempt、1 次模型 retry、单场景 600 秒；provider call、review 和 recovery 默认不吃满场景预算。本机 API key/route 可以放在 `C:\Users\Administrator\.asteria\model.routes.local.ps1`，runtime 自动读取但不导出、不提交，当前 shell 环境变量优先。
- provider adapter 已支持受 flag/env 控制的流式调用和 telemetry；真实验收已抽出统一 `DeadlineBudget`，从 scenario budget 派生 run/review/recovery/provider/stream idle 子预算，并写入 acceptance/smoke 证据。provider deadline 同时约束流式和非流式调用，stream idle timeout 只约束流式 chunk 间隔。下一步要把流式 chunk 从 adapter 内部证据推进到 runtime 用户可见进度和取消语义。
- `provider_route_strategy.strong_goal_spec` 已进入 policy 契约，用来产品化判定 strong `goal_spec` 路由何时继续使用 primary GLM、何时允许 cost-saver、何时 retry/downgrade、何时阻断小真实任务灰度；控制面通过 `route_guidance.provider_route_strategy` 暴露当前判定。
- `provider_route_strategy.strong_goal_spec` 已开始影响执行路径：`PlanCommand` 会为 GoalSpec 生成 `goal_spec_execution_plan`，健康时继续 strong，transient 不稳时可 retry/downgrade，低风险文档类目标可降级到 medium，并通过 `model_route_selected` event 和 gray summary 记录；release gate 和小真实任务批次仍然要求 route guidance healthy。
- `gray` / `gray-run --dry-run` 会把 `route_guidance_blocked` 的具体原因和 `provider_route_strategy` 推荐动作前置到 plan summary，避免用户只看到泛化的“未 ready”。
- CLI 长任务应展示低噪声进度：当前 phase、模型 route、最近 token/chunk 心跳、最近 artifact/evidence 写入时间和剩余 deadline；避免用户等待很久却看不到系统是否还活着。
- gray/release gate 应逐步要求真实 strong/medium route 具备流式 evidence，否则只能进入受限灰度，不能作为 release-ready 证据。

P0：命令暴露面产品化。

- 当前命令数量已经能覆盖开发、灰度、验收和运维，但能力仍偏散；下一步按 Claude Code 式“少入口、多模式、强工作流”重构控制面，不把内部命令原样暴露给最终用户。
- 普通用户主线冻结为 `init -> goal/run -> status -> resume -> review -> accept`：用户表达目标、查看进度、处理阻塞、审查结果和接受候选，不需要理解 `execute/debug/acceptance-gate` 等内部步骤。CLI 顶层 help 已把这些命令放在 Start 产品工作流中，`run` 继续作为 `goal` 的兼容别名。
- 维护者主线冻结为 `doctor -> gate -> gray -> evidence-bundle`：`gate` 默认只读串联 `version/package-check/doctor/gate-status`，`gate --stage release` 串联发布前 `ruff/mypy/pytest/acceptance-gate` 重检查，`gray` 承载真实 provider 放量前的 readiness/rollout plan。
- `real-model-smoke`、`real-model-acceptance`、`acceptance-gate`、`capability-report`、`promotions`、`plugins` 等保留为专家/内部入口，但默认 help、README 和 Studio 主屏不应把它们当普通用户路径。
- 命令暴露面收敛计划维护在 [命令暴露面收敛计划.md](./命令暴露面收敛计划.md)：入口按用户旅程、维护者旅程和内部能力层组织；新增命令前必须证明它是新的用户意图，而不是现有 workflow 的一个 stage、子动作、JSON 字段或 report section。
- 后续控制面输出要从“命令结果列表”升级为“结论、阻断原因、证据链、下一步动作”：失败 observation 必须映射到 diagnose/repair/replan/ask/stop，而不是把 stdout/stderr 扔给用户。

P0.5：Alpha dogfooding 与运营证据闭环。

- 可以开始规划把 Asteria 打包成 alpha 产品，在真实外部项目中受控使用，并把运行痕迹反向用于改进 Asteria 本体。
- 最小闭环是：发布 alpha 包 -> 用户在真实项目执行小任务 -> 导出脱敏诊断包 -> Codex/维护者分析 -> 生成 Asteria 改进任务和新增验收场景。
- 诊断包必须默认只读、脱敏、可审计；不得包含 API key、`.env`、`secrets/`、私钥、证书或未授权源码全文。
- 运营视图应优先展示真实过程证据：timeline、task/worker 状态、candidate diff、promotion queue、验证结果、模型路由、成本、阻塞决策和用户最终处理动作。
- 可视化的目标不是先做漂亮 dashboard，而是帮助用户判断“我的真实体验”和“系统记录”是否一致，识别报告误导、证据缺口和产品体验问题。
- Asteria Studio 已进入 P0 规划：它作为 `studio/` 独立本地 Web 控制台消费 runtime CLI JSON 和 `.asteria/` evidence，不进入 runtime 内核。第一版只读展示 overview、doctor、package-check、gate-status、runs、model routes，并提供 evidence bundle 导出。
- 2026-05-20 已完成 opencode、Claude Code、Codex 的展示调研，Studio 展示方向收敛为“任务驾驶舱 + 证据 Inspector”，详见 [Asteria Studio 竞品调研与展示设计.md](./archive/Asteria%20Studio%20竞品调研与展示设计.md)。本轮实现优先把 gate/route/runtime readiness、session timeline、selected evidence/artifact 和 recent files 放到同一工作台，避免退化成普通聊天页或营销 dashboard。
- dogfooding 分析结果应进入 roadmap：command surface 收敛、deadline 体系、candidate worktree/promotion queue、报告口径、acceptance 场景、route guidance 和文档修正。

P1：动态多智能体协作能力补足。

- 不走 unrestricted agent chatroom，而是继续把 WorkerInvocation / AgentRunGraph 做成受控子 worker 协作机制。
- 已完成基础策略与落盘图；机制细节维护在 [架构设计.md](./架构设计.md)、[数据模型.md](./数据模型.md) 和 [运行命令.md](./运行命令.md)。
- 下一步补协作协议：子 worker 产物互不污染，ReviewAgent 汇总差异和冲突，DebugAgent 可针对失败 child worker 重试或替换路线，最终由 merge gate/promotion queue 统一合并。
- AgentRunGraph 的 `collaboration_summary` 已显式记录协作协议：写入 worker 使用独立 candidate workspace，ReviewAgent 汇总 child diff/conflict/release risk，DebugAgent 基于失败 evidence 重试或替换 child worker，最终由 merge gate 和 promotion queue 统一合并。
- 长期大规模“堆料”能力只允许在只读、检索、生成候选资料、可丢弃草稿等低风险任务上放大；上百/上千 worker 需要队列化调度、分片 context、全局预算硬停、速率限制和采样汇总，不能直接套用代码写入 worker。
- 下一轮实现顺序应先落 ReviewAgent child diff/conflict 汇总，再落 DebugAgent 对失败 child worker 的替换/重试，最后把 Planner 的 worker 数量策略与 capability profile 和 write-scope 风险更紧地绑定。

P1：候选工作区升级。

- 有 git 仓库且 tracked 文件干净时优先使用 Git worktree/candidate branch。
- 无 git 时 fallback 到复制候选目录。
- 未跟踪过程产物不应阻止 worktree；tracked dirty 文件必须降级或停下提示风险。
- RuntimeProfile.sandbox_profile 与 CandidateWorkspace 必须使用同一套 backend selector，并记录选择原因。
- MergeGate 和 Runtime OS gate 必须继续证明失败候选、promotion failure 和 discard 不会污染主工作区。
- promotion queue 已进入可操作控制面；`status`、`sessions --context`、`run` final report、weekly/capability Runtime OS evidence 已开始共享 candidate promotion 计数口径。下一步重点是评估是否默认启用人工审批模式，并把 release gate 的 promotion 风险阈值显式化。
- 当前默认仍保持自动 promotion 后记录队列，避免过早改变用户写入体验；是否启用 `promotion.manual_approval_default=true` 应在下一批真实小任务和 core gate 后再做 DecisionPoint。

P1：执行命令层瘦身后的回归护栏。

- 新增执行能力时优先挂到 `ExecutionCoordinator`、`WorkerRunner`、`TaskAttemptRunner`、`ExecutionEvidenceSink` 或对应 gateway/finalizer，不在 `ExecuteCommand` 里重新拼工具、候选晋升、阻塞或收尾细节。
- Planner 生成的 `allowed_tools` 必须和工具注册表中的安全只读/写入工具保持一致；gray suite 的 `gray_file_artifact` 已证明漏放安全只读工具会导致候选产物无法晋升。
- 每次较大执行边界改动后至少跑 offline gate、真实 `real-model-gate`、完整 gray suite 和 core acceptance gate；gray 只能证明真实路由和典型路径，core gate 仍是 Runtime OS 发布门槛。

P1：工程化扩展点、插件和日志体系。

- 参考 Claude Code/opencode/Codex 一类工程化 agent runtime 的共同方向：核心执行流必须有稳定生命周期事件、结构化日志、受控扩展点和明确安全边界，而不是把 agent 串联写死在命令函数里。
- 工程化横切能力的主文档是 [工程化体系.md](./工程化体系.md)：它把日志、权限、用户/身份、配置、hooks、skills、plugins、MCP、诊断导出和控制面放到同一套约束里。
- `RuntimeHookManager` 与 `runtime_hooks.jsonl` 是插件体系前的内部 hook 层，覆盖 worker/tool 的 `before/after/error` 生命周期事件；默认观测型，handler 失败只记录 `runtime_hook_handler_failed`，不破坏主运行。
- 当前推进顺序：先补 `HookPolicy`、`PluginManifest` schema、启停/权限声明和日志脱敏；再补只读 control surface、hook handler 超时、版本兼容；最后才开放外部插件执行。
- Skills 与 MCP 不应绕过核心 runtime：skills 提供领域工作流和模板，MCP 作为 source/tool/evidence/report adapter 接入；两者都必须经过权限、预算、schema、日志和验证门禁。
- 插件只能通过 runtime policy、预算、schema、protected paths 和 audit log 进入系统。`hooks.plugins_enabled=false` 时，manifest 可以被校验和报告，但不得注册 executable handler；公开插件市场属于后置能力，不是当前 alpha 阻塞项。

P1：工程治理与技术债控制。

- 工程治理主文档是 [工程治理体系.md](./工程治理体系.md)，用于把 ADR/RFC、公共契约、schema 兼容、迁移、错误分类、feature/capability flag、golden trace、发布分级、deprecation、威胁模型和供应链治理制度化。
- 下一步优先建立 ADR/RFC 目录和模板，并为 JSON/JSONL 优先、candidate workspace isolation、插件执行阶段、MCP adapter 边界等长期决策补 ADR。
- `ErrorTaxonomy` 应进入 blocked evidence、doctor、gate-status、capability profile 和 final report，避免用户只看到 traceback 或模糊 blocked。
- `.asteria/` 状态、policy、hook event、plugin manifest、capability profile 的 schema 演进必须补 migration registry，不再依赖零散 loader 补默认值。
- Feature flag 控制功能启停，capability flag 描述当前环境能力；gate/report 必须同时显示二者，避免“开关打开但环境不支持”。
- Golden trace 契约测试应覆盖文档只写任务、多文件小工具、merge gate block、runtime request resume、promotion failure 等标准轨迹，用来防止重构后行为漂移。

P2：体验和可读性。

- 优先增强 CLI report、weekly report、acceptance report。
- Dashboard 只有在 CLI 报告、Runtime OS evidence、handoff/resume 稳定后再做。

## 6. 文档维护规则

- `docs/zh` 是主事实源。
- `docs/en` 是辅助参考，除非明确同步，否则不能作为当前阶段判断依据。
- `docs/zh/archive` 是历史参考，不参与当前实现决策。
- `AGENTS.md` 只保存高优先级、短而硬的项目规则；详细计划必须链接到本文档。
- 新增重大能力时，同时更新本文档的已完成基线、当前差距或近期优先级。
