# 当前状态与路线

更新时间：2026-06-03

本文是 Asteria 当前阶段的事实入口。进入开发前先读根目录 `AGENTS.md`，再读本文；需要展开设计时再读 `docs/zh/文档导航.md` 中列出的专题文档。

本文只保留当前事实、有效架构、剩余差距和下一步优先级。历史流水账、旧验证次数、旧 release gate 记录和已经完成的阶段计划不再保留。

## 1. 当前阶段

Asteria 当前处于：

```text
模型主导的 Asteria Runtime OS 收口阶段
```

产品目标是：

```text
本地优先、可恢复、可审计、可控成本的长任务自主开发运行时。
```

核心原则：

- 模型负责在能力边界内判断下一步。
- Runtime 负责权限、预算、schema、上下文、候选工作区、证据、恢复和 gate。
- Gate 采用适应性分层：低风险探索、readonly、fake-path planner 保持灵活，只做轻量 trace；写入主工作区、promotion、merge、rollback、远程 push、真实 provider 放量和发布验收等风险边界才强 gate。详见 `docs/zh/adr/0004-adaptive-gates-preserve-agent-flexibility.md`。
- 控制面遵守 Active Next Step 原则：用户和模型默认只看到当前可执行的下一步；历史失败必须分类为 active、superseded、historical 或 maintainer-only，不能继续驱动默认 `recommended_actions`。新增 gate 前必须说明风险边界、恢复动作和降级路径，避免为了处理模型宽泛回答而不断累积代码分支。详见 `docs/zh/adr/0005-active-next-step-over-rule-accumulation.md`。
- 主执行路径遵守 Fast Path / Tiered Review / Context Slimming 原则：简单文档、单文件、小修复任务默认走 medium/deterministic 和瘦身上下文；strong goal_spec、strong review、完整 raw evidence 只在高风险、验证失败、发布验收或用户明确要求时升级。详见 `docs/zh/adr/0008-fast-path-tiered-review-and-context-slimming.md`。
- CLI、Studio、报告消费同一套 `.asteria/` evidence，不各自发明状态。
- 固定 validation suite 是回归健康信号，不等同于长期自主能力完成。

## 2. 已落地能力

### Runtime OS 基线

- `init`、`plan/run`、`execute`、`status`、`debug`、`replan`、`review`、`accept`、`gate-status`、`validation` 等主入口可用。
- `.asteria/` 持久化 run、task、model call、worker、runtime profile、context mount、task execution evidence、validation、review、final report 等对象。
- Candidate workspace、merge gate、promotion queue 和 protected path policy 已作为写入边界的一部分。

### 模型可见能力

- PromptEnvelope、ContextEnvelope、CapabilityManifest、AgentRoleContract 已进入模型调用证据。
- ModelToolSurfaceAdapter 已把模型侧 `read/list/search/edit/shell/test/todo` 原语映射到内部 registry，并保留 `model_tool_name` 审计字段。
- Tool、MCP、Skill、subagent 分离执行，但复用 capability decision evidence。
- 任务级 capability catalog 已记录 visible / selected / skipped / blocked 和原因。
- ContextBudgetMeter v2 已记录 request-level context estimate、context window ratio、section 归因、重复内容信号、compact boundary、文件级 hash/diff refs 和 subagent child context snapshot。

### Agent Harness 循环契约

`AgentLoopDecision` 已是稳定 schema。模型下一步动作限定为：

```text
tool | subagent | repair | replan | ask | stop
```

每个 action 必须携带：

- `reason`
- `target_task_id`
- `capability_ref`
- `expected_observation`
- `risk`
- `budget_hint`
- `evidence_refs`

当前闭环 evidence：

- `agent_loop_decisions.jsonl`：模型或 Runtime 代写的下一步决策。
- `agent_loop_execution_results.jsonl`：Runtime 对决策的分派结果。
- `agent_loop_observations.jsonl`：执行后的模型可消费 observation。
- `agent_loop_run_summary.json`：bounded loop 的退出原因、轮数、下一步命令和最终 evidence refs。

当前 action 状态：

- `tool`：进入 Tool Gateway / verification，并写入 tool result observation。
- `subagent`：校验 `capability_ref.type == "subagent"`、`target_task_id`、`risk`、`budget_hint` 后，写入 WorkerInvocation / WorkerResult dispatch evidence；`ExecuteCommand` 主链路已能启动 child worker planner/decomposer + 多轮 bounded tool loop，并把 child plan、调度策略、worker completion append-only evidence 回灌成父 loop observation。
- `repair`：分派到 debug/recovery，并写入 repair dispatch summary。
- `replan`：分派到 replan，并写入 replan dispatch summary。
- `ask`：Runtime-owned ask 或 runtime request 会创建 DecisionPoint，并在 summary/status 中给出 `decide --list`。
- `stop`：写入 stop observation 和 loop exit summary。

### Bounded Agent Loop

`ExecuteCommand` 已从“一轮模型提案”升级为受 Runtime 约束的 bounded loop：

```text
AgentLoopDecision -> AgentLoopExecutionResult -> AgentLoopObservation -> next AgentLoopDecision
```

当前行为：

- 默认每个 task 最多 2 轮，可通过 policy `agent_loop.max_rounds_per_task` 调整，上限 8。
- 每轮 observation 会回灌给下一轮 `CoderAgent.propose_action`。
- 只有模型在 `expected_observation` 中显式声明 `next_recommended_action`、`requires_follow_up_decision` 或 `auto_repair_on_failure` 时才自动进入下一轮，避免普通失败任务盲目自旋。
- 退出原因统一写入 `agent_loop_run_summary.json`。

当前支持的退出原因：

```text
completed | tool_failed | max_rounds | budget_hard_stop | ask | stop |
subagent_pending | repair_dispatch | replan_dispatch | no_action
```

### Gate 和状态面

- RuntimeReadinessGate 已把 model role/deadline/streaming、route guidance、context pressure、observation decision、agent loop execution、capability selection 纳入 readiness 判断。
- `status` / `sessions --context` 已展示 latest model progress、AgentLoopDecision、AgentLoopExecutionResult、AgentLoopObservation 和 AgentLoopRunSummary。
- `gate-status` 对 validation failure 的下一步优先使用 Runtime execution result，而不是只按模型意图推断。

### Provider 和 deadline

- model call 记录 role contract、route、deadline、streaming telemetry。
- strong route timeout/deadline 可 fallback 到 medium，并在 model-check / model_calls evidence 中记录。
- review / recovery / validation timeout 会进入 repair / replan / ask / stop 链，而不是只停在 provider/review 层。

## 3. 当前主要差距

### 3.1 Subagent 执行器已进入主链路最小闭环

当前 `subagent` action 已能产生 WorkerInvocation / WorkerResult dispatch evidence；`ExecuteCommand` 主链路已能启动 child worker planner/decomposer 和多轮 bounded tool loop，把 `subagent_child_plans.jsonl`、subagent worker completion 追加写入 evidence，再映射成父 loop 可消费的 `AgentLoopObservation(subagent_result)`。

已保留的父子与并行接口：

- primary worker -> subagent worker -> child candidate workspace 的父子 id。
- `subagent_child_plans.jsonl` 记录 parent decision/execution、worker slot、child task decomposition、readonly/disjoint write scheduling strategy 和 parallel safety。
- runtime profile 中的 `worker_kind`、`parent_runtime_profile_id`、`parallel_safety`。
- context mount 中的 `isolation_policy = subagent_child_context`。
- candidate manifest / task execution evidence / agent run graph 中的 parent worker、child plan、worker kind 和 parallel safety。
- agent run graph 已汇总 `candidate_workspaces`、`promotion_queue` 和 `merge_gate_summary`，用于展示候选 workspace、promotion 状态、merge gate 通过/阻断数量和 violations。
- RuntimeReadinessGate / gate-status 已消费 candidate promotion safety；未解决的 promotion 进入 review，merge gate blocked / promotion failed 进入 blocked。
- agent run graph 已补 `promotion_recovery_summary`，把 rejected / discarded / promoted 映射成 recovered / settled，把 blocked / promotion_failed 映射成 unresolved；discarded candidate 也会计入恢复汇总。
- RuntimeReadinessGate 会把 rejected / discarded 视为恢复完成后的 ready 状态，并在摘要里说明 recovery action 数。

差距：

- child worker 已具备 runtime-owned planner/decomposer，可按 `readonly_fanout` 和 `disjoint_write_workers` 产出多 child task 与调度策略；`readonly_fanout` 已能真实并行执行只读 child worker，写工具会被 gate 阻断，并进入 RuntimeReadinessGate / gate-status 汇总。
- `disjoint_write_workers` 已具备 fake-path gate：调度器侧要求 child task 标记 `disjoint_writes`、声明非空且互斥的 `write_scope`、具备 changed-artifact 与 verification contract；readiness 侧进一步要求每个 child 具备 candidate workspace / promotion 证据、merge gate 通过、promotable files 落在 write_scope 内，且 promotion/recovery 不存在 unresolved 状态。allow/block 结果已进入 RuntimeReadinessGate / gate-status。真实并行写 worker 仍保持关闭。
- 子 agent 的 context isolation 已接入 ContextBudgetMeter v2，能记录 child context token 归因、compact boundary 和重复上下文降噪信号。
- 父子 worker graph 已能表达 child plan refs、candidate workspace、promotion queue、merge gate summary 和 promotion recovery summary；真实文件 rollback 语义还未开放。
- 失败 worker 已可进入 gate 纠偏检查；deterministic-first review 会区分历史失败和最新已恢复的 task execution evidence。真实并行写 worker 的失败/恢复放量仍需后续 provider 灰度验证。

### 3.2 ContextBudgetMeter v2

已具备：

- request-level context estimate 与 section-level 粗归因。
- `context_budget_snapshots.jsonl`：Runtime profile 挂载时记录 context token 归因。
- subagent child context snapshot：记录 `scope = subagent_child`、`isolation_policy`、parent worker/runtime profile、section token、重复内容 hash/估算 token。
- compact boundary：输出 `not_required | dedupe_recommended | recommended | required`，并给出 preserve / droppable sections、before/after token 和 delta。
- 恢复摘要：记录可恢复 sections 与 evidence refs，不把原始上下文内容塞回 snapshot。
- 文件级 hash/diff 与上下文噪声归因：记录 file refs、hash refs、diff refs、changed refs、largest sections 和 duplicate signals。
- gate-status / RuntimeReadinessGate 消费 subagent child snapshot；缺失 snapshot 进入 review，hard-stop boundary 进入 blocked。

仍需要：

- context-heavy 真实维护任务验证这些 v2 字段在 final report / evidence bundle / Inspector 消费侧是否足够可读。
- context pressure 来源在 Studio Inspector 中更细展示。

### 3.3 Capability Selection Audit

已生成 catalog 和 capability decision evidence，但还需要：

- 把 catalog 注入更多模型入口。
- 对齐模型真实 tool / Skill / MCP / subagent 选择与 catalog 选择状态。
- 报告“可见但未用”“被权限阻断”“被风险策略阻断”“模型未选择”的原因。

### 3.4 真实小任务滚动验证

固定 suite 是回归门槛，不是产品能力证明。还需要连续 3-5 个 scoped 真实开发任务，观察：

- route/deadline 是否稳定。
- failure 是否进入 loop decision / observation / run summary。
- context pressure 是否可解释并触发 compact。
- capability selection 是否和 catalog 一致。
- 最终产物和验证是否可复现。

### 3.5 Studio 消费层

Studio 不作为 Runtime P0 阻塞项，但需要继续只消费 runtime evidence：

- 主线程展示 user_progress、artifact、DecisionPoint、loop exit、下一步。
- Inspector 展示 raw evidence、route、schema refs、context/capability 诊断。
- 默认主屏不暴露 maintainer 命令。

## 4. 当前研发优先级

当前可用性口径约为 80%。Runtime OS 主骨架、证据链、gate、bounded loop、candidate/promotion/recovery 图谱、disjoint write fake-path safety、后台使用信号闭环、route guidance refresh 和 ContextBudgetMeter v2 可观测性已经形成。`v0.1.0-alpha.1` 已归档；`v0.1.0-alpha.2` 的本机 dogfooding、route guidance 和 runtime readiness 已 ready。

最新真实 provider P0 matrix 暴露出新的产品级瓶颈：工具调用和文件读写开销很小，耗时主要集中在 strong `goal_spec`、strong `review` 和大上下文模型等待。2026-06-03 的 fast path 修复已把真实 `doc_update` P0 case 从 4 次模型调用、1 次 strong `run_review`、1 次 repair、103.024 秒，收敛为 2 次 medium 调用、0 次 strong、0 次 repair；最新 readback review 修复后复验为 47.850 秒。rolling fast path v1 已固定 `doc_update`、`single_file_bugfix`、`context_maintenance` 三项：初跑暴露 bugfix/context 仍会因 Planner 拆分、结构化 patch 和大小写验收进入 repair；scope 修复后风险 case 复验降为 `single_file_bugfix` 3 次 medium、0 strong、0 repair、41.090 秒，`context_maintenance` 2 次 medium、0 strong、0 repair、33.073 秒。因此下一阶段不是继续围绕失败尾巴加规则，而是把 Runtime 主路径校正为成熟产品风格：快路径优先、风险升级、会话叙事、Inspector 查证。

当前有效事实：

- P0 targeted probes 已覆盖 parent subagent、readonly fanout、readonly write-tool blocking、disjoint write unsafe fanout 和 parent loop stop；readonly/disjoint write 阻断是安全证据，不等同于真实并行写入可放量。
- alpha.2 第二批 scoped validation、三项 scoped dogfooding task 和 route guidance refresh 已 accepted；`ops-signal --summary --analyze` 显示 `next_batch_plan.status=completed`。
- 最新 fresh evidence bundle 为 `.asteria/evidence_bundles/evidence-2026-06-03T003702-0800.zip`；`gate-status --json` 显示 `route_guidance.status=healthy`、`runtime_readiness_gate.status=ready`。
- `evidence-bundle` 已新增 `v0.2_rolling_validation_summary.json`，用于把最近 3-5 个 scoped 真实任务汇总成 route、context、capability、loop、worker 五类证据覆盖情况；`gate-status --json` 已消费最新 bundle manifest 的 `v0_2_rolling_validation` 摘要，并把 `needs_more_samples` / `needs_evidence` 转成 next actions。
- 真实 provider fast path 子集已验证：`rolling-fastpath-v1` 固定覆盖 `doc_update`、`single_file_bugfix`、`context_maintenance` 并可通过；`goal_spec` 默认走 medium，`task_execution` 对低风险文档/文件/维护任务使用 slim context。matrix summary 已记录 strong、task execution、task repair、run review 调用计数，默认 `/run` 的 review 不再因为共享 model client 而强制模型复审；只有显式 `review_model_client` 的维护者/测试路径才强制模型评审。
- 文本产物执行准备器会移除“写 `docs/foo.md` 前先 `list_files docs`”这类父目录探测，避免空 workspace 下低风险文档任务进入无意义 repair。
- 真实 disjoint write workers 继续默认关闭；并行内核后续必须以 sandbox、candidate promotion、merge gate、rollback/reject/discard recovery 和 per-worker context/cost 为放量前提。

后续研发权重：

- **45% Fast Path / Tiered Review / Context Slimming**：把任务分成 `doc_update`、`simple_file`、`single_file_bugfix`、`complex_change`、`high_risk`；简单任务默认 medium/deterministic，不再固定强 goal_spec/强 review；上下文默认 slim，只在风险升级时扩大。
- **25% Studio 会话主路径**：让用户不记命令也能创建任务、查看运行、处理决策、接受结果和导出诊断包；主窗口只呈现 goal、plan/todo、tool use、verify、repair/ask/stop、result。
- **15% Provider route/deadline 性能校准**：用真实 evidence 调整 strong route deadline、retry、downgrade 和 provider SLA；慢 provider 不应拖慢低风险任务。
- **10% Inspector / Evidence 查证层**：右侧只做点选后的证据、diff、route、worker、validation、context breakdown 查证。
- **5% 并行内核 / sandbox / promotion-recovery**：保留并行和子 agent 的父子接口，但真实写入并行继续在 sandbox、candidate promotion、merge gate 和 rollback/reject/discard recovery 满足后再放量。

后台使用信号是运维辅助模块，不进入用户显性主流程。用户侧产品主体仍是 goal -> plan -> execution -> validation -> artifact -> report。

## 5. 当前执行计划

### P0

- **FastPathPolicy 主路径收口**：已接入 plan/run/execute/review；`doc_update`、`simple_file`、`single_file_bugfix` 默认使用 medium/deterministic route、slim context 和 deterministic-first review。`doc_update` / `simple_file` 允许 artifact readback 作为确定性证据；`single_file_bugfix` 仍要求 command-level verification。固定 rolling 子集已落地，下一步重点是持续比较强模型调用、等待时间、slim 覆盖率和 medium schema retry。
- **Tiered Review 收口**：review 顺序固定为 deterministic verify -> medium semantic review -> strong review；强 review 只作为风险升级和发布验收手段。第一层 deterministic-first 已接入 `ReviewCommand`：低风险、任务完成、验证通过、无未恢复 worker/merge/runtime/cost blocker 的默认真实路径可直接生成 `eval_report.json`，不创建 provider client；显式传入 `review_model_client` 的调试/测试/维护者路径仍保留模型评审。
- **Context Slimming 接入**：主路径模型调用只消费当前 goal/todo/task、直接相关文件/摘要/diff、最近 observation、预算/权限/风险摘要；raw evidence、route timeline、worker topology、全量 model_calls 进入 Inspector。第一层已接入 CoderAgent task_execution 和 ReviewCommand：低风险 slim context 只保留最近 evidence，并在 `raw_evidence_refs` 中记录 total/kept/omitted；CoderAgent prompt 会复用同一策略裁剪 `tool_observations`、`harness_observations`、`context_package` 列表和长文件内容，同时保留 `raw_context_refs` 和 context envelope refs；显式维护者/测试 review client 仍保留完整上下文用于查证。
- **Studio 会话主路径定型**：主窗口连续展示 Plan/Todo -> Tool Use -> Verify -> Repair/Ask/Stop -> Result；点击过程块联动 Inspector，但默认不把内部 gate/provider 字段搬回主屏。

### P1

- **Provider 小灰度性能回归**：`model_calls.jsonl` 已记录 `context_mode` 与 `fast_path_task_kind`；real-provider matrix case summary 已汇总 `context_strategy`，`status/gate/review` 文本可展示 context strategy 记录数、slim 调用覆盖率和 context mode 分布。下一批 3-5 个 scoped 真实任务重点看 strong 调用次数、总模型等待时间、context size、deterministic review 命中率、slim 覆盖率、历史失败恢复判定和用户可见下一步一致性。
- **Capability Selection Audit**：把 catalog 注入更多模型入口，对齐真实 tool / Skill / MCP / subagent 选择与 catalog 状态，并报告未选择、被阻断、被替代原因；不要让 catalog 变成默认主屏噪声。
- **ContextBudgetMeter v2 消费侧**：已用隔离 context-heavy 维护任务验证主链路能读取多份上下文并用 slim task context 生成维护摘要；下一步仍需检查 final report / evidence bundle / Inspector 的可读性，主路径只展示 lightweight context window。

### P2

- **Studio 消费层**：默认主线程只展示用户能理解的 goal、plan、progress、decision、artifact、loop exit、result、next step；Inspector 展示 raw evidence、provider route、schema refs、context sections 和 capability diagnostics。

第二批 scoped probes：repair_replan_path(run-20260602-0005)、ask_stop_path(run-20260602-0006)、context_pressure_path(run-20260602-0007)、capability_selection_path(run-20260602-0011) 均已 accepted。
