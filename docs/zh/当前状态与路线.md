# 当前状态与路线

更新时间：2026-06-02

本文是 Asteria 当前阶段的事实入口。进入开发前先读根目录 `AGENTS.md`，再读本文；需要展开设计时再读 `docs/zh/文档导航.md` 中列出的专题文档。

本文只保留当前事实、有效架构、剩余差距和下一步优先级。历史流水账、旧验证次数、旧 release gate 记录和已经完成的阶段计划不再保留。

## 1. 当前阶段

Asteria 当前处于：

```text
模型主导的 Asteria Runtime OS 收口阶段
```

产品目标是：

```text
本地优先、可恢复、可审计、可控成本的长任务自主开发运行时。
```

核心原则：

- 模型负责在能力边界内判断下一步。
- Runtime 负责权限、预算、schema、上下文、候选工作区、证据、恢复和 gate。
- Gate 采用适应性分层：低风险探索、readonly、fake-path planner 保持灵活，只做轻量 trace；写入主工作区、promotion、merge、rollback、远程 push、真实 provider 放量和发布验收等风险边界才强 gate。详见 `docs/zh/adr/0004-adaptive-gates-preserve-agent-flexibility.md`。
- CLI、Studio、报告消费同一套 `.asteria/` evidence，不各自发明状态。
- 固定 validation suite 是回归健康信号，不等同于长期自主能力完成。

## 2. 已落地能力

### Runtime OS 基线

- `init`、`plan/run`、`execute`、`status`、`debug`、`replan`、`review`、`accept`、`gate-status`、`validation` 等主入口可用。
- `.asteria/` 持久化 run、task、model call、worker、runtime profile、context mount、task execution evidence、validation、review、final report 等对象。
- Candidate workspace、merge gate、promotion queue 和 protected path policy 已作为写入边界的一部分。

### 模型可见能力

- PromptEnvelope、ContextEnvelope、CapabilityManifest、AgentRoleContract 已进入模型调用证据。
- ModelToolSurfaceAdapter 已把模型侧 `read/list/search/edit/shell/test/todo` 原语映射到内部 registry，并保留 `model_tool_name` 审计字段。
- Tool、MCP、Skill、subagent 分离执行，但复用 capability decision evidence。
- 任务级 capability catalog 已记录 visible / selected / skipped / blocked 和原因。
- ContextBudgetMeter v1 已记录 request-level context estimate、context window ratio、section 归因和重复内容信号。

### Agent Harness 循环契约

`AgentLoopDecision` 已是稳定 schema。模型下一步动作限定为：

```text
tool | subagent | repair | replan | ask | stop
```

每个 action 必须携带：

- `reason`
- `target_task_id`
- `capability_ref`
- `expected_observation`
- `risk`
- `budget_hint`
- `evidence_refs`

当前闭环 evidence：

- `agent_loop_decisions.jsonl`：模型或 Runtime 代写的下一步决策。
- `agent_loop_execution_results.jsonl`：Runtime 对决策的分派结果。
- `agent_loop_observations.jsonl`：执行后的模型可消费 observation。
- `agent_loop_run_summary.json`：bounded loop 的退出原因、轮数、下一步命令和最终 evidence refs。

当前 action 状态：

- `tool`：进入 Tool Gateway / verification，并写入 tool result observation。
- `subagent`：校验 `capability_ref.type == "subagent"`、`target_task_id`、`risk`、`budget_hint` 后，写入 WorkerInvocation / WorkerResult dispatch evidence；`ExecuteCommand` 主链路已能启动 child worker planner/decomposer + 多轮 bounded tool loop，并把 child plan、调度策略、worker completion append-only evidence 回灌成父 loop observation。
- `repair`：分派到 debug/recovery，并写入 repair dispatch summary。
- `replan`：分派到 replan，并写入 replan dispatch summary。
- `ask`：Runtime-owned ask 或 runtime request 会创建 DecisionPoint，并在 summary/status 中给出 `decide --list`。
- `stop`：写入 stop observation 和 loop exit summary。

### Bounded Agent Loop

`ExecuteCommand` 已从“一轮模型提案”升级为受 Runtime 约束的 bounded loop：

```text
AgentLoopDecision -> AgentLoopExecutionResult -> AgentLoopObservation -> next AgentLoopDecision
```

当前行为：

- 默认每个 task 最多 2 轮，可通过 policy `agent_loop.max_rounds_per_task` 调整，上限 8。
- 每轮 observation 会回灌给下一轮 `CoderAgent.propose_action`。
- 只有模型在 `expected_observation` 中显式声明 `next_recommended_action`、`requires_follow_up_decision` 或 `auto_repair_on_failure` 时才自动进入下一轮，避免普通失败任务盲目自旋。
- 退出原因统一写入 `agent_loop_run_summary.json`。

当前支持的退出原因：

```text
completed | tool_failed | max_rounds | budget_hard_stop | ask | stop |
subagent_pending | repair_dispatch | replan_dispatch | no_action
```

### Gate 和状态面

- RuntimeReadinessGate 已把 model role/deadline/streaming、route guidance、context pressure、observation decision、agent loop execution、capability selection 纳入 readiness 判断。
- `status` / `sessions --context` 已展示 latest model progress、AgentLoopDecision、AgentLoopExecutionResult、AgentLoopObservation 和 AgentLoopRunSummary。
- `gate-status` 对 validation failure 的下一步优先使用 Runtime execution result，而不是只按模型意图推断。

### Provider 和 deadline

- model call 记录 role contract、route、deadline、streaming telemetry。
- strong route timeout/deadline 可 fallback 到 medium，并在 model-check / model_calls evidence 中记录。
- review / recovery / validation timeout 会进入 repair / replan / ask / stop 链，而不是只停在 provider/review 层。

## 3. 当前主要差距

### 3.1 Subagent 执行器已进入主链路最小闭环

当前 `subagent` action 已能产生 WorkerInvocation / WorkerResult dispatch evidence；`ExecuteCommand` 主链路已能启动 child worker planner/decomposer 和多轮 bounded tool loop，把 `subagent_child_plans.jsonl`、subagent worker completion 追加写入 evidence，再映射成父 loop 可消费的 `AgentLoopObservation(subagent_result)`。

已保留的父子与并行接口：

- primary worker -> subagent worker -> child candidate workspace 的父子 id。
- `subagent_child_plans.jsonl` 记录 parent decision/execution、worker slot、child task decomposition、readonly/disjoint write scheduling strategy 和 parallel safety。
- runtime profile 中的 `worker_kind`、`parent_runtime_profile_id`、`parallel_safety`。
- context mount 中的 `isolation_policy = subagent_child_context`。
- candidate manifest / task execution evidence / agent run graph 中的 parent worker、child plan、worker kind 和 parallel safety。
- agent run graph 已汇总 `candidate_workspaces`、`promotion_queue` 和 `merge_gate_summary`，用于展示候选 workspace、promotion 状态、merge gate 通过/阻断数量和 violations。
- RuntimeReadinessGate / gate-status 已消费 candidate promotion safety；未解决的 promotion 进入 review，merge gate blocked / promotion failed 进入 blocked。
- agent run graph 已补 `promotion_recovery_summary`，把 rejected / discarded / promoted 映射成 recovered / settled，把 blocked / promotion_failed 映射成 unresolved；discarded candidate 也会计入恢复汇总。
- RuntimeReadinessGate 会把 rejected / discarded 视为恢复完成后的 ready 状态，并在摘要里说明 recovery action 数。

差距：

- child worker 已具备 runtime-owned planner/decomposer，可按 `readonly_fanout` 和 `disjoint_write_workers` 产出多 child task 与调度策略；`readonly_fanout` 已能真实并行执行只读 child worker，写工具会被 gate 阻断，并进入 RuntimeReadinessGate / gate-status 汇总。
- `disjoint_write_workers` 已具备 fake-path gate：调度器侧要求 child task 标记 `disjoint_writes`、声明非空且互斥的 `write_scope`、具备 changed-artifact 与 verification contract；readiness 侧进一步要求每个 child 具备 candidate workspace / promotion 证据、merge gate 通过、promotable files 落在 write_scope 内，且 promotion/recovery 不存在 unresolved 状态。allow/block 结果已进入 RuntimeReadinessGate / gate-status。真实并行写 worker 仍保持关闭。
- 子 agent 的 context isolation 已接入 ContextBudgetMeter v2，能记录 child context token 归因、compact boundary 和重复上下文降噪信号。
- 父子 worker graph 已能表达 child plan refs、candidate workspace、promotion queue、merge gate summary 和 promotion recovery summary；真实文件 rollback 语义还未开放。
- 失败 worker 已可进入 gate 纠偏检查，但还需要真实 provider 小灰度验证。

### 3.2 ContextBudgetMeter v2

已具备：

- request-level context estimate 与 section-level 粗归因。
- `context_budget_snapshots.jsonl`：Runtime profile 挂载时记录 context token 归因。
- subagent child context snapshot：记录 `scope = subagent_child`、`isolation_policy`、parent worker/runtime profile、section token、重复内容 hash/估算 token。
- compact boundary：输出 `not_required | dedupe_recommended | recommended | required`，并给出 preserve / droppable sections。
- gate-status / RuntimeReadinessGate 消费 subagent child snapshot；缺失 snapshot 进入 review，hard-stop boundary 进入 blocked。

仍需要：

- 文件级 hash/diff 降噪：减少重复读取未变文件。
- compact 后的 before/after token 对比和恢复摘要。

### 3.3 Capability Selection Audit

已生成 catalog 和 capability decision evidence，但还需要：

- 把 catalog 注入更多模型入口。
- 对齐模型真实 tool / Skill / MCP / subagent 选择与 catalog 选择状态。
- 报告“可见但未用”“被权限阻断”“被风险策略阻断”“模型未选择”的原因。

### 3.4 真实小任务滚动验证

固定 suite 是回归门槛，不是产品能力证明。还需要连续 3-5 个 scoped 真实开发任务，观察：

- route/deadline 是否稳定。
- failure 是否进入 loop decision / observation / run summary。
- context pressure 是否可解释并触发 compact。
- capability selection 是否和 catalog 一致。
- 最终产物和验证是否可复现。

### 3.5 Studio 消费层

Studio 不作为 Runtime P0 阻塞项，但需要继续只消费 runtime evidence：

- 主线程展示 user_progress、artifact、DecisionPoint、loop exit、下一步。
- Inspector 展示 raw evidence、route、schema refs、context/capability 诊断。
- 默认主屏不暴露 maintainer 命令。
