﻿# 当前状态与路线

## 1. 文档定位

本文档是当前阶段的事实入口，用来回答三个问题：

- 当前系统已经做到什么程度。
- 现在最重要的产品和工程差距是什么。
- 下一轮开发应该沿哪条主线推进。

详细产品边界看 [产品规格.md](./产品规格.md)，详细架构看 [架构设计.md](./架构设计.md)，长期 Runtime OS 重构思路看 [编排式Agent运行时重构计划.md](./编排式Agent运行时重构计划.md)。

## 2. 当前阶段

当前项目处于：

```text
编排式 Agent Runtime OS 阶段
```

产品能力描述是：

```text
长任务自主开发 Runtime
```

也就是说，当前重点不是继续堆聊天能力或 dashboard，而是把系统打造成一个可编排、可隔离、可恢复、可审计、可控成本的本地优先自主开发运行时。

## 3. 已完成基线

当前已经具备的核心闭环：

- CLI runtime：`/init`、`/new`、`/run`、`/execute`、`/debug`、`/review`、`/final`、`/handoff`、`/resume`。
- 结构化状态：`.agent/` 下持久化 run、task、decision、cost、context snapshot、evidence、report。
- 任务契约：TaskContract、expected artifacts、validation commands、write scope、completion contract。
- 候选执行证据：`task_execution_evidence.jsonl`、`workers.jsonl`、`worker_results.jsonl`、`runtime_profiles.jsonl`、`context_mounts.jsonl`、`validation_results.jsonl`。
- 受控执行：失败、超预算、pending decision、策略拦截时硬停，不盲目无限修复。
- 长任务控制面：`daily-*` 和 `long-run-*` 已经表达周期计划、执行、报告和预算守卫；“daily”只是默认时间盒，不是架构边界。
- 真实验收：core/nightly acceptance、失败提升修复、acceptance gate、capability report、Runtime OS release gate。
- Runtime OS gate：并发只读、disjoint writes、失败 worker、merge gate 阻断、runtime request 后 resume、ContextPackage `read_scope` 切片、sandbox backend selection、Planner scope quality、capability feedback、debug/review evidence consumption 都已进入验收。
- 报告复用：`/acceptance-gate`、`/capability-report`、`/weekly-report` 已共享 Runtime OS gate evaluator，并输出 TaskGraph/WorkerInvocation release evidence。
- ContextPackage 已接入 ContextMount，发布门槛已经开始验证它按 `read_scope` 切片，并继续要求 runtime request、worker result 与 merge gate evidence 被纳入 worker 上下文包。
- Coordinator 边界：`ExecutionCoordinator` 已承接 ready node selection、selection event 和串行/并发 worker 分发；`WorkerRunner` 已承接单个 worker 的 RuntimeProfile 挂载、执行回调和 WorkerResult 记录；`TaskAttemptRunner` 已承接候选工作区、工具执行、contract/merge gate 和 TaskExecutionEvidence；`RuntimeRequestPolicy` / `ToolPermissionPolicy` 已承接 runtime request、policy decision 和工具权限边界；`WorkerExecutionRecorder` 已统一记录 WorkerInvocation / WorkerResult。
- Evidence 消费：`/debug`、`/review`、`/resume` 已优先读取 Runtime OS evidence 包，包括 task execution evidence、worker results、merge gate evidence 与 runtime requests。

## 4. 当前主要差距

现在最大差距不再是“有没有命令”，而是 Runtime OS 的可靠性和可解释性：

- TaskGraph 仍在从线性 task board 过渡到更明确的 DAG 执行模型。
- WorkerInvocation 已经有统一记录器、WorkerRunner、TaskAttemptRunner 和 runtime policy 层，debug/review/resume 已开始消费统一 evidence；Coordinator 到 Worker 的边界还需要继续把 action 规范化、验证兜底和候选晋升细节从命令层收敛出去。
- 候选工作区已有隔离能力和 merge gate，但 Git worktree/candidate branch 形态仍需增强。
- ContextPackage 还需要从“按 refs 加载证据”升级为“按任务 scope 裁剪上下文包”，避免 worker 默认吃全量历史。
- capability profile 已能吸收模型调用、worker、runtime request、validation pass rate 与 merge gate block 信号，下一步需要扩大实战数据量，让模型路由和 Planner 调整更可信。
- acceptance gate 已经覆盖 Runtime OS 证据，但真实模型 core 全量运行仍有成本和耗时压力。
- 文档刚完成主线收敛，后续新增能力必须先更新当前状态和验收入口，避免再次变成开发日志堆叠。

## 5. 近期研发优先级

P0：Runtime OS 发布门槛继续硬化。

- 继续扩展 TaskGraph、WorkerInvocation、MergeGate、ContextMount 的真实 core release evidence。
- 确保 capability report、weekly report 和 acceptance gate 的 Runtime OS 判断保持一致。
- Runtime OS gate 的证据口径必须覆盖 ContextPackage 切片、sandbox backend、runtime request resume、merge gate block 和 worker validation 结果。
- 保持 full core acceptance 作为发布门槛，开发期优先跑场景子集和 failed-only。

P1：Coordinator 到 WorkerInvocation 的执行边界收敛。

- 减少命令层直接拼接执行细节。
- 让执行尝试统一通过 ExecutionCoordinator / WorkerExecutionRecorder 产生 WorkerInvocation、WorkerResult、TaskExecutionEvidence。
- 让 `/debug`、`/review`、`/resume` 后续继续减少对旧 tool/model/event 日志的直接依赖。

P1：候选工作区升级。

- 有 git 仓库时优先使用 Git worktree/candidate branch。
- 无 git 时 fallback 到复制候选目录。
- RuntimeProfile.sandbox_profile 与 CandidateWorkspace 必须使用同一套 backend selector，并记录选择原因。
- MergeGate 必须继续证明失败候选不会污染主工作区。

P2：体验和可读性。

- 优先增强 CLI report、weekly report、acceptance report。
- Dashboard 只有在 CLI 报告、Runtime OS evidence、handoff/resume 稳定后再做。
