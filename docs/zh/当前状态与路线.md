# 当前状态与路线

## 1. 文档定位

本文档是当前阶段的事实入口，用来回答三个问题：

- 当前系统已经做到什么程度。
- 现在最重要的产品和工程差距是什么。
- 下一轮开发应该沿哪条主线推进。

详细产品边界看 [产品规格.md](./产品规格.md)，详细架构看 [架构设计.md](./架构设计.md)，长期 Runtime OS 重构思路看 [编排式Agent运行时重构计划.md](./编排式Agent运行时重构计划.md)。

## 2. 当前阶段

当前项目处于：

```text
编排式 Asteria Runtime OS 阶段
```

产品能力描述是：

```text
长任务自主开发 Runtime
```

也就是说，当前重点不是继续堆聊天能力或 dashboard，而是把系统打造成一个可编排、可隔离、可恢复、可审计、可控成本的本地优先自主开发运行时。

## 3. 已完成基线

当前已经具备的核心闭环：

- CLI runtime：`/init`、`/new`、`/run`、`/execute`、`/debug`、`/review`、`/final`、`/handoff`、`/resume`。
- 结构化状态：`.asteria/` 下持久化 run、task、decision、cost、context snapshot、evidence、report。
- 任务契约：TaskContract、expected artifacts、validation commands、write scope、completion contract。
- 候选执行证据：`task_execution_evidence.jsonl`、`workers.jsonl`、`worker_results.jsonl`、`runtime_profiles.jsonl`、`context_mounts.jsonl`、`validation_results.jsonl`。
- 受控执行：失败、超预算、pending decision、策略拦截时硬停，不盲目无限修复。
- 长任务控制面：`daily-*` 和 `long-run-*` 已经表达周期计划、执行、报告和预算守卫；“daily”只是默认时间盒，不是架构边界。`long-run-plan` 会优先处理 pending decision、candidate promotion release risk、blocked route guidance、failed acceptance，再考虑执行 ready task。

- Runtime OS gate：并发只读、disjoint writes、失败 worker、merge gate 阻断、runtime request 后 resume、ContextPackage `read_scope` 切片、sandbox backend selection、Planner scope quality、capability feedback、debug/review evidence consumption 都已进入验收。
- 报告复用：`/acceptance-gate`、`/capability-report`、`/weekly-report` 已共享 Runtime OS gate evaluator，并输出 TaskGraph/WorkerInvocation release evidence。
- ContextPackage 已接入 ContextMount，发布门槛已经开始验证它按 `read_scope` 切片，并继续要求 runtime request、worker result 与 merge gate evidence 被纳入 worker 上下文包。

## 4. 当前主要差距

现在最大差距不再是“有没有命令”，而是 Runtime OS 的可靠性和可解释性：

- TaskGraph 仍在从线性 task board 过渡到更明确的 DAG 执行模型。
- WorkerInvocation 已经有统一记录器、WorkerRunner、TaskAttemptRunner、ExecutionActionPreparer、ExecutionEvidenceSink、CandidateExecutionGateway、ToolExecutionGateway、TaskBlockingHandler、RunStateFinalizer 和 runtime policy 层，debug/review/resume 已开始消费统一 evidence；Coordinator 到 Worker 的边界已把 worker/result id 成对分配下沉为 WorkerExecutionSlot，action 准备、工具执行、候选晋升、阻塞处理、验证结果记录、experiment/artifact/failure 持久化和 run 收尾都已从命令层剥离；这轮已用 `ruff`、`mypy`、`package-check`、完整 `pytest`、真实 gate、完整 gray suite 和 core gate 交叉验证。后续重点从“继续拆 ExecuteCommand”转为“防止执行细节回流命令层，并把候选工作区、上下文裁剪和报告证据继续做厚”。
- 候选工作区已有隔离能力和 merge gate，但 Git worktree/candidate branch 形态仍需增强。
- Git worktree candidate branch 已有 MVP：tracked clean 的 git workspace 优先使用 `asteria/candidate/...` 分支，未跟踪过程产物不会阻止 worktree；候选 manifest 已写入 `.asteria/runs/<run-id>/candidates/`，worktree 候选和复制候选分别放入短路径 `wt/` 与 `cw/`；`promotions` 控制面已能 list/approve/reject/retry/discard，promotion queue 写入 `.asteria/runs/<run-id>/candidate_promotions.jsonl` 并保留 `pending_manual_approval`、`approved`、`promoted`、`blocked`、`promotion_failed`、`rejected`、`discarded` 状态；promote 前会重检 merge gate、candidate workspace、promotable files 和 git worktree/source path 状态，失败会结构化写入 queue 而不是只抛异常；`RunCommand` final report 与 `sessions --context` 已能消费最新 promotion 状态。
- ContextPackage 已在按 refs 加载证据基础上增加 `scope_summary`、`write_scope_files`、`evidence_scope` 和 `recent_failures`，明确区分 read scope、write scope、证据 refs 与最近失败；后续继续把这些分层信号用于 Planner 和模型路由，避免 worker 默认吃全量历史。
- capability profile 已能吸收模型调用、worker、runtime request、validation pass rate 与 merge gate block 信号；`ContextLoader` 已把 actionable capability feedback 注入 Planner runtime context，Planner 会在 task notes 中保留“收窄 scope / 复核 route / 加强验证”等提示；RuntimeProfile route selection 已开始消费 route guidance，对弱 medium/cheap 路线升级到 stronger tier，并把相关 guidance 放入 worker runtime context。下一步需要扩大实战数据量，观察这些信号对成本和成功率的真实影响。
- acceptance gate 已经覆盖 Runtime OS 证据，当前已有 release-ready 基线；`gate-status --json` 已增加按 git 变更规模生成的 `validation_recommendation`，用于提示 targeted、core subset 或 full gray/core 验证路线；后续仍要保持 core gate 复跑，避免单次通过被误当成长期稳定性证明。
- 历史 gray suite 暴露出多文件 scope 场景接近预算上限；补上 planned verification 兜底后，2026-05-16 单场景复跑和 2026-05-17 完整 gray suite 复跑中的 `gray_multi_file_scope` 均已从 `near_limit` 回到 `within_budget`；2026-05-17 installed 小真实任务批次曾暴露文档/只写文件任务会因 runtime request 后的 repair verification 命令生成不稳而 blocked，现已在 `ExecutionActionPreparer` 为 `.md/.txt/.rst` 文本产物按需替换为稳定的存在且非空验证，并保留有效的内容断言；同时收窄 Coder/DebugAgent 提示以避免 standalone 文档任务过早请求 runtime context。复测中两个文档/文本只写任务完成，文档 verification 老问题未复现；扩展到小 CLI 和 pytest 测试生成任务时仍暴露 artifact 创建不稳定、验收范围漂移和 DebugAgent 非 JSON 输出风险，说明下一步应继续收敛实现类任务的 action 生成、planner scope 与 debug JSON 稳定性。
- 系统已有本地 wheel 与灰度 runbook 基线；安装包复验、升级/回滚说明、安装后自检样例和用户侧诊断入口已产品化到 `docs/zh/灰度试运行手册.md`、`package-check` 和 `doctor`。后续仍需在真实小任务批次中验证用户能否按 runbook 独立定位失败。
- 首轮灰度入口已具备模板和诊断字段，且控制面已能识别全局 provider fallback；2026-05-16 重建 wheel 后已在干净 venv/no-index 安装环境中通过 `init`、`doctor`、strong/medium `model-check` 和最小 `/run`，确认 wheel 用户路径与仓库开发路径一致。
- 文档刚完成主线收敛，后续新增能力必须先更新当前状态和验收入口，避免再次变成开发日志堆叠。

## 5. 近期研发优先级

### 5.0 90% 完成度门槛

在开启打包部署测试前，项目应达到约 90% 的 Runtime OS alpha 完成度。判定标准：

- release gate 不只检查 acceptance report，还必须阻断 unresolved candidate promotion：`pending_manual_approval`、`approved`、`blocked`、`promotion_failed` 都不能进入 release-ready。
- `gate-status --json` 必须同时反映 route environment、route guidance、gray/core gate 和按变更规模推荐的验证路线；如果 capability profile 标记 route blocked，不能继续扩大真实灰度。
- capability profile 的反馈必须至少进入 Planner 和控制面；自动切换模型可以后置，但路线风险不能只停留在报告文本里。
- long-run plan 必须优先处理 pending decision、unresolved candidate promotion、blocked route guidance 和 failed acceptance，不能在这些风险存在时继续扩大执行预算。
- ContextPackage 必须持续保持 read scope、write scope、evidence scope、recent failures 分层，避免复杂任务默认吃全量历史。
- candidate workspace 必须证明失败候选、promotion failure、discard 不污染主工作区。
- full `pytest`、`ruff`、`mypy`、`package-check`、core acceptance gate 必须稳定通过；进入部署测试前再跑真实 `real-model-gate` 和完整 gray suite。
- 灰度 runbook 必须覆盖安装、配置、升级、回滚、自检、失败收集和暂停/恢复。

P0：Runtime OS 发布门槛继续硬化。

- 继续扩展 TaskGraph、WorkerInvocation、MergeGate、ContextMount 的真实 core release evidence。
- 确保 capability report、weekly report 和 acceptance gate 的 Runtime OS 判断保持一致。
- Runtime OS gate 的证据口径必须覆盖 ContextPackage 切片、sandbox backend、runtime request resume、merge gate block 和 worker validation 结果。
- Runtime OS gate / acceptance gate 已开始检查 candidate promotion release risks；后续继续把 release 风险阈值产品化。
- 保持 full core acceptance 作为发布门槛，开发期优先跑场景子集和 failed-only。

P0：产品化灰度前置条件。

- 维持真实 `core` suite 与 `acceptance-gate` 的 release-ready 基线；gray suite 只能作为进入 core 的候选门槛，不能替代发布门槛。
- 把 `gate-status --json` 作为灰度入口的单一状态判断，明确 blocked / conditional / release_ready 的用户可见含义。
- 固化可重复安装包：本地 wheel、版本号、默认配置模板、示例 `.asteria/` 初始化结果、安装后 `version/package-check/doctor/gate-status` 自检和卸载说明。
- 在干净目录或新虚拟环境中执行首轮安装后自检样例，并保存 `version/package-check/doctor/gate-status/model-check` 输出作为灰度证据。
- 成本优先灰度阶段 strong route 先用 `glm-4.7` 消耗免费 token 额度；额度耗尽、质量不足或发布门槛复验时切到 `glm-5.1`。
- 明确灰度运行边界：默认只允许本地文件系统 + JSON/JSONL 状态；不启用破坏性 shell；不读取 protected paths；真实 API key 只从环境变量或 secret 注入。
- 建立灰度 runbook：安装、配置 GLM/MiniMax 路由、运行 gate、运行 gray/core acceptance、查看报告、暂停/恢复、故障收集和回滚。
- 将首轮灰度限定为少量真实开发任务：文件产出、多文件小工具、测试修复、文档更新和受控重构；暂不开放长时间无限制自动推进。
- installed 小真实任务灰度批次已覆盖文档只写、handoff 文档、小 CLI 和 pytest 测试生成：文档/文本只写任务的 verification 生成已 targeted 修复，重建 wheel 后在干净 installed CLI 中完成文档/文本任务；小 CLI 和 pytest 测试生成任务仍会因 artifact 创建不稳定、跨 run 依赖或验收范围扩张进入 repair/replan，暂不作为 90% 门槛的绿色证据，下一步需要专门收敛实现类任务的 action 生成、Planner 对既有 artifact 的 read/write scope 和 DebugAgent JSON 输出。

P1：Coordinator 到 WorkerInvocation 的执行边界收敛。

- 减少命令层直接拼接执行细节；当前 `ExecuteCommand` 已基本退为加载 run/context、调用 coordinator/worker 和返回结果的编排入口。
- 让执行尝试统一通过 ExecutionCoordinator / WorkerExecutionRecorder / TaskAttemptRunner / ExecutionEvidenceSink 产生 WorkerInvocation、WorkerResult、TaskExecutionEvidence 与验证证据。
- 让 `/debug`、`/review`、`/resume` 后续继续减少对旧 tool/model/event 日志的直接依赖。

P1：候选工作区升级。

- 有 git 仓库且 tracked 文件干净时优先使用 Git worktree/candidate branch。
- 无 git 时 fallback 到复制候选目录。
- 未跟踪过程产物不应阻止 worktree；tracked dirty 文件必须降级或停下提示风险。
- RuntimeProfile.sandbox_profile 与 CandidateWorkspace 必须使用同一套 backend selector，并记录选择原因。
- MergeGate 和 Runtime OS gate 必须继续证明失败候选、promotion failure 和 discard 不会污染主工作区。
- promotion queue 已进入可操作控制面；`status`、`sessions --context`、`run` final report、weekly/capability Runtime OS evidence 已开始共享 candidate promotion 计数口径。下一步重点是评估是否默认启用人工审批模式，并把 release gate 的 promotion 风险阈值显式化。

P1：执行命令层瘦身后的回归护栏。

- 新增执行能力时优先挂到 `ExecutionCoordinator`、`WorkerRunner`、`TaskAttemptRunner`、`ExecutionEvidenceSink` 或对应 gateway/finalizer，不在 `ExecuteCommand` 里重新拼工具、候选晋升、阻塞或收尾细节。
- Planner 生成的 `allowed_tools` 必须和工具注册表中的安全只读/写入工具保持一致；gray suite 的 `gray_file_artifact` 已证明漏放安全只读工具会导致候选产物无法晋升。
- 每次较大执行边界改动后至少跑 offline gate、真实 `real-model-gate`、完整 gray suite 和 core acceptance gate；gray 只能证明真实路由和典型路径，core gate 仍是 Runtime OS 发布门槛。

P2：体验和可读性。

- 优先增强 CLI report、weekly report、acceptance report。
- Dashboard 只有在 CLI 报告、Runtime OS evidence、handoff/resume 稳定后再做。

## 6. 文档维护规则

- `docs/zh` 是主事实源。
- `docs/en` 是辅助参考，除非明确同步，否则不能作为当前阶段判断依据。
- `docs/zh/archive` 是历史参考，不参与当前实现决策。
- `AGENTS.md` 只保存高优先级、短而硬的项目规则；详细计划必须链接到本文档。
- 新增重大能力时，同时更新本文档的已完成基线、当前差距或近期优先级。
