# 当前状态与路线

更新时间：2026-05-27

本文是 Asteria 当前阶段的事实入口。进入开发前先读根目录 `AGENTS.md`，再读本文，然后按 [文档导航.md](./文档导航.md) 选择详细设计文档。

本文只记录当前事实、长期有效口径、当前差距和下一步优先级。过程性旧计划不放在这里；已过时、错误或理解不正确的内容应直接从长期文档中删除、改写或归档，而不是再新增诊断文档解释旧错误。

## 1. 当前阶段

Asteria 当前处于：

```text
编排式 Asteria Runtime OS 阶段
```

产品能力目标是：

```text
本地优先、可恢复、可审计、成本受控的长任务自主开发运行时。
```

架构总原则：

- 模型主导工作循环。
- Runtime 负责护栏、证据、权限、计费、schema、恢复和验证边界。
- 状态机只作为给大模型和专业智能体的角色工作骨架建议，是智能体协同模型策略，不绑死，不做业务流程脚本。
- 程序负责边界、协议、权限、预算、证据、schema 和 fallback；模型在边界内根据目标、上下文和能力清单动态组织工作。

当前重点不是 unrestricted agent chatroom，也不是让 Studio/dashboard 反向牵引后端，而是把紧凑用户目标稳定转成经过验证的产物：目标规格化、任务分解、动态上下文、受控工具调用、证据记录、验证、修复、成本控制、最终交付。

## 2. 用户入口与过程可见性

用户入口：

- Goal / Plan 是主入口。
- Ask 是轻量入口。
- Brainstorm、AutoResearch、Research、Debug、Review、Coder、多智能体、`run/status/review/accept/debug/gate/gray` 等专业链路或命令，是专家命令、维护命令或产品背后的 runtime action。

交互侧要求：

- 无论背后走哪个链路，用户都必须能看到实时的大模型判断结论。
- 接口调用过程、工具调用过程、关键思考摘要、验证过程和失败修复过程必须能进入用户进展事件。
- 过程完成后，系统必须整理最终结果、交付物、验证结论、残余风险和下一步。
- 普通用户不应看到裸 trace、schema dump、provider raw error 或 backend 字段；这些进入 debug / ops / Inspector。

Studio 定位：

- 当前优先完成通用智能体 Asteria 的后端 runtime。
- Studio 是 Asteria 的独立产品交互面，是通用智能体的前端载体，不只是命令包装器。
- Studio 未来消费 runtime evidence、user_progress 和 Inspector，不决定后端核心架构优先级。
- Studio 的产品设计长期有效，负责用户心流、实时过程展示、文件预览/对比、Git 集成、MCP 管理、plugin 管理、skills 管理、session 管理、用户管理、token 额度查看、权限设置、模型设置和展示/配置管理。
- 后端协议稳定前，Studio 进度可以略落后；但 Studio 的整体设计不应被临时后端实现反向绑死。

## 3. 当前事实

已经具备的工程基线：

- CLI/runtime loop 已有 `init`、`goal/run`、`status`、`review`、`accept`、`doctor`、`gate`、`gray` 等入口。
- `.asteria/` 下已经持久化 run、task、worker、runtime profile、context mount、evidence、validation、report 等运行对象。
- Runtime OS 对象已经覆盖 TaskGraph、WorkerInvocation、WorkerResult、RuntimeProfile、ContextMount、TaskExecutionEvidence、MergeGate。
- ContextPackage 已能按 read scope、write scope、artifact refs、failure refs、decision refs、validation refs 裁剪 worker 上下文。
- PromptEnvelope、CapabilityManifest、AgentRoleContract、ToolObservation 已有第一版，模型调用开始记录 role、route、deadline、prompt envelope、capability manifest 等审计字段。
- 模型路由已支持 strong/medium/cheap 默认兜底，缺少 env/local route 或 capability profile 过期时不会卡死在 route guidance。
- ReviewAgent 已有 strong -> medium -> cheap 的降级 fallback，失败时能产生可审计 metadata。
- `status --debug`、JSON、gate、doctor、acceptance 等工程控制面已有较多底层证据。
- `ActiveGoalMemory` 已同时写 `.asteria/memory/active_goal.json` 和 `.asteria/memory/active_goal.md`；JSON 是结构化长期状态协议第一版，Markdown 是用户可读永久记忆。
- 普通 `status` 已开始从结构化长期状态渲染用户状态卡片，而不是整段 dump Markdown。
- Plan 已产出 `WorkspaceEnvelope`，Chat/Status/Sessions 已开始消费该 envelope。
- 权限策略已有 `ask_everything`、`reviewed_auto`、`auto` 三档基础 profile，工具权限侧已开始使用 permission profile。
- Chat 已按问题意图挂载动态上下文：普通 Ask 不再默认读取 `.asteria/memory/active_goal.md`，状态/进展/计划/下一步类问题才挂载长期任务记忆。
- Chat 模型请求已携带 `ContextEnvelope`，并在 metadata 中记录 envelope id/hash/path；旧 `safe_project_context` 兼容字段已下线；Chat envelope payload 已接入 CapabilityInvocationPolicy 第一版。
- ChatIntentPolicy 已从 ChatCommand 中独立出来。
- ContextPackageBuilder 已为 worker 任务级上下文包嵌入同类 ContextEnvelope，并将 envelope 持久化为独立审计文件；CoderAgent/DebugAgent 模型调用已记录 worker context envelope path/hash；capability report 已纳入 ContextEnvelope 审计统计。

最近完整验证基线：

- `pytest tests/unit -q`：389 passed。
- `pytest tests/integration/test_plan_command.py -q`：4 passed。
- `mypy src`：通过。
- `ruff check src tests`：通过。
- 最近 pushed commit：`4e35ff8 docs: clarify remote push safety boundary`。

## 4. 当前主要差距

当前差距以 [代码现状差距与研发计划.md](./代码现状差距与研发计划.md) 为准。摘要如下：

1. Runtime 产品契约正在收敛为代码，但覆盖面还不完整。
   - 文档第一刀已经完成，后续是持续治理，不再作为阻塞 P0。
   - WorkspaceEnvelope、权限 profile、Chat 动态上下文已经落地第一阶段。
   - 全局 workspace index、输出目录产品化、ContextEnvelope 和 user_progress 全链路覆盖仍需继续实现。

2. 长任务记忆协议还需要补齐来源覆盖和冲突处理。
   - 当前已有结构化 `active_goal.json` 和 Markdown 用户视图。
   - 已记录 `source_run_id`、`updated_by`、`update_reason`、当前目标、完成项、阻塞、问题和下一步。
   - 后续仍需覆盖 `review`、`resume`、`repair` 的细分更新来源，以及冲突处理和恢复策略。

3. Status 用户视图已完成第一阶段，但还需要继续产品化。
   - 当前普通 `status` 已从结构化长期状态渲染状态卡片。
   - 后续要把状态卡片进一步接入 user_progress、Studio 和更多真实任务灰度。

4. 用户实时过程协议还不完整。
   - 当前已有 `user_progress` 和部分模型/工具事件，但尚未覆盖所有 Goal/Plan/Ask、专业智能体和工具链路。
   - 目标是用户能看到实时判断、调用过程、工具过程、关键思考摘要、验证与最终整理。

5. ContextPackage 和 Chat Context 第一阶段已收敛，仍需扩大审计消费面。
   - 长任务 worker 已有 ContextPackage。
   - ChatContextBuilder 已负责构建 Chat 上下文、生成 ContextEnvelope 并持久化 envelope 文件。
   - ContextPackageBuilder 已为 Goal Loop worker 任务级上下文包嵌入同类 envelope，并写入独立审计文件。
   - CoderAgent/DebugAgent 模型调用已记录 worker context envelope path/hash，并已把 ContextEnvelope 纳入 capability report 审计统计。
   - 剩余目标是把 Review/Plan 等更多 Goal Loop 模型调用、weekly/gate 视图、user_progress 和 Inspector 继续接入同一审计链。

6. 工具、MCP、Skills 调用时机还缺少策略表。
   - 目标是“策略约束 + 模型选择 + observation 验证”，而不是只靠模型临场猜。

7. Research、Brainstorm、AutoResearch、多智能体等链路还缺少场景型 loop profile。
   - 目标是让每条链路按自身业务语义运行。
   - 核心 Goal Loop 负责动态调度和最终验收，不把这些原子能力压平成同一个通用模板。
   - 能力和智能体链路应像 Skills/MCP 一样注册为模型可理解、可审计、可验证的原子能力。

8. Workspace 和输出位置还没有产品化。
   - Asteria 是通用目标完成产品，不应默认只在当前目录做单工程开发。
   - 目标是让用户能选择 workspace、输入目录、输出目录、候选工作区策略、git 策略和权限模式。
   - 多工程目标必须明确每个目录的 read/write scope，并让用户知道产物输出到哪里。
   - 单工程 run/session/evidence/artifact 必须落在 workspace 内；用户目录下的全局 `.asteria/` 只保存 recent workspace、current workspace、模型 route、账号引用和 UI 偏好。

- 权限模式已有 `ask_everything`、`reviewed_auto`、`auto` 三档基础 profile。
- 工具权限侧已开始使用 permission profile。
- user_progress 已增加 workspace、permission、tool、validation 等基础事件。

### 已完成：Ask / Chat 动态上下文第一阶段

- 普通 Ask/Chat 不默认读取 `.asteria/memory/active_goal.md`。
- 状态/进展/计划/下一步类问题才读取长期任务记忆。

### 已完成：长期任务记忆协议化与 Status 用户状态视图第一阶段

- active goal memory 已从 Markdown 渲染副产物升级为结构化长期任务状态第一版。
- Markdown 继续作为用户可读永久记忆。
- `run` 和 `accept` 更新时已记录来源和原因。
- 普通 status 已输出用户状态卡片：当前目标、已完成、当前状态、需要用户做什么、下一步。

### P0：长期任务记忆协议补齐

- 继续补齐 `review`、`resume`、`repair` 的细分更新来源和原因。
- 增加冲突处理和恢复策略。
- 将状态卡片接入更多 user_progress / Studio 消费场景。

### 已完成：ContextEnvelope 第一阶段收敛

- 已新增 Chat 可使用的 ContextEnvelope 结构。
- 已明确 audience、intent、sections、refs、redaction policy。
- Chat 模型请求已记录 envelope id/hash/path，envelope 已持久化为审计证据。
- ContextPackageBuilder 已嵌入并持久化 worker envelope，旧 `safe_project_context` 已下线，ChatIntentPolicy 已独立。
- CoderAgent/DebugAgent 模型调用已记录 worker context envelope path/hash。
- capability report 已汇总 context envelope 数量、hash 和模型调用关联统计。
- Chat envelope payload 已接入 CapabilityInvocationPolicy 第一版。
- ContextEnvelope 同时服务模型输入、用户过程展示和审计证据，不只是给模型拼 prompt。

### P1：能力调用策略

- ChatContextBuilder 已接入 CapabilityInvocationPolicy 第一版；下一步建立 Goal/Plan/Tool 执行侧的工具、MCP、Skills 调用策略表。
- 普通 Ask 默认 no tool/no MCP/no skill。
- 长任务按 task_kind、risk、permission 开放能力。
- 每次能力选择记录 reason，失败进入 diagnose/repair/replan/ask/stop。

### P1.5：场景型智能体链路与专业入口

- 把 Research、Brainstorm、AutoResearch、Debug、Review、Coder、多智能体调度升级为具备业务方法论的 loop profile。
- 新增能力注册层，把工具、MCP、Skills 和智能体链路暴露为模型可理解的 manifest/profile。
- Research 链路输出深度研究结论、证据等级、验证动作和未确认风险。
- Brainstorm 链路输出开放型候选方向、项目特征、机会、风险和可进入 Plan/Goal 的建议。
- 多智能体链路支持 UI、架构、测试、代码等角色在隔离上下文和 sandbox 中并发工作，再由 Review/MergeGate 收敛。
- 普通用户看到实时过程、阶段性判断和体系化结果；debug/ops 视图进一步展示 worker graph、provider route、候选差异和合并细节。

### P2：Studio 产品交互面

- Studio 作为独立工程长期建设，不作为 Runtime 后端 P0 的前置依赖。
- Studio 消费 runtime evidence、user_progress、Inspector、配置和管理接口。
- Studio 重点是用户心流、实时过程、文件预览/对比、Git、MCP、plugin、skills、session、用户、token、权限和模型配置管理。
- 后端协议稳定前，Studio 进度可以略落后；但 Studio 的产品设计不能被临时后端实现反向绑死。
