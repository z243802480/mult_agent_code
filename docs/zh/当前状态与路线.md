# 当前状态与路线

更新时间：2026-05-27

本文是 Asteria 当前阶段的事实入口。进入开发前先读根目录 `AGENTS.md`，再读本文，然后按 [文档导航.md](./文档导航.md) 选择详细设计文档。

本文只记录当前事实、当前差距和下一步优先级。过程性旧计划不再放在这里；已过时计划应删除，永久设计进入对应设计文档。

## 1. 当前阶段

Asteria 当前处于：

```text
编排式 Asteria Runtime OS 阶段
```

产品能力目标是：

```text
本地优先、可恢复、可审计、成本受控的长任务自主开发运行时。
```

当前重点不是 dashboard，也不是 unrestricted agent chatroom，而是把紧凑用户目标稳定转成经过验证的产物：目标规格化、任务分解、动态上下文、受控工具调用、证据记录、验证、修复、成本控制、最终交付。

## 2. 当前事实

已经具备的工程基线：

- CLI/runtime loop 已有 `init`、`goal/run`、`status`、`review`、`accept`、`doctor`、`gate`、`gray` 等入口。
- `.asteria/` 下已经持久化 run、task、worker、runtime profile、context mount、evidence、validation、report 等运行对象。
- Runtime OS 对象已经覆盖 TaskGraph、WorkerInvocation、WorkerResult、RuntimeProfile、ContextMount、TaskExecutionEvidence、MergeGate。
- ContextPackage 已能按 read scope、write scope、artifact refs、failure refs、decision refs、validation refs 裁剪 worker 上下文。
- PromptEnvelope、CapabilityManifest、AgentRoleContract、ToolObservation 已有第一版，模型调用开始记录 role、route、deadline、prompt envelope、capability manifest 等审计字段。
- 模型路由已支持 strong/medium/cheap 默认兜底，缺少 env/local route 或 capability profile 过期时不会卡死在 route guidance。
- ReviewAgent 已有 strong -> medium -> cheap 的降级 fallback，失败时能产生可审计 metadata。
- `status --debug`、JSON、gate、doctor、acceptance 等工程控制面已有较多底层证据。
- `ActiveGoalMemory` 已开始写 `.asteria/memory/active_goal.md`，但还只是 Markdown 渲染器，不是完整长期状态协议。

最近完整验证基线：

- `pytest -q`：550 passed, 26 deselected。
- `mypy src`：通过。
- `ruff check src tests`：通过。
- 最近 pushed commit：`3fbdb92 runtime: add auditable model route fallback`。

## 3. 当前主要差距

当前差距以 [代码现状差距与研发计划.md](./代码现状差距与研发计划.md) 为准。摘要如下：

1. Chat 动态上下文不够准。
   - 当前 `ChatCommand` 仍会默认读取长期任务记忆。
   - 目标是普通 Chat 只使用当前对话和轻量项目上下文，只有状态/进展/下一步类问题才挂载长期任务记忆。

2. 长任务记忆还不是协议。
   - 当前 `.asteria/memory/active_goal.md` 是 Markdown 输出。
   - 目标是结构化长期任务状态 + Markdown 用户视图，并记录更新来源和原因。

3. Status 用户视图还不够产品化。
   - 当前普通 `status` 已开始面向用户，但仍偏“整段状态文件输出”。
   - 目标是用户状态卡片：当前目标、已完成、当前状态、需要用户做什么、下一步。

4. ContextPackage 和 Chat Context 断裂。
   - 长任务 worker 已有 ContextPackage。
   - Chat 仍在手工拼 `safe_project_context`。
   - 目标是收敛到可审计的 ContextEnvelope。

5. 工具、MCP、Skills 调用时机还缺少策略表。
   - 目标是“策略约束 + 模型选择 + observation 验证”，而不是只靠模型临场猜。

6. Research、Brainstorm、多智能体等链路还缺少场景型 loop profile。
   - 目标是让每条链路按自身业务语义运行：Research 走深度研究方法论，Brainstorm 走开放型发散与收敛，多智能体按角色、上下文、provider 和 sandbox 并发协同。
   - 核心 Goal Loop 负责动态调度和最终验收，不把这些原子能力压平成同一个通用模板。
   - 需要避免把调度逻辑写死在程序分支里；能力和智能体链路应像 Skills/MCP 一样注册为模型可理解、可审计、可验证的原子能力。

7. 文档体系刚开始清理。
   - 目标是保留权威事实入口、永久设计文档和当前执行计划。
   - 过时过程计划应删除，避免后续 agent 读错方向。

## 4. 当前研发优先级

### P0：文档收敛

先清理中文文档，确保后续开发依据正确：

- 保留当前事实入口、永久设计、协议、规格、命令参考、数据模型、质量评估和当前代码计划。
- 删除已经被吸收的过程性旧计划。
- 建立 [文档状态审计.md](./文档状态审计.md)，给主文档标记 `current`、`design`、`reference`、`deleted`。
- 让新 agent 默认只需要读 3 到 5 份文档即可知道当前阶段和下一步。

### P0：Goal / Plan / Ask 与动态上下文修正

完成文档清理后立即修：

- 用户主入口收敛为 Goal / Plan / Ask；`init/run/status/review/accept` 保留为 runtime 内部智能体阶段、专家命令或产品界面背后的动作。
- 普通 Ask/Chat 不默认读取 `.asteria/memory/active_goal.md`。
- 状态/进展/计划/下一步类问题才读取长期任务记忆。
- 调试类问题才暴露 backend 字段。
- 当 Plan 产生多个行动优先级时，由用户确认下一步执行哪个。
- 增加回归测试，防止普通 Ask/Chat 被旧目标污染。
- 前台输出负责友好解释内部阶段，而不是把后台阶段名直接交给普通用户。

### P0：长期任务记忆协议化

- 把 active goal memory 从 Markdown 渲染副产物升级为结构化长期任务状态。
- Markdown 继续作为用户可读永久记忆。
- `run`、`review`、`accept`、`resume`、`repair` 更新时记录来源和原因。
- `accept` 表达验收回顾：目标、验收标准、测试/验证证据、交付物、残余风险和下一步。

### P0.5：ContextEnvelope 收敛

- 新增 Chat/Goal 都可使用的 ContextEnvelope 结构。
- 明确 audience、intent、sections、refs、redaction policy。
- 模型请求记录 envelope hash/path。

### P1：能力调用策略

- 建立工具、MCP、Skills 调用策略表。
- 普通 Chat 默认 no tool/no MCP/no skill。
- 长任务按 task_kind、risk、permission 开放能力。
- 每次能力选择记录 reason，失败进入 diagnose/repair/replan/ask/stop。

### P1.5：场景型智能体链路

- 把 Research、Brainstorm、Debug、Review、Coder、多智能体调度升级为具备业务方法论的 loop profile。
- 新增能力注册层，把工具、MCP、Skills 和智能体链路暴露为模型可理解的 manifest/profile。
- 调度由用户目标、动态上下文、能力清单、预算、风险和验收标准共同驱动，避免把组合方式写死在核心程序里。
- Research 链路输出深度研究结论、证据等级、验证动作和未确认风险。
- Brainstorm 链路输出开放型候选方向、项目特征、机会、风险和可进入 Plan/Goal 的建议。
- 多智能体链路支持 UI、架构、测试、代码等角色在隔离上下文和 sandbox 中并发工作，再由 Review/MergeGate 收敛。
- 普通用户只看到体系化结果；debug/ops 视图才展示 worker graph、provider route、候选差异和合并细节。
