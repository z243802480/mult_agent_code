# Asteria 用户交互模型

## 1. 结论

Asteria 面向普通用户只暴露三种模式：

1. `goal`：长任务目标模式。用户给出一个长期目标，系统持续运行、计划、执行、修复、评审和汇报。
2. `plan`：只读综合计划模式。系统分析目标，给出合适、全面、可执行的计划，但不修改工作区。
3. `chat`：日常问答模式。系统回答问题，辅助读取公开/非敏感上下文和少量安全工具，不进入长任务执行。

`run/status/review/accept/gate/promotions/gray` 等仍然存在，但它们是 runtime 内部机制、专家调试命令或 CI/维护命令，不应成为普通用户主路径。

## 2. 设计哲学

Asteria 的用户体验应以结果为导向，而不是以内部阶段为导向。

用户不应该被迫理解：

```text
run -> status -> review -> accept -> gate -> promotion -> gray
```

用户应该只需要表达：

```text
goal: 我要长期完成什么
plan: 帮我分析怎么做，不要改
chat: 我问一个问题
```

内部仍然可以保留 GoalSpec、TaskGraph、WorkerInvocation、TaskExecutionEvidence、Review、Acceptance、PromotionGate、ContextSnapshot 和 cost control，但这些是系统质量保证结构，不是普通用户的操作流程。

## 3. 三种用户模式

### 3.1 goal：长任务目标模式

定位：默认主模式。

适用：

- 用户希望系统持续推进一个项目、功能、修复、研究复现或产品化目标。
- 用户接受系统在权限策略内进行文件修改、命令执行、验证、修复和阶段性汇报。
- 任务可能跨多轮、跨天、跨多个 ContextSnapshot。

用户输入示例：

```bash
asteria goal "持续完善这个项目，优先做通普通用户闭环"
```

系统内部动作：

1. 理解目标并生成 GoalSpec。
2. 必要时做研究或读取项目上下文。
3. 生成任务图和综合计划。
4. 根据权限等级判断哪些动作可自动执行，哪些必须询问。
5. 执行任务、记录 evidence、验证、修复。
6. 自动进行内部 review。
7. 形成结果报告、进度摘要和下一轮建议。

用户可见输出：

- 当前目标摘要。
- 当前正在做什么。
- 已完成产物。
- 阻塞原因。
- 需要用户决策的问题。
- 下一步系统将做什么。
- 最终结果和证据报告。

用户不需要手动调用 `review` 或 `accept`。这些应由 goal loop 在内部自动使用；只有在明确需要人工确认时才暴露为 DecisionPoint。

### 3.2 plan：只读综合计划模式

定位：分析、规划、评估，不修改。

适用：

- 用户还没决定是否执行。
- 用户要一个全面研发计划、产品方案、技术路线、风险评估或拆解。
- 用户希望类似“先让我看看你会怎么做”。

用户输入示例：

```bash
asteria plan "把这个项目做成可内测产品"
```

强约束：

- 不修改用户业务文件。
- 不执行破坏性命令。
- 不进行候选代码 promotion。
- 不自动进入长任务执行。
- 可以读取非敏感项目上下文。
- 可以产出计划文件或只打印计划；若需要落盘，应写入 `.asteria/` 或明确的报告路径。

输出应包含：

- 目标理解。
- 分阶段计划。
- 关键里程碑。
- 风险和待确认点。
- 权限与成本建议。
- 推荐的 goal 模式启动方式。

### 3.3 chat：日常问答模式

定位：轻量问答和辅助。

适用：

- 用户问项目现状、某个文件含义、某个设计选择。
- 用户问一般技术问题。
- 用户让系统解释错误、比较方案、总结文档。

强约束：

- 默认不修改文件。
- 默认不执行会改变状态的命令。
- 可以使用安全只读工具。
- 涉及不确定、高风险或需要修改时，应建议切换到 `plan` 或 `goal`。

用户输入示例：

```bash
asteria chat "当前项目最大的产品风险是什么？"
```

## 4. 权限等级

用户应在启动 goal/plan/chat 时选择权限等级。权限等级决定敏感动作前是否询问。

建议初始等级：

| 等级 | 名称 | 行为 |
|---|---|---|
| `ask` | 保守确认 | 修改文件、执行 shell、联网、安装依赖、删除/移动文件、push/deploy 前都询问 |
| `balanced` | 平衡默认 | 低风险读写和验证命令可自动执行；敏感、不可逆、高成本、隐私相关动作必须询问 |
| `auto` | 自动推进 | 在项目策略允许范围内自动执行大多数低/中风险动作；高风险动作仍询问 |

无论权限等级如何，以下动作默认仍需显式确认或被禁止：

- 读取 `.env`、密钥、secrets、私钥。
- 破坏性 shell 操作。
- 全局安装包。
- 远程 push。
- 生产部署。
- 大规模删除、覆盖、迁移。
- 超出预算 hard-stop。

权限等级应映射到内部 `decision_granularity`、`permissions` 和 DecisionPoint 策略，而不是让用户学习内部字段。

## 5. 模型切换

用户应能选择模型策略，而不是直接理解每个内部 agent 的模型路由。

建议用户可见模型策略：

| 策略 | 用途 |
|---|---|
| `auto` | 默认，根据任务选择 strong/medium/cheap |
| `quality` | 更重视规划、复杂代码和 review 质量 |
| `economy` | 更重视成本，适合简单任务和文档任务 |
| `local` | 优先本地或隐私优先模型 |

内部仍可保留：

- `goal_spec`
- `planning`
- `coding`
- `review`
- `debugging`
- `summarization`

但普通用户只需要选择模型策略。

## 6. 命令分层

### 用户主命令

```text
goal
plan
chat
```

### 专家/调试命令

```text
status
sessions
resume
review
accept
execute
debug
replan
compact
handoff
promotions
```

这些命令允许保留，但在帮助、文档和产品介绍中应标注为高级命令。

### 维护/CI 命令

```text
doctor
gate
gray
acceptance
package-check
real-model-*
```

这些命令面向维护者、CI 和发布流程，不属于普通用户体验。

## 7. 研发落地顺序

P0 研发顺序：

1. 新增 `goal` 入口，作为长任务默认入口，内部复用当前 `RunCommand`。
2. 将 `plan` 明确定义为只读综合计划，不进入执行，不修改用户业务文件。
3. 新增 `chat` 入口，先实现安全问答骨架和上下文摘要，后续接模型。
4. 在 CLI help 中把 Start 收敛为 `goal/plan/chat`，其他命令下沉到 Advanced/Maintain。
5. 将权限等级和模型策略作为 `goal/plan/chat` 的用户可见参数。
6. 后续再把 goal loop 做成真正可持续运行：自动 review、自动修复、阶段报告、必要时 DecisionPoint。

## 8. 成功标准

短期成功标准：

- 用户看到 help 时，只会把 `goal/plan/chat` 当作主入口。
- `plan` 明确是只读分析，不会误触发执行。
- `goal` 能启动长任务目标，不要求用户手动理解 review/accept。
- `chat` 能作为轻量问答入口存在，遇到执行需求时引导到 plan/goal。

中期成功标准：

- 一个普通用户可以只使用 `goal` 长期推进项目。
- 系统只在权限、风险、成本和不可逆动作处打断用户。
- 内部 evidence/review/accept/gate 全部服务于结果质量，而不是增加用户操作负担。
