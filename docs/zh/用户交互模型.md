# Asteria 用户交互模型

更新时间：2026-05-27

本文定义普通用户应该如何使用 Asteria。它约束产品路径，不是 runtime 内部命令清单。

## 1. 核心结论

Asteria 的用户侧入口应收敛为两类主模式：

1. `goal`：目标执行模式。用户说出想完成什么，系统在权限、预算和验收边界内持续推进。
2. `plan`：只读计划模式。用户要求分析、拆解、比较、制定方案，系统不修改用户业务文件。

`chat` / `ask` 不是第三条复杂产品主线。它可以存在为轻量问答入口，但语义上是一个低风险、只读、短回合的简单 goal：回答用户当前问题，不进入长任务执行，不默认读取长期任务记忆。

Brainstorm、Research、Debug、Review、Coder、多智能体等专业智能体链路可以作为显式专家入口，也可以作为 Goal / Plan 背后的 runtime action。它们不是普通用户必须理解的主入口，但必须通过产品界面转译成可理解的实时过程。

用户不应该直接面对一串 runtime 命令，例如：

```text
run -> status -> review -> accept -> gate -> promotion -> validation
```

这些内部能力不是要删除，而是要降级为 runtime 的智能体阶段、专家命令、维护命令或产品背后的 action，并被 Goal/Plan/Ask 的意图识别、权限策略和调试视图包装起来。每个阶段本身都是一个小的大模型核心循环，只是阶段目标不同：

- `init`：初始化项目长期记忆、项目摘要、规则和运行时状态，为后续深度工作建立稳定上下文。
- `run`：执行核心大模型循环，围绕目标进行计划、工具调用、观察、修复和验证。
- `status`：读取当前运行状态，把实现过程翻译成用户能理解的进展、阻塞和下一步。
- `review`：任务完成后复盘目标、验收标准、证据、遗漏和风险。
- `accept`：收尾，固化结果、验收回顾、长期记忆和下一步建议。

这套体系化智能体流程能让目标完成得更好，但不需要显性告诉普通用户。用户只对屏幕输出负责：看到实时的大模型判断结论、接口调用过程、工具调用过程、关键思考摘要、验证进展、问题、最终结果整理和下一步，而不是看到内部阶段名、裸 trace、schema dump 和后台字段。

## 2. 产品模式

### 2.1 Goal

Goal 是默认主模式。

适用：

- 用户希望系统完成一个开发、修复、研究、文档或产品化目标。
- 用户接受系统按策略读取项目上下文、修改文件、运行验证、修复失败并汇报结果。
- 任务可能跨多轮、跨天、跨 ContextSnapshot。

用户输入示例：

```bash
asteria goal "把普通用户闭环做通，并修掉明显阻塞"
```

系统内部可以使用：

- GoalSpec
- TaskGraph
- ContextEnvelope / ContextPackage
- WorkerInvocation
- ToolObservation
- ReviewAgent
- ValidationResult
- Acceptance review
- ContextSnapshot
- init / run / status / review / accept 等内部阶段循环

但普通用户看到的是：

- 目标理解。
- 当前计划。
- 正在做什么，以及为什么这样做。
- 接口和工具调用过程。
- 关键思考摘要。
- 已完成什么。
- 是否需要用户选择优先级或确认风险。
- 验证是否通过。
- 最终结果整理。
- 下一步建议。

### 2.2 Plan

Plan 是只读计划模式。

适用：

- 用户还不确定是否执行。
- 用户要求技术方案、产品路线、风险评估、任务拆解或优先级建议。
- 系统需要给出多个行动候选，让用户选择下一步。

强约束：

- 不修改用户业务文件。
- 不执行会改变状态的命令。
- 不做候选 promotion。
- 可以读取非敏感项目上下文。
- 如果需要保存计划，优先写入 `.asteria/` 或明确的报告路径。

当 Plan 产出多个行动优先级时，系统必须让用户引导确认下一步执行哪个。Plan 的输出不应自动变成执行。

### 2.3 Ask / Chat

Ask/Chat 是轻量问答。

适用：

- 用户问一个普通问题。
- 用户要求解释某段代码、某份文档、某个错误。
- 用户询问当前项目状态或下一步。

约束：

- 默认不修改文件。
- 默认不执行会改变状态的命令。
- 默认不读取长期任务记忆。
- 当用户询问“当前状态、进展、下一步、计划、恢复”时，才按需读取长期任务状态。
- 当问题需要执行或写入时，建议切到 Plan 或 Goal。

因此 Chat 不是长期记忆驱动的万能会话。它应该基于当前对话和按需动态上下文给出最好的当下回答。

## 3. 意图识别

界面可以让用户显式选择 Goal 或 Plan，也可以通过意图识别自动路由。

建议路由：

```text
明确要求分析/比较/计划/不修改
  -> Plan

明确要求实现/修复/生成文件/运行验证/推进项目
  -> Goal

普通问答/解释/总结
  -> Ask

询问当前状态/进展/下一步
  -> Ask + 按需挂载长期任务状态

高风险、不可逆、成本高、方向不明确
  -> Ask user / DecisionPoint
```

Cursor 一类产品会把 Plan、Debug、Multitask、Ask、Image、Models、Skills、MCP Servers 放在一个菜单里。Asteria 可以借鉴这种“模式 + 上下文/工具选择”的信息架构，但普通用户主入口不应膨胀成一串 runtime 命令。

在 Asteria 中：

- Plan / Goal 是主要模式。
- Ask 是轻量模式或默认自然语言入口。
- Debug 是高级/运维能力，不是普通主线。
- Models、Skills、MCP Servers 是上下文和能力配置，不是用户任务模式。
- Multitask 是 Goal 内部的执行策略，不是默认让用户选择的复杂模式。
- Image 等领域能力应按任务类型或 Skill 暴露，不应污染 Runtime Core 主线。

## 4. 用户确认和优先级选择

当系统产生多个可行动方向时，必须让用户引导确认，例如：

- 先做产品体验，还是先做路由稳定性。
- 先修文档，还是先改代码。
- 先做低风险验证，还是扩大真实任务验证。
- 是否允许读取更大范围上下文。
- 是否允许写文件、运行命令、联网、使用更强模型或增加预算。

这些确认不一定都叫 `accept`。它们更接近 DecisionPoint 或用户优先级选择。

## 5. Accept 的含义

`accept` 不应被设计成普通用户必须理解的 backend 命令。它是 runtime 收尾阶段的一部分。

更准确的语义是：

```text
Acceptance review = 对验收标准、验证证据和交付结果的回顾。
```

只要系统动了代码，就必须按需引入验证：

- 最小变更：运行相关单元测试、lint/typecheck 或针对性脚本。
- 多文件/共享逻辑变更：扩大到相关测试集合。
- 用户可见行为变更：需要结果说明、验收标准回顾，必要时加回归测试。
- 无法运行测试：必须说明原因、风险和替代验证。

`accept` 的产品含义不是“流程结束按钮”，而是：

- 回顾原始目标。
- 回顾验收标准。
- 回顾做了什么。
- 回顾测试/验证是否支持“功能正确”。
- 标出残余风险。
- 给出下一步。

在前台，accept 可以表现为一段友好的验收回顾，而不是让用户看到“现在请运行 accept 命令”。它类似大模型思考过程里的最终自检：内部发生了复盘和收束，用户看到的是可信的结论。

如果验收不充分，系统不能假装完成；应该进入修复、补测、重新计划或询问用户。

## 6. 权限等级

用户可选择权限等级，但不需要理解内部 policy 字段。

| 等级 | 名称 | 行为 |
| --- | --- | --- |
| `ask_everything` | 每步询问 | 任何写入、shell、联网、安装依赖、删除/移动、push/deploy、外部接口调用和高成本动作前都询问。询问卡片必须提供“允许一次”“允许这类开头/同类命令本次会话都通过”“拒绝”“改为计划模式”等选择。 |
| `reviewed_auto` | 自动审查 | 默认模式。内置低风险动作自动通过，例如只读搜索、读取非敏感项目文件、写入明确输出目录、运行测试、格式化、查看 git diff；敏感、不可逆、高成本、越权、联网、删除/移动、push/deploy 等动作询问。询问时同样提供“允许一次”“允许同类动作本次会话都通过”“拒绝”“改为计划模式”。 |
| `auto` | 全自动推进 | 用户认为本次目标已完全授权，由大模型循环接管目标推进。系统自动使用体系化能力、专业智能体、工具、MCP、Skills、候选工作区和验证链路完成目标，不要求用户自行操作；但 runtime 仍必须拦截 secrets、受保护路径、生产部署、远程 push、大规模删除、破坏性 shell、预算 hard-stop 等高爆炸半径动作，并自动采用更安全的候选工作区、备份、diff、验证和回滚策略。 |

> **默认档持久化（Studio）**：用户在顶栏齿轮 **Settings** 里选的权限等级保存到 `.asteria/studio/settings.json`，作为**默认档**给新消息打底；任一条消息仍可在 Composer 里临时改档。三套历史词表（server 显示串 / Composer / 运行时 `--permission-level`）已归一到单一真源 `studio/src/permissionTiers.ts`（`ask_everything→ask`、`reviewed_auto→balanced`、`auto→auto`）。无论哪档，下方 hard-stop 始终拦截。

始终需要显式确认或默认禁止：

- 读取 `.env`、密钥、secrets、私钥。
- 破坏性 shell。
- 全局安装包。
- 远程 push。
- 生产部署。
- 大规模删除、覆盖、迁移。
- 超出预算 hard-stop。

权限询问不是简单 yes/no。每次询问都应说明：

- 系统想做什么。
- 为什么需要这个动作。
- 影响哪些文件、目录、网络目标或外部系统。
- 风险等级和可回滚方式。
- 可选项：允许一次、允许同类动作本次会话都通过、拒绝、改成只读计划、修改输出位置或缩小 scope。

`auto` 不是放弃安全，而是从“用户逐步操作”切换为“模型在 runtime 护栏内自动完成”。模型可以自主拆解、调度专业智能体、调用工具、修复失败、运行验证和整理结果；runtime 必须继续负责权限、计费、protected paths、schema、证据、候选工作区、merge gate 和恢复。

## 6.1 Workspace 与输出位置

Asteria 是通用目标完成产品，不应假设用户永远只在当前目录做单工程开发。用户开始 Goal 或 Plan 前，产品必须能明确工作发生在哪里、产物输出到哪里。

Workspace 选择应支持：

- 当前目录作为 workspace。
- 最近 workspace 列表。
- 用户选择一个本地目录。
- 多工程 workspace：一个目标可挂载多个项目目录，但必须为每个目录声明读写权限。
- 临时 workspace / candidate workspace：用于实验、生成、修复和多智能体候选实现。
- 只读 source workspace + 明确 output directory：适合报告、研究、文档、生成物、迁移计划和不应直接改源码的任务。

产品界面应有 Project / Workspace Switcher：

- 展示最近 workspace，名称类似 `site_soe`、`fileCollector`、`mult_agent_code`。
- 支持 `Open folder...` 选择本地目录。
- 切换 workspace 后，session 列表、run、文件预览、Git 状态、plugin 和 workspace skills 配置视图切到该 workspace；MCP server catalog 默认来自产品/用户层配置，只显示当前 workspace 是否允许使用和运行限制。
- 单工程输出文件、运行证据、Studio session thread 和 `.asteria/runs/` 都在 workspace 目录下。
- 只有全局配置、最近 workspace 索引、模型 route 本机配置、账号和产品偏好放在用户目录，例如 `C:\Users\<User>\.asteria\`。

每个目标启动前应形成 Workspace Envelope：

```text
workspace_root
input_roots
output_root
candidate_workspace_policy
read_scope
write_scope
artifact_policy
git_policy
permission_mode
```

用户侧必须能看懂：

- 当前正在处理哪个 workspace。
- 可以读取哪些目录。
- 可以写入哪些目录。
- 结果会输出到哪里。
- 是否会使用 candidate workspace / git worktree。
- 哪些变更需要用户审批后才合并回主工程。

如果用户没有指定输出位置，系统必须给出安全默认：

- 代码修改：优先在候选工作区或受控 patch 中完成，验证通过后再进入 promotion / review。
- 报告和研究：默认写入 `.asteria/reports/` 或用户指定目录。
- 生成型产物：默认写入明确的 output directory，不散落到项目根目录。
- 多工程任务：默认不跨项目写入，除非 Workspace Envelope 明确授权。

## 7. 模型策略

用户应选择模型策略，而不是内部 agent route。

| 策略 | 用途 |
| --- | --- |
| `auto` | 默认，根据任务选择 strong/medium/cheap |
| `quality` | 重视规划、复杂代码、review 和验收质量 |
| `economy` | 重视成本，适合简单任务和文档任务 |
| `local` | 优先本地或隐私优先模型 |

内部可以继续按 goal_spec、planning、coding、review、debugging、summarization 选择模型 tier、provider、deadline 和 fallback，但普通用户只需要知道当前策略和必要的用户级解释。

## 8. 命令暴露面

### 普通用户主入口

```text
goal
plan
ask/chat
```

### 高级/调试入口

```text
status --debug
sessions
resume
review
accept
execute
debug
replan
compact
handoff
promotions
```

这些命令可以保留给维护者、开发者和自动化系统，也可以作为产品界面背后的动作，但不应作为普通用户产品路径宣传。

### 维护/CI 入口

```text
doctor
gate
validation
acceptance
package-check
real-model-*
evidence-bundle
```

这些命令面向维护、验证、发布和诊断，不属于普通用户心智模型。

## 9. 成功标准

短期成功标准：

- 用户看到默认帮助时，只会把 Goal/Plan/Ask 当成主入口。
- Plan 不会误触发执行。
- Goal 可以推进长任务，并在必要时询问优先级或权限。
- Ask 可以回答轻量问题，状态类问题按需挂载长期任务状态。
- 普通回答不泄漏 run_id、evidence、model_route 等 backend 字段。

中期成功标准：

- 普通用户可以只用自然语言和 Goal/Plan/Ask 长期推进项目。
- 系统只在权限、风险、成本、优先级和不可逆动作处打断用户。
- 内部 evidence/review/accept/gate 全部服务于结果质量，而不是增加用户操作负担。
