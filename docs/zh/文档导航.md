## 5. 当前阶段

当前项目处于：

```text
编排式 Asteria Runtime OS 阶段
```

阶段判断：

- 后台工程闭环已经具备：规划、执行、debug、replan、review、final report、acceptance gate、capability report。
- 长任务控制平面已经具备基础入口：`/daily-*` 与 `/long-run-*` 可用于时间盒或里程碑式运行；“每日”只是默认周期，不是架构边界。
- 当前主线已经切换为“编排式 Asteria Runtime OS”：`WorkerInvocation`、`TaskGraph`、`RuntimeProfile`、`MergeGate`、`ContextMount` 是近期核心对象。
- 产品能力描述为“长任务自主开发 Runtime”：目标是长时间、可恢复、可审计地推进真实开发任务，而不是把运行周期写死为自然日。
- 下一步重点不是 dashboard，而是证明 `/run`、`/execute`、`/debug`、`/handoff`、`/resume`、`/acceptance` 在严格 task contract、候选工作区和 merge gate 下可稳定闭环。
- Dashboard 原型应晚于 CLI 报告、worker evidence、handoff/resume 恢复链路稳定之后。

当前验证方式：

1. 本机：`python -m pip install -e ".[dev]"` 后执行 `.\scripts\verify.ps1`，覆盖 CLI smoke、context snapshot、handoff 和 `sessions --context` 恢复入口，并写入 `.asteria/verification/latest.json`。
2. Docker：`docker build -t asteria-runtime:verify .` 后执行 `docker run --rm asteria-runtime:verify`。
3. CI：GitHub Actions 使用同一套验证脚本，覆盖 Python 3.11 和 3.13。
4. 离线模型：设置 `AGENT_MODEL_PROVIDER=fake` 后可不依赖 API key 跑 CLI smoke。
5. 本地模型：设置 `AGENT_MODEL_PROVIDER=ollama` 和 `AGENT_MODEL_NAME=qwen2.5-coder:7b` 后可连接本机 OpenAI-compatible 服务。
6. 分层路由：设置 `AGENT_MODEL_STRONG_PROVIDER`、`AGENT_MODEL_MEDIUM_PROVIDER`、`AGENT_MODEL_CHEAP_PROVIDER`
   后可分别路由强模型、普通模型和便宜/离线模型。
7. 真实模型 smoke：执行 `asteria real-model-smoke`，命令会在隔离 workspace 内完成最小闭环，详见
   [开发指南.md](./开发指南.md)。
8. 真实模型灰度门槛：先执行 `asteria real-model-gate --summary-json .asteria/model/real_model_gate_report.json`，
   再执行 `asteria real-model-acceptance --suite gray --summary-json .asteria/verification/real_model_acceptance_gray.json`。
   2026-05-16 的 GLM coding route strong + MiniMax medium 组合已通过该灰度基线；2026-05-17 planned verification 兜底修复后完整 gray suite 复跑 4/4 通过，`gray_multi_file_scope` 为 `within_budget`；GLM coding endpoint 使用 `https://open.bigmodel.cn/api/coding/paas/v4`。
9. 真实模型验收：执行 `asteria real-model-acceptance --suite core`；额度允许时执行
   `--suite nightly`，摘要会记录耗时、模型/工具调用、token 估算、修复次数、任务状态分布和评审状态。
10. 真实 API key 只能通过环境变量或 secret 注入，不能写入仓库、文档、日志或测试夹具。
11. 编排式运行时验收：全量 `pytest` 必须覆盖 `workers.jsonl` / `worker_results.jsonl` 写入、worker failure evidence、merge gate 阻止越权 promotion、context snapshot/handoff 携带 worker summary，以及 resume 后继续执行受控任务。

## 6. 文档维护原则

- 主文档用于执行和评审。
- 原始分册用于追溯和细节参考。
- 需求不能因为合并而消失。
- 暂缓需求必须进入路线图、风险处理或后续任务池。
- 高风险能力必须在设计层有控制机制。
- 每轮较大开发完成后，应优先更新 [当前状态与路线.md](./当前状态与路线.md)，再按需更新详细文档。
