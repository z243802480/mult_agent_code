# 代码现状差距与研发计划

更新时间：2026-06-01

本文是当前研发计划的执行依据。已经完成的阶段任务不再列为待办；历史 validation 次数、runtime matrix 通过数和旧 release gate 记录只作回归参考。

## 1. 当前工程判断

Asteria 已从“补 Runtime OS 基础对象”进入“模型主导 agent loop 收口”阶段。

当前已经具备：

- 模型侧工具原语、Skill、MCP、subagent、capability catalog 的第一版暴露和审计。
- role / route / deadline / streaming telemetry 的 model call evidence。
- `AgentLoopDecision`、`AgentLoopExecutionResult`、`AgentLoopObservation` 和 `AgentLoopRunSummary`。
- `ExecuteCommand` bounded loop：observation 可回灌下一轮模型决策。
- RuntimeReadinessGate 对 route/deadline/context/capability/loop execution/observation 的统一检查。
- `ask` 到 DecisionPoint 的闭环。
- `subagent` 到 WorkerInvocation / WorkerResult dispatch evidence 的闭环；`ExecuteCommand` 主链路已支持 child worker planner/decomposer + 多轮 bounded tool loop，并把 child plan、调度策略与 worker completion 回灌父 loop observation。
- status / sessions / gate-status 对 loop decision、execution result、observation、run summary 和下一步命令的消费。

当前仍不能声称完整长任务自主开发已经完成。真实差距集中在：

- subagent 主链路已具备 runtime-owned child planner/decomposer、多 child task plan、readonly/disjoint write 调度证据、多轮 child worker tool loop、readonly fanout 真实并行执行，以及 readonly/disjoint write readiness gate/report 汇总；disjoint write workers 已在 fake path 验证 allow/block，并覆盖 candidate workspace、merge gate、promotion queue/recovery 组合，仍未开放真实并行。
- context compaction / isolation 还不够强。
- capability catalog 与真实模型选择的审计还不够闭环。
- 真实 provider 小任务滚动验证还不够。

设计边界：
- Gate 必须按风险分层，不把所有 agent 输出都变成材料审批。低风险探索、readonly、fake-path planner 和 debug/replan 保持灵活；promotion、merge、rollback、远程 push、真实 provider 放量、发布验收等不可逆或污染风险边界才强 gate。
- 新增 gate 前必须说明风险类型、适用阶段和恢复路径；如果只提升维护者可见性，应优先做 warning/review/trace，而不是默认 blocked。

## 3. 当前 P0

### P0.1 Subagent 执行器深化

目标：

```text
把 subagent dispatch evidence 升级为可执行、可隔离、可回灌父 loop 的子 agent loop。
```

当前状态：

- `subagent` action 会校验 capability_ref、target_task_id、risk、budget_hint。
- Runtime 会写入 `workers.jsonl`、`worker_results.jsonl`，并把 worker ids 回填到 execution result。
- AgentLoopRunner 和 ExecuteCommand 主链路都能把 worker succeeded / failed / timeout 映射为父 loop `AgentLoopObservation(subagent_result)`。
- subagent 执行前会写入 `subagent_child_plans.jsonl`，记录 parent decision/execution、worker slot、child task decomposition、scheduling strategy、parallel safety 和 evidence refs。
- readiness gate 会检查 subagent worker evidence，并要求失败 worker 被父 loop repair / replan / ask / stop 纠偏。
- status 能展示 worker/profile 和 subagent pending。
- worker/runtime profile evidence 已保留 `worker_kind`、`parent_worker_invocation_id`、`parent_runtime_profile_id` 和 `parallel_safety` 接口。
- child candidate workspace manifest 和 task execution evidence 已记录 parent worker、worker kind 与 parallel safety。
- child context mount 已记录 `isolation_policy = subagent_child_context`。
- ContextBudgetMeter v2 已写入 `context_budget_snapshots.jsonl`，subagent child snapshot 记录 token 归因、parent worker/runtime profile、compact boundary 和重复上下文信号。
- RuntimeReadinessGate 会检查最新 subagent worker 是否有 child context snapshot；缺失进入 review，hard-stop/required compact boundary 进入 blocked。

差距：

- child worker planner/decomposer 已支持多 child task decomposition、readonly fanout 与 disjoint write scheduling evidence；readonly fanout 已能真实并行执行、阻断写工具，并进入 RuntimeReadinessGate / gate-status 汇总。
- compact 后的 before/after token 对比、恢复摘要和文件级 hash/diff 降噪还未完成。
- subagent 写入隔离、候选 workspace、merge/promotion 的父子关系已进入 agent run graph；candidate workspace、promotion queue、merge gate summary、promotion recovery summary 已进入 graph，candidate promotion safety 已进入 RuntimeReadinessGate / gate-status；真实文件 rollback 语义仍未开放。

验收：

- subagent 可以在隔离 context 中执行一个只读或小写入任务。
- subagent child plan 能表达 parent decision/execution、worker slot 和 child task decomposition。
- subagent child plan 能按 readonly fanout / disjoint write strategy 产出多个 child task，并记录 scheduling strategy。
- readonly fanout child worker 可以并行真实执行，且写工具会被 Runtime gate 阻断。
- RuntimeReadinessGate 会检查 readonly fanout child worker 是否具备 worker/result/runtime profile/context snapshot/validation refs，并在 gate-status 文本中汇总成功数与成本。
- RuntimeReadinessGate 会检查 disjoint write child plan 是否具备互斥 `write_scope`、changed-artifact/verification contract、candidate workspace / promotion 证据、通过的 merge gate、落在 write_scope 内的 promotable files，且无 unresolved promotion/recovery；allow/block 结论会进入 gate-status。真实 disjoint write workers 仍关闭。
- agent run graph 会汇总 candidate workspace、promotion queue 和 merge gate summary；RuntimeReadinessGate 会对未解决 promotion 标记 review，对 merge gate blocked / promotion failed 标记 blocked。
- agent run graph 会把 rejected / discarded / promoted 映射为 recovered / settled，把 blocked / promotion_failed 映射为 unresolved；RuntimeReadinessGate 会把 rejected / discarded 视为恢复完成后的 ready 状态。
- worker result 能转成父 loop 可消费的 `AgentLoopObservation`。
- 父 loop 能基于 worker result 决定 tool / repair / replan / ask / stop。
- worker graph 能表达父子关系、profile、status 和 evidence refs。

### P0.2 RuntimeReadinessGate 加强 loop run summary 检查

目标：

```text
gate 不只检查 decision/execution/observation，还检查 bounded loop 是否有明确退出原因和下一步命令。
```

当前状态：

- `agent_loop_run_summary.json` 已落盘。
- status / sessions 已能消费 summary。

差距：

- gate 还未强制要求最新 bounded loop 存在 run summary。
- summary 与 latest observation / execution 的一致性还未进入 gate。
- `max_rounds`、`budget_hard_stop`、`ask`、`subagent_pending` 等退出原因还需要在 gate-status 中形成更清晰的 next actions。

验收：

- 缺 summary 的最新 loop execution 被 gate 标记 review/block。
- summary 的 latest ids 与 JSONL evidence 对不上时被 gate 标记 review/block。
- gate-status 能把 exit_reason 映射到 debug / replan / decide / compact / execute / status。

## 6. 版本化研发节奏

当前不能继续按“每次迭代一个很小局部”的方式推进。后续任务必须挂到明确版本、验收口径和真实使用证据上；不能证明版本前进的任务默认降级或暂缓。

当前完成度按产品可用性口径估算约为 75%：Runtime OS 的骨架、证据、gate、bounded loop、candidate/promotion/recovery 图谱、disjoint write fake-path safety、后台使用信号分析、首个真实 provider scoped 验证、P0 targeted probe 扩面、route guidance fresh window 和 alpha.1 验收报告已经形成闭环。剩余差距不再是 alpha.1 证明动作，而是 alpha.2 的小批量 dogfooding 样本、版本验收信号门槛、恢复压力样本和真实并行写入继续关闭状态。

重要边界：后台使用信号是辅助模块，不进入核心 runtime 架构主概念。用户侧产品主体仍是 goal -> plan -> execution -> validation -> artifact -> report；后台只留下脱敏证据指纹，供运维和研发复盘使用。不要让用户显性感知“系统在收集反馈”，也不要把 release / feedback / ops 术语散落到普通执行链路里。

### 6.2 `v0.1.0-alpha.1` Definition of Done

`v0.1.0-alpha.1` 已完成，以下条件均已有最小真实证据：

1. `ruff check .`、`mypy src`、`pytest -q` 通过。
2. `python -m asteria_runtime validation-run --root <workspace>` 输出 `validation_plan.probe_results`，并能区分 `passed`、`failed`、`missing_evidence`。
3. 至少 1 个真实 provider scoped 任务完成运行，证据覆盖 route/deadline、loop decision、worker evidence、validation、final report。
4. `python -m asteria_runtime evidence-bundle --root <workspace>` 能导出脱敏诊断包，且不包含 route/key/.env/private key。
5. 后台使用信号进入一等运维对象：至少包含任务类型、期望结果类别、产物是否被接受、阻塞类别、信任风险、体验体感摘要、失败归因和证据包引用。
6. daily/weekly/report/roadmap 能读取脱敏信号摘要，输出下一轮产品改进建议。
7. 验收报告明确写出：允许进入内测、阻断原因、恢复动作和下一次验证命令。

### 6.3 后台使用信号状态

- 已有 `ops-signal` 后台 intake 能力，可把运行结果、用户是否采纳产物、阻塞类别和 evidence bundle/run id 绑定；该能力默认由运维命令或后台流程触发，不作为普通用户主流程。

- dogfooding 信号转 roadmap / DecisionPoint 的稳定规则，避免把一次性 provider 波动误判为产品方向。
