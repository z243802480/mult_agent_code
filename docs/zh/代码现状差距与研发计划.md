更新时间：2026-05-29

本文是当前研发计划的执行依据。已完成的阶段性任务不再列为待办；历史 validation 次数、runtime matrix 通过数和旧 release gate 记录只作为回归参考。

## 1. 当前工程判断

Asteria 已从“补 Runtime OS 基础对象”进入“模型主导 agent loop 收口”阶段。

当前已经具备：

- 模型侧工具原语、Skill、MCP、subagent、capability catalog 的第一版暴露和审计。
- role / route / deadline / streaming telemetry 的 model call evidence。
- `AgentLoopDecision` schema 和 Runtime execution result。
- RuntimeReadinessGate 对 route/deadline/context/capability/loop execution 的统一检查。
- `ask` 到 DecisionPoint 的闭环。
- `subagent` 到 WorkerInvocation / WorkerResult dispatch evidence 的闭环。
- status / gate-status 对最新 loop decision、execution result 和下一步命令的消费。

当前还不能声称完整长期自主开发已经完成。真实差距集中在“多轮循环自动推进”和“真实小任务连续验证”。

## 3. 当前 P0

### P0.1 Agent loop runner 多轮化

目标：

```text
把一轮 AgentLoopDecision 分派升级为受 Runtime gate 约束的多轮模型循环。
```

当前状态：

- 模型能返回 `tool | subagent | repair | replan | ask | stop`。
- Runtime 能校验、持久化和分派。
- Tool/subagent/recovery/ask 已有第一版执行证据。

差距：

- 每次 tool/subagent/recovery observation 后，还没有统一回到模型生成下一轮 decision。
- loop stop 条件需要统一：完成、ask、budget hard stop、context hard stop、permission block、重复低价值循环、gate block。
- failure observation 需要统一成模型可读输入，而不是分散在 debug/replan/status 中。

验收：

- 一个小任务至少能经历两轮 decision。
- 每轮都有 decision、execution result、observation、next action。
- status 能显示当前 loop position 和下一步。
- gate 能阻断缺失 execution/observation 的 loop。

### P0.2 Subagent 执行器深化

目标：

```text
把 subagent dispatch evidence 升级为可执行的子 agent loop。
```

当前状态：

- `subagent` action 会校验 capability_ref、target_task_id、risk、budget_hint。
- Runtime 会写入 `workers.jsonl`、`worker_results.jsonl`，并把 worker ids 回填到 execution result。
- readiness gate 会检查 subagent worker evidence。

差距：

- subagent worker 还没有独立上下文窗口和完整 execution loop。
- worker completion / failed observation 还没有统一回灌到父 loop。
- subagent 写入隔离、候选 workspace、merge/promotion 的父子关系还需要更明确。

验收：

- subagent 可以在隔离 context 中执行一个只读或小写入任务。
- 父 loop 能消费 worker result 并决定 tool/repair/replan/ask/stop。
- worker graph 能表达父子关系、profile、status 和 evidence refs。

### P0.3 RuntimeReadinessGate 加强 observation 完整性

目标：

```text
gate 不只检查 decision/execution，还检查 execution 后是否有可消费 observation。
```

差距：

- tool/subagent execution result 后的 observation 覆盖还不统一。
- 重复失败 observation 没有进入下一轮 repair/replan/ask/stop 时应 blocked。

验收：

- 缺 observation 的最新 execution 被 gate 标记 blocked/review。
- failed observation 后没有后续 loop decision 被 gate 标记 blocked。

## 6. 推荐下一步

下一步优先做：

```text
P0.1 Agent loop runner 多轮化。
```

原因：

- `tool/subagent/repair/replan/ask/stop` 的单轮分派已经基本接通。
- 继续补单个失败分支的收益下降。
- 真正的产品能力差距是“observation 后 Runtime 自动让模型决定下一步”。

建议实施顺序：

1. 新增 `AgentLoopObservation` schema：统一 tool result、subagent worker result、debug/replan result、DecisionPoint pending/resolved、stop report。
2. 在 `execute` 的 Runtime-managed action 后写 observation。
3. 增加最小 `AgentLoopRunner`：读取最新 observation，调用模型生成下一轮 `AgentLoopDecision`，受预算/gate/permission 控制。
4. gate 检查最新 execution 是否有 observation，failed observation 是否有后续 decision。
5. 用一个 fake-provider 小灰度验证两轮 loop。
