# 代码现状差距与研发计划

更新时间：2026-05-28

> 2026-05-28 同步记录：本轮已完成 loop profile 上移和权限理由审计。`AgentLoopProfileRegistry.dispatch_plan()` 成为 Plan/Run 上层分发协议，Research / Brainstorm / Multi-agent / Default profile 会随 task plan 一起落盘并进入执行前 evidence。`ToolExecutionGateway` 会在实际 Tool 调用前记录 CapabilityInvocationPolicy 决策，并把 allow/ask/deny reason 同步进 `capability_decisions.jsonl`、`tool_observations.jsonl` 和 `user_progress.jsonl`。灰度 manifest 已加入 Research、Brainstorm、Multi-agent 三类真实任务。后续不要把 Studio 完整 UI 作为后端 P0；Studio 只消费 runtime-native events/artifacts。

> 2026-05-28 追加同步：已新增 `CapabilityDecisionRecorder` 作为 Tool/MCP/Skill 共用审计入口；当前 Tool 已切换到该 recorder。这里标准化的是决策证据格式，不是执行实现：MCP/Skill 后续真实调用路径应分别接入各自 adapter，不复用 ToolExecutionGateway。`AgentLoopProfile` 已补 profile 级 output/validation/recovery/escalation 契约，并随 Plan/Run dispatch 持久化。`runtime_progress_metrics` 已接入 gray-run evidence 和 gate-status 输出，用于统计 profile 覆盖、permission reason 覆盖与 `user_progress` 覆盖。Prompt/Context 审计上下文已能携带 `agent_loop_dispatch` 摘要。

> 2026-05-28 追加同步：`ModelToolSurfaceAdapter` 已作为第一刀落地。它把内部 registry 映射为稳定的模型侧原语：`read_file`、`list_files`、`glob`、`grep`、`write_file`、`edit_file`、`shell`、`run_tests`、`todo_read`、`todo_write`。`todo_read/todo_write` 采用 run-local 模型规划状态文件 `.asteria/runs/<run_id>/model_todos.json`，读取时可从 `task_plan.json` 派生初始项，写入时不修改正式 task plan。ExecutionAction 归一化已能把模型输出的 `grep/glob/shell` 翻译为内部 `search_text/find_files/run_command`，并记录 `model_tool_name`，避免模型侧协议和内部 registry 混淆。该层只定义模型可见名称、参数契约、权限默认值和后端映射，不改变 `ToolExecutionGateway` 执行语义；缺少内部后端时必须显示 `missing/deny`，不能用旧的宽泛工具假装覆盖。MCP/Skill 的下一步仍分别做 protocol/session adapter 与 workflow/artifact adapter，只共享 capability decision 证据格式。

> 2026-05-28 MCP adapter 同步：MCP 真实调用入口已落第一版，新增 `McpAdapter` 与 `StdioMcpSession`。该实现通过独立 server/session/protocol 层执行 MCP `tools/call`，调用前复用 `CapabilityDecisionRecorder` 的 `decide_mcp()` 审计，调用记录落 `mcp_invocations.jsonl`，用户进展复用现有 `tool/tool_output` 事件并用 `data.capability_type=mcp` 标识来源。它不是 ToolRegistry/ToolExecutionGateway 包装器；已安装官方 `@modelcontextprotocol/server-everything@2026.1.26` 到 `.asteria/verification/mcp_node` 并通过 `echo` tool 真实 stdio smoke。当前官方 SDK 的 stdio transport 使用 JSONL framing，adapter 默认按 JSONL 读写，同时保留 `content-length` 兼容。

本文不是产品愿景文档，而是结合当前代码的研发差距清单。每一项都按“当前实现状态 -> 应达到状态 -> 改造方式 -> 验收方式”描述，用来约束后续开发不要在泛化 roadmap 里漂移。

## 1. 当前判断

Asteria 现在已经具备长任务 Runtime OS 的基本骨架：run、task、worker、evidence、review、accept、route fallback、context package 和 status 控制面都已经有代码实现。真正的差距不在“有没有这些对象”，而在这些对象还没有被收敛成一个稳定的模型循环协议和用户体验协议。

当前更准确的工程状态是：

- Runtime 内核能力约 65% 到 75%：能跑、能记录、能验收，WorkspaceEnvelope、permission profile 和 Chat 动态上下文已经开始形成产品契约；复杂场景的控制精度仍需继续增强。
- 用户级产品体验约 40% 到 50%：已经开始隐藏 backend dump，Plan 能产出 WorkspaceEnvelope，Chat/Status 已开始消费 WorkspaceEnvelope，普通 Ask 不再默认挂长期任务记忆；长期任务结构化记忆和 Status 状态卡片已完成第一阶段，能力调用策略和实时过程线仍未完全产品化。
- 文档体系约 80%：长期文档第一刀已经完成，主要原则和研发排序已收敛。后续文档工作是伴随代码实现持续校正，不再作为阻塞 P0 的独立阶段。

当前最关键判断：

- 继续把旧文档修到完美的边际收益已经下降。
- 已经开始进入代码阶段：WorkspaceEnvelope、权限模式、user_progress 和 Chat 动态上下文的第一批 Runtime 契约已落地。
- ContextEnvelope 已在 Chat 和 worker context package 侧做实第一阶段：ChatContextBuilder 负责构建上下文、生成 envelope 并持久化 path；ChatIntentPolicy 已独立；旧 `safe_project_context` 已下线；ContextPackageBuilder 已嵌入并持久化 worker envelope；CoderAgent/DebugAgent 模型调用已记录 worker context envelope path/hash；capability report 已纳入 ContextEnvelope 审计统计；ChatContextBuilder 已接入 CapabilityInvocationPolicy 第一版。下一步应推进 Workspace 全局索引、输出目录产品化、user_progress 全链路覆盖和更完整的能力/权限策略执行。

### 2.6 工具 / MCP / Skills 调用时机

当前实现状态：

- 长任务工具调用已有 ToolObservation 三线统一的基础。
- `ContextPackageBuilder` 能注入 failure、validation、runtime request、worker result、merge gate evidence。

应达到状态：

- 工具、MCP、Skills 不应只靠模型临场猜。
- Runtime 应先给出能力策略，再让模型在策略内选择。

改造方式：

1. 扩展 `CapabilityInvocationPolicy`：
   - `ordinary_chat`: no tool, no MCP, no skill by default
   - `project_question`: allow readonly file/context lookup
   - `progress_question`: allow active goal memory/session context

   - `debug_goal`: allow evidence + diagnostics
   - `document/presentation/spreadsheet`: allow corresponding skill only when artifact type matches
2. 将 policy 注入 PromptEnvelope/ContextEnvelope。
3. 每次 tool/MCP/skill 选择都记录 reason。
4. 失败 observation 进入 diagnose/repair/replan/ask/stop。

验收方式：

- 普通 Chat 不调用工具。
- 项目状态问题只读状态和文档。
- 长任务实现可以调用受控工具。
- Skill 只在匹配任务类型时进入 manifest。

优先级：P1。

### 2.7 场景型智能体链路

当前实现状态：

- 代码里已经有 `ResearchAgent`、`BrainstormAgent`、`DebugAgent`、`ReviewAgent`、`CoderAgent`、`MultiAgentStrategyAdvisor`、`AgentRunGraphBuilder` 等角色和链路。
- 这些链路目前更多是命令或 agent class 层面的能力，尚未统一表达为“具备业务方法论的智能体循环”。
- Research/Brainstorm/Multi-agent 的业务语义还没有落到 loop profile、上下文策略、工具策略、输出契约和验收方式上。
- 当前调度风险是继续把逻辑写死在命令分支或 if/else 中，导致能力越多，runtime 越难演进。

应达到状态：

- 每条链路都应根据场景语义定义自己的智能体循环，而不是复用一个抽象 PDCA 模板。
- Research 是深度研究循环：研究问题 -> 资料/论文/数据/代码收集 -> 方法与证据分析 -> 环境或数据验证 -> 复盘修正 -> 深度结论。
- Brainstorm 是开放型计划增强循环：发掘项目特征、约束、机会、风险和候选方向，帮助 Plan/Goal 更好地收敛。
- 多智能体是动态并发调度能力：根据目标、任务图、预算、sandbox/provider readiness，调度 UI、架构、测试、代码等角色智能体协同完成目标。
- 这些原子能力既可以被用户显式命令调用，也可以作为产品入口暴露，还可以被核心 Goal Loop 动态调度。
- Runtime 应把能力和智能体链路表达为模型可理解的 manifest/profile/context，而不是把所有组合方式写进程序。
- 程序负责权限、预算、协议、schema、证据、审计和 fallback；强模型负责在这些边界内根据用户目标动态组织能力。
- 这种架构应让能力随模型迭代持续增值：模型越强，越能理解和组合已有原子能力，而不是让产品被旧流程锁死。

改造方式：

1. 新增 `AgentLoopProfile` 或等价结构，描述每类链路：
   - `loop_kind`
   - `role`
   - `methodology`
   - `default_context_policy`
   - `allowed_capabilities`
   - `iteration_steps`
   - `output_contract`
   - `validation_contract`
   - `user_visible_summary`
   - `dispatch_hints`
   - `anti_hardcoding_notes`
2. 新增 `AgentCapabilityRegistry` 或等价注册层：

   - `user_goal`
   - `context_envelope`
   - `available_capabilities`
   - `constraints`
   - `budget`
   - `acceptance_criteria`

   - `dispatch_reason`
4. 为 Research 定义研究型 profile：
   - 研究问题和边界。

验收方式：

- Research 命令或入口输出深度研究报告，而不是普通问答摘要。

优先级：P1.5。它不是先于 Chat/Memory/Status 的 P0，但必须在能力调用策略之后尽快落地，否则现有 Research/Brainstorm/Multi-agent 会停留在“命令分叉”，无法形成真正的体系化智能体行为。
