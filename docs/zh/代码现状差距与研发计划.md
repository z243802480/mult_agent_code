# 代码现状差距与研发计划

更新时间：2026-05-29

本文是当前研发计划的执行依据。历史 validation 次数、runtime matrix 通过数和旧 release gate 只作为回归健康证据，不再作为下一阶段研发目标本身。已经完成的阶段性任务不重复列为待办；历史过程记录看 git history。

## 1. 当前工程判断

Asteria 已进入“长期自主迭代能力闭环”阶段。核心 CLI/runtime loop、模型工具面、Skill/MCP adapter、任务级 capability catalog、风险加权工具预算、ContextBudgetMeter 第一阶段、runtime matrix evidence 和真实 provider validation 基线都已经落地。

当前不能再用“validation suite 7/7”或“runtime matrix 8/8”来代表系统已经具备长期自主研发能力。这些数字只能说明一组固定回归样例当前没有退化。真正的下一步判断标准应是：

- 长任务能否在恢复、冲突、权限阻断、上下文压缩后继续朝目标推进。
- 模型是否能看见完整能力选择面，并留下选择、跳过、阻断的理由。
- 上下文窗口是否能按 section 解释，而不是只记录整体 token 估算。
- gate/report 是否能清楚区分当前实现缺口、证据缺口、历史噪声、route 健康和 release 回归结果。
- Studio 是否继续薄消费 runtime evidence，而不是反向定义后端协议。

## 3. 当前差距

### 3.1 长期任务恢复与冲突闭环

当前状态：

- `gate-status --json` 已输出 `recovery_pressure`。
- resume、replan、repair、permission_block、damaged_memory、multi_run_conflict、compact_continuation 都已进入 recovery pressure 链路。
- `ActiveGoalMemory` 在发现 `active_goal.json` 损坏时会回退到 Markdown，并写入 `.asteria/memory/recovery_events.jsonl`。
- 跨 run 写入未完成 active goal 时会记录 multi-run conflict 恢复事件，保留 previous/current run 证据。
- `CompactCommand` 生成的 context snapshot 和 `context_compacted` 事件已纳入 compact continuation 证据。

仍需推进：

- 用真实小任务继续滚动验证恢复质量，而不是只看链路覆盖。
- 多 run 冲突后续可进一步接入更细的同文件 diff / candidate workspace 合并策略。
- permission block 后继续推进还要在真实 provider 小任务中复验完整用户决策路径。

验收：

- `recovery_pressure.ready == true`。
- 缺口链路为 0。
- 每条恢复链路都有 run_dir、user_progress、决策点、最终结果和残余风险。

### 3.2 ContextBudgetMeter v2

当前状态：

- 已新增 `src/asteria_runtime/core/context_budget.py`。
- 模型调用前已记录 request-level context estimate，并按 system prompt / prompt envelope / context envelope / tool output / memory / file excerpts / conversation 做粗粒度 section 归因。
- `cost_report.json` 已输出 `latest_context_estimated_tokens`、`max_context_estimated_tokens`、`context_window_tokens`、`context_window_ratio`、`context_pressure_status`、`latest_context_sections`、`max_context_sections` 和 `context_duplicate_content_hashes`。
- `BudgetController.pressure()` 已纳入 `context_window` 维度。
- `model_calls.jsonl` 已记录脱敏 context estimate 摘要，便于 Inspector 定位。
- `gate-status` 与 `capability-report` 已能展示 context pressure 来源；旧 run 没有这些字段时会显示 `no_current_context_estimates` 或 0。

仍需推进：

- compact 时记录 compact boundary：压缩前后 token、保留/丢弃 section、恢复摘要和 evidence refs。
- Worker / subagent 引入隔离 context window，避免临时大文件读取污染主线。
- 对重复读取未变化文件建立更精确的 file hash / diff 策略；当前只有请求内容 hash 层面的重复信号。

验收：

- 新真实 run 中 `max_context_estimated_tokens > 0`。
- report 能解释 context window ratio 来自哪些 section。
- near-limit context pressure 能触发 compact，而不是依赖模型调用次数或工具次数。

### 3.3 Capability Selection Audit

当前状态：

- 任务级 capability catalog 已生成。
- catalog 已解释能力 visible / selected / skipped / blocked 的初始状态。
- `capability-report` 已新增 Capability selection audit，聚合 task 数、visible / selected / skipped / blocked 数量和主要选择理由。

仍需推进：

- 把 catalog 注入更多模型入口，而不是只在 dispatch evidence 中可见。
- 将真实模型输出中的工具/Skill/MCP/profile 选择行为与 catalog 对齐。
- 记录模型为什么选择、跳过、阻断某能力，以及能力不可用时的替代路径。
- 在 capability-report 中聚合“可见但未用”“被权限阻断”“被风险策略阻断”“模型未选择”的原因。

验收：

- 每个 task 都能解释模型看到、选择、跳过和阻断的能力。
- denied / ask / allow 都有 reason。
- capability-report 推荐动作与 capability catalog 证据一致。

### 3.4 Gate / Report 解释口径

当前状态：

- `gate-status` 当前能给出 release-ready 回归结论。
- `capability-report` 已把被最新 acceptance 覆盖的旧 Runtime OS catalog 缺口标记为 `historical_evidence_noise`，route guidance 的旧 blocker 降级为 review，不再同时表达 release ready 与 route blocked。

仍需推进：

- 清理旧 Runtime OS catalog 中已被新实现替代的能力项。
- 将 release validation、runtime matrix、capability report、route guidance、recovery pressure 的主次关系写清。
- 历史证据只能标记为 superseded / stale / regression baseline，不能与当前阻断混写；本轮已完成 capability-report 的第一层降噪，后续继续清理 catalog 本身。

验收：

- 同一份报告不再同时暗示 ready 和 blocked。
- 阻断原因只保留一个主因，并列出辅助风险。
- next actions 直接指向当前缺口，而不是推荐重复跑旧 gate。

### 3.5 Studio 薄消费

当前状态：

- Studio run detail 暂以 `user_progress.jsonl` 为主线。
- MCP / Skill invocation、provider route、schema refs、raw evidence 留给 Inspector。

仍需推进：

- 不扩大 Studio 功能面，不新增 dashboard 驱动的后端协议。
- 只补 timeline 消费质量、artifact 链接、context pressure 摘要和 Inspector 可读性。

验收：

- 普通用户主线不展示 raw evidence dump。
- Inspector 能定位 MCP / Skill / provider route / schema refs / context sections。

## 4. 当前研发顺序

1. 长期任务恢复与冲突闭环：damaged memory、multi-run conflict、permission block 后继续推进、compact 后继续推进。
2. ContextBudgetMeter v2：section 级 token 归因、compact boundary、重复文件读取 hash/diff 降噪。
3. Capability selection audit：模型真实选择/跳过/阻断行为与 task capability catalog 对齐。
4. Gate/report 解释收敛：清理历史 catalog 噪声，统一 release / matrix / route / recovery 口径。
5. 真实小任务滚动验证：连续 3-5 个小真实目标，观察恢复、context、catalog、provider route、progress 质量。
6. Studio 继续薄消费：只读 user_progress 主线与 artifacts，Inspector 展示 raw evidence 明细。
