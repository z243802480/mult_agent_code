# 代码现状差距与研发计划

更新时间：2026-05-27

本文不是产品愿景文档，而是结合当前代码的研发差距清单。每一项都按“当前实现状态 -> 应达到状态 -> 改造方式 -> 验收方式”描述，用来约束后续开发不要在泛化 roadmap 里漂移。

## 1. 当前判断

Asteria 现在已经具备长任务 Runtime OS 的基本骨架：run、task、worker、evidence、review、accept、route fallback、context package 和 status 控制面都已经有代码实现。真正的差距不在“有没有这些对象”，而在这些对象还没有被收敛成一个稳定的模型循环协议和用户体验协议。

当前更准确的工程状态是：

- Runtime 内核能力约 60% 到 70%：能跑、能记录、能验收，但复杂场景的控制精度还不稳定。
- 用户级产品体验约 30% 到 40%：已经开始隐藏 backend dump，但回答、状态、长期任务记忆和调试视图还没有完全分层。
- 文档体系约 50%：有大量有效内容，但 `当前状态与路线.md` 已经混入事实入口、开发日志、验收记录和长期规划；部分旧文档仍在主导航里，容易让 agent 读到过时目标。

## 2. 代码级差距表

### 2.1 Chat 动态上下文

当前实现状态：

- `ChatCommand._safe_context()` 无条件读取 `ActiveGoalMemory(self.root).read()`，并把 `.asteria/memory/active_goal.md` 放进 refs。
- 位置：`src/asteria_runtime/commands/chat_command.py:195-233`。
- `_system_prompt()` 明确要求进度、计划、下一任务优先使用 `safe_project_context.active_goal_memory`。
- 位置：`src/asteria_runtime/commands/chat_command.py:454-466`。
- 单元测试也固化了这个行为：状态类问题要求 `chat_model.context["active_goal_memory"]` 存在。
- 位置：`tests/unit/test_user_workflow_loop.py:653-691`。

应达到状态：

- Chat 默认只挂载当前对话、轻量项目配置、必要的 session 摘要。
- 只有当用户问题属于状态、进展、计划、下一步、恢复、验收一类意图时，才挂载长期任务记忆。
- Chat 的上下文选择应该是可测试的显式策略，而不是散在 `_safe_context()` 的固定字段。

改造方式：

1. 新增 `DynamicContextBuilder` 或 `ChatContextBuilder`，输入为 `question`、`mode`、`root`、`current_session`。
2. 定义最小 intent 分类：
   - `ordinary_chat`
   - `project_question`
   - `progress_question`
   - `debug_question`
   - `execution_request`
3. `ordinary_chat` 不读取 active goal memory。
4. `progress_question` 才读取 `.asteria/memory/active_goal.md`。
5. `debug_question` 才挂载 route timeline、evidence path、run id 等 backend 字段。
6. 修改 `ChatCommand._safe_context()`，让它调用 builder，而不是自己拼 context。

验收方式：

- 新增测试：普通问题不会把 `active_goal_memory` 放进模型上下文。
- 保留测试：状态类问题会挂载 `active_goal_memory`。
- 新增测试：普通 chat 输出不含 `run_id`、`task_execution_evidence`、`.asteria/`、`model_route`。
- 新增测试：调试问题可以看到 backend 字段。

优先级：P0。

### 2.2 长任务 Markdown 记忆

当前实现状态：

- 新增了 `ActiveGoalMemory`，固定写入 `.asteria/memory/active_goal.md`。
- 位置：`src/asteria_runtime/core/active_goal_memory.py:10-197`。
- `RunCommand._write_final_report_summary()` 和 `_write_final_report()` 会调用 `_write_active_goal_memory()`。
- 位置：`src/asteria_runtime/commands/run_command.py:470-513`、`src/asteria_runtime/commands/run_command.py:1390-1452`。
- `AcceptCommand.run()` 也会在 accept 后更新 active goal memory。
- 位置：`src/asteria_runtime/commands/accept_command.py:174-203`。
- 当前写法是 Markdown 渲染器，没有 schema、版本、事件来源、冲突处理、更新原因。

应达到状态：

- 长期任务记忆是“用户级长期状态协议”，不是普通渲染副产物。
- Markdown 是用户可读视图，底层应有结构化来源，至少能说明每次更新来自 run、review、accept、repair、pause 还是 resume。
- 该文件只服务长任务循环和状态查询，不应自动污染普通 Chat。

改造方式：

1. 增加 `.asteria/memory/active_goal.json` 或在现有 Markdown front matter 中记录结构化元数据。
2. 字段包括：
   - `schema_version`
   - `memory_id`
   - `goal_id`
   - `source_run_id`
   - `updated_by`
   - `update_reason`
   - `current_goal`
   - `current_result`
   - `overall_plan`
   - `completed_work`
   - `how_completed`
   - `current_blockers`
   - `questions_for_user`
   - `accepted_decisions`
   - `watch_items`
   - `next_task`
3. `ActiveGoalMemory.write_from_run()` 改为先生成结构化对象，再渲染 Markdown。
4. 对外读取分成 `read_user_markdown()` 和 `read_structured()`。
5. 添加 schema validation，避免长期记忆被坏数据写坏。

验收方式：

- 测试 Markdown 不泄漏 run_id/evidence/model_route。
- 测试 JSON/structured memory 通过 schema。
- 测试 run/review/accept 三个入口更新 `update_reason`。
- 测试普通 Chat 不自动读取，Status 默认读取。

优先级：P0。

### 2.3 Status 用户视图与调试视图

当前实现状态：

- `StatusResult.to_text(debug=False)` 如果存在 active goal memory，就直接返回 `_user_text()`。
- 位置：`src/asteria_runtime/commands/status_command.py:362-376`。
- `_user_text()` 会整段输出 Markdown，并提示 debug 命令。
- 位置：`src/asteria_runtime/commands/status_command.py:367-375`。
- `_debug_text()` 仍然保留大量 runtime 细节，包括 route、evidence chain、candidate promotions、worker、model progress。
- 位置：`src/asteria_runtime/commands/status_command.py:378-520`。

应达到状态：

- 普通 `status` 应返回“用户级当前状态卡片”，而不是直接 dump 整个 active_goal.md。
- 长期 Markdown 文件是状态来源，不等于命令输出格式。
- `status --debug` 才展示 runtime 细节。

改造方式：

1. 新增 `UserProgressView` 或 `StatusPresenter`。
2. 输入 active goal structured memory、session context、blocker、recommended command。
3. 输出固定 5 段：
   - 当前目标
   - 已完成
   - 当前状态
   - 需要用户做什么
   - 下一步
4. `StatusResult.to_dict()` 保留结构化字段，但普通文本只走 presenter。
5. `--json` 保留完整机器字段，`--debug` 保留工程排障文本。

验收方式：

- 普通 `status` 不出现 `Evidence chain`、`Model route timeline`、`runtime_profile` 等词。
- `status --debug` 继续显示这些内容。
- 当 active goal 缺失时，普通 `status` 仍能从 session context 给出下一步。

优先级：P0。

### 2.4 模型路由默认兜底

当前实现状态：

- 默认路由已存在：strong=GLM 5.1、medium=MiniMax M2.7、cheap=fake-offline。
- 位置：`src/asteria_runtime/models/default_routes.py:14-45`。
- `route_diagnostic_for_tier()` 在缺少 env/local route 时会使用 default route，并记录 `fallback.used/source/reason`。
- 位置：`src/asteria_runtime/models/route_diagnostics.py:57-97`。
- `RuntimeProfileBuilder._route_hint_is_stale()` 会在 capability profile 过期且当前 route 来自 default policy 时忽略旧 hint。
- 位置：`src/asteria_runtime/core/runtime_profile_builder.py:500-507`。
- 已有测试覆盖 stale capability profile fallback。
- 位置：`tests/unit/test_runtime_profiles.py:268-331`。

应达到状态：

- route resolution 和 executable readiness 要分清：
  - resolution：系统总能选择一个可审计 route。
  - readiness：真实 provider 是否具备 API key、deadline、streaming evidence。
- 用户级输出只说“系统已选择默认模型策略/当前需要配置真实模型”，不暴露内部 route 字段。
- 工程级输出保留 fallback source、reason、deadline、missing requirements。

改造方式：

1. 在 route resolution 输出中增加 `resolution_status` 与 `execution_readiness`，不要只靠 `configured` 一个布尔值承载两层语义。
2. `gate-status` 和 `doctor` 继续检查真实 provider readiness。
3. `Chat/Status` 普通视图只展示用户级模型策略说明。
4. `ReviewAgent` 的 fallback 链路继续使用 strong -> medium -> cheap，但把“为什么降级”写入审计记录，不进入普通答复。

验收方式：

- 缺少 env route 时，runtime profile 仍有 model route resolution。
- 缺少 API key 时，gate/status debug 能说明 readiness blocker。
- 普通用户答复不出现 `fallback.source`、`AGENT_MODEL_*`，除非用户问调试。

优先级：P1，基础已完成，剩余是语义拆分和用户视图。

### 2.5 ContextPackage 与 Chat Context 断裂

当前实现状态：

- 长任务 worker 已有 `ContextMountBuilder` 和 `ContextPackageBuilder`。
- 位置：`src/asteria_runtime/core/context_mount_builder.py:10-43`、`src/asteria_runtime/core/context_package_builder.py:14-65`。
- 它们能按 read scope、write scope、artifact refs、failure refs、decision refs、validation refs 裁剪上下文。
- 但 Chat 没有复用这套机制，`ChatCommand._safe_context()` 自己拼 project/policy/current_run/session_context/active_goal_memory。
- 位置：`src/asteria_runtime/commands/chat_command.py:195-233`。

应达到状态：

- Chat 和 Goal Loop 都应该走同一类 Context Envelope，只是 mount policy 不同。
- Chat 需要的是轻量 envelope，Goal Worker 需要的是任务级 envelope。
- 两者都应该有 refs、included_sections、excluded_backend_fields、audience。

改造方式：

1. 抽象 `ContextEnvelope`：
   - `audience`: user / debug / worker / reviewer
   - `intent`
   - `sections`
   - `refs`
   - `redaction_policy`
   - `backend_fields_allowed`
2. `ContextPackageBuilder` 保留 worker/task 专用能力。
3. 新增 `ChatContextEnvelopeBuilder`，不直接复用 worker read_scope，但复用 envelope 结构和 redaction 规则。
4. 模型调用 metadata 记录 envelope hash，方便复盘上下文为什么这样选。

验收方式：

- Chat 模型请求中出现 `context_envelope`，而不是未约束的 `safe_project_context` 大字典。
- 普通 Chat 的 envelope 不含 active goal memory，状态 Chat 的 envelope 含 active goal memory。
- Debug Chat 的 envelope 可含 route/evidence，但输出必须标记 debug。

优先级：P0.5。

### 2.6 工具 / MCP / Skills 调用时机

当前实现状态：

- 长任务工具调用已有 ToolObservation 三线统一的基础。
- `ContextPackageBuilder` 能注入 failure、validation、runtime request、worker result、merge gate evidence。
- Skills/MCP 的产品策略主要还在文档和 prompt envelope/capability manifest 层，缺少“意图 -> 允许能力 -> 触发条件 -> 禁止条件”的可测试策略表。

应达到状态：

- 工具、MCP、Skills 不应只靠模型临场猜。
- Runtime 应先给出能力策略，再让模型在策略内选择。
- 普通 Chat 默认不触发重工具；长任务根据任务类型和权限触发。

改造方式：

1. 新增 `CapabilityInvocationPolicy`：
   - `ordinary_chat`: no tool, no MCP, no skill by default
   - `project_question`: allow readonly file/context lookup
   - `progress_question`: allow active goal memory/session context
   - `implementation_goal`: allow planner + controlled tools
   - `debug_goal`: allow evidence + diagnostics
   - `document/presentation/spreadsheet`: allow corresponding skill only when artifact type matches
2. 将 policy 注入 PromptEnvelope/ContextEnvelope。
3. 每次 tool/MCP/skill 选择都记录 reason。
4. 失败 observation 进入 diagnose/repair/replan/ask/stop。

验收方式：

- 普通 Chat 不调用工具。
- 项目状态问题只读状态和文档。
- 长任务实现可以调用受控工具。
- Skill 只在匹配任务类型时进入 manifest。

优先级：P1。

### 2.7 场景型智能体链路

当前实现状态：

- 代码里已经有 `ResearchAgent`、`BrainstormAgent`、`DebugAgent`、`ReviewAgent`、`CoderAgent`、`MultiAgentStrategyAdvisor`、`AgentRunGraphBuilder` 等角色和链路。
- 这些链路目前更多是命令或 agent class 层面的能力，尚未统一表达为“具备业务方法论的智能体循环”。
- Research/Brainstorm/Multi-agent 的业务语义还没有落到 loop profile、上下文策略、工具策略、输出契约和验收方式上。
- 当前调度风险是继续把逻辑写死在命令分支或 if/else 中，导致能力越多，runtime 越难演进。

应达到状态：

- 每条链路都应根据场景语义定义自己的智能体循环，而不是复用一个抽象 PDCA 模板。
- Research 是深度研究循环：研究问题 -> 资料/论文/数据/代码收集 -> 方法与证据分析 -> 环境或数据验证 -> 复盘修正 -> 深度结论。
- Brainstorm 是开放型计划增强循环：发掘项目特征、约束、机会、风险和候选方向，帮助 Plan/Goal 更好地收敛。
- 多智能体是动态并发调度能力：根据目标、任务图、预算、sandbox/provider readiness，调度 UI、架构、测试、代码等角色智能体协同完成目标。
- 这些原子能力既可以被用户显式命令调用，也可以作为产品入口暴露，还可以被核心 Goal Loop 动态调度。
- Runtime 应把能力和智能体链路表达为模型可理解的 manifest/profile/context，而不是把所有组合方式写进程序。
- 程序负责权限、预算、协议、schema、证据、审计和 fallback；强模型负责在这些边界内根据用户目标动态组织能力。
- 这种架构应让能力随模型迭代持续增值：模型越强，越能理解和组合已有原子能力，而不是让产品被旧流程锁死。

改造方式：

1. 新增 `AgentLoopProfile` 或等价结构，描述每类链路：
   - `loop_kind`
   - `role`
   - `methodology`
   - `default_context_policy`
   - `allowed_capabilities`
   - `iteration_steps`
   - `output_contract`
   - `validation_contract`
   - `user_visible_summary`
   - `dispatch_hints`
   - `anti_hardcoding_notes`
2. 新增 `AgentCapabilityRegistry` 或等价注册层：
   - 注册工具、MCP、Skills 和智能体 loop profile。
   - 向模型提供当前目标下可用能力的结构化 manifest。
   - 记录能力颗粒度、成本、风险、前置条件、输出类型和验证方式。
   - 避免在命令层硬编码“某意图只能调用某 agent”的固定映射。
3. 新增动态调度请求对象：
   - `user_goal`
   - `context_envelope`
   - `available_capabilities`
   - `constraints`
   - `budget`
   - `acceptance_criteria`
   - `dispatch_decision`
   - `dispatch_reason`
4. 为 Research 定义研究型 profile：
   - 研究问题和边界。
   - source/data/code 收集策略。
   - 论文方法、实验、数据、限制分析。
   - 环境搭建和数据验证触发条件。
   - 复盘修正和证据等级。
   - 最终深度研究报告。
5. 为 Brainstorm 定义开放型 profile：
   - 项目特征提取。
   - 多方向发散。
   - 约束与风险识别。
   - 候选方案聚类和价值排序。
   - 向 Plan/Goal 输出可执行启发。
6. 为 Multi-agent 定义并发调度 profile：
   - 子智能体角色选择。
   - 上下文差异化分发。
   - sandbox/workspace 隔离。
   - provider 并发和预算控制。
   - 候选结果合并、冲突检测、Review/MergeGate 验证。
7. 将 `AgentRoleContract`、`PromptEnvelope`、`ContextEnvelope` 和 `CapabilityInvocationPolicy` 连接起来，让不同链路获得不同 prompt contract、上下文和工具能力。
8. 调度逻辑只做边界判断和候选能力过滤；能力组合由模型在 manifest/profile/context 中做结构化选择，并写入审计记录。

验收方式：

- Research 命令或入口输出深度研究报告，而不是普通问答摘要。
- Brainstorm 命令或入口输出开放型候选方向，并能转化为 Plan/Goal 输入。
- Multi-agent 测试能证明多个 worker 使用不同上下文并发产出候选，并由 Review/MergeGate 收敛。
- 新能力接入时只需要注册 profile/manifest 和测试，不需要修改核心调度 if/else。
- 调度决策记录 `dispatch_reason`、输入上下文、候选能力、最终选择和证据路径。
- 普通用户输出不泄漏 worker graph；debug 视图可审计每个子智能体的 role、context、provider route、evidence 和结果。

优先级：P1.5。它不是先于 Chat/Memory/Status 的 P0，但必须在能力调用策略之后尽快落地，否则现有 Research/Brainstorm/Multi-agent 会停留在“命令分叉”，无法形成真正的体系化智能体行为。

### 2.8 文档体系过载

当前实现状态：

- `docs/zh/当前状态与路线.md` 是事实入口，但已经接近 4 万字，混入大量完成记录、路线、验收、灰度、Studio、provider streaming、command surface 等内容。
- `docs/zh/文档导航.md` 仍把很多 2026-05-18/19 的旧主文档列为主文档。
- `docs/zh/archive/` 已存在，但主目录仍有较多“可能已吸收但未归档”的历史文档。

应达到状态：

- 文档分为三类：
  - 当前事实入口：短，回答“现在在哪、下一步是什么”。
  - 当前设计协议：少量权威设计文档。
  - 历史归档：调研、旧计划、旧实现方案。
- Agent 默认只读 3 到 5 份权威文档，不再被旧计划干扰。

改造方式：

1. 新增 `docs/zh/文档状态审计.md`，给每个中文文档标记：
   - `current`
   - `reference`
   - `superseded`
   - `archive_candidate`
2. 缩短 `当前状态与路线.md`，只保留：
   - 当前阶段
   - 已完成基线摘要
   - 当前 P0/P1 优先级
   - 最新验收状态
   - 权威文档链接
3. 把详细历史记录迁移到对应专题文档或 archive。
4. `文档导航.md` 增加“当前必读 5 篇”，其余降级为 reference。

验收方式：

- 新 agent 只读 AGENTS + 当前状态 + 本计划 + 模型主导设计 + 数据模型，即可知道下一步。
- 过时文档不再出现在“推荐阅读顺序”的第一屏。
- 每个文档都有状态标签。

优先级：P1，但应尽早做第一刀，否则后续计划会继续被旧文档污染。

## 3. 分阶段执行计划

### Phase 0：立即修正当前偏差

目标：让 Ask/Chat 不再默认使用长期记忆，修正用户主线和调试主线的边界，并把普通用户入口收敛为 Goal / Plan / Ask。`init/run/status/review/accept` 保留为 runtime 内部智能体阶段和专家命令，由前台翻译成友好进展。

任务：

1. 修改 `ChatCommand`，增加问题意图判断。
2. 普通 Ask/Chat 不读取 active goal memory。
3. 状态/进展/下一步类 Ask/Chat 才读取 active goal memory。
4. 修改相关测试，新增普通 Chat 不挂载 memory 的回归测试。
5. 保持 debug 问题可见 backend 字段。
6. Plan 输出多个行动优先级时，必须提示用户确认下一步，而不是自动执行。
7. 保留 `init/run/status/review/accept` 阶段语义，但普通用户输出只展示目标理解、进展、验收回顾和下一步。

## 4. 近期执行顺序

最合理的顺序是：

1. 先修 Chat 默认挂载长期记忆的问题。
2. 再把 active goal memory 协议化。
3. 然后把 Status 普通输出从“整段 Markdown”改成用户状态卡片。
4. 再推进 Context Envelope。
5. 再做工具/MCP/Skills 调用策略。
6. 然后把 Research/Brainstorm/Multi-agent 升级为场景型智能体 loop profile。
7. 最后做剩余文档大清理。

原因是当前最容易造成用户体验偏差的是 Chat：它如果默认携带长期目标，就会把普通对话误导成长任务状态问答。这个问题比继续扩大 gray task 更基础。
