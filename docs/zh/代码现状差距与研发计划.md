# 代码现状差距与研发计划

更新时间：2026-05-29

本文是当前代码阶段的执行依据。已完成的阶段性任务不再作为待办重复出现；历史过程记录看 git history。

## 1. 当前工程判断

Asteria 已进入“真实运行证据和策略闭环”阶段。Runtime OS 的主要结构已经落地：

- Goal / Plan / Run / Status / Review / Accept 主循环可用。
- WorkspaceEnvelope、ContextEnvelope、PromptEnvelope、CapabilityManifest 已进入运行证据。
- ContextBudgetMeter 第一阶段已接入模型调用：按 `ChatRequest.messages` 估算 context token，写入 `cost_report.json`，并作为 `context_window` 压力参与 budget guard。
- Agent-facing tool surface 已接入 Plan / Run / Worker 主循环，模型侧稳定原语映射内部 registry。
- Tool / MCP / Skill 分离执行，复用 CapabilityDecisionRecorder 的权限审计证据格式。
- Skill adapter、MCP adapter、Research / Brainstorm / Multi-agent loop profile、runtime progress metrics、recovery pressure report 已有第一阶段代码和测试。
- 工具预算已改为风险加权：保留 `tool_calls` 原始审计，同时用 `tool_budget_units` 作为风险加权 emergency brake；默认 `autonomous_long_task` profile 放大阈值，读/搜/列目录类探索默认不消耗工具预算，写入、shell、MCP、Skill 和外部连接继续严格消耗预算并走权限 reason。
- Studio 暂保持薄消费：主线读取 `user_progress.jsonl` 和 artifacts；raw evidence、adapter invocation、provider route、schema refs 进入 Inspector。

当前主要风险不再是“入口缺失”。本轮已经把 runtime matrix 和真实 validation evidence 拉到发布阈值；后续风险集中在证据持续性和解释口径稳定性：

1. 真实 provider / 真实任务证据需要继续滚动刷新，避免只靠一次通过。
2. 模型可见能力选择面需要进入更多模型入口和审计摘要。
3. gate / capability report 必须持续区分实现缺口、证据缺口、历史证据噪声和 route 健康。
4. Studio 不能抢跑成新的后端协议来源。

## 3. 当前差距

### 3.1 真实验证证据闭环

当前状态：

- `benchmarks/runtime_validation_matrix.json` 已定义固定验证目录。
- `gate-status --json` 输出 `runtime_validation_matrix`、`runtime_progress_metrics` 和 `recovery_pressure`。
- 已新增受控 runtime matrix evidence 记录能力，用同一套 runtime stores 记录 Skill、MCP、profile、permission reason 和 `user_progress` 证据。
- 本地 `gate-status --json` 当前读取完整 validation summary：7 个 validation 场景通过，strong / medium route evidence 均存在，`runtime_validation_matrix.passed == 8`。

仍需推进：

- 将这批真实 provider 样例纳入稳定回归流程，避免只靠一次手动合并的 summary。
- 扩大 Skill / MCP / profile / recovery 的真实任务样本，覆盖失败、重试、恢复和权限阻断。
- 每次验证都保留 summary、run_dir、evidence_refs、source summaries 和阻断原因。

验收：

- `runtime_validation_matrix.passed == case_count`。
- `gap_summary.implementation_missing == 0`。
- `gap_summary.evidence_missing == 0`。
- `runtime_progress_metrics.runtime_native_progress_coverage.matrix_evidence_coverage_ratio == 1.0`。

### 3.2 任务级 capability catalog

当前状态：

- 已新增任务级 capability catalog，汇总模型侧工具、Skills、MCP server catalog 和权限决策。
- 每项能力记录 `visible`、`selection_state`、`policy_decision`、`selection_reason`、`skipped_reason` 或 `blocked_reason`。
- AgentLoopProfile dispatch 已把每个 task 的 `capability_catalog` 写入 `agent_loop_dispatch.json`。

仍需推进：

- 在更多模型调用入口展示该 catalog，而不是只在 dispatch evidence 中可见。
- 将真实模型“选择了什么 / 跳过了什么”的行为与 catalog 对齐，形成审计摘要。
- Studio Inspector 展示 capability catalog，但主时间线只展示用户可理解摘要。

验收：

- 每个 task 都能看到任务级 capability catalog。
- catalog 能解释工具、Skill、MCP 的选择、跳过和阻断原因。
- denied / ask / allow 都有 reason。

### 3.3 Gate 与 capability report 解释口径

当前状态：

- `runtime_validation_matrix` 已区分：
  - `implementation_missing`
  - `evidence_missing`
  - `historical_evidence_noise`
- `gate-status --json` 已新增 readiness explanation，用于解释 release state 与 runtime evidence 的关系。
- `capability-report` 已增加 Evidence health，不再把 acceptance 通过误写成整体 release ready。

仍需推进：

- 继续消除旧 acceptance/runtime_os 历史证据造成的噪声。
- `capability-report` 继续收敛 acceptance 结果、runtime OS gate 结果、route guidance 和 matrix evidence 的主次关系。
- release gate 阻断时，保持“一个主因 + 辅助风险”的解释结构。

验收：

- 不再出现同一报告同时暗示 “ready” 和 “blocked” 的混乱表述。
- `gate-status` 能说明是缺 validation suite、缺实现、缺证据、历史噪声还是 route health。
- `capability-report` 的 recommended actions 与 Evidence health 一致。

### 3.4 Studio 薄消费

当前状态：

- Studio run detail 以 `user_progress.jsonl` 为主线。
- MCP / Skill invocation、provider route、legacy events、schema refs 留给 Inspector。

仍需推进：

- 不扩大 Studio 产品面，不新增 dashboard 驱动的后端协议。
- 只补齐 timeline 消费质量、Inspector 可读性和 artifacts 链接。

验收：

- 普通用户主线不展示 raw evidence dump。
- Inspector 能定位 MCP / Skill / provider route / schema refs。

### 3.5 工具预算与权限哲学

当前状态：

- `tool_calls` 是审计字段，记录所有真实工具调用次数。
- `tool_budget_units` 是预算字段，按工具风险加权；它是 emergency brake，不是智能体稳定性的主要来源。
- `active_budget_profile` 选择当前预算口径：`validation` 用于发布验证短闭环，`balanced` 用于普通研发，`autonomous_long_task` 用于长期自主迭代。
- 默认权重：
  - read/search/list/diff/todo_read：0
  - run_tests/todo_write：1
  - write/apply/restore：2
  - shell：2
  - MCP/Skill/external：3
- 权限仍由 permission profile、CapabilityDecisionRecorder 和 shell guard 决定，不因预算权重为 0 而绕过 protected path 或 deny 规则。

仍需推进：

- MCP / Skill adapter 自身已纳入同一风险加权预算，不只限于内部 ToolRegistry。
- `capability-report` 已展示 raw tool calls 与 weighted tool budget 的差异，避免误解。
- 对重复、低收益的 read/search 行为增加质量信号，而不是简单次数硬停。

验收：

- 大量低风险读搜不会触发预算 DecisionPoint。
- 写入、shell、外部连接、修复、replan 和模型调用仍有上限，但默认长期迭代阈值放宽；稳定性主要由上下文压力、权限边界、provider 健康和重复低价值循环检测保证。
- gate 报告明确区分“探索充分”和“高风险动作过多”。

### 3.6 ContextBudgetMeter 与长期上下文治理

当前状态：

- 已新增 `src/asteria_runtime/core/context_budget.py`，提供 CJK/ASCII 混合的轻量 token 估算。
- `FakeModelClient`、`MeteredModelClient`、`OpenAICompatibleClient`、`MiniMaxClient` 在模型调用前记录 context estimate。
- `BudgetController.cost_report()` 输出 context window 相关字段。
- `BudgetController.pressure()` 将 `context_window` 纳入独立压力维度。
- policy `context.model_context_window_tokens` 默认 200000，配合 `compaction_threshold=0.75` 和 `hard_stop_threshold=0.9`。

仍需推进：

- 将 estimate 从 request 整体拆成 PromptEnvelope、ContextEnvelope、tool output、conversation、memory 等 section 级归因。
- compact 时记录 compact boundary：压缩前后 token、保留/丢弃 section、恢复摘要和 evidence refs。
- Worker / subagent 引入隔离 context window，避免临时大文件读取污染主线。
- 对重复读取未变化文件建立 context hash / diff 策略，减少同一内容反复进入模型窗口。
- capability-report / gate-status / Studio Inspector 展示 context pressure 和 section 明细。

验收：

- cost report 能解释当前 context window ratio。
- near-limit context pressure 能触发 compact，而不是依赖模型调用次数或工具次数。
- hard-stop context pressure 会产生可解释 DecisionPoint。
- 长任务恢复后仍保留目标、不变量、文件触点、失败证据、验证结论和下一步。

## 4. 当前研发顺序
