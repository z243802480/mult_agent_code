# 工程治理体系

## 1. 文档定位

本文档定义 Asteria 的工程治理机制。它关注的不是某个功能怎么做，而是如何让长期演进不失控：决策可追溯、schema 可兼容、状态可迁移、错误可恢复、变更可灰度、发布可验证、安全风险可建模。

与其他文档的关系：

- [工程化体系.md](./工程化体系.md)：定义日志、权限、配置、hooks、skills、plugins、MCP 等横切能力。
- [工程治理体系.md](./工程治理体系.md)：定义 ADR/RFC、兼容性、迁移、错误分类、feature flag、golden trace、发布分级和威胁模型。
- [数据模型.md](./数据模型.md)：定义具体 schema 和落盘对象。
- [质量与评估.md](./质量与评估.md)：定义测试和验收方法。
- [当前状态与路线.md](./当前状态与路线.md)：决定当前优先级。

## 2. 总原则

- 决策要留痕：重大架构、产品、权限、数据模型和发布策略必须有 ADR 或 RFC。
- 契约要分级：明确哪些 CLI、schema、文件路径、Python 模块和报告字段是稳定契约，哪些仍是实验内部实现。
- 迁移要可回滚：`.asteria/` 状态、policy、run evidence、plugin manifest 和 capability profile 演进时，必须有迁移路径和失败策略。
- 错误要可分类：所有阻塞都应落入可解释、可恢复、可报告的错误分类。
- 新能力要可关：hooks、plugins、MCP、并发 worker、streaming、provider route、promotion policy 等必须能被 feature/capability flag 控制。
- 行为要可对比：核心运行链路要有 golden trace，防止重构后“测试过了但行为漂了”。
- 发布要按风险分级：不同变更规模匹配不同验证套件，不把所有验证都靠人工记忆。
- 安全要前置建模：插件、MCP、模型工具调用、诊断导出和候选 promotion 必须有 threat model。

## 3. ADR / RFC 决策体系

### 3.1 ADR

ADR 用于记录已经做出的长期架构决策。每条 ADR 应短而硬，避免写成讨论日志。

建议路径：

```text
docs/zh/adr/
  0001-use-jsonl-before-sqlite.md
  0002-candidate-workspace-isolation.md
```

模板：

```markdown
# ADR-0001: 标题

## 状态

Accepted / Superseded / Deprecated / Proposed

## 背景

为什么必须做这个决定。

## 选项

- 选项 A：收益、代价。
- 选项 B：收益、代价。

## 决策

选择什么，以及边界是什么。

## 后果

短期收益、长期约束、迁移成本。

## 回滚或替代条件

什么信号出现时需要重评。
```

必须写 ADR 的情况：

- 状态存储形态变化，例如 JSON/JSONL -> SQLite。
- CLI 或公共 schema 兼容策略变化。
- 插件/MCP 执行权限从声明阶段进入执行阶段。
- 默认 sandbox、candidate workspace 或 promotion policy 变化。
- 模型路由、成本策略或 deadline 策略成为默认行为。
- 引入高风险依赖、远程服务、上传诊断包或多用户能力。

### 3.2 RFC

RFC 用于尚未接受的大型方案。RFC 可以比 ADR 更长，允许记录未决问题和实验计划。

建议路径：

```text
docs/zh/rfc/
  0001-plugin-runtime-execution.md
  0002-mcp-adapter-boundary.md
```

RFC 进入实现前必须明确：

- 用户价值。
- 非目标。
- 数据模型影响。
- 权限和安全影响。
- 迁移计划。
- 验收场景。
- 回滚策略。

## 4. 公共契约与兼容性策略

Asteria 必须区分公共契约和内部实现，防止插件、脚本或用户工作流绑定不稳定细节。

公共契约候选：

- CLI 用户主入口：`init`、`run`、`status`、`resume`、`review`、`accept`。
- `.asteria/` 中明确文档化的 schema 对象。
- 报告中的稳定 JSON 字段，例如 `gate-status --json`、`doctor --json`、`status --json`。
- `PluginManifest`、未来 `SkillManifest`、MCP adapter manifest。
- hook name 和 `RuntimeHookEvent` 的核心字段。

内部实现候选：

- 命令内部 helper。
- Python 私有模块和未文档化函数。
- acceptance 场景内部 fixture。
- 临时灰度证据字段。
- 未进入数据模型文档的 JSON key。

兼容规则：

- 公共契约新增字段必须向后兼容，消费者应忽略未知字段。
- 公共契约删除或重命名字段必须先 deprecated，再迁移。
- schema 中实验字段应标注 `experimental` 或放在 `metadata` / `extensions` 区。
- 0.x 阶段允许较快演进，但每次破坏性变更必须写入当前状态或 ADR。
- 1.0 后公共契约应有明确 deprecation 周期。

## 5. Schema 版本与迁移体系

### 5.1 版本策略

每个持久化对象必须保留 `schema_version`。版本含义：

- patch：字段描述或宽松兼容修正，不需要迁移。
- minor：新增可选字段或默认值，可由 loader 自动补齐。
- major：删除、重命名、语义改变或状态机变化，必须提供 migration。

### 5.2 迁移注册表

`SchemaMigrationRegistry` 已在 `src/asteria_runtime/core/schema_migration.py` 实现，支持版本化迁移链。当前已注册的迁移：

- `policy_config` 0.1.0 → 0.2.0：新增 `feature_flags` 和 `capability_flags` 顶层区。
- `plugin_manifest` 0.1.0 → 0.2.0：新增 `blocked_reason` 和 `loaded_at` 可选字段。

每次迁移会记录审计日志（`MigrationRecord`），包含 schema 名、版本和描述。`load_policy_config` 已在读取后自动运行迁移。

后续新增迁移时应在 `build_default_registry()` 中注册，并在此处更新列表。旧版建议保留在下方作为参考：

```text
src/asteria_runtime/migrations/
  __init__.py
  registry.py
  v0001_agent_to_asteria.py
  v0002_policy_hooks_defaults.py
```

迁移对象必须记录：

- migration id。
- 输入版本和输出版本。
- 影响路径。
- 是否可逆。
- dry-run 摘要。
- 失败恢复策略。

### 5.3 迁移原则

- loader 可以补齐缺失默认 key，但不能静默改变用户语义。
- 高风险迁移必须先备份原文件或写 migration journal。
- 迁移失败时必须保留原始状态，并给出可执行修复建议。
- `.asteria/runs/<run-id>/` 的历史 evidence 默认只读；除非明确需要，不主动重写历史 run。
- 迁移结果必须能被 `doctor` 检查和解释。

## 6. ErrorTaxonomy 错误分类与恢复策略

统一错误分类用于日志、报告、doctor、debug、capability profile 和用户解释。

基础分类：

```text
configuration
authentication
permission
protected_path
budget
provider
network
timeout
schema
validation
merge_gate
promotion
candidate_workspace
plugin
skill
mcp
tool
model_output
context_budget
task_contract
internal
```

每类错误必须定义：

- 用户可见摘要。
- 是否可自动恢复。
- 推荐下一步命令。
- 是否需要 DecisionPoint。
- 是否影响 release gate。
- 是否写入 capability profile。

示例：

```text
provider.timeout
  user_summary: 模型 provider 超时
  auto_recovery: 可重试，受 deadline budget 限制
  next_action: model-check / 降级 route / 调整 timeout
  release_gate: strong/medium route 超时会阻断 release-ready
```

原则：

- 不直接把 Python exception message 当用户解释。
- `blocked` 必须有错误分类，否则报告无法聚合。
- 插件/MCP 错误默认隔离，不能被归成普通 internal error。
- schema 错误优先提示迁移或版本不兼容，而不是让用户读 traceback。

## 7. Feature Flag 与 Capability Flag

Feature flag 控制“是否启用某个功能”。Capability flag 描述“当前环境是否具备某个能力”。

实现位置：`src/asteria_runtime/core/flag_resolver.py`。`FlagResolver.from_policy()` 从 policy 和环境状态构建 resolver，`resolve(name)` 同时检查 feature 开关和所需能力。`gate-status --json` 的 `feature_flags` 和 `capability_flags` 字段由 `FlagResolver` 生成。

Feature flag 示例：

```text
hooks.enabled
hooks.plugins_enabled
mcp.enabled
skills.enabled
parallel_readonly_workers.enabled
parallel_write_workers.enabled
streaming_provider.enabled
candidate_worktree.enabled
promotion_manual_approval.enabled
diagnostic_export.enabled
```

Capability flag 示例：

```text
capability.git_worktree_available
capability.strong_route_configured
capability.medium_route_streaming
capability.sandbox_backend_available
capability.package_installed_cli
capability.core_gate_release_ready
```

规则：

- 新能力先 behind flag，再灰度默认启用。
- flag 默认值必须写入 `policies.default.json` 或由 `doctor` 明确解释。
- capability flag 由检测结果生成，不能让用户手写伪造 release-ready。
- gate/report 必须同时显示 feature flag 状态和 capability flag 状态，避免“开关开了但环境不支持”。
- flag 删除必须走 deprecation policy。

## 8. Golden Trace 与契约测试

Golden trace 是标准运行轨迹，用来验证重构后行为没有意外漂移。

建议结构：

```text
tests/golden_traces/
  doc_only_task/
    goal.txt
    expected_task_plan.json
    expected_runtime_hooks.jsonl
    expected_worker_summary.json
    expected_final_report.md
  multi_file_small_tool/
  merge_gate_block/
  runtime_request_resume/
```

Golden trace 不要求逐字比较所有时间戳和 id，但必须比较：

- 任务拆解数量和依赖形态。
- allowed tools 与 write scope。
- WorkerInvocation/WorkerResult 状态。
- runtime hook 类型序列。
- validation result 状态。
- candidate promotion 状态。
- final report 的关键段落和阻塞解释。

适用场景：

### 8.1 已有 Golden Trace 覆盖

以下 golden trace 已作为 unit test 实现：

- `test_failed_candidate_does_not_pollute_main_workspace`：验证 discard 后主工作区无任何残留 artifact，候选工作区完全清理。这是 candidate workspace isolation 的核心契约保证。
- `test_gate_status_blocks_release_when_plugin_manifests_are_blocked`：验证 blocked plugin manifest 会阻断 release stage。
- `test_gate_status_blocks_gray_when_candidate_promotions_are_unresolved`：验证未解决 promotion 阻断 release。
- `test_merge_gate_rejects_files_outside_write_scope`：验证 merge gate 拒绝超出 write scope 的变更。
- `test_merge_gate_passes_in_scope_changes`：验证合法 scope 内的变更能通过 merge gate。
- `test_merge_gate_rejects_when_no_changes_but_promotion_required`：验证无变更时不允许 promotion。
- `test_merge_gate_rejects_failed_verification`：验证验证失败时阻断 promotion。
- `test_policy_migration_adds_flags_without_losing_budgets`：验证 schema 迁移不丢失用户数据。
- `test_migration_chain_runs_in_order`：验证多步迁移按顺序执行。
- `test_feature_flag_disabled_not_active`：验证禁用 feature flag 不激活。
- `test_feature_flag_missing_capability_not_active`：验证环境能力不足时 feature 不激活。

- Coordinator、WorkerRunner、Gateway、Policy、Planner、ContextPackage、Report 发生重构。
- schema 或迁移逻辑改变。
- 插件/MCP/skills 接入运行链路。
- 模型输出解析策略改变。

## 9. 发布分级与验证矩阵

变更按风险分级：

```text
XS: 文档、注释、无行为改动
S: 单模块内部修复，有明确 unit test
M: runtime 边界、schema、CLI JSON 字段、报告口径变更
L: Coordinator/Worker/Gateway/Policy/Context/Promotion 等核心链路变更
XL: provider、plugin/MCP 执行、迁移、权限默认值、发布 gate 变更
```

推荐验证：

```text
XS -> doc/link check
S  -> targeted unit tests + ruff
M  -> targeted + related integration + package-check/doctor when relevant
L  -> core subset + acceptance-gate + capability/report checks
XL -> full pytest + ruff + mypy + package-check + real-model-gate + gray suite + core gate
```

规则：

- `gate-status --json` 的 `validation_recommendation` 应逐步消费这个矩阵。
- release-ready 不能只依赖最近一次通过；必须检查 unresolved promotion、route capability、schema/migration 状态和核心 gate。
- 真实 provider 灰度不能替代 offline/core gate；两者验证不同风险。

## 10. Deprecation Policy

对象范围：

- CLI 命令和 flag。
- JSON schema 字段。
- `.asteria/` 文件路径。
- hook name。
- plugin/skill/MCP manifest 字段。
- Python 公共 API。

流程：

1. 标记 deprecated，并在文档和 `doctor`/report 中提示替代项。
2. 至少保留一个迁移周期。
3. 提供自动迁移或清晰手动步骤。
4. 删除前写 ADR 或 release note。
5. 删除后保留明确错误信息，避免 silent failure。

0.x 阶段可以缩短周期，但不能无记录地破坏主文档承诺。

## 11. 威胁模型

必须建模的风险：

- Secret 泄露：日志、诊断包、provider prompt、plugin/MCP 上传。
- 越权写入：工具、插件、MCP、候选 promotion 修改 protected paths。
- 恶意插件：注册高频 hook、读取源码、执行 shell、外传数据。
- MCP 数据外传：通过外部 connector 上传未授权上下文。
- 模型幻觉命令：生成危险 shell、错误验证命令、错误路径。
- 状态污染：失败候选污染主工作区，旧 run evidence 被错误复用。
- 成本失控：repair/replan 循环、provider retry、并发 worker 放大。
- 报告误导：final report 声称完成但 artifact/validation 不成立。

每个高风险能力进入实现前必须回答：

- 攻击面是什么。
- 默认是否关闭。
- 如何授权。
- 如何审计。
- 如何检测异常。
- 如何回滚或禁用。
- 哪个 gate 阻断发布。

## 12. 供应链与依赖治理

当前 Asteria 应继续偏标准库和少依赖。引入新依赖时必须说明：

- 为什么标准库或已有依赖不够。
- 是否影响安装包体积和离线运行。
- 是否涉及网络、原生扩展、许可证或供应链风险。
- 是否需要 lockfile、SBOM 或依赖审计。

插件/MCP 阶段额外要求：

- 插件来源、版本和校验信息必须可记录。
- 默认禁止插件隐式安装依赖。
- 允许安装时必须走用户确认和审计日志。
- 公共市场之前必须具备签名/校验、禁用列表和回滚机制。
