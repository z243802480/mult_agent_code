# 真实模型验收

本文档记录真实模型 provider 的手动验收和定期验收流程。它和离线验证分开维护，因为真实验收会消耗 API 调用额度。

验收证据必须绑定当前目标 Workspace。`.asteria/model`、`.asteria/verification`、`.asteria/acceptance`、`.asteria/runs` 和 `user_progress.jsonl` 都是 Workspace-local 运行产物；全局用户目录只保存模型 route、账号引用、recent/current workspace、UI 偏好和缓存。历史通过记录只能作为研发参考，进入新机器、新 Workspace、安装包路径或用户内测前，必须在目标环境重新生成 summary 和 evidence，且不得把 API key、本机 route 文件、账号凭证或其他 Workspace 的 session 打包进诊断/验收结果。

## 套件

- `smoke`：最小文件创建闭环。
- `validation`：验证发布候选验证，覆盖文件产出、多文件 scope、debug 修复和 runtime request resume。
- `core`：`file_smoke`、`password_cli`、`markdown_kb`、`safe_file_renamer`、`multi_file_todo_cli`、`config_driven_report`，以及 Runtime OS 发布门槛场景。
- Runtime OS 场景：`runtime_parallel_readonly`、`runtime_disjoint_writes`、`runtime_worker_failure`、`runtime_merge_gate_block`、`runtime_request_resume`、`runtime_context_package_slice`、`runtime_sandbox_backend_selection`、`runtime_planner_scope_quality`、`runtime_capability_feedback`、`runtime_evidence_consumption`。
- `advanced`：失败测试修复和决策点处理。
- `nightly`：所有不依赖用户数据、适合定期运行的真实验收场景。
- `offline`：只用于 fake provider 的脚本自身覆盖。

## 推荐命令

先跑 provider 健康检查：

```powershell
python -m asteria_runtime /model-check --root . --tier strong
python -m asteria_runtime /model-check --root . --tier medium
```

如果 `doctor --json` 显示 medium 通过全局 `AGENT_MODEL_*` fallback 生效，而 `real-model-gate` 要求显式 tier route，可在当前 shell 中把全局 MiniMax 路由映射到 medium tier；不要把 key 写入文档或提交到仓库：

```powershell
$env:AGENT_MODEL_MEDIUM_PROVIDER = $env:AGENT_MODEL_PROVIDER
$env:AGENT_MODEL_MEDIUM_NAME = $env:AGENT_MODEL_NAME
$env:AGENT_MODEL_MEDIUM_API_KEY = $env:AGENT_MODEL_API_KEY
$env:AGENT_MODEL_CHEAP_PROVIDER = "fake"
```

验证发布验证前必须先跑真实模型 gate：

```powershell
asteria real-model-gate --summary-json .asteria/model/real_model_gate_report.json
```

该 gate 不等同于完整 acceptance。它只证明当前 key、endpoint、strong/medium 路由、最小 `/run`、Worker evidence、TaskExecutionEvidence 和成本日志可用。只有 gate 通过后，才进入 core/nightly acceptance 或小范围真实任务验证。

运行验证候选场景集：

```powershell
asteria real-model-acceptance --suite validation --summary-json .asteria/verification/real_model_acceptance_validation.json
```

`validation` suite 会在 summary 中写入 `validation_ready`。只有 `validation_ready=true` 且 `aggregate.route_evidence` 显示 strong/medium route 都被实际使用，才继续进入 core acceptance。
安装包隔离 venv 中运行 `validation` suite 时，所选 `--python` 解释器需要可用 `pytest`；`validation_debug_repair` 会执行 `python -m pytest test_buggy_math.py -v`。若使用临时 venv 验证 wheel，请先在该 venv 内安装 pytest，或通过 `--python` 指向已有 pytest 的解释器。

运行最小真实模型闭环：

```powershell
asteria real-model-smoke --summary-json .asteria/verification/real_model_smoke.json
```

运行当前真实任务验收集：

```powershell
asteria acceptance --suite core --allow-fake
asteria acceptance-gate --suite core --min-scenarios 10 --min-capabilities 10
```

额度允许时运行更完整的 nightly 验收：

```powershell
asteria real-model-acceptance --suite nightly --summary-json .asteria/verification/real_model_acceptance_nightly.json
```

持久化可对比历史：

```powershell
asteria real-model-acceptance --suite core --summary-json .asteria/verification/real_model_acceptance_core.json --history-jsonl .asteria/verification/real_model_acceptance_history.jsonl
```

`scripts/real_model_smoke.py`、`scripts/real_model_gate.py` 和 `scripts/real_model_acceptance.py` 仍保留为仓库开发兼容 wrapper；安装包和验证用户路径应优先使用 `asteria real-model-*`。

## 摘要指标

`asteria real-model-smoke` 会写入：

- `duration_seconds`
- `diagnostics.run_status`
- `diagnostics.review_status`
- `diagnostics.review_score`
- `diagnostics.task_status_counts`
- `diagnostics.model_calls`
- `diagnostics.tool_calls`
- `diagnostics.estimated_input_tokens`
- `diagnostics.estimated_output_tokens`
- `diagnostics.repair_attempts`
- `diagnostics.context_compactions`

`asteria real-model-acceptance` 会把这些成本和稳定性指标按场景聚合。
提供 `--history-jsonl` 时，脚本会把每次 summary 追加到 JSONL 历史，并在当前 summary 中写入
`trend.previous` 和数值 delta，覆盖通过/失败数量、耗时、模型/工具调用、token 估算、修复次数和
context compaction 次数。runtime 的 `asteria /acceptance` 默认会把历史写入
`.asteria/acceptance/history.jsonl`。

查看 runtime 工作区历史：

```powershell
python -m asteria_runtime /acceptance-history --root . --limit 5
```

查看脚本级自定义历史文件：

```powershell
python -m asteria_runtime /acceptance-history --root . --history-jsonl .asteria/verification/real_model_acceptance_history.jsonl
```

把趋势告警作为本地门禁：

```powershell
python -m asteria_runtime /acceptance-history --root . --suite nightly --fail-on-warning
```

也可以让 `/acceptance` 在同一次验收中直接因为趋势告警失败：

```powershell
python -m asteria_runtime /acceptance --root . --suite core --fail-on-trend-warning
```

告警阈值可以配置：

```powershell
python -m asteria_runtime /acceptance-history --root . --warn-model-call-delta 5 --warn-duration-delta 120 --warn-repair-delta 1 --fail-on-warning
python -m asteria_runtime /acceptance --root . --suite core --warn-model-call-delta 5 --warn-duration-delta 120 --warn-repair-delta 1 --fail-on-trend-warning
```

## 通过标准

一个场景只有满足以下条件才算通过：

- `/model-check` 成功。
- 期望产物存在，并包含期望文本。
- 必要运行产物存在且非空。
- `run.json` 状态为 `completed`。
- `eval_report.json` 的 overall status 为 `pass`。
- 当前有效任务均为 done；`discarded` 只允许作为被 replan 替代的历史修复记录。
- 成本计数和 JSONL 日志数量一致。

真实验收失败不应被忽略，应通过 `asteria /acceptance --promote-failures` 纳入修复闭环。

## 能力画像

验收报告应写入 `scenario_metadata`，并在每个场景上保留 `capability` 和 `tier`。runtime
读取旧历史时会根据已知场景名回填这些字段，避免 `asteria capability-report` 和
`asteria acceptance-gate` 把历史能力覆盖统计成 `unknown`。

最新发布状态以 `.asteria/acceptance/acceptance_report.json` 为准，因为它包含 runtime
计算出的趋势告警；脚本级 `history.jsonl` 可能只包含原始 summary。

常用门禁：

```powershell
python -m asteria_runtime /acceptance-gate --root . --suite core --min-scenarios 3 --min-capabilities 3
python -m asteria_runtime /acceptance-gate --root . --suite core --min-scenarios 3 --min-capabilities 3 --allow-trend-warnings
```

`core` / `nightly` release gate 默认要求 Runtime OS 证据：worker invocation/result、runtime profile、context mount、validation result、失败 evidence、candidate isolation、merge gate block、resume recovery、ContextPackage 按 `read_scope` 切片、sandbox backend 选择原因、Planner scope quality、capability feedback，以及 debug/review 对 Runtime OS evidence 的消费。只有在兼容旧报告时才使用 `--no-require-runtime-os`。

第一条会因为成本或稳定性趋势告警阻断。第二条允许趋势告警，把状态标记为
`conditional`，适合在更宽的真实基线已经通过、但仍需要继续优化成本时使用。
## Runtime OS core gate 组合命令

发布前的完整 core gate 应把普通真实模型场景和 Runtime OS 场景放在同一次 core suite 里运行，避免后一次报告覆盖前一次报告导致 gate 只看到部分场景：

```powershell
python -m asteria_runtime /acceptance --root . --suite core --fail-on-trend-warning
python -m asteria_runtime /acceptance-gate --root . --suite core --min-scenarios 10 --min-capabilities 10
```

如果只想快速验证 Runtime OS release gate 的结构化证据，可以单独跑确定性的 Runtime OS 子集；这适合开发期回归，不等价于完整真实模型 core gate：

```powershell
python -m asteria_runtime /acceptance --root . --suite core --allow-fake --scenario runtime_parallel_readonly --scenario runtime_disjoint_writes --scenario runtime_worker_failure --scenario runtime_merge_gate_block --scenario runtime_request_resume
python -m asteria_runtime /acceptance-gate --root . --suite core --min-scenarios 5 --min-capabilities 5
```

Runtime OS gate 的能力清单和 required evidence 由 `src/asteria_runtime/acceptance/runtime_os_catalog.py` 维护，检查逻辑由 `RuntimeOSGateEvaluator` 统一执行。后续 `capability-report`、`weekly-report` 或 dashboard 如果需要复用发布门槛，应消费 evaluator 结果，而不是重新硬编码 capability 名称。
