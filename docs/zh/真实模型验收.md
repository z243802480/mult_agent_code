# 真实模型验收

本文档记录真实 provider 验收的当前口径和推荐命令。它是 reference 文档，不替代 [当前状态与路线.md](./当前状态与路线.md)。

真实验收会消耗 API 调用额度，必须绑定当前目标 Workspace。`.asteria/model`、`.asteria/verification`、`.asteria/acceptance`、`.asteria/runs` 和 `user_progress.jsonl` 都是 Workspace-local 运行产物；全局用户目录只保存模型 route、账号引用、recent/current workspace、UI 偏好和缓存。历史通过记录只能作为研发参考，进入新机器、新 Workspace、安装包路径或用户内测前，必须重新生成 summary 和 evidence，且不得把 API key、本机 route 文件、账号凭证或其他 Workspace 的 session 打包进诊断/验收结果。

## 当前口径

- 固定 release/validation gate 仍要求 strong/medium route 都健康，并在对应 suite 中形成实际调用证据。
- 低风险 fast-path 小任务不要求每次都出现 strong 调用。`doc_update`、`simple_file` 和部分 `single_file_bugfix` 的目标是 medium/deterministic-first、slim/focused context、0 或最少 strong 调用。
- 判断真实任务质量时，优先看产物和验证是否可复现、`model_calls.jsonl` 是否记录 `context_mode` / `fast_path_task_kind`、deterministic review 是否命中、repair/replan 是否有边界，以及最终报告是否可读。
- 历史的 4/4、7/7、10/10、8/8 只能说明当时固定样例没有退化；长期自主研发能力必须继续看真实任务中的上下文压力、能力选择理由、权限阻断、恢复/冲突处理和最终产物验证。

## 推荐命令

先跑 provider 健康检查：

```powershell
python -m asteria_runtime model-check --root . --tier strong --json
python -m asteria_runtime model-check --root . --tier medium --json
```

发布/放量前置 gate：

```powershell
asteria real-model-gate --summary-json .asteria/model/real_model_gate_report.json
asteria real-model-acceptance --suite validation --summary-json .asteria/verification/real_model_acceptance_validation.json
asteria acceptance --suite core --allow-fake
asteria acceptance-gate --suite core --min-scenarios 10 --min-capabilities 10
python -m asteria_runtime gate-status --root . --json
```

Fast path / context slimming 小灰度：

```powershell
asteria real-model-smoke --matrix-preset rolling-fastpath-v1 `
  --no-research `
  --model-max-retries 0 `
  --matrix-output-dir .asteria/verification/real_provider_matrix/<run-id>
```

`--allow-fake` 只用于脚本或 offline baseline 覆盖，不作为真实 provider 质量证据。
offline baseline 的 matrix summary 会标记 `provider_mode=fake`；真实小灰度必须使用 `provider_mode=real` 的 summary。

## 摘要指标

`asteria real-model-smoke` / matrix summary 应重点保留：

- `duration_seconds`
- `diagnostics.run_status`
- `diagnostics.review_status`
- `diagnostics.model_calls`
- `diagnostics.tool_calls`
- `diagnostics.repair_attempts`
- `context_strategy.model_call_count`
- `context_strategy.context_modes`
- `context_strategy.fast_path_task_kinds`
- `context_strategy.slim_model_calls`
- `context_strategy.strong_model_calls`
- `context_strategy.task_execution_model_calls`
- `context_strategy.task_repair_model_calls`
- `context_strategy.run_review_model_calls`
- `agent_loop.budget_repair_attempts`
- `provider_mode`
- `trend.cases.<case>.task_execution_model_calls_avg/max`
- `trend.cases.<case>.retry_classifications`
- `trend.warnings`
- `/run` 生成的 `final_report_summary.json.provider_matrix_guidance`
- 每条 `model_calls.jsonl` 的 `purpose`、`model_tier`、`provider`、`model_name`、`duration_ms`、`streaming.first_chunk_ms`

`asteria real-model-acceptance` 会把这些成本和稳定性指标按场景聚合。提供 `--history-jsonl` 时，脚本会把每次 summary 追加到 JSONL 历史，并在当前 summary 中写入 `trend.previous` 和数值 delta，覆盖通过/失败数量、耗时、模型/工具调用、token 估算、修复次数和 context compaction 次数。

## 通过标准

一个真实 smoke/matrix case 只有满足以下条件才算通过：

- `model-check` 成功，或 case summary 明确记录当前 provider failure 为环境/route 证据。
- 期望产物存在，并包含期望文本。
- 必要运行产物存在且非空。
- `run.json` 状态为 `completed`。
- `eval_report.json` 的 overall status 为 `pass`（**仅当已单独跑过 review 时适用**，见下注）。
- 当前有效任务均为 `done`；`discarded` 只允许作为被 replan 替代的历史修复记录。
- 成本计数和 JSONL 日志数量一致。
- 低风险 fast-path case 应解释 strong 调用数、repair 次数、context mode 和 deterministic review 是否符合预期。

> **review 是独立一步（现状）**：`/run` 自身不再内联跑 review（见 `运行命令.md` §3.7）。`eval_report.json` 与
> `diagnostics.review_status` 由独立的 `asteria review` 或 accept/acceptance 栈产出。纯 `asteria real-model-smoke`
> 的 `run_smoke`（init → model-check → run → validate）不调 review，此时 `eval_report.json` 缺失、
> `diagnostics.review_status` 为 `unknown`/`None`——上面「overall status 为 `pass`」一条只在 review 已运行的
> case 生效；要覆盖它，需在 smoke/matrix 流程中显式加一步 `asteria review`（属行为改动，须显式选择，非默认）。
> 上表中带 `run_review` / deterministic-first review 的历史行反映的是 review 尚在 `/run` 内联时的旧状态。

真实验收失败不应被忽略，应通过 `status`、`review`、`capability-report`、`evidence-bundle` 和必要的 `debug` / `replan` 纳入恢复闭环。
