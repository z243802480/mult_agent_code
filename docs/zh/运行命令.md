# 多智能体自主开发系统 - 运行时命令与任务拆解

## 1. 文档目的

本文档定义运行时命令规格和 PlannerAgent 的任务拆解原则。

本文档是完整命令参考，不负责判断当前研发阶段，也不定义普通用户产品路径。进入开发前先阅读 [当前状态与路线.md](./当前状态与路线.md) 和 [用户交互模型.md](./用户交互模型.md)，再按需查本文件中的具体命令。

普通用户主入口以 Goal / Plan 为主，Ask 为轻量入口。Brainstorm、Research、Debug、Review、Coder、多智能体等专业链路，以及 `init`、`run`、`status`、`review`、`accept`、`execute`、`debug`、`promotions`、`gate`、`validation`、`real-model-*` 等命令，是专家命令、维护命令或产品背后的 runtime action；可以保留给系统和维护者，但默认不应要求普通用户理解。

本文是 reference 文档，不单独决定当前研发优先级。当前实现顺序以 [当前状态与路线.md](./当前状态与路线.md) 为准。阅读本文时应区分三层：

- 产品入口：Goal / Plan 是主入口，Ask 是轻量入口；交互侧必须展示实时模型判断、接口/工具调用过程、关键思考摘要、验证过程和最终整理。
- 专家命令：Brainstorm、Research、Debug、Review、Coder、多智能体，以及 `run`、`status`、`review`、`accept`、`debug`、`resume` 等用于当前 CLI/runtime loop 和排障。
- 维护命令：`doctor`、`gate`、`validation`、`real-model-*`、`acceptance-*` 等用于 provider、验证和发布门槛。

命令不是 prompt 快捷方式，而是可复用、可观测、可审计的工作流。任务拆解不是简单列清单，而是把目标切成大小适中、可验收、有明确产物的执行单元。

## 1.1 命名与兼容策略

2026-05-17 起，当前主线统一使用 Asteria 命名：

- 安装包：`asteria-runtime`。
- Python 模块：`asteria_runtime`。
- CLI 入口：`asteria`。
- 状态目录：`.asteria/`。

项目尚未发布 1.0，也没有外部稳定 API/CLI 兼容承诺。为避免后续与通用 `agent` 命令、其他 Python 包或开源工程名称冲突，旧 `agent` 命令和 `agent_runtime` 模块不作为公共兼容入口保留。文档、脚本和示例应继续使用 `asteria`；只有 `.asteria/` 状态目录暂时沿用，因为它已经是持久化对象、运行证据和 agent-ready workspace 约定的一部分。

命令示例优先使用无斜杠形式，例如 `asteria run`、`asteria status`、`asteria accept`。历史文档中的 `/run`、`/status`、`/accept` 等斜杠前缀保留为兼容别名，用于旧脚本、迁移期文档和专家排障；新增普通用户文档不应把斜杠形式作为首选入口。

## 1.1.1 Project / Workspace / Session 边界

Asteria 的产品层级是：

```text
Project / Workspace
  -> Session
       -> Run / Evidence / Artifacts
```

- Project / Workspace 是本地目录，例如 `H:\mult_agent_code`、`site_soe`、`fileCollector`。
- Session 是 workspace 内的一段目标上下文。
- Run 是 session 的内部执行记录。
- 单工程输出文件、运行证据、Studio session thread、`.asteria/runs/` 都必须在 workspace 目录下。
- 用户目录下的全局 `.asteria/` 只保存 recent workspaces、current workspace、模型本机 route、账号引用、UI 偏好和缓存。
- 切换 workspace 后，`sessions`、`status`、`run`、`review`、`accept` 都只解析该 workspace 内的 `.asteria/`。

## 1.2 默认用户主线

面向普通用户的默认心智应收敛为：

```text
Goal / Plan / Ask
```

- `Goal` 接收目标并启动可审计 agent loop。
- `Plan` 只读分析和拆解，不进入执行。
- `Ask` 轻量问答，状态类问题按需挂载长期任务状态。
- Brainstorm、Research 和其他专业智能体可以作为显式专家入口，也可以作为 Goal / Plan 背后的 runtime action。

内部 runtime 仍然可以采用体系化智能体阶段：

```text
init -> run -> status -> review -> accept
```

- `init` 初始化项目长期记忆、项目摘要、规则和运行时状态。
- `run` 执行核心大模型循环。
- `status` 把当前实现过程翻译成用户进展。
- `review` 在任务完成后复盘验收标准、证据、遗漏和风险。
- `accept` 收尾并固化验收回顾、长期记忆和下一步。

这些 runtime 阶段可以作为专家命令或产品界面背后的动作存在，但不是普通用户必须理解的线性流程。前台必须把它们翻译成实时模型判断、接口/工具调用过程、关键思考摘要、验证过程、最终整理和下一步。

`accept` 的产品语义是收尾阶段中的 Acceptance review：对原始目标、验收标准、验证证据、测试结果、交付物和残余风险的回顾。只要修改代码，就必须按需引入测试或等价验证来支撑“功能正确”的判断；无法验证时必须说明原因和风险。

新增或调整命令时，优先判断它是否应隐藏在 Goal / Plan / Ask 背后，还是属于专业智能体、维护或调试命令。只有当它代表新的用户意图时，才新增普通用户可见入口。

## 2. 通用命令结构

每个命令都应定义：

- 名称。
- 目的。
- 输入参数。
- 读取上下文。
- 允许工具。
- 参与智能体。
- 状态变化。
- 输出产物。
- 成本预算。
- 失败处理。
- 是否允许 agent 自行调用。

通用执行流程：

```text
parse command
  -> load root guidance
  -> load relevant memory
  -> check permissions and budget
  -> run command workflow
  -> write artifacts
  -> update event log
  -> update task state
  -> summarize result
```

## 3. 初始命令集

### 3.1 `/init`

目的：

将目录初始化为 agent-ready 工作区。

输出产物：

- `AGENTS.md`
- `.asteria/project.json`
- `.asteria/policies.json`
- `.asteria/context/root_snapshot.json`
- `.asteria/tasks/backlog.json`

`init --root <path>` 初始化的是该 workspace 自己的 `.asteria/`。它不应把 session、run 或工程产物写到用户全局目录；全局目录只更新 `%USERPROFILE%/.asteria/workspaces.json` 中的 recent/current workspace、output_root 和 artifact_root 指针。

验收：

- 空目录可初始化。
- 已有目录可初始化。
- 重复运行安全。
- 不覆盖用户手写内容。

Agent 自调用：

默认不允许。通常由用户或首次运行流程触发。

### 3.2 `/plan`

目的：

将用户目标转化为结构化目标规格和任务计划。

输出产物：

- `goal_spec.json`
- `task_plan.json`
- `task_plan_eval.json`
- `workspace_envelope.json`
- 更新后的任务看板。

验收：

- 目标不只是原句复述。
- 包含完成定义。
- 包含验证策略。
- 对模糊目标给出合理假设。
- `task_plan_eval.json` 至少达到 `warn`，否则应优先重规划而不是直接执行。

当前实现：

- `TaskPlanEvaluator` 会检查任务数量、ready 入口、依赖有效性、验收可观察性、预期产物、工具权限和任务颗粒度。
- 评估结果写入 `.asteria/runs/<run_id>/task_plan_eval.json`，并记录到 `events.jsonl`。
- `workspace_envelope.json` 记录 workspace_root、input_roots、output_root、artifact_root、worktree_policy、read/write scope、permission_mode 和 scope_summary。
- `PlanResult.to_text()` 会展示 output_root 和 artifact_root，普通用户能知道后续产物落点。
- `plan` 支持 `--input-root`（可重复）、`--output-root`、`--artifact-root`、`--worktree-policy controlled_patch|worktree|isolated_copy`，用于多工程目标和明确输出落点。

### 3.2.0 `/new`

目的：

开启一个新的隔离目标上下文，并把它设为当前 session。

当前实现：

- `asteria new "目标"` 会在必要时自动初始化工作区。
- 内部复用 `/plan` 生成 `goal_spec.json` 和 `task_plan.json`。
- 写入 `.asteria/current_session.json`，后续不显式传 `session_id` 的命令优先使用这个 current session。
- 用于避免多个目标之间因为默认“最新记录”而串上下文。

### 3.2.0.1 `/sessions`

目的：

找回、查看和切换历史 session 上下文。

概念边界：

- `Session` 是用户心智：一个目标、一段上下文、一个可恢复的工作会话。
- `Run` 是内部记录：落盘在 `.asteria/runs/<run_id>/` 的执行轨迹。

当前实现：

- `asteria sessions` 列出最近 session，并标记 current session。
- `asteria sessions --session-id <id>` 查看指定 session。
- `asteria sessions --session-id <id> --set-current` 将指定 session 设为当前上下文。
- `asteria sessions --context` 会显示每个 session 最新的 snapshot、handoff、最近验证状态、推荐下一步、待处理决策数、任务统计、promotion queue 摘要和 worker tree，方便后续 agent 恢复现场。

命令暴露原则：

- 最终用户入口应保持少而稳定：Goal / Plan 表达主要用户意图，Ask 表达轻量问题；Brainstorm、Research、专业智能体和 `init`、`run`、`status`、`resume`、`review`、`accept` 等是 runtime action 或专家命令，不要求普通用户理解内部 gate、smoke、acceptance runner 和 evidence 文件。前台应把这些阶段翻译成实时模型判断、调用过程、工具过程、验证进展、最终结果和下一步。
- 验证/运维入口应表达阶段：`doctor`、`gate`、`validation` 这类命令面向维护者和 alpha 验证，负责串联环境诊断、真实模型 gate、validation suite、小任务验证和 release gate；发布前完整检查作为 `gate --stage release` 暴露。
- 内部/专家入口可以继续存在：`real-model-smoke`、`real-model-acceptance`、`acceptance-gate`、`capability-report`、`promotions` 等用于开发调试、CI 门禁和问题复盘，但不应成为普通用户完成任务的必经心智模型。
- `validation` 不是新的普通用户概念，而是真实 provider 放量前的受控中间层。后续应优先把 `package-check -> doctor -> gate-status -> real-model-gate -> real-model-acceptance --suite validation -> validation-run -> acceptance-gate` 包装进少数阶段化入口，例如 `gate --stage release` 和 `validation`，而不是继续增加并列命令。
- 新增命令前必须先判断它属于用户主入口、验证/运维入口还是内部/专家入口；如果只是已有流程中的一步，优先作为现有命令的子命令、flag、JSON 字段或报告字段实现。

- `asteria version` / `asteria --version` 显示当前 runtime 版本；`asteria version --json` 输出 package、version、Python 版本和 executable，供验证诊断和 bug report 使用。
- `asteria package-check` / `asteria packaging` 检查本地打包前置条件：pyproject、build backend、console script、版本同步和验证文档。
- `python scripts/build_package.py --root . --clean` 用当前 Python/pip 构建本地 wheel 到 `dist/`，用于产品验证安装验证。
- `asteria status` 显示当前 Runtime OS 控制面状态：current session、workspace root、output/artifact root、run/task/cost、pending decisions、blockers、latest execution、worker 成功/失败/并发摘要、promotion queue 风险和推荐下一步。
- `asteria doctor` 只读检查本地运行环境：`.asteria`、AGENTS、policy/project config、git backend、strong/medium 有效模型路由和 real-model gate 报告；模型路由诊断与实际 runtime 路由一致，支持 tier-specific 配置、全局 `AGENT_MODEL_*` fallback、本机私有 `C:\Users\Administrator\.asteria\model.routes.local.ps1` 和 provider 原生 key。环境变量优先于本机私有文件；本机文件只用于保存当前机器 API key 和 route，不应提交或导出。
- `asteria gate-status` 汇总真实模型发布门槛阶段：real_model_gate、validation suite、core acceptance，以及下一步动作；历史 gate 通过但当前 shell 缺少有效 strong/medium 路由时会降为 blocked。
- `asteria gate-status --json` 还会输出 `validation_recommendation` 和 `promotion_release_risks`，按当前 git 变更规模推荐 targeted、core subset 或 full validation/core 验证路线，并在 candidate promotion queue 存在未解决发布风险时阻断 release-ready；验证建议不替代 release gate。
- `asteria real-model-acceptance --suite validation|core` 在跑完整 suite 时会写入 canonical summary：`.asteria/verification/real_model_acceptance_<suite>.json`。如果用户同时传 `--summary-json`，会额外写入指定历史文件；单场景 `--scenario` 不覆盖 canonical summary。
- `asteria gate-status --json` 会在 `.asteria/verification/` 下选择最新同 suite 的 `real_model_acceptance_<suite>*.json` 作为 validation/core 证据，并在 `evidence_sources` 中暴露实际使用的报告路径，避免旧失败 summary 覆盖后续修复后的通过证据。
- `asteria gate-status --json` 的 `plugin_risks` 字段会检查 `.asteria/plugins/` 下的 manifest 是否有 blocked 状态；blocked manifest 直接阻断 release（stage 降为 `plugin_manifests_blocked`），必须修复或禁用后才能继续。
- `promotion_release_risks` 新增 `threshold_reasons` 字段，在 pending/blocked 超过策略阈值时给出具体的 approve/reject/discard 操作指引，降低"为什么 release blocked"的认知成本。
- `validation_recommendation` 现在识别 schema、policy、hook/plugin governance 文件变更，自动升级为 `full_validation_core` 验证路线。
- `asteria gate-status --json` 新增 `feature_flags` 和 `capability_flags` 字段。`feature_flags` 由 `FlagResolver` 从 policy 和环境状态生成，每个 flag 同时检查功能开关是否启用、所需环境能力是否具备；只有两者都满足时 `active` 才为 `true`。`capability_flags` 自动推导当前环境的 strong_model、medium_model、plugin_execution、real_model、provider_streaming 能力状态；streaming 默认启用，只有 strong/medium route 被显式设置为 `*_STREAMING=0` 时才视为不可用。
- `real_disjoint_write_workers` 是默认关闭的 feature flag，用于真实并行 disjoint write worker 最小安全开关；启用前必须先通过真实 provider 灰度 probe，并继续让 RuntimeReadinessGate / gate-status 能阻断 candidate workspace、merge gate、promotion recovery 和 write_scope 风险。
- `asteria gate --json` 是默认只读阶段化门禁入口，当前包装 `version -> package-check -> doctor -> gate-status`，用于 alpha 维护者快速判断环境、包元数据和 release/validation 状态；它不运行真实模型、不修改候选工作区。
- `asteria gate --stage release --report <acceptance_report.json>` 是发布前重检查阶段，串联 `ruff check .`、`mypy src`、普通 pytest（排除 `real_provider`）和 `acceptance-gate`；它复用 `gate` 入口，不新增独立 `release` 命令。
- `asteria validation --json` 是 dry-run 验证入口，当前包装 `gate-status -> validation-run --dry-run`，会生成小真实任务验证计划或解释 route guidance、promotion、plugin、环境等阻断原因；它不会启动正式小任务。
- `asteria validation-run --dry-run` 在 real-model gate、validation suite、core acceptance 和当前路由环境都通过后生成小任务验证计划；计划会写入 `validation_plan`，明确采用适应性 gate：低风险探索 trace-only，promotion/merge/真实并行写/发布边界 strong gate，并列出 subagent 选择、readonly fanout、写工具阻断、disjoint write gate 阻断和父 loop stop 等 probes。去掉 `--dry-run` 后会创建受控真实任务 session，并把 `probe_results` 同步写入 `validation_plan` 和 `evidence.validation_probe_results`；普通 validation-run 中 `failed` probe 会使 validation-run 失败，`missing_evidence` 只进入 next actions，避免低风险缺样本被误当成硬失败。summary 写到 `.asteria/validation_runs/<id>/summary.json`。`--probe-id <id>` 可指定 targeted probe，支持重复传入；summary 会写入 `validation_plan.next_probe_goals` 和 `recommended_probe_runs`，把 missing probe 转成下一条可执行 scoped validation-run 命令。targeted probe 的目标 probe 若仍为 `missing_evidence`，本次 validation-run 必须标记为 `failed`，不能把“产物完成但能力未证明”算作通过。真实执行阶段如果 provider/network/plan/run 抛出异常，`validation-run --json` 会写出 `status=failed` summary，并把 `latest_failure.json`、`evidence.execution_failure` 和 next actions 留在同一个证据链里，而不是只向终端抛 traceback。`readonly_fanout_succeeds` targeted probe 会被收敛成 runtime-managed 单任务调度探针：PlanCommand 注入 `runtime_profile_hints.validation_probe_ids` 和 `readonly_fanout` 策略，ExecuteCommand 生成 parent `subagent` 决策，并让 readonly child 只做确定性只读验证；该探针验证调度和 gate 证据，不硬要求 medium worker 模型调用。`readonly_write_tool_blocked` 和 `disjoint_write_gate_blocks_unsafe_fanout` 属于“预期阻断”targeted probe，validation-run 会把执行轮数收敛到 1，并让 RuntimeReadinessGate 把受控阻断视为安全证明，而不是要求 repair/replan。
- `validation-run` 第二批 scoped dogfooding 已具备明确 probe 入口，不再以 tiny file artifact 作为主要证明。`validation_plan.second_batch_probe_goals` 会列出 `repair_replan_path`、`ask_stop_path`、`context_pressure_path` 和 `capability_selection_path`，分别要求 repair/replan decision-execution-observation、DecisionPoint/stop-report 边界、context budget compact-boundary 或 compaction evidence、以及 capability decision / adapter / progress coverage。第二批 runtime-managed probe 必须一次只运行一个；如果同一条命令传入多个第二批 probe，`validation-run` 会在启动 `RunCommand` 前返回 `status=blocked` 并输出逐个运行建议，避免不同 probe 覆盖 task contract 或污染最新 readiness。示例：`python -m asteria_runtime validation-run --probe-id repair_replan_path --root . --json`。`repair_replan_path` 使用 runtime-managed controlled failure：首轮生成失败 tool observation，第二轮进入 repair dispatch；`ask_stop_path` 使用 runtime-managed stop boundary：首轮生成 `stop` decision/execution/observation/run summary，证明 Runtime 会停在边界而不是猜过去；`context_pressure_path` 使用 runtime-managed context pressure snapshot：首轮写入 `compact_boundary=required` 的 context budget snapshot，再 stop 收尾；`capability_selection_path` 使用 runtime-managed capability evidence：首轮写入 reasoned `capability_decisions.jsonl`、`mcp_invocations.jsonl` 和 progress event，task-local `allowed_mcp/mcp_servers` 会持久化到 task plan 并进入 dispatch capability catalog，确保 selected MCP capability 可与实际 evidence 对齐。所有 targeted probe 若缺目标证据必须失败；对应的 readiness block 只在 probe 白名单内放行，用于刷新证据，不用于绕过高风险 gate。
- `asteria evidence-bundle --json` 导出产品化内测或 dogfooding 后的脱敏诊断包，默认写入 `.asteria/evidence_bundles/evidence-<timestamp>.zip`，包含 gate/acceptance/capability summary、validation-run 目录 summaries、`.asteria/validation_runs/*.json` 根层 summary、ops usage signals/analysis、最近 run 的 events/model_calls/task/worker/validation evidence tail 和 route latency 聚合指标；它会排除 API key、本机 route 文件、`.env`、`secrets/`、`.git/`、证书和私钥。
- `asteria ops-signal` 是 Maintainer/Inspector 侧后台使用信号入口，不属于普通用户主流程。它把脱敏运维信号写入 `.asteria/ops/usage_signals.jsonl`，可绑定 `run_id`、证据包引用、产物采纳结果、阻塞类别和信任风险；`asteria ops-signal --summary --root .` 查看聚合，`asteria ops-signal --summary --analyze --root .` 写入 `.asteria/ops/usage_signal_analysis.json`，生成 priority items、roadmap tasks、候选 DecisionPoint、`dogfooding_gate`、`acceptance_signal_gate` 和 `next_batch_plan`。`dogfooding_gate` 至少要求 3 个 active clean scoped signals，且不能有 unresolved outcome、blocker 或 trust risk，才会标记 `ready_for_next_batch=true`。`weekly-report` 和 `roadmap-update` 会把 ready 的 `next_batch_plan` 转成具体下一批 scoped dogfooding 动作；`daily-plan`、`weekly-report`、`roadmap-update` 只消费聚合/分析摘要，不把“收集反馈”暴露为用户必须理解的产品概念。
- 当 `next_batch_plan` 的 `real_repair_task`、`multi_file_small_feature` 和 `context_pressure_maintenance` 都有 accepted usage signal 后，analysis 会进入 `status=completed`，并在 `evidence_refs` 中同时保留显式证据路径和 `run:<id>` 引用，便于 fresh evidence bundle、weekly report 和 roadmap 复盘完整批次。
- GoalSpec 路由会消费 `provider_route_strategy.strong_goal_spec`：健康时继续 strong primary/cost-saver；出现 transient timeout/rate-limit/network 时可先 retry；当目标是低风险文档类任务且 strong goal_spec route 不稳定但不是认证/预算硬失败时，可把 GoalSpec 降级到 medium，并在 run events 的 `model_route_selected` 和 validation summary 的 `goal_spec_execution_plan` 中记录原因。route guidance 会输出 strong goal_spec 的最近真实调用窗口；`glm-5` 与 provider 实际回传的 `glm-5.1` 作为受限 alias 匹配，避免新鲜成功证据被旧配置名噪声遮蔽。release gate 在新鲜真实 release evidence 存在、provider route strategy 已恢复 `continue_primary` 时，可把 stale fake/offline 或旧 route hint 降为 `superseded_review`，并让 RuntimeReadinessGate 不再把这类历史噪声计入 review；扩大真实任务 batch 前仍必须检查 `gate-status` 的 `release_ready`、`runtime_readiness_gate` 和 active route review 项。
- `asteria version --json`、`asteria package-check --json`、`asteria status --json`、`asteria doctor --json`、`asteria gate-status --json` 输出机器可读 JSON；后续 TUI / GUI / 自动化验证门禁应复用这些控制面数据口径。
- Control surface JSON commands: `asteria version --json`, `asteria package-check --json`, `asteria status --json`, `asteria doctor --json`, `asteria gate-status --json`, `asteria gate --json`, `asteria validation --json`, `asteria validation-run --json`, `asteria weekly-report --json`, and `asteria roadmap-update --json` emit `control_surface` metadata. `version` / `package-check` use maintainer preflight fields, `gate-status` / `gate` use release validation fields, `validation` uses release validation fields, `validation-run` uses validation execution fields, `weekly-report` / `roadmap-update` use maintainer ops reporting fields, and ordinary users should continue to prefer `status`.
- `control_surface.stability` 当前为 `additive`：消费者可以依赖 `stable_fields` 中列出的字段继续存在，运行时可以在不破坏旧消费者的前提下追加新字段；删除、重命名或改变含义需要先形成 DecisionPoint 并更新 schema/documentation contract。
- `docs/en/examples/version_control_surface.json`、`docs/en/examples/package_check_control_surface.json`、`docs/en/examples/status_control_surface.json`、`docs/en/examples/doctor_control_surface.json`、`docs/en/examples/gate_status_control_surface.json`、`docs/en/examples/gate_control_surface.json`、`docs/en/examples/validation_control_surface.json` 和 `docs/en/examples/validation_run_control_surface.json` 是对应 `--json` 控制面的契约样例；新增稳定字段时必须同步 `control_surface.stable_fields`。
- `schemas/control_surface.schema.json` 定义 `control_surface` 元数据的最小 schema：`schema_version`、`command`、`audience`、`stability`、`stable_fields` 均为必填，且当前只允许 `stability=additive`。
- Current `control_surface.audience` values: `status` uses `user_workflow`; `version` / `package-check` / `doctor` use `maintainer_preflight`; `gate-status` / `gate` use `maintainer_release_validation`; `validation` also uses `maintainer_release_validation`; `validation-run` uses `maintainer_validation_execution`; `weekly-report` / `roadmap-update` use `maintainer_ops_reporting`.
- `asteria runs`、`asteria history` 和 `--run-id` 保留为兼容别名；新文档和新流程使用 `sessions` / `--session-id`。
- `run`、`execute`、`review`、`debug`、`decide`、`resume`、`compact` 等命令在未传 `session_id` 时优先使用 current session。
- `asteria verification` / `asteria verify-status` 显示最近一次统一 verify 的覆盖摘要，来源是 `.asteria/verification/latest.json`。
- `asteria promotions` / `asteria candidates` 查看并操作当前 session 的 candidate promotion queue；支持 `list`、`approve --promotion-id <id>`、`approve --all-pending`、`reject --promotion-id <id> --reason <text>`、`retry --promotion-id <id>` 和 `discard --promotion-id <id>`，并支持 `--json` 输出。
- promotion queue 落盘在 `.asteria/runs/<run-id>/candidate_promotions.jsonl`。`pending_manual_approval`、`blocked`、`promotion_failed` 会留在队列中供 `sessions --context` 和最终报告继续消费；`approve/retry` 会在 promote 前重新检查 merge gate、candidate workspace、promotable files 和 git worktree/source path 状态，失败时写入结构化 `failure`。
- `asteria plugins` 查看和诊断 `.asteria/plugins/*.plugin.json`。当前阶段支持 `list`、`doctor`、`enable --plugin-id <id>`、`disable --plugin-id <id>` 和 `--json` 输出；命令只操作 PluginManifest 与 hook policy 控制面，不加载或执行外部插件代码。
- `plugins doctor` 必须解释 `hooks.enabled`、`hooks.plugins_enabled`、允许 hook、脱敏 key、handler timeout 和每个 manifest 的状态。`plugins_enabled=false` 时，enabled manifest 仍会显示为不可执行，避免用户误以为插件已经生效。
- `asteria model-check --tier strong|medium|cheap --json` 可按模型层级检查 provider 配置和一次 JSON 健康调用。验证阶段推荐先检查 `strong=GLM coding route`、`medium=MiniMax`，再进入真实模型 smoke；当前成本优先阶段可先用 `strong=glm-4.7`，发布门槛复验再切到 `glm-5.1`。provider adapter 默认使用 OpenAI-style SSE 流式调用，并在 `model-check` 与 `model_calls.jsonl` 记录 first_chunk_ms、last_chunk_ms、chunk_count、idle_timeout_ms、deadline_ms 和 duration_ms；如果 provider 明确不支持 streaming，会自动降级为普通 HTTP 并记录 `streaming_fallback_non_streaming`。显式设置 `AGENT_MODEL_<TIER>_STREAMING=0` 或全局 `AGENT_MODEL_STREAMING=0` 时继续使用非流式调用并记录 duration。统一 timeout budget 同时覆盖流式和非流式：provider deadline 对两者生效，stream idle timeout 只在 streaming route 生效。
- `asteria real-model-gate` 是验证发布前置 gate：它串联 strong/medium `model-check`、最小真实模型 smoke，并检查 model_calls、worker_results、task_execution_evidence 和 cost_report 证据是否完整。
- `asteria real-model-acceptance --suite validation` 是 gate 之后、core/nightly 之前的验证候选场景集；summary 中的 `validation_ready` 必须为 true，且 `aggregate.route_evidence` 必须证明 strong/medium route 被实际使用。`validation_debug_repair` 会通过所选 `--python` 执行 `python -m pytest`，隔离 venv 验证 wheel 时需要先安装 pytest 或指定已有 pytest 的解释器。`scripts/real_model_*.py` 仍保留为兼容 wrapper，新流程优先使用安装包内的 `asteria real-model-*` 命令。
- `asteria acceptance-history` / `asteria acceptance-trend` 显示 `.asteria/acceptance/history.jsonl` 中的真实验收历史和趋势 delta。
- `asteria acceptance-history --fail-on-warning` 可把趋势告警转换为非零退出码，用于本地门禁。
- `asteria acceptance --fail-on-trend-warning` 可让验收命令本身在趋势回归时失败。
- `asteria acceptance --failed-only` 会读取最新 `acceptance_report.json`，只重跑失败或未闭环的场景。
- 真实验收默认把场景工作区放到 `.asteria/acceptance/workspaces/` 下，避免污染仓库根目录。
- `asteria acceptance-gate` / `asteria release-gate` 会读取最新 `acceptance_report.json` 并作为发布门槛；维护者发布前优先通过 `asteria gate --stage release --report <acceptance_report.json>` 统一触发 lint、typecheck、pytest 和 acceptance gate。验收失败未闭环、趋势告警、suite、场景数量、能力覆盖、分层覆盖或 Runtime OS evidence 不足都会返回非零退出码。Runtime OS gate 覆盖并发、worker、merge gate、runtime request resume、ContextPackage 切片、sandbox backend、Planner scope quality、capability feedback 和 debug/review evidence consumption。
- `asteria capability-report` 汇总最近 acceptance 趋势、能力覆盖、失败类型、平均修复轮次、模型/工具/context 成本、常见阻塞和推荐动作；工具成本应同时区分 raw `tool_calls` 与风险加权 `tool_budget_units`，context 成本应展示最大估算上下文 token 与窗口占比，避免把大量低风险读搜误判为失控。报告同时从 `model_calls.jsonl`、`workers.jsonl`、`worker_results.jsonl`、`validation_results.jsonl` 和 runtime request / merge gate evidence 生成 `.asteria/model/capability_profile.json`，按 provider、model、purpose、tier 记录成功率、token 成本、worker 成功率、验证通过率和失败类型，为后续 model routing 提供依据。
- 旧 acceptance 历史如果缺少 `capability` / `tier`，runtime 会根据已知场景名回填，避免能力画像退化为 `unknown`。
- `asteria weekly-report` 汇总最近长任务周期、acceptance、模型画像、风险和下一步动作，并写入 `.asteria/reports/weekly_report_<week>.json` 与 Markdown 报告；`--json` 输出包含 `control_surface` 的机器可读摘要。
- `asteria roadmap-update` / `asteria prd-update` 从 weekly report、acceptance 和模型画像生成项目级路线图，写入 `.asteria/product/project_roadmap.json` 与 `docs/zh/自动路线图.md`；`--json` 输出包含 `control_surface` 的机器可读摘要。
- 如果 `.asteria/model/capability_profile.json` 显示某个 provider/model/purpose route 成功率偏低，`asteria daily-plan --cycle-id <id>` 会优先生成 `model_route_review` 只读动作，提示先检查或切换模型路线，再继续扩大长任务执行预算。
- `asteria daily-plan` 生成的 action 会标注 `responsible_role`，例如 Product、Coder、Debugger、Evaluator；`daily-report` 和 execution evidence 会保留该字段，方便复盘长任务里是谁负责判断、执行、修复或验收。
- `asteria acceptance --promote-failures` 会根据失败 scenario 的 capability 生成定向 `repair_focus`。例如 `multi_file_change` 会强调包布局、入口文件和跨文件 import；`configuration_change` 会强调配置文件是输入输出和过滤逻辑的 source of truth，并只要求单场景复验。
- `asteria execute --parallel-disjoint-writes`、`asteria run --parallel-disjoint-writes` 和 `asteria resume --parallel-disjoint-writes` 会并发执行 `parallel_safety=readonly` 或 `parallel_safety=disjoint_writes` 且 `write_scope` 不冲突的 ready tasks。写任务仍在独立 candidate/worktree 中执行，验证通过后才 promote 回主工作区；冲突写任务留到后续轮次串行处理。
- Planner 会为任务写入基础多 worker 策略：`serial_worker`、`readonly_fanout`、`disjoint_write_workers` 或 `plan_then_serial`。运行后 `.asteria/runs/<run-id>/agent_run_graph.json` 会记录 child worker plan、预算、上下文、路由、协作角色、验证证据和汇总状态，供 `status`、`sessions --context` 和报告命令复用。
- `/execute` 为每个 worker 注入 ContextMount / ContextPackage。ContextPackage 必须按 `read_scope` 和挂载 refs 裁剪 root guidance、GoalSpec、TaskContract、文件片段、artifact、failure、decision、validation、runtime request、worker result 与 merge gate evidence，避免无差别加载全量历史；当前包内已显式区分 `scope_summary`、`read_scope_files`、`write_scope_files`、`evidence_scope` 和 `recent_failures`。
- `asteria daily-plan` / `asteria daily-run` / `asteria daily-report` 是早期兼容入口；产品语义已经扩展为长任务运行周期，不限定为自然日。
- `asteria daily-plan` / `asteria daily-run` / `asteria daily-report` 当前承载长任务周期入口，支持 `--cycle-id` 和 `--objective`，用于表达“一段可暂停、可恢复、可审计的长任务自动化运行”。`long-run-*` 仍作为兼容别名存在，但新文档优先使用 `daily-*` 当前命令面。
- `asteria long-run --execute` 会使用预算守卫控制 action 数、运行时长、模型调用、风险加权工具预算和修复次数；失败、超预算或需要人工决策时会硬停，并在报告里写入 `stop_reason`、风险、下一步建议和 `task_execution_evidence.jsonl` 证据路径。

### 3.2.1 `/run`

目的：

提供 MVP 的一键闭环入口，将规划、执行、修复、评审、压缩和最终报告串联起来。

调用方式：

- `asteria run "目标"` 或 `asteria /run "目标"`：创建新 session 并执行闭环。
- `asteria run` 或 `asteria /run`：继续当前 session。
- `asteria run --session-id <id>`：继续指定历史 session。

流程：

```text
init if needed
  -> plan
  -> execute ready tasks
  -> debug blocked tasks when possible
  -> review
  -> compact
  -> final_report.md
```

输入：

- `goal` 用户目标，可选；不传时继续当前 session。
- `session_id` 可选，指定要继续的历史 session；兼容旧参数 `run_id`。
- `root` 工作区根目录。
- `max_iterations` 可选，默认读取策略预算。
- `max_tasks_per_iteration` 可选，默认每轮执行 1 个任务。
- `input_root` 可重复，指定多工程目标的输入目录。
- `output_root` 指定用户可见产物输出目录。
- `artifact_root` 指定报告、导出和 runtime-managed artifact 目录。
- `worktree_policy` 指定后续候选工作区策略：`controlled_patch`、`worktree` 或 `isolated_copy`。

输出产物：

- `goal_spec.json`
- `task_plan.json`
- `task_plan_eval.json`
- `review_report.md`
- `final_report.md`
- 更新后的事件、工具、模型和成本日志。

决策交互：

- 当 `/review` 发现高影响 follow-up，例如输出形态、隐私、网络、预算或技术栈选择，会创建 `DecisionPoint`。
- 当 `/execute` 发现某个工具调用触碰策略边界，例如被禁止的 shell 控制符、破坏性命令、远程推送、部署或全局安装，会创建一次性执行审批决策。
- 执行 ready 任务前会刷新 `task_plan_eval.json`。如果计划质量失败，runtime 会先做一次确定性的自动计划修补，例如补 ready 入口、移除坏依赖、补可观察验收、补具体产物、补写入和验证工具；修补后仍失败才创建 `DecisionPoint` 并暂停。
- 新 goal 的 workspace/input/output/worktree 选择会进入 Plan 生成的 `WorkspaceEnvelope`，并继续进入最终报告和 final_report_summary。
- 产生待处理决策时，run 状态变为 `paused`，当前阶段变为 `DECISION`。
- `final_report.md` 会列出 `Pending Decisions`，用户用 `/decide` 解析后再执行 `/resume`。
- 一次性执行审批只对同一任务、同一工具、同一参数指纹生效，不修改全局策略。

失败处理：

- 任务验证失败时先通过备份清单回滚本次候选改动，并在 `experiments.jsonl` 记录为 `discard`。
- 回滚后任务进入 `/debug`；DebugAgent 基于失败证据和干净基线提出下一次最小修复。
- 修复后仍阻塞则停止执行循环并进入 `/review`，报告阻塞原因。
- 无 ready 任务且状态无进展时停止循环，避免空转。

### 3.3 `/brainstorm`

目的：

对宽泛、创意型或欠规格目标进行发散和收敛。

流程：

```text
generate candidates
  -> cluster
  -> score
  -> select recommendation
  -> create tasks or decision points
```

评分维度：

- 用户目标匹配度。
- 可行性。
- 实现成本。
- 使用价值。
- 风险。
- 新颖性。
- 验证难度。

当前实现：

- `asteria brainstorm "目标"` 会生成 `brainstorm_report.json` / `brainstorm_report.md`。
- 未传目标时，命令会默认使用 current session 的 GoalSpec。
- `--apply` 会把 `task_candidates` 追加到 `task_plan.json` / `.asteria/tasks/backlog.json`，并把 `decision_candidates` 写入 `decisions.jsonl`。
- `/brainstorm` 只创建规划产物和决策点，不直接修改业务代码。

### 3.4 `/research`

目的：

将外部资料、论文、成熟产品、开源项目或行业实践转化为可执行假设、设计简报、任务约束和决策候选。

质量要求：

- 观点必须带来源或明确标记为模型推断。
- 调研必须转化为任务、实验、约束或决策点。
- 不允许只输出泛泛摘要。

当前实现：

- `asteria research "问题"` 会创建或复用 run，收集资料并生成 `research_report.json` / `research_report.md`。
- 资料源采用可插拔 adapter：本地文档、显式 URL、Serper 搜索 API。
- 默认只启用本地文档检索；URL/搜索必须满足策略 `allow_network=true`。
- MCP、skills、专用论文库可以作为后续 source adapter 接入，而不是绑定在核心流程里。
- 报告必须包含来源、带来源的 claims、需求扩展、风险和决策候选。
- 成本账本累计 `research_calls` 和模型调用。
- 当前支持 `--type`：`general`、`product_research`、`architecture_research`、`implementation_research`、`competitive_research`、`paper_research`、`open_source_research`、`risk_research`、`design_pattern_research`。这些类型复用现有 source adapter 和 report 落盘机制，可新增 design brief / pattern candidates，而不是另起一套调研系统。
- `product_research` 和 `competitive_research` 用于吸收 Claude Code、Cursor、Codex、Copilot、OpenHands 等成熟产品的交互边界、checkpoint、session/resume、background agents、PR-style promotion 等设计思想；输出只能作为 Asteria 自身的设计约束和验证任务，不能直接复制专有实现。

### 3.5 `/compact`

目的：

压缩上下文，支持长任务续航和智能体交接。

必须保留：

- 目标。
- 完成定义。
- 用户决策。
- 活跃任务。
- 修改文件。
- 验证结果。
- 失败修复。
- 未解决风险。
- 下一步行动。

上下文使用：

- 运行时会通过 `ContextLoader` 汇总 `.asteria/memory/*.jsonl`、最近的 context snapshot 和 handoff package。
- `/plan` 会把该上下文传给 GoalSpecAgent，并在确定性任务 notes 中记录可审计摘要。
- `/execute` 和 `/debug` 会把同一类裁剪后的上下文传给 CoderAgent / DebugAgent。
- 上下文输入有数量限制，只传递近期 memory、活跃任务、最近失败、风险和推荐下一步，避免无界 prompt 膨胀。

### 3.5.1 `/execute`

目的：

消费当前 run 中可执行的 `ready` 任务，驱动 CoderAgent 生成工具调用计划并执行。

输入：

- `session_id` 可选，默认 current session；兼容旧参数 `run_id`。
- `max_tasks` 控制单次最多执行多少个任务。

输出产物：

- 更新后的 `task_plan.json`。
- 同步后的 `.asteria/tasks/backlog.json`。
- `events.jsonl`。
- `runtime_hooks.jsonl`。
- `tool_calls.jsonl`。
- `model_calls.jsonl`。
- `cost_report.json`。

状态推进：

```text
ready -> in_progress -> testing -> reviewing -> done
```

工具失败、验证失败或模型返回非法行动时进入 `blocked`，等待 `/debug`、修复循环或用户决策。验证失败的候选会先尝试 `restore_backup`，成功候选才会写入 `artifacts.jsonl`。

如果工具计划被策略拦截，`/execute` 不会先执行部分候选，而是创建 `DecisionPoint` 并暂停 run。用户选择 `approve_once` 后，`/resume` 会把原任务重新置为 `ready`，并只放行同一条命令；选择 `skip` 则保留阻塞状态，等待重新规划或人工调整。

约束：

- 只能使用任务 `allowed_tools` 与工具注册表同时允许的工具。
- 默认不做真实网络调研、不读取密钥、不部署。
- 每次执行必须累计成本报告，不能覆盖已有模型调用和 token 记录。
- worker/tool 的生命周期边界必须通过 `RuntimeHookManager` 记录到 `runtime_hooks.jsonl`，供后续插件、报告和排障消费。

### 3.6 `/decide`

目的：

创建用户决策点。

决策请求必须包含：

- 问题。
- 推荐选项。
- 2-4 个选择。
- 每个选择的取舍。
- 每个选择的结构化动作：`create_task`、`record_constraint`、`cancel_scope` 或 `require_replan`。
- 默认选择。
- 对预算、范围、风险、质量的影响。

当前实现：

- `asteria decide --question ... --options-json ...` 创建 pending 决策点。
- `asteria decide --list-pending` 列出待用户处理的决策。
- `asteria decide --decision-id ... --select-option-id ...` 解析为用户选择。
- `asteria decide --decision-id ... --use-default` 采用默认选项。
- 决策写入 `decisions.jsonl`，并记录 `decision_created` / `decision_resolved` 事件。
- 每次创建或解析决策都会累计 `user_decisions` 成本计数，避免频繁询问用户。

### 3.6.1 `/resume`

目的：

在用户处理完 `/decide` 决策后，恢复同一个 paused run，不重新规划、不重新调研。

当前实现：

- `asteria resume --session-id ...` 恢复指定 session；不传 `session-id` 时默认 current session。
- 如果仍有 pending 决策，命令会停止并提示待处理决策。
- 已解析但尚未应用的决策会记录 `decision_applied` 事件。
- 对需要执行的选项，生成后续任务并接回 `/run` 的 execute/review/compact/final report 闭环。
- `create_task` 和 `require_replan` 会生成后续任务。
- `require_replan` 生成 `PlannerAgent` 后续任务，并把当前 run 的 `task_plan.json` 作为期望产物。
- `record_constraint` 和 `cancel_scope` 不创建任务，但会写入 `.asteria/memory/decisions.jsonl`，供后续规划和交接读取。
- 所有已应用决策都会写入长期 memory，内容包含问题、选择、动作和应用效果。
- 旧决策没有 `action` 字段时，运行时会根据选项 id/label 做兼容推断。
- `final_report.md` 会列出 `Accepted Decisions`。

### 3.7 `/review`

目的：

评审代码、需求覆盖、UX、测试和风险。

评审维度：

- 正确性。
- 需求覆盖。
- 测试充分性。
- 安全风险。
- 体验问题。
- 范围膨胀。
- 可维护性。

当前实现：

- 读取 `goal_spec.json`、`task_plan.json`、`cost_report.json`。
- 汇总最近的事件、工具调用和模型调用。
- 生成确定性检查项，如任务完成率、阻塞任务数、验证通过率、成本状态。
- 调用 ReviewAgent 生成 `eval_report.json`。
- 同步生成面向人的 `review_report.md`。
- 根据 `overall.status` 更新 run 状态：`pass -> completed`，`partial -> running`，`fail -> blocked`。

### 3.8 `/accept`

目的：

接受当前已通过评审的结果，结清候选 promotion，并把 run 固化为可交接的完成状态。`accept` 是普通用户主线的收尾入口，不等同于用于测试套件的 `acceptance`，也不要求用户直接操作 promotion queue。

调用方式：

- `asteria accept`：接受 current session。
- `asteria accept --session-id <id>`：接受指定 session。
- `asteria accept --no-promote`：不自动批准 pending promotion；若仍有候选，会返回 blocker 和下一步。
- `asteria accept --skip-review`：复用最新 `eval_report.json`，不重新运行 review；主要用于测试或已知评审结果的受控流程。
- `asteria accept --json`：输出机器可读 `AcceptResult`。

流程：

```text
load current or specified run
  -> ensure review status is pass, or run review
  -> approve pending candidate promotions unless --no-promote
  -> block if review or promotion remains unresolved
  -> write final_report.md
  -> update run status and event log
```

状态变化：

- 成功时：`status=completed`，`current_phase=ACCEPTED`，写入 `ended_at` 和 `run_accepted` 事件。
- 阻塞时：`status=blocked`，`current_phase=ACCEPT`，写入 `accept_blocked` 事件，并在结果中列出 blockers 和 next actions。

输出产物：

- `final_report.md`：作为 durable handoff artifact。
- `events.jsonl`：记录 `run_accepted` 或 `accept_blocked`。
- `candidate_promotions.jsonl`：如果自动 promotion 成功，会记录 promoted files 和 decision。

安全与边界：

- `accept` 只处理当前 run 的候选 promotion，不发布、不部署、不推送远程。
- 若 review 不是 `pass`，或 promotion 仍 pending/blocked/failed，必须阻塞并提示 `review`、`debug`、`replan` 或 `promotions` 下一步。
- 是否默认自动批准 pending promotion 是产品策略点；当前实现提供 `--no-promote` 逃生口，后续若改变默认策略必须先形成 DecisionPoint。

### 3.9 `/debug`

目的：

分析失败并提出最小修复。

流程：

```text
collect evidence
  -> summarize failure
  -> generate hypotheses
  -> choose minimal fix
  -> rerun verification
```

当前实现：

- 读取 blocked 任务。
- 汇总最近的 `tool_calls.jsonl`、`model_calls.jsonl` 和 `events.jsonl` 作为失败证据。
- 调用 DebugAgent 生成结构化修复动作。
- 执行修复工具调用和验证工具调用。
- 成功时推进 `blocked -> ready -> in_progress -> testing -> reviewing -> done`。
- 修复验证失败时回滚该次修复候选，在 `experiments.jsonl` 记录为 `discard`，并保持 `blocked`。
- 累计 `repair_attempts`、模型调用、工具调用和 token 成本。

### 3.10 `/handoff`

目的：

为另一个智能体或未来运行创建续接包。

必须包含：

- 当前目标。
- 当前状态。
- 活跃任务。
- 已接受决策。
- 最近 diff。
- 验证状态。
- 风险。
- 推荐下一步。

当前实现：

- `asteria handoff --to ReviewerAgent` 会基于当前或指定 session 自动生成一个 `ContextSnapshot`。
- 命令会在 `.asteria/context/handoffs/` 下写入机器可读交接包。
- 交接包会引用 snapshot、活跃任务、最近产物、已知风险和推荐下一步命令。
- `--next-command` 可显式指定建议命令；未指定时会按 `debug -> execute -> review` 顺序推断。

## 4. 命令预算建议

```yaml
init:
  model_calls: 2
  tool_budget_units: 30
plan:
  model_calls: 4
  tool_budget_units: 20
brainstorm:
  model_calls: 4
  tool_budget_units: 20
research:
  model_calls: 6
  tool_budget_units: 40
compact:
  model_calls: 1
  tool_budget_units: 10
review:
  model_calls: 3
  tool_budget_units: 30
debug:
  model_calls: 4
  tool_budget_units: 30
handoff:
  model_calls: 1
  tool_budget_units: 10
```

这里的 `tool_budget_units` 不是原始工具次数。`tool_calls` 继续完整记录到 evidence；预算守卫按风险权重计算：读文件、搜索、列目录、diff 等低风险探索默认不消耗工具预算，验证和状态工具低消耗，写入、shell、MCP、Skill 和外部连接高消耗并继续走权限审批。
这些命令级数值是调度建议，不是全局硬上限。全局策略通过 `active_budget_profile` 选择：`validation` 用较紧阈值做发布验证，`balanced` 用于普通研发，默认 `autonomous_long_task` 放大阈值以支持长期自主迭代。稳定性主要由上下文压缩、权限边界、修复/replan 限制、provider 健康和重复低价值循环检测保证，`max_tool_calls_per_goal` 只作为风险加权 emergency brake。

超过预算时应：

1. 尝试压缩上下文。
2. 降级模型。
3. 减少候选数量。
4. 请求用户批准继续。

## 5. 任务拆解原则

好的任务拆解应该做到：

- 不太大，大到无法一次实现和验收。
- 不太小，小到调度成本高于实现价值。
- 每个任务都有明确产物。
- 每个任务都有可验证验收条件。
- 任务之间依赖清晰。
- 能支持多 agent 协作和后续自动评估。

建议单任务大小：

```text
预计实现时间：15-90 分钟
文件改动：1-5 个文件
验收条件：2-6 条
依赖数量：0-3 个
输出产物：1-4 个
```

## 6. 标准任务结构

```json
{
  "task_id": "task-0001",
  "title": "实现密码强度评分模块",
  "description": "根据长度、字符多样性和常见弱密码规则计算评分，并返回解释",
  "role": "CoderAgent",
  "priority": "high",
  "depends_on": [],
  "acceptance": [
    "输入密码后返回 0-100 分",
    "返回至少 2 条可解释原因",
    "包含常见弱密码检测",
    "包含单元测试"
  ],
  "expected_artifacts": [
    "src/scoring.ts",
    "tests/scoring.test.ts"
  ],
  "verification": [
    "npm test"
  ]
}
```

## 7. 任务类型

- Research Task：调研和证据收集。
- Product Task：需求扩展和产品判断。
- Architecture Task：技术方案和模块边界。
- Implementation Task：代码实现。
- UI/Experience Task：界面、报告或交互产物。
- Verification Task：测试和评估。
- Repair Task：失败修复。
- Documentation Task：README、报告、使用说明。

## 8. 拆解方法

### 8.1 能力链路拆解法

适合软件工具：

```text
输入
  -> 解析/导入
  -> 核心处理
  -> 存储/状态
  -> 输出/展示
  -> 验证
  -> 文档
```

### 8.2 风险优先拆解法

适合不确定性高的任务。

先拆：

- 技术可行性验证。
- 第三方依赖验证。
- 性能验证。
- 隐私和安全验证。
- UX 输出形态验证。

### 8.3 垂直切片拆解法

适合 MVP。

优先做一条完整闭环：

```text
最小输入
  -> 最小处理
  -> 最小输出
  -> 最小测试
  -> 最小文档
```

## 9. 任务质量评分

每个任务生成后应打分：

```text
clarity_score：描述是否清晰
testability_score：是否可验收
size_score：大小是否合适
dependency_score：依赖是否清楚
artifact_score：产物是否明确
risk_score：风险是否可控
```

当前实现会把评分写入任务对象的 `quality` 字段，并同步写入 `notes` 方便人工查看。
如果 requirement 过于模糊、没有验收条件或缺少明确产物，PlannerAgent 会先做一次确定性 refinement，
补足描述、验收条件和预期产物，再进入任务看板。

建议阈值：

```text
clarity_score >= 0.75
testability_score >= 0.75
size_score >= 0.70
artifact_score >= 0.75
```

低于阈值时，PlannerAgent 应重写任务。

## 10. 拆解反模式

坏任务：

```text
优化搜索。
界面好看。
实现完整知识库。
接入在线泄露密码 API。
```

好任务：

```text
实现 BM25 + 向量混合搜索，并用固定查询集评估命中率。
在 1366x768 下核心按钮不重叠，搜索结果列表可滚动，主要流程可完成。
实现 Markdown 导入器。
创建关于泄露检测方案的 DecisionPoint，比较不接入、本地导入和在线 API。
```

## 11. PlannerAgent 输出要求

PlannerAgent 输出任务计划时必须包含：

- 任务列表。
- 依赖关系。
- 阶段划分。
- 每个任务验收条件。
- 每个任务预期产物。
- 每个任务建议角色。
- 重大决策点。
- 风险任务标记。
- MVP 任务和后续任务区分。

## 12. 任务拆解验收

一个任务计划合格的标准：

- 每个 must 需求至少被一个任务覆盖。
- 每个任务都有验收条件。
- 每个任务都有预期产物。
- 高风险选择有 DecisionPoint。
- 第一阶段任务能形成可运行闭环。
- 暂缓需求进入后续阶段，而不是消失。
