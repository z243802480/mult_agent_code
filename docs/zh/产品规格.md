# 多智能体自主开发系统 - 产品规格

## 1. 产品愿景

构建一套本地优先的自主研发工作台。用户只需要输入一个较小的系统目标，系统就能通过受控的多智能体循环，持续把目标转化为可使用的软件、研究产物、报告或交互式系统。

系统不是智能体聊天室，而是一套 Asteria runtime。它要把模型调用转化为可验证的工作产物：计划、任务、代码补丁、实验、UI 输出、报告、测试、评审和可复用记忆。

## 2. 核心目标

给定用户的一段简短目标，平台应该能够：

1. 将目标澄清为结构化规格。
2. 根据目标、领域和使用场景推断缺失但合理的需求。
3. 当用户目标描述不足且涉及产品体验、架构方向或长期路线时，按策略参考公开优秀产品、开源系统、常见工作流和标准功能集；低风险窄范围修复不强制联网调研。
4. 判断是否需要调研、实现、UI、报告、实验，或者它们的组合。
5. 让用户选择 workspace、输入目录、输出目录、候选工作区策略和权限模式。
6. 将目标拆解为可追踪、可验收的任务。
7. 将任务分配给专门角色的智能体。
8. 让智能体在隔离或受控工作区中工作。
9. 产出代码、文档、UI、报告和实验结果。
10. 通过测试、评估、截图和验收条件验证产物。
11. 自动修复失败。
12. 保留成功变更，回滚失败尝试。
13. 将有价值的知识沉淀为长期记忆。

## 3. 产品定位

本项目是一套自进化研发与软件构建工作台。

更准确地说，它不是围绕某个模型供应商或某个订阅计划构建的代码调用器，而是一套自主可控的产品生产系统。模型供应商只是可替换的算力与推理资源，运行时、任务体系、证据体系、记忆体系、验收门槛和产品决策能力才是系统核心资产。

本项目追求的是个人或小团队在 AI 时代建立自己的“产品公司内核”：

- 能持续把产品想法转化为规格、任务、代码、测试、报告和可发布增量。
- 能在多个模型之间选择、路由、交叉评审和沉淀能力画像。
- 能保留本地状态、决策、经验、失败证据和项目记忆，不把核心工作流绑定在外部 SaaS 黑盒中。
- 能长期积累自己的产品方法论、代码资产和研发节奏。
- 能在成本、风险和质量可控的前提下，逐步自动化日常研发工作。
- 能作为通用目标完成产品处理多工程、多目录、多输出形态的任务，而不是只服务当前终端目录里的单一代码库。

它吸收以下方向的思想：

- Agentic coding 系统，例如 Claude Code、OpenCode、OpenHands 和 SWE-agent。
- 自主实验循环，例如 autoresearch；并在此基础上扩展产品研发、架构调研、实现选型、开源借鉴、风险分析和设计模式沉淀。
- 自动化科研系统。
- 本地知识库系统中的检索、记忆和结构化项目上下文。

系统可以学习公开架构思想，但不能复用泄露或专有源码。

系统与公开 code agent 的关系：

- 可以学习其交互体验、工具边界、补丁验证、上下文管理、权限提示词、工作区选择和多工具协同思想。
- 不以复刻某个现有工具为目标。
- 不把“能聊天写代码”作为核心卖点。
- 核心差异是本地优先、过程可审计、多智能体协作、多模型路由、长期记忆、workspace/输出位置可控、产品化验收和可持续自动运行。

### 3.1 设计情报吸收循环

Asteria 的长任务价值不只是“执行更久”，还必须能吸收成熟产品和工程实践。系统应在合适场景下使用 ResearchAgent 或后续专门 research profile，形成结构化设计简报，而不是只输出资料摘要。

Research 不只包括论文路线，也包括：

- `product_research`：成熟产品交互、用户工作流和状态表达。
- `architecture_research`：runtime、sandbox、多智能体编排、恢复机制。
- `implementation_research`：库、API、开源实现和集成方案。
- `competitive_research`：Claude Code、Cursor、Codex、Copilot、OpenHands 等系统的能力边界比较。
- `open_source_research`：开源项目结构和可复用模式。
- `risk_research`：权限、安全、成本、隐私、发布风险。
- `design_pattern_research`：沉淀可复用设计模式。

这些研究结果应转成 design brief、pattern candidates、DecisionPoint、任务约束、验证策略和项目 memory。详见 [设计情报吸收循环.md](./设计情报吸收循环.md)。

## 4. 自迭代与自主需求扩展

系统不能表现得像“一步指令执行器”。它应该把用户的一句简短目标视为完整产品、研究或工程任务的种子。

当用户给出较笼统目标时，系统应该自主完成：

1. 深入理解目标领域，识别该类工具或系统通常应具备的能力。
2. 按需调研或审阅公开优秀产品、开源系统、工作流、边界场景、用户期待和质量标准。
3. 将初始目标扩展为合理产品需求集。
4. 区分必需功能、应该具备功能和可选功能。
5. 构建第一个可用版本。
6. 评估结果只是“能跑”，还是确实“有用、好用”。
7. 针对缺失能力、糟糕体验、薄弱测试或不完整文档创建后续任务。
8. 持续迭代，直到系统达到可用且相对好用的基线，或触及预算和安全边界。

示例：

如果用户说“做一个密码测试工具”，系统不应该只做一个输入框和评分。合格的 ProductAgent 和 ResearchAgent 应该在策略允许时参考公开优秀产品、开源实现和安全实践，发现常见工具可能包含密码强度评分、熵估算、常见弱密码检测、泄露列表检查方案、哈希示例、编码和解码辅助、随机密码生成、密码短语生成、策略检查、本地隐私保证和清晰安全提示。系统随后应根据用户场景判断哪些功能合适，实现一个连贯的功能子集，并评估最终工具是否真的可用。

## 5. 主要使用场景

### 5.1 构建小型软件工具

示例：

```text
构建一个本地 Markdown 知识库系统，支持语义搜索和问答。
```

期望输出：

- 可运行的本地应用。
- 导入和索引流程。
- 搜索和问答界面。
- 测试。
- README。
- 最终实现报告。

### 5.2 自主扩展模糊产品目标

示例：

```text
做一个密码测试工具。
```

期望输出：

- 对常见密码、安全、编码类工具进行产品调研。
- 扩展出必需功能和可选功能需求。
- 实现本地优先且隐私安全的工具。
- 在合适时提供强度评分、策略检查、生成辅助，以及部分编码或哈希工具。
- 清晰说明工具能证明什么、不能证明什么。
- 在最终报告前进行可用性评审和后续迭代。

### 5.3 调研并复现想法

示例：

```text
调研本地知识库的混合检索方法，并实现最合适的方案。
```

期望输出：

- 文献和开源项目调研。
- 结构化观点与证据。
- 实现计划。
- 实验循环。
- 基准结果。
- 保留或丢弃的补丁。

### 5.4 改进已有代码库

示例：

```text
让这个项目更容易使用，并修复明显的问题。
```

期望输出：

- 仓库扫描。
- 改进计划。
- 补丁。
- 测试。
- 评审总结。

### 5.5 Alpha dogfooding 与后台运维复盘

Asteria 进入 alpha 后，系统应支持用户把它安装到真实项目中试用。用户主流程仍然是提出目标、查看计划、确认关键决策、得到产物和报告；后台运维侧保留脱敏使用信号和诊断证据，用于改进 Asteria 本体。

典型流程：

```text
发布 Asteria alpha 包
  -> 用户在其他项目中用 Asteria 完成真实小任务
  -> Asteria 保留脱敏运行证据和过程产物索引
  -> 维护者在诊断/Inspector 视图中复盘证据指纹
  -> Codex 或维护者分析脱敏诊断包
  -> 形成 Asteria 本体的改进任务、验收场景和发布风险清单
```

期望能力：

- 在每个项目的 `.asteria/` 中保留可审计运行证据：goal、task graph、worker invocation/result、candidate workspace、promotion queue、validation result、model call 摘要、cost report、failure attribution、user decision 和 final report。
- 提供只读、脱敏的诊断导出能力，默认排除 `.env`、`secrets/`、私钥、证书、未授权源码全文和 provider API key。
- 提供 maintainer/Inspector 式证据视图，用于查看运行时间线、任务状态、候选产物、合并决策、失败类型、成本、模型路由、review/repair 过程和产物采纳信号。它不是 Studio 首页，也不代表优先建设 dashboard。
- 诊断视图不能只展示“系统自认为成功”；它必须帮助维护者识别哪些是实际使用阻塞，哪些可能是日志、证据或模型报告的误导。
- 诊断分析应能生成产品改进建议：新增 acceptance 场景、调整 command surface、修复 timeout/deadline、改进 candidate promotion、修正报告口径或优化模型路由。
- 该能力属于后台运维期能力，但必须在 alpha 阶段预埋数据结构、脱敏策略和诊断入口，避免真实使用数据散落在不可复盘的日志里。

## 6. 用户角色

用户、运行时 actor、agent role、worker invocation 和后续 plugin identity 的工程化边界见 [工程化体系.md](./工程化体系.md)。产品层面不把 Asteria 设计成多租户 chatroom；当前默认是本地单用户拥有项目，运行时和插件都必须为该 owner 生成可审计证据。

### 6.1 人类所有者

提供目标、设置预算、审查关键决策，并接收最终产物。

### 6.2 智能体运行时

受控执行环境，负责管理上下文、工具、工作区、权限、记忆、日志、成本和评估。

### 6.3 专门智能体

长期角色集与 **当前实现状态**（详见 [研发总计划.md](./研发总计划.md) §3）：

| 角色 | 状态 | 说明 |
| --- | --- | --- |
| GoalSpecAgent | Implemented | 目标澄清 |
| PlannerAgent | Implemented | 任务分解（含 RequirementPlanner） |
| CoderAgent | Implemented | 执行 + agent loop |
| ReviewerAgent | Implemented | tiered review |
| DebugAgent / AutoCorrectionAgent | Implemented | repair |
| ResearchAgent | Implemented | 调研 brief |
| ArchitectAgent | Deferred | Phase 4+ / North Star |
| ProductAgent | Deferred | GoalSpec + Research 覆盖 MVP |
| UIExperienceAgent | Deferred | 非代码 artifact 先用 Coder+prompt |
| TesterAgent | Partial | verification 命令，非独立 agent 类 |
| MemoryAgent | Deferred | Phase 6+ |
| ReleaseAgent | Deferred | accept/report 覆盖 MVP |

多智能体复杂任务 MVP 阶段通过 **subagent 委托** 表达，不假装 12 个独立进程均已实现。

## 7. 功能需求摘要

系统必须支持：

- 目标输入和 GoalSpec 生成。
- 规划和任务看板。
- 项目初始化和根指导文件。
- 命令与工作流系统。
- 上下文管理和 `/compact`。
- 人类决策交互和可配置决策颗粒度。
- 工具系统和权限控制。
- 结构化日志、诊断导出、权限策略和配置管理。
- 受控 hooks、skills、plugins、MCP 扩展体系。
- 工作区隔离或受控写入。
- 调研自动化。
- 自动实验 keep/discard 循环。
- 实现、验证、自动纠错、评审和最终报告。
- 记忆存储和检索。
- Alpha dogfooding 闭环：打包试用、诊断导出、运行证据分析、运营可视化和改进任务生成。

## 8. 非功能需求摘要

系统必须满足：

- 本地优先。
- 模型无关，支持 OpenAI-compatible provider。
- 可观测，所有运行可审计。
- 成本可控。
- 可恢复，失败可回滚或阻塞。
- 可扩展，可增加 agent、tool、command、eval、model provider。
- 可治理，扩展点必须有权限声明、日志、schema、禁用/回滚和诊断入口。
- 可复盘，运行证据、脱敏使用信号和产品改进任务之间必须有可追踪链路。使用信号是后台运维辅助能力，不应打断用户主流程，也不应让用户显性感到产品在“收集反馈”。

## 9. 成功标准

MVP 成功标准：

1. 接收自然语言目标。
2. 生成结构化目标规格和任务计划。
3. 至少能将简单欠规格目标扩展为合理验收条件。
4. 至少使用一个编码智能体编辑文件。
5. 运行验证命令。
6. 检测失败并尝试自动修复。
7. 记录每次尝试。
8. 保留成功补丁并丢弃失败补丁。
9. 生成最终报告。

完整系统成功标准：

1. 多个智能体能在隔离工作区并发运行。
2. 调研结果能转化为实现任务。
3. 能自主将模糊目标扩展为连贯产品需求和实现计划。
4. 能构建合适体验产物。
5. 跨项目维护长期记忆。
6. 不只评估最终结果，也评估执行轨迹。
7. 持续自迭代，直到产物可用、连贯且相对好用。
8. 能按日自动运行受控研发循环，输出日报、失败证据、推荐动作和次日计划。
9. 能根据历史运行数据调整模型路由、任务拆分、验收策略和预算策略。
10. 能通过 alpha dogfooding 留下真实项目运行证据和脱敏使用信号，并用后台诊断分析反向改进 Asteria 本体。

## 10. 非目标

早期版本不应尝试：

- 取代完整工程团队。
- 在没有策略控制的情况下运行无限制 shell。
- 在运行时稳定前构建庞大无代码平台。
- 依赖单一专有模型提供商。
- 在核心循环跑通前优先打磨漂亮 dashboard。
- 让大量智能体在没有任务、产物和评估约束下自由聊天。
- 在产物达到约定可用基线后继续无限追求完美。
