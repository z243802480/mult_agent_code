# 多智能体自主开发系统 - 交付计划

## 1. 文档目的

本文档保留交付路线、历史阶段和任务清单。

当前阶段、已完成基线和下一轮研发优先级以 [当前状态与路线.md](./当前状态与路线.md) 为准；本文档中的早期 MVP 阶段用于追溯，不应覆盖当前 Runtime OS 主线。

原则：

- 可以分阶段实现。
- 不能因为 MVP 收窄就删除有价值需求。
- 暂缓需求必须进入路线图、风险处理或后续任务池。
- 高风险能力必须在设计层给出控制机制。
- 成本控制是系统能力的一部分。

## 1.1 当前交付主线

当前交付主线是：

```text
编排式 Agent Runtime OS
```

产品能力目标是：

```text
长任务自主开发 Runtime
```

近期交付判断：

- 已完成后台工程闭环和长任务控制面的基础入口。
- 已完成 Runtime OS release gate 的第一版验收覆盖。
- 当前不优先做 dashboard。
- 当前优先增强 TaskGraph、WorkerInvocation、RuntimeProfile、ContextMount、MergeGate 和 execution evidence 的端到端闭环。
- 每次新增核心能力都必须进入 acceptance/gate 或 integration test，避免只停留在命令层实现。

下一轮开发优先级：

1. Runtime OS 发布门槛继续硬化，让 gate、capability report、weekly report 复用同一套 Runtime OS evaluator。
2. 收敛 Coordinator 到 WorkerInvocation 的边界，让执行、debug、review、resume 都优先消费统一 execution evidence。
3. 升级候选工作区策略，有 git 时优先走 worktree/candidate branch，无 git 时 fallback 到复制候选目录。
4. 继续产品化 CLI/Markdown 报告，dashboard 仍排在 CLI report 和 runtime evidence 稳定之后。

## 2. MVP 定位

本节及后续 MVP 阶段是历史路线图和范围约束，用于理解项目来源。当前开发决策应先参考第 1.1 节和 [当前状态与路线.md](./当前状态与路线.md)。

MVP 的目标是验证最关键的 agent harness 闭环：

```text
初始化项目
  -> 接收目标
  -> 生成目标规格
  -> 扩展基本需求
  -> 拆解任务
  -> 执行实现
  -> 运行验证
  -> 自动修复
  -> 保留或丢弃
  -> 压缩上下文
  -> 输出最终报告
```

### Phase 6：生产控制平面和长任务自动化

目标：

- 让系统从“手动触发的后台工程”进入“长任务可受控运行的产品生产系统”。
- 支持长任务周期计划、执行、验收、报告和下一周期推荐动作。
- “每日”只是默认时间盒，不是架构边界；运行周期可以是一小时、一天、多天或一个明确的产品里程碑。
- 支持按项目、按任务、按模型、按预算的运行策略。
- 避免长时间盲跑，默认只执行少量高价值任务和定向验收。

第一批产物：

- `/daily-plan`：根据当前目标、任务看板、失败证据和预算，选择今日任务。
- `/daily-run`：执行今日计划，严格限制模型调用、工具调用、修复次数和运行时长。
- `/daily-report`：输出完成项、阻塞项、失败证据、成本、风险和次日建议。
- `/long-run-plan` / `/long-run` / `/long-run-report`：表达同一套能力的长任务入口，支持 `--cycle-id` 和 `--objective`，避免把运行周期写死为自然日。
- `/acceptance --failed-only`：只重跑最近失败场景。
- `.agent/daily/<date>/`：保存每日计划、执行证据、报告和状态。
- 模型能力画像：记录不同模型在 planning、coding、debugging、review 等用途上的成功率、成本和常见失败类型。

默认每日自动化策略：

```yaml
max_daily_model_calls: 20
max_daily_tool_calls: 60
max_daily_runtime_minutes: 60
max_daily_repair_attempts: 2
default_acceptance_mode: failed_only
full_core_acceptance: manual_or_release_gate
nightly_acceptance: scheduled_only
pause_on_pending_decision: true
pause_on_repeated_model_format_error: true
```

验收：

- 能在无人值守模式下跑一个短周期，不修改受保护路径。
- 运行结束后必须生成日报。
- 失败时必须保留 evidence，而不是继续无限修复。
- 用户第二天能根据日报继续或调整方向。

### Phase 7：个人公司产品生产底座

目标：

- 支持多个产品项目长期并行推进。
- 支持跨项目记忆和方法论沉淀。
- 支持产品 brief、PRD、研发计划、发布记录和运营复盘。
- 支持可替换模型资源池，避免绑定单一模型供应商。
- 支持按周/月生成生产能力报告。

这一阶段才考虑更完整的可视化界面。Web dashboard 的目标不是展示炫酷图表，而是让用户能快速看懂：今天系统做了什么、为什么卡住、下一步怎么推进、风险和成本是否可接受。

### Phase 8：编排式 Agent Runtime OS

目标：

- 把系统从“长任务 CLI 控制平面”升级为“可编排、可隔离、可恢复、可审计的 Agent Runtime OS”。
- 用 `TaskGraph` 取代线性任务假设，明确串行、只读并发和 disjoint writes 并发边界。
- 每个执行单元都生成 `WorkerInvocation` 和 `WorkerResult`，并沉淀 runtime profile、tool permission profile、context mount、validation refs 和 failure evidence。
- 所有候选修改先进入隔离 workspace，再由 `MergeGate` 根据 write scope、verification 和 contract check 决定是否 promotion。
- `/compact`、`/handoff`、`/sessions --context`、`/resume` 必须能恢复 worker runtime state，而不是只恢复聊天式摘要。

当前 P0：

1. [x] 本地全量验证基线。
   - `ruff check .`
   - `mypy src`
   - 全量 `pytest`
   - 离线 acceptance 或 CLI smoke

2. [x] 路线图更新到新主线。
   - `文档导航.md` 不再把“每日自动化”描述为当前唯一主线。
   - 当前主线明确为 `WorkerInvocation`、`TaskGraph`、`RuntimeProfile`、`MergeGate`、`ContextMount`。

当前 P1：

1. [x] Worker/merge gate 端到端验收。
   - `/execute` 写入 `workers.jsonl` 和 `worker_results.jsonl`。
   - worker 失败进入 `task_execution_evidence.jsonl`、`task_failures.jsonl` 和 `WorkerResult.failure_evidence_refs`。
   - `MergeGate` 阻止越权或验证失败的 candidate promotion。
   - `/compact` 与 `/handoff` 携带 worker summary，`/resume` 在相同 run state 上继续受控执行。

2. [x] Runtime OS 级发布门槛。
   - 为 core acceptance 增加编排式场景：并发只读、disjoint writes、失败 worker、runtime request 后 resume。
   - `acceptance-gate` 增加 worker evidence 与 merge gate 覆盖检查。
   - gate 会检查 `workers.jsonl`、`worker_results.jsonl`、`runtime_profiles.jsonl`、`context_mounts.jsonl`、`validation_results.jsonl`、failure evidence、candidate isolation、merge gate block 和 resume recovery。

当前 P2：

1. [ ] Dashboard 原型评估。
   - 不早于 CLI report、weekly report、roadmap update 和 Runtime OS 验收稳定之后。

## 4.1 下一阶段开发计划：从后台工程到按天运行

当前项目已经具备可运行的后台闭环，但真实 `core` 验收暴露出两个关键问题：

- 完整验收耗时较长，不适合每次修复都全量运行。
- 复杂任务失败后，系统还会消耗较多模型调用，缺少更硬的停止和定向修复策略。

因此下一阶段不应继续堆命令数量，而应优先完成“可持续运行控制”。

### 近期 P0（已完成）

1. [x] 验收成本控制。
   - 新增 `--failed-only`。
   - 支持只跑最近失败 scenario。
   - 完整 core/nightly 只作为发布门槛或计划任务。
   - 单 scenario 支持模型调用、修复轮次和运行时长上限。

2. [x] 验收工作区隔离。
   - 默认将真实验收工作区放入 `.agent/acceptance/workspaces/<run-id>/`。
   - 不再污染仓库根目录。
   - 验收结束后保留摘要、transcript、final report 和失败证据。

3. [x] 失败后硬停策略。
   - 连续非 JSON 响应、pending decision、重复 contract violation、超预算时立即暂停。
   - 输出 repair recommendation，而不是继续自动修复。

4. [x] 长任务自动化 MVP。
   - 实现 `/daily-plan`、`/daily-run`、`/daily-report` 的最小闭环。
   - 先由用户或系统计划任务触发，不急于做常驻 daemon。
   - `daily-run` 默认只生成计划和日报；需要无人值守执行时显式传 `--execute`，防止早期阶段误触发长时间模型调用。
   - `daily-run --execute` 必须在每个 action 前后检查预算，失败或超预算时硬停，并把结果写入日报和 `task_execution_evidence.jsonl`。

### 近期 P1（已完成）

1. [x] 多模型能力画像。
   - 记录 provider、model、purpose、成功率、成本、失败类型。
   - 为 model routing 提供数据，而不是靠固定偏好。
   - `capability-report` 必须持久化 `.agent/model/capability_profile.json`，让长任务运行周期能够复用历史模型表现。
   - 当画像显示某个 route 表现弱时，`long-run-plan` 必须先生成只读的 model route review 动作，避免继续扩大长任务执行预算。

2. [x] 多智能体职责固化。
   - Product/Planner 负责产品判断和验收定义。
   - Coder 负责候选实现。
   - Debugger 负责基于 evidence 的修复。
   - Reviewer/Evaluator 负责交叉评审和发布门槛。
   - `long-run-plan` 的每个 action 必须标注 `responsible_role`，让长任务报告和 evidence 能追踪责任边界。

3. [x] 定向修复当前失败能力。
   - `multi_file_change`
   - `configuration_change`
   - 只跑单场景短验证，不再盲跑完整 core。
   - acceptance failure promotion 必须根据 capability 写入 `repair_focus`、目标文件、定向验收和单场景复验命令。

### 近期 P2（进行中）

1. [x] 每周生产能力报告。
   - `weekly-report` / `production-report` 聚合 long-run 周期、acceptance、模型画像、风险和下一步动作。
   - 报告持久化到 `.agent/reports/weekly_report_<week>.json` 和 Markdown，作为个人公司生产复盘入口。
2. [x] 项目级 Roadmap/PRD 文档自动更新。
   - `roadmap-update` / `prd-update` 从 weekly report、acceptance 和模型画像生成 `.agent/product/project_roadmap.json` 与 `docs/zh/自动路线图.md`。
3. [ ] Dashboard 原型评估，但不早于 daily report 稳定之后。

## 8. 需求保留策略

每个需求都应处于以下状态之一：

- `mvp`
- `v1`
- `v2`
- `v3`
- `research`
- `blocked`

不能使用“删除”作为默认处理方式。

如果需求风险过高，应转化为：

- 权限控制。
- 预算限制。
- 人类决策点。
- 沙箱隔离。
- 验证门禁。
- 灰度启用。
