# 命令暴露面收敛计划

更新时间：2026-05-23

## 1. 目标

Asteria 当前已经具备很多真实能力：规划、执行、调试、审查、验收、灰度、报告、插件治理、模型路由和 Runtime OS evidence。但这些能力仍然像“工具箱里的一堆工具”，用户需要记住太多入口，agent 也容易把内部命令当成产品流程。

命令暴露面收敛的目标不是删能力，而是把能力串成少数稳定工作流：

- 普通用户只需要理解“开始任务、看状态、继续、审查、接受结果”。
- 维护者只需要理解“诊断、门禁、灰度、证据导出”。
- 内部命令继续存在，但默认隐藏在工作流背后，作为 runtime 编排步骤和专家排障入口。

## 2. 借鉴 Claude Code 的设计哲学

本项目不复制 Claude Code 的品牌、文案或 provider 绑定，但要吸收它经受市场验证的产品化方法：

- **少入口，多模式**：用户不应面对几十个并列命令；入口表达用户意图，模式和 flag 表达阶段差异。
- **工作流优先于工具清单**：读代码、改文件、跑命令、派子 agent、压缩上下文、审查结果都属于一次 agent loop，而不是用户手动拼接的流程。
- **权限和风险在模型外执行**：模型知道能力边界，但最终由 runtime policy、sandbox、budget、protected path、schema 和 gate 执行约束。
- **提示词、能力和证据是同一条链**：PromptEnvelope 告诉模型能做什么，ToolObservation 记录做了什么，gate/report 验证这些证据是否足够。
- **渐进暴露**：默认帮助只展示主入口；高级命令可以保留，但放在“排障/内部/CI”层。
- **失败要变成下一步动作**：失败不是一屏 stdout，而是 diagnose、repair、replan、ask、stop 或 gate block 的结构化选择。

## 3. 产品控制面模型

命令应按“用户旅程”组织，而不是按内部模块组织。

### 普通用户主线

这条线是默认 README、quickstart、help 和 Studio 首页应该展示的路径：

```text
init -> run -> status -> resume -> review -> accept
```

- `init`：初始化 workspace，发现项目规则、命令、protected paths 和 runtime 状态目录。
- `run`：输入目标，启动或继续一个可审计 agent loop。
- `status`：查看当前 session、进度、阻塞、候选变更、预算和下一步。
- `resume`：处理 DecisionPoint、预算暂停、失败修复或上下文恢复。
- `review`：查看当前结果、风险、验证证据和候选差异。
- `accept`：后续产品化入口，语义应收敛为“接受当前已验证候选或完成状态”，不能和 `acceptance` 或 `promotions approve` 混淆。

### 维护者主线

这条线面向 alpha 维护、灰度和 release：

```text
doctor -> gate -> gray -> evidence-bundle
```

- `doctor`：本地环境、模型路由、policy、sandbox、schema、plugin/hook 状态诊断。
- `gate`：统一门禁入口。默认只读；`--stage release` 触发发布前重检查。
- `gray`：真实 provider 放量前的受控中间层，先解释 readiness，再生成或执行小真实任务。
- `evidence-bundle`：导出脱敏诊断包，用于 dogfooding、排障和产品改进闭环。

### 内部能力层

这些能力继续存在，但不应成为普通用户完成任务的心智模型：

- 规划/恢复：`plan`、`execute`、`debug`、`replan`、`compact`、`handoff`
- 验收/报告：`acceptance`、`acceptance-gate`、`capability-report`、`weekly-report`
- 模型/灰度：`model-check`、`real-model-smoke`、`real-model-gate`、`real-model-acceptance`、`gray-run`
- 候选/治理：`promotions`、`plugins`、`verification`、`gate-status`
- 研发辅助：`research`、`brainstorm`、`daily-*`、`long-run-*`、`roadmap-update`

内部能力的原则：可以被 CLI 直接调用，但默认文档、主 help 和 Studio 主屏不把它们铺开给用户。

## 4. 入口收敛矩阵

| 用户意图 | 推荐入口 | 背后编排能力 | 暴露原则 |
| --- | --- | --- | --- |
| 第一次接入项目 | `init` | project guidance、commands、policy、schema init | 主入口 |
| 开始/继续一个目标 | `run` / `resume` | plan、execute、debug、review、compact、handoff | 主入口 |
| 看当前情况 | `status` | sessions、task graph、worker evidence、promotion queue、cost | 主入口 |
| 审查结果 | `review` | validation、diff、risk、ToolObservation、MergeGate | 主入口 |
| 接受结果 | `accept` | promotion approve、completion contract、final report | 先冻结语义再实现 |
| 环境诊断 | `doctor` | package、routes、sandbox、plugins、schema | 维护入口 |
| 发布前检查 | `gate --stage release` | ruff、mypy、pytest、acceptance-gate、Runtime OS gate | 维护入口 |
| 灰度放量 | `gray` | gate-status、real-model gate、gray acceptance、gray-run | 维护入口 |
| 导出诊断 | `evidence-bundle` | reports、events、model calls、worker/result evidence | 维护入口 |
| CI/专家排障 | 内部命令 | acceptance、capability report、model-check、promotions 等 | 高级帮助/CI 文档 |

## 5. Gate/Gray 的阶段化设计

`gate` 不再扩张成多个并列命令，而是成为统一门禁：

- `gate` / `gate --stage read-only`：只读聚合 `version -> package-check -> doctor -> gate-status`。
- `gate --stage release --report <acceptance_report.json>`：执行发布前重检查，串联 `ruff check .`、`mypy src`、普通 pytest（排除 `real_provider`）和 `acceptance-gate`。
- 后续可以增加 `gate --stage route`、`gate --stage evidence` 等阶段，但必须证明它们是同一门禁工作流的一部分，而不是新命令伪装成 flag。

`gray` 是放量前的受控入口：

- 默认先解释为什么 ready、conditional 或 blocked。
- dry-run 生成小真实任务计划，不直接扩大执行面。
- 正式执行前必须消费 gate 状态、route guidance、预算、provider capability、promotion risk 和 release evidence。

## 6. Help 和文档展示规则

默认帮助只展示两组：

```text
Start: init, run, status, resume, review
Maintain: doctor, gate, gray, evidence-bundle
```

高级帮助再展示：

```text
Advanced: plan, execute, debug, replan, compact, handoff, promotions, plugins
CI/Reports: acceptance, acceptance-gate, capability-report, weekly-report
Models: model-check, real-model-smoke, real-model-gate, real-model-acceptance
```

文档也按这个规则拆：

- README / quickstart：只讲主线和维护者最小闭环。
- 运行命令：讲完整命令，但先按工作流分组，再列内部命令。
- CI / release runbook：可以直接讲 `acceptance-gate`、`capability-report` 等内部入口。
- Studio：主屏展示任务驾驶舱和 readiness，不做“命令大全”。

## 7. 迁移路线

### P0：冻结主入口语义

- `run` 成为默认 agent loop，内部消费 plan/execute/debug/review，而不是让用户手动拼。
- `status` 成为用户可见进度和阻塞的唯一主入口。
- `gate` 已收敛 release 检查，不再新增独立 `release` 命令。
- `gray` 继续收敛真实 provider 放量路径，避免 `real-model-*` 泄漏到默认引导。
- `accept` 先写清语义和 safety，再实现命令。

### P0.5：重构帮助与报告

- CLI help 增加默认/advanced 分组，避免一屏铺满内部命令。
- `gate` 输出从“命令结果列表”升级为 readiness report：结论、阻断原因、证据链、下一步动作。
- `gray` 输出从“dry-run 包装”升级为 rollout plan：route、budget、risk、expected evidence。
- `status` 把 ToolObservation failure next_hint 转成用户可选动作。

### P1：让工作流真正吞掉内部命令

- `run` 正式消费 PromptEnvelope、CapabilityManifest 和 ToolObservation，不把它们只当审计旁路。
- `review` / `debug` 优先读取 tool_observations.jsonl，把失败 observation 映射到 diagnose/repair/replan/ask/stop。
- `accept` 串起 promotion queue、MergeGate、completion contract 和 final report。
- Studio 复用同一套 JSON 输出，展示工作流状态而不是内部命令树。

## 8. 新命令准入规则

新增命令前必须回答：

1. 它是新的用户意图，还是现有工作流的一步？
2. 它是否能作为现有命令的 `--stage`、子动作、JSON 字段或 report section？
3. 它是否会要求普通用户理解内部对象，例如 WorkerInvocation、PromptEnvelope、acceptance report？
4. 它是否绕过 policy、budget、schema、protected path、ToolObservation 或 gate？
5. 它是否有明确输出、失败动作和 evidence 链？

如果答案显示它只是内部步骤，默认不新增命令。

## 9. 验收标准

- 新用户能用 `init -> run -> status -> resume/review` 理解系统，不需要知道 `execute/debug/acceptance-gate`。
- 维护者能用 `doctor -> gate -> gray -> evidence-bundle` 完成一次灰度判断，不需要手拼十几个命令。
- `gate --stage release` 能解释 manifest、cache break、model call metadata、acceptance report 和 Runtime OS evidence 的关系。
- 默认 pytest 不收集真实 provider 层；真实模型只通过显式 marker、gray 或 release/CI 流程触发。
- 内部命令仍可被 CI、专家和测试调用，但默认文档不把它们当普通用户路径。
- 每个失败都必须给出结构化下一步，而不是只输出 stdout/stderr。

## 10. 不做清单

- 不把 Asteria 改成 unrestricted agent chatroom。
- 不复制 Claude Code 的品牌、专有文案或 provider 绑定。
- 不通过堆命令替代 Runtime OS 编排。
- 不让模型绕过 runtime policy、schema、budget、protected paths 或 gate。
- 不为了“看起来强大”把内部对象原样暴露给最终用户。
