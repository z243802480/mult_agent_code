# 用户进展与证据协议

本文合并原 `Asteria Runtime 用户进展事件协议.md`、`长任务进度与候选审批.md` 和 `真实使用证据包.md`。它定义用户可见进展、长任务 heartbeat、候选审批和脱敏诊断包如何共享同一套 runtime evidence。

目标不是让用户理解内部状态机，而是让 CLI、Studio 和诊断报告都能回答：

- 当前在哪个 workspace 工作？
- 我的目标是否被理解了？
- 计划和执行进展是什么？
- 是否需要我授权？
- 产物、验证和证据在哪里？
- 结果是什么？
- 下一步我可以做什么？

## 1. 用户进展事件

正式 schema：

```text
src/asteria_runtime/schemas/user_progress_event.schema.json
```

事件文件必须落在当前 workspace 的：

```text
.asteria/runs/<run_id>/user_progress.jsonl
```

不能写入用户全局目录。`workspace_id` 用于关联 Studio project switcher、CLI `--root` 和 workspace-local evidence。

标准阶段：

```text
understand -> plan -> execute -> review -> result -> next
blocked
```

`channel` / `event_type` 是 Runtime 和证据层的兼容字段，不是 Studio 主会话的产品语义。
主会话必须优先消费 `transcript_kind`：

```text
user_message | assistant_message | plan | todo_update | tool_use | tool_result |
file_change | verification | permission_request | decision_request | repair |
ask | stop | final | context_status | subagent_summary | progress | diagnostic
```

`transcript_kind` 表达的是 harness 生命周期边界，而不是穷举模型行为。模型可以生成任意自然语言，
但 Runtime 只能在稳定边界上把它落成少数用户可理解事件：计划、工具使用、工具结果、文件变更、
验证、权限/决策、恢复、询问、停止和最终结果。

主屏事件还必须携带 `ui_intent`：

```text
inform | work_progress | needs_input | needs_attention | result
```

Studio 可以用 `channel` / `event_type` 兼容旧 run，但不得继续把 provider route、gate、schema、
JSONL 文件名、route guidance、model-check 等内部字段映射成主屏文案。需要用户看到的信息，
必须由 Runtime 生产侧先写成 `display_level=main` 的用户语义事件；raw evidence 仍进入 Inspector。

最小事件：

```json
{
  "schema_version": "0.1.0",
  "event_id": "upe-...",
  "workspace_id": "workspace-...",
  "run_id": "run-...",
  "session_id": "session-...",
  "created_at": "2026-05-21T00:00:00Z",
  "sequence": 1,
  "channel": "progress",
  "event_type": "delta",
  "phase": "plan",
  "status": "running",
  "title": "制定计划",
  "summary": "正在把目标拆成可执行步骤。",
  "content_delta": "先确认目标、约束和验收标准。",
  "display_level": "main",
  "transcript_kind": "plan",
  "ui_intent": "work_progress",
  "actions": [],
  "artifact_refs": [],
  "evidence_refs": []
}
```

## 2. 多通道输出

runtime 需要同时支持一次性读取和流式订阅。事件先落盘为 JSONL，外部可以 tail、轮询、SSE 或 WebSocket 转发。

标准通道：

- `conclusion`：结论、最终结果、下一步。
- `progress`：用户可见任务进展。
- `model`：模型 start/delta/end/error、provider、route、token、耗时。
- `tool`：工具调用、shell 命令、stdout/stderr 摘要。
- `file`：文件创建、修改、删除、diff 摘要。
- `evidence`：产物、报告、验证、证据引用。
- `call_chain`：模型、agent、tool 的调用链。
- `execution_chain`：任务、worker、验证、promotion 的执行链。
- `diagnostic`：heartbeat、deadline、retry、fallback、budget pressure。
- `workspace`：workspace 切换、输出目录、candidate workspace、git/worktree 状态摘要。

Studio 主线程只展示 `display_level=main` 且具有用户语义的 `transcript_kind` 事件：用户任务进展、权限请求、文件和产物摘要；Inspector 展示命令、stdout/stderr、model telemetry、artifact refs、evidence refs 和 raw events。

## 3. 权限与 capability decision

`user_progress.jsonl` 是 Tool 权限决策的用户侧主线。每次 Tool 调用前必须记录 `permission/permission_decision`，并在 `data.capability_decision` 中包含：

- `decision`
- `allowed`
- `requires_decision`
- `intent`
- `task_kind`
- `risk`
- `permission_mode`
- `reason`

对应原始证据写入 `capability_decisions.jsonl`，执行观察写入 `tool_observations.jsonl`。Tool、MCP、Skill 是不同执行机制，但共享 capability decision 记录格式；各自调用证据分别进入对应 evidence。

## 4. 长任务 Heartbeat

真实 provider 的 `real-model-gate`、`real-model-acceptance` 和 `real-model-smoke` 链路会在等待子进程时输出低噪声 heartbeat，避免长时间无反馈。

- 默认间隔：`ASTERIA_HEARTBEAT_SECONDS=30`
- 禁用方式：`ASTERIA_HEARTBEAT_SECONDS=0`
- 输出位置：stderr
- 输出内容：当前任务、elapsed、remaining、run id、run status、model/tool call 数、最近 runtime event、最近模型 route/provider/streaming 摘要

heartbeat 只读取当前 workspace 下 `.asteria/` 的运行元数据，不输出 prompt、模型正文、API key 或 protected paths 内容。Studio 可以把 heartbeat 和 `user_progress.jsonl` 映射为用户侧过程线，原始命令输出进入 Inspector。

## 5. 候选审批策略

`promotion.manual_approval_default` 已具备完整运行语义。

- `ask_everything`：每次候选 promotion 都进入 `pending_manual_approval`，任务进入 `blocked`，主工作区不被写入，除非用户明确 approve。
- `reviewed_auto`：低风险、写入范围明确、验证通过且未触发 release risk 的候选可以自动 promotion；高风险、跨目录、大范围变更、测试失败、预算异常或策略命中时进入 `pending_manual_approval`。
- `auto`：允许模型主导的自动 promotion，但仍必须通过 MergeGate、write scope、diff、验证、成本/风险检查和回滚策略；protected paths、secrets、破坏性删除、远程 push、生产部署和 Workspace 越界不能因为 `auto` 自动放行。
- `promotion.manual_approval_default=true`：无论权限模式如何，验证通过后只写入 `pending_manual_approval`，任务进入 `blocked`，主工作区不被写入。
- `promotion.manual_approval_default=false`：在当前权限模式允许时保持自动 promotion 路径，验证通过后尝试合并到主工作区，并记录 `auto_approved -> promoted`。

人工审批命令：

```powershell
asteria promotions approve --promotion-id <id>
asteria promotions reject --promotion-id <id>
asteria promotions discard --promotion-id <id>
```

在人工审批模式下，candidate workspace 会保留到 operator 明确 approve/reject/discard；release gate 会继续把 unresolved promotion 视为 release blocking risk。

## 6. 真实使用证据包

真实项目中导出诊断包：

```powershell
asteria evidence-bundle --root . --json
asteria evidence-bundle --root . --output .asteria/evidence_bundles/my-run.zip
```

该命令只读，不会重新调用模型，不会修改任务状态。默认输出：

```text
.asteria/evidence_bundles/evidence-<timestamp>.zip
```

证据包是 workspace-local 产物：默认只导出当前 workspace 内 `.asteria/` 的脱敏证据。用户目录下的全局 `.asteria/` 只允许读取版本、recent workspace 指针、模型 route 配置是否存在等摘要，不能打包本机 route/key 文件、账号文件或跨 workspace 的 session/run。

默认包含：

- `manifest.json`：版本、Python/系统信息、模型 route 聚合指标、完成度评估。
- `.asteria/model/real_model_gate_report.json`
- `.asteria/model/real_model_smoke_summary.json`
- `.asteria/model/capability_profile.json`
- `.asteria/verification/real_model_acceptance_*.json`
- `.asteria/validation_runs/<validation-run-id>/summary.json`
- `.asteria/ops/usage_signals.jsonl`
- `.asteria/ops/usage_signal_analysis.json`
- 最近若干 run 的 `run.json`、`cost_report.json`、`events.jsonl` tail、`model_calls.jsonl` tail、task/worker/validation evidence tail。
- 当前 workspace id、workspace name、相对路径摘要、git branch 摘要。

默认排除：

- API key、token、authorization、password、secret。
- `.env`、`.env.*`。
- `secrets/`。
- `.git/`。
- `*.pem`、`*.key`。
- 本机 route/key 文件。
- `%USERPROFILE%\.asteria\accounts\`、全局 cache、全局 logs 和其他 workspace 的 recent session/run。
- 未经授权的业务源码全文。

证据包用于区分 provider deadline、规划质量、验证质量、repair、promotion、人工决策和用户体验问题。用户分享前仍应确认没有私有业务内容。

## 7. 运维信号

诊断排障或 dogfooding 时，可以额外记录：

- 网络/VPN/代理环境。
- 运行时间段。
- 体感问题：长时间无输出、首包慢、执行慢、验证反复、最终报告不可信。
- 任务类型、期望结果、最终产物是否接受。
- 最大阻塞点：安装/初始化、模型等待、规划不准、验证不可信、权限/审批困惑、报告看不懂、产物质量不达标。
- 信任问题：哪些操作让用户不敢继续，哪些证据不足以让用户相信结果。

这些补充信息应进入运维侧 `UsageSignal` / `OpsInsight`，并与 `run_id`、`evidence-bundle`、失败归因和 roadmap task 绑定。当前入口是 `asteria ops-signal`，写入 `.asteria/ops/usage_signals.jsonl`；`asteria ops-signal --summary --analyze` 生成 `.asteria/ops/usage_signal_analysis.json`。该能力是后台埋点和脱敏证据指纹，不作为普通用户显性的反馈流程。

## 8. 当前落地口径

- `plan`、`run`、provider streaming、ToolExecutionGateway、文件写入类工具、MCP/Skill adapter 已接入用户进展或 capability decision 证据。
- Studio run detail 默认 timeline 来自 `user_progress.jsonl`，Inspector 读取 raw evidence。
- alpha.2 scoped validation、next scoped dogfooding 和 route guidance refresh 已完成；下一步进入 Studio MVP、Runtime 稳态验证、并行内核 sandbox/promotion-recovery 样本和 Design Intelligence Loop 四条主线。

历史 heartbeat、deadline、route guidance 和 alpha 验收记录只作为设计来源；当前状态以 `当前状态与路线.md` 为准。
