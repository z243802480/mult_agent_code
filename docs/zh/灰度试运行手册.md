# 灰度试运行手册

本文档定义本地产品包进入小范围灰度试运行前后的固定流程。目标是让系统可安装、可诊断、可暂停、可回滚，而不是直接进入长时间无人值守运行。

## 1. 灰度范围

首轮只开放低风险开发任务：

- 文档更新和 `.md/.txt/.rst` 文本只写产物。
- 小型 CLI 或脚本。
- 多文件小工具。
- 测试修复。
- 受控重构。

暂不开放：

- 生产部署。
- 远程 push。
- 破坏性 shell。
- 读取 protected paths。
- 长时间无限制自动推进。

## 2. 模型路线

当前推荐路线：

```powershell
$env:AGENT_MODEL_STRONG_PROVIDER = "glm"
$env:AGENT_MODEL_STRONG_BASE_URL = "https://open.bigmodel.cn/api/coding/paas/v4"
$env:AGENT_MODEL_STRONG_NAME = "glm-4.7"
$env:AGENT_MODEL_STRONG_API_KEY = "<your glm coding key>"

$env:AGENT_MODEL_MEDIUM_PROVIDER = "minimax"
$env:AGENT_MODEL_MEDIUM_NAME = "MiniMax-M2.7"
$env:AGENT_MODEL_MEDIUM_API_KEY = "<your minimax key>"

$env:AGENT_MODEL_CHEAP_PROVIDER = "fake"
```

仓库同时提供可复制的配置模板：`templates/model.routes.gray.example.ps1`。不要把真实 API key 写回仓库；在目标 PowerShell 会话中粘贴，或复制到本机私有配置 `C:\Users\Administrator\.asteria\model.routes.local.ps1` 后再替换占位符。runtime 会自动读取该本机文件，环境变量仍然优先于本机文件；也可以用 `ASTERIA_HOME` 指向其他私有配置目录。该文件只保存本机 key 和 route，不进入 git、诊断包或提交记录。

配置后先运行：

```powershell
python -m asteria_runtime doctor --root . --json
python -m asteria_runtime model-check --root . --tier strong
python -m asteria_runtime model-check --root . --tier medium
```

真实 provider route 默认优先使用流式调用；如需临时关闭，可设置 `AGENT_MODEL_STRONG_STREAMING=0` 或 `AGENT_MODEL_MEDIUM_STREAMING=0`。必要时设置 `AGENT_MODEL_<TIER>_STREAM_IDLE_TIMEOUT_SECONDS` 控制 chunk 间隔空闲超时。流式是增量能力，不替代原有非流式调用；如果 provider 或模型明确返回 streaming 不支持，adapter 会自动降级为普通 HTTP chat completion，并在 telemetry 中记录 `streaming_fallback_non_streaming`。随后使用 `model-check --json` 查看 `streaming.first_chunk_ms`、`chunk_count`、`idle_timeout_ms`、`deadline_ms` 和 `duration_ms`，并检查 run 目录里的 `model_calls.jsonl` 是否落下同一组 telemetry。显式关闭 streaming 时，非流式路径仍会记录 `duration_ms`，用于判断 provider call 是否已经吃满外层场景预算。

如果 `doctor --json` 的 `routes.medium.configured=false`，必须先补齐输出里的 `routes.medium.missing`。诊断口径与实际模型路由一致：优先使用当前 shell 的 `AGENT_MODEL_MEDIUM_*`，其次读取本机 `C:\Users\Administrator\.asteria\model.routes.local.ps1`，没有 tier-specific 配置时允许回退到全局 `AGENT_MODEL_*`，并识别 provider 原生 key（如 `MINIMAX_API_KEY` / `MINIMAX_CN_API_KEY`、`GLM_API_KEY`、`ZAI_API_KEY`）。不要在 medium route 缺失时进入真实灰度，因为 worker 执行和 repair 证据会失真。

`glm-4.7` 用于成本优先灰度，消耗免费 token 额度。额度耗尽、质量不足、真实 core release gate 或最终灰度发布复验时，把 `AGENT_MODEL_STRONG_NAME` 切到 `glm-5.1`。

## 3. 打包前检查

在仓库根目录运行：

```powershell
python -m asteria_runtime version --json
python -m asteria_runtime package-check --root . --json
ruff check .
mypy src
python -m pytest
```

`package-check` 必须通过。它会检查：

- `pyproject.toml` 项目名和版本。
- build backend。
- `asteria` console script。
- runtime `__version__` 与 pyproject version 是否一致。
- `templates/model.routes.gray.example.ps1` 灰度模型路由模板是否存在。
- 灰度文档是否存在。
- `dist/` 下是否已有 wheel/source artifact。

没有 `dist/` artifact 不阻断代码提交，但阻断正式灰度包交付。当前推荐用仓库脚本构建本地 wheel：

```powershell
python scripts/build_package.py --root . --clean
python -m asteria_runtime package-check --root . --json
```

如果目标机器没有可用的 `python -m build` 入口，也可以使用 pip 的 PEP 517 wheel 构建路径：

```powershell
python -m pip wheel . -w dist --no-deps
python -m asteria_runtime package-check --root . --json
```

## 3.1 安装包复验

正式灰度前必须证明 wheel 用户路径通过，而不是只证明仓库源码路径通过。推荐在全新 venv 和全新 workspace 中执行：

```powershell
$base = Join-Path $env:TEMP "asteria-installed-gray"
$venv = Join-Path $base "venv"
$workspace = Join-Path $base "workspace"
python -m venv $venv
$python = Join-Path $venv "Scripts\python.exe"
$asteria = Join-Path $venv "Scripts\asteria.exe"
& $python -m pip install --no-index --find-links .\dist asteria-runtime
& $python -m pip install pytest
& $asteria version --json
& $asteria init --root $workspace
& $asteria doctor --root $workspace --json
& $asteria real-model-gate --root $workspace --summary-json "$workspace\.asteria\model\real_model_gate_report.json"
& $asteria real-model-acceptance --root $workspace --suite gray --summary-json "$workspace\.asteria\verification\real_model_acceptance_gray.json" --python $python
& $asteria acceptance --root $workspace --suite core --allow-fake
& $asteria acceptance-gate --root $workspace --suite core --min-scenarios 10 --min-capabilities 10
& $asteria gate-status --root $workspace --json
& $asteria evidence-bundle --root $workspace --json
```

验收标准：

- `real-model-gate` 通过，且 strong/medium route 都有实际调用证据。
- `real-model-acceptance --suite gray` 7/7 通过，`gray_ready=true`。
- `acceptance --suite core --allow-fake` 10/10 通过。
- `acceptance-gate --suite core` 通过。
- `gate-status --json` 输出 `release_ready=true`，且 `route_guidance.status=healthy`。
- `evidence-bundle` 成功导出脱敏 zip，不包含 API key、本机 route 文件、`.env`、`secrets/`、`.git/`、证书或私钥。

## 4. 发布门槛

灰度前固定顺序：

```powershell
python -m asteria_runtime doctor --root . --json
python -m asteria_runtime model-check --root . --tier strong
python -m asteria_runtime model-check --root . --tier medium
asteria real-model-gate --summary-json .asteria/model/real_model_gate_report.json
asteria real-model-acceptance --suite gray --summary-json .asteria/verification/real_model_acceptance_gray.json
python -m asteria_runtime gate-status --root . --json
```

如果在隔离安装 venv 中验证 wheel，先确认该 venv 的 Python 可运行 `python -m pytest`；`gray_debug_repair` 场景会用它验证修复结果。也可以在执行 `asteria real-model-acceptance` 时用 `--python <path>` 指向已有 pytest 的解释器。

只有 `gate-status --json` 输出：

```json
{
  "rollout_state": "conditional",
  "stage": "ready_for_core_acceptance"
}
```

才进入真实 core acceptance：

```powershell
asteria acceptance --suite core --allow-fake
python -m asteria_runtime acceptance-gate --root . --suite core --min-scenarios 10 --min-capabilities 10
python -m asteria_runtime gate-status --root . --json
```

`release_ready=true` 且 `route_guidance.status=healthy` 才允许进入小范围真实任务灰度。历史上 2026-05-16 到 2026-05-19 已经有 real model gate、gray suite、core acceptance gate 和 Runtime OS gate 的通过记录；当前 gray suite 已扩展为 7 个场景。进入新机器内测时必须以目标环境重新生成的 canonical summary 为准，不能沿用旧机器上的历史通过证据。

`gate-status --json` 会同时检查当前 shell 的 strong/medium 有效路由环境。如果历史 gate 已通过但当前环境缺少可用的 tier-specific 配置、全局 `AGENT_MODEL_*` fallback 或 provider 原生 key，输出会降为 `stage=current_environment_incomplete`、`rollout_state=blocked`，此时不能开始真实任务灰度。

进入灰度前仍需在目标安装环境复跑：

```powershell
python -m asteria_runtime version --json
python -m asteria_runtime package-check --root . --json
python -m asteria_runtime doctor --root . --json
python -m asteria_runtime gate-status --root . --json
```

## 5. 首个真实任务

每个灰度任务都必须写清：

- Definition of Done。
- 写入范围。
- 验证命令。
- 模型和工具预算。
- 回滚方式。

推荐命令形态：

```powershell
python -m asteria_runtime /run "<small scoped goal>" --root . --max-iterations 3 --max-tasks-per-iteration 1 --no-research
python -m asteria_runtime status --root . --json
python -m asteria_runtime review --root .
```

灰度期默认任务边界由 `doctor --json` 和 `gate-status --json` 的 `gray_task_limits` 字段给出。首轮真实任务必须保持：

- `max_iterations=3`。
- `max_tasks_per_iteration=1`。
- `max_repairs=1`。
- `max_replans=1`。
- 只做文档更新、文件产出、小型 CLI/脚本、多文件小工具、测试修复或受控重构。

文档/文本只写任务应把目标文件放进 `expected_artifacts` / `expected_changed_files`，并优先使用“文件存在且非空”的验证；不要为了 standalone checklist、handoff note、README 这类任务扩大 read scope 或请求 runtime context。测试生成任务要先确认被测 artifact 已在当前 workspace 中存在，并把验收约束限定在既有 CLI/API 行为，避免把新的 stdin/help/错误格式要求混入测试任务。

如果出现 blocked task：

```powershell
python -m asteria_runtime debug --root . --max-repairs 1
python -m asteria_runtime replan --root . --max-items 1
```

不要在灰度期无限增加 repair/replan 次数。

如果 `status`、`review` 或 evidence 显示 `cost_status=near_limit`，应停止当前任务，收集证据并缩小任务范围；不要通过增加迭代数掩盖上下文包过大或任务拆分不清的问题。

## 6. 故障收集

出现失败时先收集：

```powershell
python -m asteria_runtime version --json
python -m asteria_runtime status --root . --json
python -m asteria_runtime doctor --root . --json
python -m asteria_runtime gate-status --root . --json
python -m asteria_runtime capability-report --root .
python -m asteria_runtime evidence-bundle --root . --json
```

保留以下运行态证据，但不要提交真实 API key 或完整敏感 transcript：

- `.asteria/model/latest_failure.json`
- `.asteria/model/real_model_gate_report.json`
- `.asteria/verification/real_model_acceptance_gray.json`
- `.asteria/verification/real_model_acceptance_core.json`
- `.asteria/acceptance/acceptance_report.json`
- `.asteria/runs/<run-id>/final_report.md`
- `.asteria/runs/<run-id>/task_execution_evidence.jsonl`
- `.asteria/runs/<run-id>/worker_results.jsonl`
- `.asteria/runs/<run-id>/candidate_promotions.jsonl`
- `.asteria/evidence_bundles/<timestamp>.zip`

如果 release gate 因 candidate promotion queue 阻断，先运行：

```powershell
python -m asteria_runtime promotions --root . list
python -m asteria_runtime promotions --root . approve --all-pending
python -m asteria_runtime promotions --root . retry --promotion-id <promotion-id>
python -m asteria_runtime promotions --root . discard --promotion-id <promotion-id>
```

`pending_manual_approval`、`approved`、`blocked`、`promotion_failed` 都属于 release-blocking 状态；进入发布门槛前必须处理到 `promoted`、`rejected` 或 `discarded`。

## 7. 暂停和恢复

长任务暂停、上下文压缩或交接前运行：

```powershell
python -m asteria_runtime compact --root .
python -m asteria_runtime handoff --root . --to FutureRun
```

恢复前先看：

```powershell
python -m asteria_runtime sessions --root . --context
python -m asteria_runtime status --root . --json
```

## 8. 回滚和退出标准

出现以下情况应暂停灰度：

- `gate-status` 不是 `conditional` 或 `release_ready`。
- provider response 反复不符合 schema。
- 预算频繁 `near_limit` 或 hard stop。
- merge gate 出现误 promotion 风险。
- protected path 风险。
- session 无法恢复。
- 报告无法解释完成项、阻塞项和成本。

回滚方式：

- 未 promotion 的候选工作区直接丢弃。
- 已进入 git 分支的候选改动用普通 git revert 或新修复提交处理。
- 不使用 destructive shell 清理工作区。
- 先生成 handoff/context snapshot，再处理失败证据。

升级方式：

- 用新 wheel 在新 venv 中安装，先跑第 3.1 节的安装包复验。
- 旧 `.asteria/` 不直接删除；如需迁移，先复制 workspace 或保留 git 分支。
- 升级后第一件事运行 `asteria doctor --json`、`asteria gate-status --json` 和 `asteria sessions --context`。
- 如果升级后 gate 降级，停止真实任务灰度，保留旧 venv 和新 venv 的 `version --json`、`doctor --json`、`gate-status --json` 输出用于对照。
