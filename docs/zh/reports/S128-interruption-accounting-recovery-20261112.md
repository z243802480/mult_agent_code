## 核实后修复

**取消顺序先纠正。** 现有 CancelCommand 是进程停止后的记录收尾，并不向活 worker 发取消请求；持 writer 锁时最多等6秒然后返回 alive。S126 控制器先 cancel 后 SIGTERM，906.52秒和 running 残留符合这个契约。原报告“请求取消”的表述应按此理解，不能当成正常取消失败。副本上停进程后 Cancel 正确 cancelled 且幂等，原记录不改。新联合控制器若到期先停止进程、再调用 Cancel。

**预算恢复确有缺口。** 无模型回放实际 Execute._read_cost→Budget.from_report，原报告2模型/0工具被直接恢复，已完成42模型/108工具不参与。现以 `Budget.from_run` 校验原报告和模型/本地/技能/MCP账本，恢复不降低的高水位，不重编号、不补伪记录。执行预算绑定已有 fsync+replace 原子存储：模型请求预留、已返回 usage、工具尝试在动作边界保存，超限异常也保存尝试。原无绑定的独立预算对象仍可在内存使用。

工具记录增加可选 `budget_charged`，区分前置权限拒绝和真正进入预算计数的动作，覆盖预算拒绝与适配器；旧缺字段记录保守计入并标识 `accounting_recovery.precision=conservative`。缺失 usage 保持未知，预留但未完成记录的调用保留，不冒充服务端精确账单。根/包内 schema 同步。执行入口之外的规划、摘要、独立 Review 预算没有因此全部变成实时检查点，不宣称全生命周期断电计费完备。

**恢复也要能继续调度。** 新跨进程测试复现工具批已完成后 os._exit(23)，旧 Resume 留下 in_progress 任务不再调度，返回 running。现 Resume 在现有 writer 锁内恢复未结束任务为 ready；保留 done/discarded 和原目标。工具批事件边界复用已有 stat 进度检查点与摘要，签名/任务契约匹配才沿用，验证须重跑。旧无检查点的磁盘文件不被猜成已完成修改；编辑边界变化也使旧证明失效。Execute 仅更换初始化与既有事件回调，未改 Run 的编排循环。

未初始化 Resume 不因锁文件而隐式初始化；活 worker 旁不能改任务。死进程收尾若遇损坏账本，仍如实取消，明确报计量恢复失败并保留原费用和账本，不能刷0。
