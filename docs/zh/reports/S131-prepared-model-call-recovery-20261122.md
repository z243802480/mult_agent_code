## 核实与修复

原预算检查点已经在模型调用入口保留额度，进程退出后不会因为缺少终局日志就自动退款；本轮修复的是响应前缺少输入来源的持久记录。`ModelCallLogger.record_prepared` 在进入后端前，用现有 schema / JSONL flush、fsync / 可选审计链落盘，生成独立 UUID，终局 ModelCall 显式带回该 ID。没有原始提示、消息、命令或输出采集；仅保留消息 hash、已有有界 input_evidence 和归因字段。

prepared 是本地逻辑调用准备事实，不证明网络发送、服务端接收/执行、HTTP 重试次数或模型理解，不是提供商幂等键。这个区分借鉴 [RFC 9110 §9.2.2 对未知响应与幂等语义的区分](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)。本轮没有改变既有 HTTP 重试策略，也不据准备记录自动重放、结清或补写旧请求。

恢复以终局行数加尚未唯一关联的 prepared 形成调用下界，继续与检查点高水位取 max；同一次准备和终局不重复收费。未结请求保留调用额度、总 tokens 未知，已有可知部分以 recovery 时的下界保留。重复 ID 或 run/task/purpose/tier 冲突先失败，不能覆盖成本检查点。无准备 ID 的旧日志保持兼容、不回填；孤立终局不替别的准备记录销账。配置的 provider/model 名称与服务端回显不同不构成 scope 冲突。

首次调查漏了独立的 `MiniMaxOpenAICompatibleClient`：初冻只接 OpenAI-compatible、Metered、Fake 三入口，真实场全部走第四入口，prepared 为 0。原场照既定协议跑完并保留，不能算新日志通过。补修只给这条现有入口接同一个日志接口（4 行），两个 HTTP 客户端共享同一参数化重试控制；不加模型语义、措辞、格式或授权分支。factory 的实际客户端入口与所有 `chat` 实现已逐项核实。
