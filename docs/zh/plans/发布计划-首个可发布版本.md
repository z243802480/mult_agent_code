#### 🔑 真实 golden 验证结论（2026-06-28，推翻"传输层是主因"的假设）

拉真实失败 run 的底层证据（temp `agent-real-acceptance-*/.../model_calls.jsonl` + `run_loop_summary.json`）：

- **传输层是健康的**：每次 model call 都 `status=success` / `finish_reason=stop` / `output_tokens>0` / 无 `error_type`，流式 first_chunk ~2–4s。→ **#1/#2 是正确的防御性硬化，但不是这些失败的主因；#3–#5 同理，暂不投入。**
- **真实根因**：medium 模型（minimax）在 trivial 任务上 **execution-action 合规率低**——单次约 1/4，独立单次 **0/3**。两种签名：① round-1 选 `stop` 不写文件（"stop is not grounded"）；② 跑满 `max_rounds=2` 但 `changed_files=[]`（contract_violation）。route 证据显示 **strong(glm-5.2) 从没被用过**。
- [x] **根因修复已落地+测+推送**（commit `8a888c6`）：`coder_agent.py` 的 in-agent 重试 **medium→strong 升级**（仅首次失败后触发，成本可控）+ ungrounded-stop 专用强提示词点名未写文件。`execute_command.py`（DO_NOT_TOUCH）未碰。760 unit 通过（+1 新测试）。
- [x] **升级后 golden 量化（10 次独立单次：4/4 + 4/6 = 8/10）**。**注意 strong 实际路由 = `provider=zai / model=glm-5.2`**（env `glm/glm-5` 是别名）；10 次里 strong 触发 4 次，实证机制有效（`go4l85ph`：medium 失败→升级 strong→write_file 落地）。
- [x] **残余失败已完整刻画为两类**：
  - **① ungrounded stop**（model round-1 选 stop 不写）：升级 strong **大部分救回**，但 strong 偶尔也 stop（batch run1：minimax→glm-5.2 两次都 stop）。
  - **② no-write**（动作 schema 合规但目标文件没落地 / 先 verify 后没 write）：**不经 CoderAgentError，升级路径不触发**（batch run4：greet.py 从未写出，verify `python greet.py Alice` 退 2 → tool_failure）。发生在 `execute_command` 的 contract/repair 层（DO_NOT_TOUCH 重构）。
- [x] **DecisionPoint 已决（维护者，2026-06-28）**：不追求单次成功率；靠**循环收敛**（CC 式 tool→verify→retry，多轮稳定成功）+ **强弱模型委派**（默认强、grunt 才给中档、智能切换）做到产品级稳定。
- [x] **委派+循环切片已落地+测+推送**（commit `8a712c7`）：
  - `coder_agent._execution_tier()` 执行**默认 strong**；仅显式 `task.execution_tier` 标记 grunt 才降 medium/cheap；重试恒走 strong。
  - `debug_agent` task_repair→strong；`policies.default.json` model_routing coding/debugging→strong（配置=行为一致）。
  - `agent_loop.max_rounds_per_task` **2→5**（policy 驱动，**不碰 DO_NOT_TOUCH 的 execute_command**），对齐参考简报 S17 "像 CC 单会话内 tool→verify→retry"。
- [x] **default-strong golden（6 次独立单次）**：**5/6 过**，全部 exec=`glm-5.2`。**模型合规类失败（①stop/②no-write）已消除**：通过的多为**单轮即成**，run3 **跨两轮自愈收敛**。唯一失败是 **provider stream 超时**（transport，可重试，非模型问题）——失败模式从"模型不会做"转为"网络偶发抖动"。
- [x] **transport 收尾（strong-tier stream deadline）已落地+测+复跑**：根因＝strong 模型（glm-5.2）流式比 medium 基线（minimax）慢，而 worker/repair 角色契约 deadline 仍按 medium 标定（worker 90s / repair 75s），escalate 到 strong 后偏紧 → 单次 `provider_timeout`/"stream deadline exceeded" 直接中止任务（未进 5 轮循环）。
  - **修复（方案①·deadline 层 tier 感知补偿）**：`models/request_deadline.py` 新增 `_apply_strong_tier_headroom`——当 `request.model_tier=="strong"` 且角色契约 `default_model_tier!="strong"`（即超出 medium 基线被升格的 coding/debugging）时，给 `provider_call_seconds` ×1.7 余量（worker 90→153、repair 75→128）。已按强标定的 goal_spec/planner/review/brainstorm 保持原 deadline；显式 `request.timeout_seconds` 仍为权威、不加余量。
  - **不碰契约默认值**：角色契约仍如实声明 medium 基线（90/75），余量只在运行期 deadline 解析处加 → 不动 `_ROLE_DEFAULTS`、不破坏 5 处钉 `provider_call_seconds=90` 的契约测试，也不动 DO_NOT_TOUCH 的 `execute_command.py`。验收/smoke 经 `effective_model_deadline` 同一收口点自动吃到余量（契约 90 优先级高于 `apply_deadline_budget_env` 的 env 默认，叠加余量后 153），无需改 `deadline_budget.py`。
  - **拒绝 strong→medium 回退**：`routing._should_fallback_to_medium` 既未触发、也非期望（medium 合规率低，正是默认强要解决的）；本修复让 strong 单轮即成，不回退。
  - **证据**：新增 `tests/unit/test_request_deadline.py`（7 例覆盖升格余量/强标定不变/medium 不变/显式 timeout 权威/idle 钳制）；unit 全绿（767 passed，唯一失败 `test_documentation_contracts` 为预存在的 `.asteria/policies.json` 缺失环境问题，与本改无关、stash 后同样失败）。**real golden（validation_small_cli，7 次独立单次）7/7 过、全 exec=strong(zai)、零 `provider_timeout`**，其中 2 次总时长 ~119s 正命中此前会被 90s 钳掉的慢-strong 长尾。
