# 开发环境与验证

本文档记录本地开发、模型配置、真实模型 smoke 和提交前检查。中文主文档是项目当前更详细的事实来源。

## 1. Python 环境

项目目标运行环境是 Python 3.11+。在仓库根目录执行命令前，建议设置：

```powershell
$env:PYTHONPATH = "src"
```

如使用虚拟环境，可安装开发依赖：

```powershell
python -m pip install -e ".[dev]"
```

构建本地验证 wheel：

```powershell
python scripts/build_package.py --root . --clean
python -m asteria_runtime package-check --root . --json
```

## 2. 常用命令

查看 CLI：

```powershell
python -m asteria_runtime --help
```

初始化工作区：

```powershell
python -m asteria_runtime init --root .
```

运行最小闭环：

```powershell
python -m asteria_runtime run "实现一个本地 notes 模块" --root .
```

运行测试和静态检查：

```powershell
python -m pytest
ruff check .
mypy src
```

统一验证脚本：

```powershell
.\scripts\verify.ps1
```

## 2.1 控制面命令

后续 TUI / GUI 会复用这些只读控制面命令的数据口径。日常先用：

```powershell
python -m asteria_runtime status
python -m asteria_runtime doctor
python -m asteria_runtime gate-status
python -m asteria_runtime version --json
python -m asteria_runtime package-check --json
```

`status` 看当前 session 和阻塞点，`doctor` 看本地环境与模型路由，`gate-status` 看真实模型 gate、validation suite、core acceptance 的阶段，`version` 看 runtime 版本和 Python 入口，`package-check` 看打包元数据和验证文档前置条件。它们都支持或提供 `--json`，后续 TUI / GUI / 自动化验证门禁必须优先复用这套机器可读控制面输出，避免重新散读 `.asteria/` 运行产物。

控制面 JSON 契约要点：

- `version --json` 输出 `schema_version`、`package`、`version`、`python_version` 和 `executable`。
- `package-check --json` 输出 `checks`、`failed_checks`、`artifacts` 和 `next_actions`，用于判断本地包是否具备验证交付前置条件。
- `status --json` 输出 `schema_version`、`status`、`summary`、`blockers`、`risks`、`pending_decision_count`、`latest_failure` 和 `next_actions`。
- `doctor --json` 输出 `routes`、`sandbox`、`failed_checks` 和 `next_actions`，其中 `sandbox.preferred_backend` 会说明当前应使用 `git_worktree` 还是 `temp_workspace`。
- `gate-status --json` 输出 `release_state`、`release_ready`、`blocking_reason` 和 `gates`，用于判断当前卡在 real model gate、validation suite 还是 core acceptance。

Git worktree 候选工作区策略：

- tracked 文件干净且 git 可用时，候选工作区优先使用 `git_worktree` 和本地 `asteria/candidate/...` 分支。
- 未跟踪的过程产物，例如真实模型 transcript，不会阻止 worktree backend。
- tracked 文件存在未提交改动时会降级到 `temp_workspace`，避免把候选 promotion 和用户改动混在一起。
- 候选晋升通过 `candidate_promotions.jsonl` 记录状态。需要人工处理时使用 `asteria promotions list`、`asteria promotions approve --promotion-id <id>`、`asteria promotions reject --promotion-id <id>`、`asteria promotions retry --promotion-id <id>` 或 `asteria promotions discard --promotion-id <id>`。
- promote 前必须重检 merge gate、candidate workspace、promotable files 和 git worktree/source path 状态；失败必须记录为 `promotion_failed` 或 `blocked`，不得让失败候选污染主工作区。

## 3. 模型配置

默认 provider 是 MiniMax：

```powershell
$env:AGENT_MODEL_PROVIDER = "minimax"
$env:AGENT_MODEL_API_KEY = "<your key>"
```

MiniMax key 有区域差异。运行时默认使用 `https://api.minimax.io/v1`；当 key 以 `sk-cp-` 开头时，会自动切换到中国区端点 `https://api.minimaxi.com/v1`。如需强制指定端点，可设置：

```powershell
$env:AGENT_MODEL_BASE_URL = "https://api.minimaxi.com/v1"
```

API key 只能通过进程环境变量、CI secret 或本机密钥管理注入。不要写入 `.env`、文档、测试夹具、日志或提交记录。

OpenAI-compatible provider：

```powershell
$env:AGENT_MODEL_PROVIDER = "openai-compatible"
$env:AGENT_MODEL_BASE_URL = "https://api.openai.com/v1"
$env:AGENT_MODEL_NAME = "<model name>"
$env:AGENT_MODEL_API_KEY = "<your key>"
```

本地模型 provider：

```powershell
$env:AGENT_MODEL_PROVIDER = "ollama"
$env:AGENT_MODEL_NAME = "qwen2.5-coder:7b"
```

分层路由示例：

```powershell
$env:AGENT_MODEL_STRONG_PROVIDER = "glm"
$env:AGENT_MODEL_STRONG_API_KEY = "<your glm coding key>"
$env:AGENT_MODEL_STRONG_BASE_URL = "https://open.bigmodel.cn/api/coding/paas/v4"
$env:AGENT_MODEL_STRONG_NAME = "glm-4.7"

$env:AGENT_MODEL_MEDIUM_PROVIDER = "minimax"
$env:AGENT_MODEL_MEDIUM_API_KEY = "<your minimax key>"
$env:AGENT_MODEL_MEDIUM_NAME = "MiniMax-M2.7"

$env:AGENT_MODEL_CHEAP_PROVIDER = "fake"
```

未设置 tier 专属 provider 时，运行时会回退到全局 `AGENT_MODEL_PROVIDER`。

当前验证推荐路线是：`strong` 用 GLM coding 套餐承担高风险 goal/spec、发布复验、复杂 review、research 和后续 coordinate；`medium` 用 MiniMax 承担默认 goal_spec、coding、debug、diagnostic 等 worker 执行；`cheap` 先用 fake/local 或低价 OpenAI-compatible route 做分类、摘要和低风险只读任务。低风险 `doc_update` / `simple_file` / `single_file_bugfix` 默认应能用 medium + deterministic-first review 完成，且不要求每个小任务都出现 strong 调用。当前本项目可优先把 `AGENT_MODEL_STRONG_NAME` 设为 `glm-4.7` 消耗免费 token 额度；额度用完、质量不足或进入最终 release gate 时，再切到 `glm-5.1` 复验。后续如果接入 GPT-5.5，可以把 `AGENT_MODEL_STRONG_PROVIDER` 切到对应 OpenAI-compatible route，而不改变 Runtime OS 的 worker 编排结构。

GLM coding route 可用以下方式接入：

```powershell
# GLM coding 套餐 route
$env:AGENT_MODEL_PROVIDER = "glm"
$env:AGENT_MODEL_API_KEY = "<your glm coding key>"
$env:AGENT_MODEL_BASE_URL = "https://open.bigmodel.cn/api/coding/paas/v4"
$env:AGENT_MODEL_NAME = "glm-4.7"

# 智谱 BigModel route
$env:AGENT_MODEL_PROVIDER = "zhipu"
$env:AGENT_MODEL_API_KEY = "<your zhipu key>"
$env:AGENT_MODEL_NAME = "glm-5.1"
```

`glm-4.7` 是当前本项目的成本优先 strong model；`glm-5.1` 是质量优先 fallback 和发布门槛复验模型。

如果 provider 端点变化，优先显式设置 `AGENT_MODEL_BASE_URL`；API key 仍只能通过进程环境变量、CI secret 或本机密钥管理注入。

验证前建议分别检查强/中路线：

```powershell
python -m asteria_runtime model-check --tier strong
python -m asteria_runtime model-check --tier medium
```

通过单路由检查后，再运行真实模型验证 gate。它会在隔离 workspace 中检查 strong/medium route、执行最小 smoke，并验证 `model_calls.jsonl`、`worker_results.jsonl`、`task_execution_evidence.jsonl` 和 `cost_report.json` 是否形成可审计证据：

```powershell
asteria real-model-gate --summary-json .asteria/model/real_model_gate_report.json
```

`asteria real-model-gate` 通过后，才进入 core acceptance 或小范围真实任务验证。

验证候选场景集：

```powershell
asteria real-model-acceptance --suite validation --summary-json .asteria/verification/real_model_acceptance_validation.json
```

`validation` suite 通过时会输出 `validation_ready=true`，表示当前固定回归场景和 strong/medium 路由证据达到进入 core acceptance 的预检条件。场景数量以当前 runtime summary 为准；历史 7 个场景只是回归基线，不代表长期自主运行能力已经完成。长期能力还必须结合 capability catalog、context budget、recovery pressure、gate/report 解释和真实任务产物证据判断。

core acceptance 也通过后，进入小任务真实验证：

```powershell
asteria validation-run --dry-run
asteria validation-run "Create a tiny local validation artifact named validation_probe.txt containing one line: validation small task ok" --json
```

`validation-run` 会先记录 `version`、`package-check`、`doctor` 和 `gate-status` 的控制面结果，只有阶段为 `ready_for_small_real_task_validation` 才会启动受控真实任务。默认关闭 research、限制迭代数和每轮任务数，并在 `.asteria/validation_runs/<id>/summary.json` 中记录 goal、preflight、预算、路由期望、run result、worker result、task execution evidence、merge gate evidence 和 cost report 摘要。固定发布验证 suite 仍要求 strong/medium route 都有健康证据；但 scoped fast-path 小任务的成功标准改看任务形态是否按策略选择路由、strong 调用是否只随风险升级出现、deterministic review 是否命中、slim/focused context 是否记录，以及产物和验证是否可复现。不要因为单个低风险任务 0 strong 就判定失败。

## 4. 真实模型 smoke

推荐直接使用安装包内的真实模型 smoke 命令。命令会创建临时 workspace，执行 `/init`、`/model-check`
和最小 `/run`，并检查目标文件、session 日志、成本报告、模型调用、工具调用、review pass
状态，以及所有任务是否完成：

```powershell
asteria real-model-smoke
```

校准 fast path / context slimming 时，优先跑小 matrix 子集，而不是完整放量：

```powershell
asteria real-model-smoke --matrix-preset rolling-fastpath-v1 --no-research --model-max-retries 0 --matrix-output-dir .asteria/verification/real_provider_matrix/<run-id>
```

低风险 case 的目标不是证明 strong route 每次参与，而是证明 strong 调用被压到 0 或只在风险升级时出现，并且 matrix summary / `model_calls.jsonl` 记录 strong 调用、task execution 调用、repair 调用、`context_mode` / `fast_path_task_kind`。`rolling-fastpath-v1` 固定覆盖文档/简单文件、单文件 bugfix 和 context-heavy maintenance 三类。

仓库开发路径下仍保留兼容包装脚本：

```powershell
.\scripts\real_model_smoke.ps1
```

如果想固定输出目录或生成机器可读摘要：

```powershell
asteria real-model-smoke --root C:\temp\agent-real-smoke --summary-json C:\temp\agent-real-smoke-summary.json
```

如果网络链路偶发 TLS EOF、超时或 provider 抖动，可临时提高重试次数后重跑：

```powershell
$env:AGENT_MODEL_MAX_RETRIES = "5"
asteria real-model-smoke
```

真实 acceptance 验证默认会在未显式设置 provider timeout/retry 时使用较短预算：每个场景 1 次
run attempt、模型层 1 次 retry、provider call 默认不超过 90 秒，review/recovery 默认不超过
90 秒。只有在定位 provider 抖动时才建议临时升高重试。如果需要调整完整 `/run` 尝试次数：

```powershell
asteria real-model-smoke --run-attempts 3 --model-max-retries 5
```

真实模型 smoke 的通过标准：

- `model-check` 能返回成功。
- `.asteria/runs/<session_id>/final_report.md` 存在。
- run 状态为 `completed`。
- `eval_report.json` 的 overall status 为 `pass`。
- `task_plan.json` 中没有未完成或阻塞任务。
- 目标产物真实存在，并与用户目标一致。
- 失败、重试、工具调用和模型调用被记录到 `.asteria/` 运行日志中。
- 仓库中不出现真实 API key。

## 5. 真实任务验收集

最小 smoke 通过后，可运行真实任务验收集：

```powershell
asteria real-model-acceptance --suite core
```

当前 `core` 套件包含：

- `file_smoke`：最小文件创建闭环。
- `password_cli`：生成单文件密码强度 CLI。
- `markdown_kb`：生成单文件 Markdown 索引/搜索工具。

也可以只跑单个场景：

```powershell
asteria real-model-acceptance --scenario password_cli
```

验收集默认要求真实 provider。只有测试 runner 本身时才使用：

```powershell
asteria real-model-acceptance --suite offline --allow-fake
```

`asteria acceptance` 会把验收结果写入工作区下的 `.asteria/acceptance/`：

- `latest_summary.json`：脚本原始机器可读摘要。
- `acceptance_report.json`：经过 schema 校验的 runtime 验收报告，包含 suite、场景、结果、失败摘要和输出尾部。

如果需要把失败验收纳入后续开发闭环，可以追加 `--promote-failures`：

```bash
python -m asteria_runtime /acceptance --suite core --promote-failures
```

该选项会读取失败场景并在当前 session 的 `task_plan.json` 中生成 `ready` 修复任务，同时同步 `.asteria/tasks/backlog.json`；如果当前没有 session，会明确失败，不会静默丢弃验收结果。
生成的任务会包含验收报告路径、summary JSON 路径、场景 workspace、smoke transcript、期望产物路径，以及可直接复现的 `asteria /acceptance --scenario ...` 和底层脚本命令。
新生成的失败任务也会在 `.asteria/memory/failures.jsonl` 中记录为 `failure_lesson`，后续 agent 上下文会自动读取这些经验。
每个 promoted failure 还会写入 `.asteria/acceptance/failures/<scenario>.json` 作为结构化证据；`ContextLoader` 会把最近证据裁剪后注入后续 `/execute`、`/debug` 等 agent 上下文。
`/compact` 和 `/handoff` 也会携带最近 acceptance failure evidence，长任务交接后仍可定位失败场景、复现命令和 promoted repair task。
`asteria sessions --context` 会显示 acceptance failure 数量和最新失败场景，便于恢复当前 session 时直接判断应执行 `/debug` 还是继续 `/execute`。
如果希望生成任务后立刻继续当前 session，可以显式追加 `--run-promoted`；默认不会自动触发模型执行，避免意外产生真实模型调用成本。
如果希望修复任务执行后自动复验本次新 promoted 的失败场景，可以显式追加 `--rerun-promoted`；该选项会隐式执行 promoted 任务，只复跑这些场景，并在 `acceptance_report.json` 的 `repair_closure` 中记录 `repair_run_id`、`rerun_ok`、`closed_failures` 和 `remaining_failures`。

这些产物用于后续把真实模型验收失败接入 memory、repair task 或 benchmark 回归。

## 6. 结构化输出容错

真实模型可能返回 `<think>`、markdown code fence、近似 JSON 或轻微字段漂移。运行时在模型边界做有限容错：

- 提取最后一个可解析 JSON 对象。
- 仅在整段响应是 code fence 时剥离 fence。
- 移除 `<think>...</think>` 推理块。
- 对 `GoalSpec`、`ExecutionAction`、`EvalReport` 做有边界的字段归一化。
- 所有持久化对象仍必须通过 schema 校验。

容错不是放宽数据模型。无法安全归一化的输出必须阻塞、记录原因，并进入修复或人工决策流程。

## 7. 验证产物

`asteria run` 会在当前 workspace 的 `.asteria/runs/<run_id>/` 下写入运行证据。用户侧可以把该 run 视为 current session 的一次执行记录；session 指针由 `.asteria/current_session.json` 维护。

- `goal_spec.json`
- `task_plan.json`
- `events.jsonl`
- `tool_calls.jsonl`
- `model_calls.jsonl`
- `cost_report.json`
- `review_report.md`
- `final_report.md`

提交代码前至少确认：

- 源码能通过 `.\scripts\verify.ps1`。
- 新行为有单元测试或集成测试。
- 涉及命令、模型或安全边界的修改有失败路径测试。
- 真实模型验证只记录示例 key 前缀，不记录真实 key。

## 8. ContextSnapshot 与 Handoff

长任务暂停、交接给后续 agent、准备压缩上下文，或进入需要用户决策的阶段前，应该运行：

```powershell
python -m asteria_runtime /compact --root .
python -m asteria_runtime /handoff --root . --to-role FutureRun
```

`ContextSnapshot` 必须保留可恢复现场，而不只是聊天摘要：

- 目标摘要和 Definition of Done。
- 已接受决策和待处理决策。
- 当前 run 状态、阶段和任务状态统计。
- 活跃任务、最近 artifact、修改文件、验证结果和失败证据。
- review/final report 摘要、开放风险和下一步行动。

`HandoffPackage` 会基于 snapshot 推荐下一条命令：

- 有 pending decision 时推荐 `decide --decision-id ...`。
- 有失败或 blocked task 时推荐 `debug`。
- 有 ready/in-progress task 时推荐 `execute`。
- 任务全部完成后推荐 `review`。
