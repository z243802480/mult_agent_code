# 小真实任务灰度批次

更新时间：2026-05-19

## 目标

本批次用于验证 Asteria 在真实 provider 路由下的小范围开发任务稳定性。它不是长时间无人值守运行，也不是扩大自动化预算的许可。

批次必须在 `gate-status --json` 输出 `stage=ready_for_small_real_task_gray` 且 `route_guidance.status=healthy` 时启动。默认运行限制：

```powershell
asteria gray-run "<goal>" --max-iterations 3 --max-tasks-per-iteration 1
```

`gray-run` 内部固定关闭 research；如果直接使用 `asteria run` 复现实验，则需要显式增加 `--no-research`。

如果任一任务出现 `near_limit`、unresolved promotion、protected path 风险、route guidance blocked 或 session 无法 resume，应停止批次并收集证据。

## Provider Route 策略

`provider_route_strategy.strong_goal_spec` 是 strong `goal_spec` 路由的产品化判定来源：

- 继续使用 `glm-5`：release gate 复验、route guidance healthy、最近成功率达到 `min_success_rate_for_gray`。
- 允许使用 `glm-4.7`：小真实任务灰度、成本受限，且 cost-saver 路由最近成功率达到阈值。
- 重试或降级：primary route 出现一次 transient timeout、rate limit 或网络失败，但累计成功率仍可接受；低风险文档任务可考虑健康的 medium 路由。
- 阻断灰度：strong `goal_spec` 在达到 `min_calls_before_enforcement` 后成功率低于阈值，timeout 次数超过 `max_timeout_failures_for_gray`，出现认证/预算/配置失败，或缺少 required streaming evidence。

当前默认阈值：`min_calls_before_enforcement=3`、`min_success_rate_for_gray=0.8`、`max_timeout_failures_for_gray=1`、`provider_deadline_seconds=120`、`stream_idle_timeout_seconds=30`。

## 批次任务

第一批建议 12 个任务，每个任务独立执行并保留 `.asteria/gray_runs/<id>/summary.json`：

| 编号 | 类型 | 目标摘要 | 主要观察点 |
|---|---|---|---|
| G01 | 文档更新 | 新增一页本地工具使用说明，包含安装、运行、验证三节 | doc-only verification、artifact promotion |
| G02 | 文档更新 | 修订已有 README 的命令示例，保持范围只在文档 | write scope 收敛、无代码误改 |
| G03 | 单文件 CLI | 创建一个只用标准库的文本行数统计 CLI 和最小测试 | artifact 创建、pytest 验证 |
| G04 | 单文件 CLI | 创建 JSON pretty-print 小工具和失败输入测试 | provider JSON 输出稳定性 |
| G05 | 多文件小工具 | 拆分一个 todo parser 到 `src` 与 `tests` 两个文件 | 多文件 write scope、import 路径 |
| G06 | 多文件小工具 | 新增配置驱动报告生成器，含样例配置与测试 | 配置 source of truth |
| G07 | 测试修复 | 给一个故意失败的纯函数测试生成最小修复 | DebugAgent repair 收敛 |
| G08 | 测试修复 | 修复边界条件测试，不扩大 API 行为 | replan/repair 次数 |
| G09 | 受控重构 | 将重复 helper 提取到单文件函数并保持测试不变 | merge gate、diff 可读性 |
| G10 | 受控重构 | 重命名内部变量并更新相关测试，不改外部接口 | 小 refactor 风险 |
| G11 | 候选审批演练 | 在 `promotion.manual_approval_default=true` 的临时 workspace 中执行文档任务 | pending approval、release gate 阻断语义 |
| G12 | 恢复演练 | 制造一次 runtime request 后 resolve/resume | session 恢复、用户可理解性 |

## 通过标准

- 每个任务都有 run summary、final report、model_calls、worker_results、task_execution_evidence 和 cost_report。
- strong route 覆盖 `goal_spec` 或 review，medium route 覆盖 task execution 或 repair。
- 平均 repair 次数不高于 1.0；单任务不超过策略预算。
- 无 unresolved promotion、无 protected path 访问、无主工作区污染。
- 批次结束后运行 `capability-report`，route guidance 必须保持 `healthy` 或给出明确 review/block 行动。

## 批次后 DecisionPoint

批次完成后再评估是否翻转 `promotion.manual_approval_default=true`。判断依据：

- 自动 promotion 是否出现误写或误晋升。
- 人工审批是否明显提高安全感且认知负担可接受。
- release gate 对 pending/blocked promotion 的提示是否足够清晰。
- gray-run summary 是否能让用户独立定位失败。
