# 工程化体系

## 1. 文档定位

本文定义 Asteria 作为本地优先 autonomous development runtime 的工程化横切能力：日志、权限、用户与身份、配置、hooks、skills、plugins、MCP、诊断导出和控制面。

本文不替代 [架构设计.md](./架构设计.md)、[数据模型.md](./数据模型.md) 或 [运行命令.md](./运行命令.md)。它负责把这些横切能力统一成可实现、可验收、可长期演进的工程规范。

技术债治理、ADR/RFC、schema 兼容、迁移、错误分类、feature flag、golden trace、发布分级、威胁模型和供应链治理见 [工程治理体系.md](./工程治理体系.md)。本文只定义运行时横切能力本身。

## 2. 总原则

- 本地优先：默认状态、日志、配置和运行证据都落在 `.asteria/`。
- 安全默认拒绝：secret、protected paths、破坏性 shell、远程推送、部署、外部网络和插件执行必须显式授权。
- 结构化优先：运行证据、配置、权限和扩展声明必须有 schema，不能只靠自由文本。
- 可审计优先：系统必须解释谁在何时触发了什么动作，使用了哪个模型或工具，产生了哪些 artifact，为什么 blocked。
- 扩展受控：hooks、skills、plugins、MCP 都只能进入受控生命周期，不能绕过 runtime policy、预算、schema、日志和验证门禁。
- 用户操盘：重大决策、权限升级、预算硬停、敏感数据访问和不可逆操作必须形成 DecisionPoint 或用户显式操作。

## 3. 日志与可观测性

运行日志分层：

```text
.asteria/runs/<run-id>/
  events.jsonl
  runtime_hooks.jsonl
  tool_calls.jsonl
  model_calls.jsonl
  workers.jsonl
  worker_results.jsonl
  validation_results.jsonl
  task_execution_evidence.jsonl
  cost_report.json
  final_report.md
```

日志边界：

- `events.jsonl` 记录阶段变化、任务状态、阻塞、决策、候选工作区、promotion 和 gate 结果等高层事件。
- `runtime_hooks.jsonl` 记录 worker/tool/后续 plugin 的 before/after/error 生命周期事件。
- `tool_calls.jsonl` 记录工具名称、输入摘要、输出摘要、状态和错误，不写入 secret 或大段原文。
- `model_calls.jsonl` 记录 provider、model、tier、token/cost、耗时、失败类型和摘要，不保存完整敏感 prompt。
- `cost_report.json` 是预算与成本的聚合视图，不能只依赖日志行数推断。

日志脱敏：

- 默认脱敏 key：`secret`、`token`、`api_key`、`apikey`、`authorization`、`password`、`credential`、`raw_context`。
- 诊断导出默认排除 `.env`、`.env.*`、`secrets/`、私钥、证书、provider API key、未授权源码全文和 provider 原始响应。
- 报告可以引用证据 id、相对路径和摘要；需要源码片段时必须通过 allowlist 或用户确认。

验收要求：

- 每个较大运行必须能从 `events.jsonl`、`runtime_hooks.jsonl`、worker evidence、validation evidence 和 final report 复盘。
- `status`、`sessions --context`、weekly report、capability report、acceptance gate 应复用同一组 Runtime OS evidence helper，避免各说各话。

## 4. 权限体系

权限分层：

```text
Project policy
  -> command permission
  -> task allowed_tools
  -> tool permission profile
  -> runtime request / DecisionPoint
  -> merge gate / promotion queue
```

默认规则：

- 读写文件必须经过 protected paths 检查。
- shell 命令必须经过 risk classification；破坏性 shell 默认拒绝。
- 网络、secret read、global package install、remote push、deploy 默认拒绝。
- 工具调用必须同时满足任务 `allowed_tools` 和工具注册表权限。
- 如果模型提出越权动作，runtime 应创建 runtime request 或 DecisionPoint，而不是部分执行后再补救。

## 5. 用户、账号与身份

Asteria 当前是本地单用户优先，不做多租户服务端账号系统，但仍需要明确身份边界：

- Human Owner：拥有项目目标、预算、权限升级和最终接收/放弃产物的决策权。
- Runtime Actor：如 `ExecuteCommand`、`WorkerRunner`、`ToolExecutionGateway`，负责记录可审计动作。
- Agent Role：如 Planner、Coder、Reviewer、Debug、Release，是任务分工和模型路由依据，不等同于系统账号。
- WorkerInvocation：一次受控执行单元，必须有 `worker_invocation_id`、task、runtime profile、status 和 result。
- Plugin Identity：后续插件必须有稳定 `plugin_id`，hook handler、权限声明和日志都以它作为审计主键。

未来如果加入多用户或团队能力，必须先补 workspace owner/operator/viewer、secret provider 抽象、per-user policy overlay 和诊断导出授权记录。

## 6. 配置管理

配置来源优先级：

```text
命令行参数
  > 环境变量
  > .asteria/policies.json / project.json
  > 模板默认值
```

配置对象：

- `project.json`：项目元数据、语言/框架、默认验证命令、文档入口和工作区约束。
- `policies.json`：预算、权限、protected paths、模型路由、命令调用策略和 hook policy。
- 环境变量：模型 provider、base URL、API key、timeout/retry；真实 key 只能通过环境或 secret 注入。
- `PluginManifest`：插件声明，不直接授予权限，必须再受 policy 约束。

规则：

- `init` 可以创建缺失默认配置，但不能覆盖用户手写指导。
- `load_policy_config` 应迁移缺失默认 key，避免旧 workspace 因 schema 演进直接失效。
- 新增配置字段必须同步 schema、默认模板、文档和迁移策略。

## 7. Hooks

Hook 是运行时生命周期事件层，不是开放式插件执行层。

当前内置 hook：

```text
before_worker
after_worker
worker_error
before_tool_call
after_tool_call
tool_call_error
```

Hook policy 位于 `policies.json` 的 `hooks` 区域：

```json
{
  "enabled": true,
  "plugins_enabled": false,
  "allowed_hook_names": ["before_worker", "after_worker"],
  "redacted_data_keys": ["secret", "token", "api_key"],
  "handler_timeout_ms": 1000
}
```

约束：

- hook 事件必须写入 `runtime_hooks.jsonl` 并通过 schema 校验。
- hook 数据只能是小型结构化摘要，写入前必须脱敏。
- handler 失败只能记录 `runtime_hook_handler_failed`，默认不得破坏主执行。
- 外部 plugin handler 只有在 `plugins_enabled=true`、manifest enabled、订阅 hook 允许、权限声明通过后才能注册。

## 8. Skills

Skill 是面向模型和 agent 的能力包，用来描述“如何完成某类任务”。它更接近提示、工作流、模板、脚本和领域知识，不应默认拥有运行时权限。

边界：

- Skill 可以提供任务方法、上下文模板、检查清单、生成规范和本地脚本入口。
- Skill 不能绕过工具权限、protected paths、预算、网络策略或验证门禁。
- Skill 输出应转化为 task/action/verification/evidence，而不是直接修改 runtime 状态。

后续数据模型应补 `SkillManifest`、skill 选择证据和 skill 运行证据。

## 9. Plugins

Plugin 是 runtime 扩展单元，可能注册 hook handler、工具、source adapter、report adapter 或 provider adapter。插件比 skill 风险更高，因此必须先声明、后授权、再执行。

阶段划分：

1. Manifest 阶段：只读取 `.asteria/plugins/*.plugin.json`，校验 id、版本、订阅 hook、入口点、权限和能力，不执行代码。
2. Internal handler 阶段：只允许内置插件或测试插件注册 handler，用于验证 hook policy、超时、脱敏和审计。
3. Local plugin 阶段：允许本地插件执行，但必须有显式 policy、权限声明、超时、错误隔离和诊断记录。
4. Marketplace 阶段：公共分发、签名、版本兼容、禁用/回滚、权限审计和用户确认全部成熟后再考虑。

插件不能：

- 读取 secret 或 protected paths，除非用户显式授权。
- 注册未声明 hook。
- 悄悄执行 shell、网络、git push 或 deploy。
- 绕过 validator 修改 `.asteria/` schema 对象。
- 把外部日志、provider 原始响应或源码全文上传到网络。

## 10. MCP 体系

MCP 适合作为外部工具、知识源和应用连接器边界，但不应直接侵入核心执行循环。

推荐接入点：

- Source adapter：检索 issue、文档、代码托管、知识库、设计稿、日历等上下文。
- Tool adapter：把 MCP tool 映射为 Asteria ToolRegistry 中的受控工具。
- Evidence adapter：把外部系统结果转为 artifact、validation result 或 failure evidence。
- Report adapter：把运行报告导出到外部系统。

约束：

- 每个 MCP server 必须有 manifest、权限声明、网络边界、数据脱敏策略和失败隔离。
- MCP tool 调用必须经过 ToolExecutionGateway、预算、权限、日志和 schema 校验。
- MCP 不能成为读取 secret、绕过 protected paths 或上传未授权源码的后门。

## 11. 控制面与诊断

工程化控制面应覆盖：

- `doctor`：环境、配置、模型路由、sandbox、schema、gate evidence、hook/plugin policy 诊断（hooks.enabled、plugins_enabled、manifest blocked、redacted_data_keys、handler_timeout_ms）。
- `status`：当前 run、阻塞项、pending decisions、promotion risks、plugin control surface、下一步建议。
- `gate-status`：release/gray 阶段判断、验证建议和阻断原因；新增 `plugin_risks` 字段检查 blocked manifest，`threshold_reasons` 字段给出 promotion approve/reject/discard 指引，governance 文件变更自动升级验证推荐为 `full_gray_core`。
- `package-check`：安装包、schema、命令入口、hook/plugin 控制面、文档 runbook 前置检查；每个 check 自动映射 `error_type`。
- `capability-report`：模型、worker、工具、验证表现和 route guidance。
- `weekly-report`：跨 run 汇总、失败类型、修复建议。

诊断导出应包含版本、配置摘要、schema 状态、最近失败、事件摘要、hook 摘要、worker graph、promotion queue、成本报告和脱敏日志片段。

ErrorTaxonomy 已进入 doctor、package-check、gate-status 和 capability-report：每个 check 自动映射到 7 个分类（candidate_workspace、configuration、internal、plugin、promotion、provider、schema），给出用户可读解释、自动恢复策略、下一步操作和 release gate 影响。详细分类见 [数据模型.md](./数据模型.md) 的 ErrorTaxonomy 章节。
诊断导出应包含版本、配置摘要、schema 状态、最近失败、事件摘要、hook 摘要、worker graph、promotion queue、成本报告和脱敏日志片段。
