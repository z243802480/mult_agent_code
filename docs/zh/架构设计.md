# 多智能体自主开发系统 - 架构与技术方案

当前阶段和近期研发优先级见 [当前状态与路线.md](./当前状态与路线.md)。本文档描述架构原则和模块边界，不作为开发进度清单。

## 1. 架构原则

系统围绕 Asteria runtime 组织。智能体是可替换工作者，运行时是稳定控制平面。

核心原则：

- Runtime first, agents second。
- 编排优先于聊天：系统应是可验证的 Asteria Runtime OS，而不是无限制 Agent 聊天室。
- 大脑与双手解耦：Coordinator 负责规划、调度、预算、权限和验收，Worker 负责受控执行。
- AgentSpec 与 Session 分离：Agent 是静态角色模板，Session 是动态任务上下文。
- 启动时挂载运行环境：同一 AgentSpec 可以通过不同 RuntimeProfile 挂载不同模型、账号、工具权限、沙盒和上下文。
- Worker 可丢弃：执行单元可以失败、销毁、重建，长期状态必须落在 Store 和 ContextSnapshot 中。
- TaskGraph 优先于线性对话：长任务应由结构化任务图、依赖、验证门禁和修复边表达。
- 硬外壳，软内核：运行时强制安全、预算、权限、持久化、验证和回滚边界，但不把模型在任务内部的推理路径、代码组织、修复策略和工具调用顺序写死成大量业务规则。
- 稳定根上下文。
- 显式状态。
- 窄工具。
- 权限边界。
- 阶段门禁。
- 可恢复路径。
- 成本预算。
- 用户操盘。
- 根文件纪律。
- 模型供应商可替换。
- 每日自动化必须可暂停、可审计、可恢复。
- 可进化机制优先：系统必须通过能力画像、验收回归、失败记忆、规则退役和路线图更新持续吸收行业进步，而不是固化为一次性的规则集合。

长期架构北极星见 [Asteria 模型主导运行时设计.md](./Asteria%20模型主导运行时设计.md) 和 [大模型循环与动态上下文设计.md](./大模型循环与动态上下文设计.md)。旧的编排式重构过程计划已被吸收，不再作为当前实现依据。

### 2.0.1 模型驾驭原则：硬外壳，软内核

模型能力会快速迭代。运行时不应把今天为了弥补模型缺陷而写出的细碎业务补丁，变成明天限制强模型发挥的固定栅栏。

本项目的边界设计应区分两类约束：

- 不可协商边界：secret、protected paths、破坏性 shell、远程推送、部署、预算硬停、schema 校验、审计日志、验证门禁和用户决策点。这些由 runtime 强制执行，不能交给模型自觉。
- 可委托弹性：在 TaskContract 允许范围内，模型可以决定实现结构、搜索顺序、补丁策略、局部重构方式、失败诊断路径、验证补充和报告组织方式。runtime 只记录、校验、回滚和评估结果。

因此，`read_scope`、`write_scope`、`allowed_tools` 和 `parallel_safety` 不是为了把模型关进固定脚本，而是为了给模型划出一个可恢复、可审计、可并发调度的工作空间。边界应尽量表达风险和所有权，而不是替模型写死每一步业务判断。

后续实现时要避免两种极端：

- 放任模型直接接管文件系统、shell、网络和长期状态，导致不可审计和不可恢复。
- 用大量确定性业务代码替代模型判断，导致模型升级后旧补丁快速失效，系统变成昂贵但僵硬的规则引擎。

理想状态是：运行时像安全壳和实验台，模型像可升级的大脑。模型越聪明，越能在同一套边界内做出更好的计划、补丁、诊断和权衡；运行时不需要频繁重写业务补丁，只需要持续强化契约、证据、验证和恢复机制。

为了让这一原则可执行，后续开发必须优先建设机制，而不是只增加规则：

- 能力画像：用真实运行数据记录不同模型、profile、任务类型的成功率、成本和失败模式。
- 验收回归：所有重要架构调整都要有 acceptance scenario 证明结果一致性。
- 失败记忆：重复失败必须沉淀为 failure_lesson、修复任务或验收场景。
- 结构化扩权：模型需要更多 scope、context、tool、budget 或强模型时，应通过结构化请求交给 Coordinator 判断。
- 规则退役：为补模型短板写的复杂特判必须能被识别和删除，避免系统长期变成补丁堆。

## 2.1 产品生产控制平面

随着系统从后台工程进入可持续生产，运行时需要明确的控制平面。控制平面不是 dashboard 优先，而是让每天的自动运行可控、可审计、可恢复。

控制平面负责：

1. 维护项目目标、当前阶段、每日重点和禁止事项。
2. 根据任务状态、验收结果、预算和风险选择下一步动作。
3. 调度 Planner、Coder、Debugger、Reviewer、Release 等角色。
4. 选择模型路由策略，而不是把任务绑定到单一模型供应商。
5. 限制每日模型调用、修复轮次、运行时长和可修改范围。
6. 输出日报、阻塞原因、失败证据、推荐动作和次日计划。
7. 在达到风险或预算阈值时暂停并生成 DecisionPoint。

每日自动化的默认形态：

```text
读取昨日状态和当前目标
  -> 选择今日候选任务
  -> 检查预算和风险
  -> 执行一个或少量高价值任务
  -> 运行定向验收
  -> 失败则生成证据和修复计划
  -> 成功则更新报告和记忆
  -> 输出 daily report
  -> 等待下一次计划运行或人工确认
```

这一路径必须优先保证“少量高价值、可验证、可暂停”，不能为了自动化而长时间盲跑。

## 2.2 受控多 Worker 协作

Asteria 支持动态多 worker / 子智能体协作，但产品形态不是开放式 agent chatroom。所有协作必须落在 WorkerInvocation、TaskGraph、ContextMount、RuntimeProfile、MergeGate 和持久化 evidence 上，由 Coordinator 调度并由控制面解释。

Planner 负责根据任务复杂度和风险给出拆分策略：

- `serial_worker`：单文件或单写入范围的常规实现任务，默认串行执行。
- `readonly_fanout`：只读、诊断、调研、验证类任务，可小规模并行。
- `disjoint_write_workers`：多个明确独立写入文件，只有在 write scope 不冲突且 merge gate / promotion queue 可兜底时并发。
- `plan_then_serial`：高复杂度写任务，先要求 Planner 生成子计划，但执行层保持串行合并。

Coordinator 负责把策略落到执行边界：

- 只并发 `parallel_safety=readonly` 或 `parallel_safety=disjoint_writes` 的 ready task。
- 每个写入 worker 在独立 candidate workspace / git worktree 中执行，验证通过后才允许 promotion。
- 冲突写入、未知 write scope、预算接近硬停或 capability guidance 阻断时，必须降级为串行、阻塞或 DecisionPoint。
- 大规模 fanout 只允许用于只读、检索、候选资料生成、可丢弃草稿等低风险任务；上百/上千 worker 必须队列化、分片 context、限速、设置全局预算硬停并采样汇总，不能直接用于代码写入。

每次 run 会生成 `agent_run_graph.json`，作为多 worker 协作的结构化运行图。它记录 child worker plan、worker budget、context/profile 路由、协作角色、coordination modes、artifact / validation / failure refs、成本和汇总状态。`status`、`sessions --context`、final report、capability report 和 weekly report 应复用同一口径，避免不同控制面各说各话。

协作协议的长期目标：

1. 子 worker 产物互不污染。
2. ReviewAgent 汇总差异、冲突和可合并结果。
3. DebugAgent 可针对失败 child worker 重试、缩小 scope 或替换 route。
4. 最终由 merge gate / promotion queue 统一决定合并、拒绝、丢弃或等待人工审批。

## 3. 核心数据流

```text
用户目标或命令
  -> 命令路由器
  -> 根指导和记忆检索
  -> 编排器状态转换
  -> 智能体提示词组装
```

对于长任务，连续性的来源应该是稳定产物，而不是临时聊天历史。

## 4. 主运行循环

本节描述的是给大模型和专业智能体参考的角色工作骨架建议，也是 runtime 可审计、可恢复的外层协同模型策略，不是模型每一步行动的业务脚本。模型主导阶段的实际工作应由 PromptEnvelope、CapabilityManifest、ToolObservation、ContextEnvelope 和场景型 AgentLoopProfile 在权限、计费、schema、证据和验证边界内动态组织。这里的步骤用于角色协同、状态记录、恢复现场、触发验证和解释进度，不能被理解为把模型锁死在固定线性流程中。

```text
1. 接收用户目标。
2. 生成 GoalSpec。
3. 构建初始任务计划。
4. 选择输出策略。
5. 检测重大决策点。
6. 在需要时压缩上下文。
7. 准备工作区。
8. 分配就绪任务。
9. 智能体使用允许工具执行工作。
10. 运行时记录产物和事件。
11. 运行验证。
12. 通过则评审并保留。
13. 失败则触发自动纠错。
14. 修复失败则回滚或标记阻塞。
15. 更新记忆。
16. 持续运行，直到完成、预算耗尽或阻塞。
17. 生成最终报告。
```

## 5. 状态机

状态机是给大模型和专业智能体的角色工作骨架建议，也是持久化、审计、恢复和用户进展解释的协同模型策略。它负责说明 run 处于哪个风险/验证/交付阶段，但不替代模型在当前目标、上下文和能力清单内选择工具、修复路径、研究路径或子 worker 调度方式。需要强制执行的是权限、protected paths、计费/预算、schema、验证门禁和用户 DecisionPoint；具体实现路线应保留给模型和场景型 loop profile。

```text
INIT
  -> SPEC
  -> PLAN
  -> BRAINSTORM 可选
  -> DECIDE 可选
  -> RESEARCH 可选
  -> DESIGN
  -> IMPLEMENT
  -> VERIFY
  -> REVIEW
  -> REPAIR 可选
  -> KEEP_OR_DISCARD
  -> MEMORY_UPDATE
  -> REPORT
  -> DONE
```

## 6. 技术栈

第一版推荐 Python 实现运行时。

```text
语言：Python 3.11+
CLI：Typer
配置：Pydantic / pydantic-settings
Schema 校验：Pydantic model + JSON Schema 导出，或 jsonschema
存储：文件系统 + JSONL，后续补 SQLite
日志：标准 logging + JSONL，后续可加 structlog
测试：pytest
模型接口：OpenAI-compatible adapter
异步：第一版同步优先，后续引入 asyncio
```

理由：

- 主流、轻量、自主可控。
- 适合编排、文件处理、自动化和测试。
- 不被 LangChain/LangGraph 等重框架绑死。
- JSONL 和文件系统便于审计和调试。
- 后续可平滑迁移 SQLite、Web dashboard 和多 agent 并发。

## 9. 统一日志与模块通讯

日志、权限、用户/身份、配置、hooks、skills、plugins、MCP 和诊断控制面的完整横切规范见 [工程化体系.md](./工程化体系.md)。本节只保留运行时内部通讯和日志链路的架构摘要。

运行时内部模块之间应通过明确对象通讯，而不是散传无结构字典。

核心通讯对象：

- `RuntimeContext`：携带 root、run_id、policy、schema validator、event logger、budget controller。
- `ToolResult`：所有工具统一返回 `ok`、`summary`、`data`、`warnings`、`error`、`status`。
- `ToolRegistry`：所有工具调用统一入口。
- `RuntimeHookManager`：运行时生命周期 hook bus，负责把 worker/tool 等关键边界写入 `runtime_hooks.jsonl`，并为后续插件提供稳定接入点。

日志原则：

- 工具调用必须写入 `tool_calls.jsonl`。
- 关键运行事件必须写入 `events.jsonl`。
- worker、tool、后续 agent/plugin 的生命周期 hook 必须写入 `runtime_hooks.jsonl`。
- 模型调用必须写入 `model_calls.jsonl`。
- 成本信息必须进入 `cost_report.json`。
- 失败必须保留错误摘要，而不是只在控制台打印。

工具调用链路：

```text
Agent / Command
  -> ToolRegistry.call()
  -> BudgetController pre-check
  -> Tool.run()
  -> ToolResult
  -> tool_calls.jsonl
  -> events.jsonl
```

预算检查必须在工具执行前发生。权限检查必须在文件读取、文件写入、shell 执行等高风险操作前发生。

生命周期 hook 链路：

```text
ExecutionCoordinator / WorkerRunner / Gateway
  -> RuntimeHookManager.emit()
  -> runtime_hooks.jsonl
  -> events.jsonl(runtime_hook_emitted)
  -> in-process hook handlers
```

当前 hook 是运行时内部扩展点，不是 unrestricted plugin。默认语义是观测型：handler 失败会写入 `runtime_hook_handler_failed`，但不会破坏主运行。安全、预算、权限、merge gate 仍由已有 policy/gateway 强制执行。后续插件体系只能挂在这层之后，并遵守 schema、权限、预算和日志约束。

Hook policy 与插件声明：

```text
.asteria/policies.json
  -> hooks.enabled / hooks.allowed_hook_names / hooks.redacted_data_keys
  -> hooks.plugins_enabled / hooks.handler_timeout_ms

.asteria/plugins/*.json
  -> PluginManifest(schema validated)
  -> declared hook subscriptions
  -> declared permissions/capabilities
  -> loaded as metadata first, executable handlers later
```

插件体系分两阶段推进：

1. 声明阶段：只读取 `PluginManifest`，校验插件 id、版本、订阅 hook、权限声明和入口点，不执行插件代码。
2. 执行阶段：只有 policy 允许、manifest enabled、hook 订阅匹配且权限声明通过时，才允许注册 handler；handler 必须受超时、日志脱敏、错误隔离和审计记录约束。

日志脱敏是 hook 层默认责任。`RuntimeHookManager` 只能写入摘要、状态、id、参数 key 和经过 redaction 的小型结构化 data；包含 `secret`、`token`、`api_key`、`authorization`、`password` 等 key 的值必须被替换为 `<redacted>`。

Skills 与 MCP 的位置：

- Skill 是面向模型和 agent 的领域能力包，提供工作流、模板、检查清单和脚本入口，不直接获得运行时权限。
- Plugin 是 runtime 扩展单元，可能注册 hook handler、工具、source adapter、report adapter 或 provider adapter，必须先声明、后授权、再执行。
- MCP server/tool 作为外部系统连接器接入时，必须映射到 ToolRegistry 或 source/evidence/report adapter，并继续经过权限、预算、日志和 schema 校验。

这种设计保证：

- 排查问题时能看到每次工具调用输入摘要、输出摘要、状态和错误。
- 超预算工具不会先执行后报错。
- 工具失败不会以异常形式散落到上层，而是转换为结构化结果。
- 后续 agent 层可以稳定依赖统一工具协议。
- 多 worker / 多 agent 协作可以通过统一生命周期事件被审计、复盘和扩展，而不是散落在命令层硬编码里。

## 10. Workspace 策略

Asteria 是通用目标完成产品，不能假设所有任务都发生在当前终端目录或单一代码库。每次 Goal / Plan 都应先形成 Workspace Envelope：

```text
workspace_root
input_roots
output_root
candidate_workspace_policy
read_scope
write_scope
artifact_policy
git_policy
permission_mode
```

默认策略：

- 当前目录可以作为默认 workspace，但用户必须能切换到最近 workspace 或手动选择本地目录。
- Project / Workspace Switcher 是产品级入口：切换 workspace 后，session、run、文件预览、Git 状态、MCP/plugin/skills 配置视图都以该 workspace 为边界。
- 多工程任务可以挂载多个 input root，但每个 root 必须有独立 read/write scope。
- 报告、研究、生成型产物必须有明确 output root，不默认散落到项目根目录。
- 代码修改优先进入 candidate workspace、受控 patch 或 git worktree，验证通过后再 promotion。
- 只读分析任务可以使用 source workspace + output directory，不获得源码写入权限。
- 全自动模式也不能绕过 Workspace Envelope；模型可以自动推进，但不能静默扩大 read/write scope。
- 单工程的 run、session、产物、证据和 `.asteria/` 状态必须落在 workspace 目录下；用户 home 下的 `.asteria/` 只保存全局配置、最近 workspace 索引、模型本机 route、账号引用、UI 偏好和缓存。

MVP 后端可先支持：

- 一个主 workspace。
- 一个明确 output directory。
- 一个临时实现 workspace 或受控写入模式。
- 在保留/丢弃前检查 diff。

后续扩展：

- 每个智能体一个 Git worktree。
- 多工程 workspace graph。
- 全局 recent workspace / current workspace 索引。
- 合并队列。
- 冲突解决器。
- 容器隔离。
