# Asteria 产品与 Harness 架构

本文定义 Asteria 的产品架构和稳定边界。研发执行顺序以
[研发总计划.md](./研发总计划.md) 为准，当前事实以
[当前状态与路线.md](./当前状态与路线.md) 为准。

## 1. 愿景

Asteria 是本地优先的通用长任务 Agent Harness。连续 Session Agent Loop 是产品架构，
不是内部状态机或控制面板。

用户交给系统一个真实目标后，系统应在同一条连续会话中理解目标、使用工具、
修改或生成产物、验证结果、解释阻塞，并把一个可信且可继续工作的结果交还给用户。

用户关心的是：

- 系统正在替我做什么。
- 它实际调用了哪些工具、修改了什么、验证了什么。
- 结果是否可信，风险在哪里。
- 如果没有完成，为什么停下，怎样继续。

内部 route、gate、task state、schema 和 evidence 文件只服务于实现、查证和恢复，
不能取代用户任务进展成为产品主叙事。

## 2. 产品主路径

```text
用户目标或追问
  -> 模型理解目标，必要时给出简短计划或向用户提问
  -> 模型选择并调用本地工具或委派受控子 Agent
     （MCP 适配器与 Skill 发现已实现，但尚未接入模型循环，见 §7 与 §8）
  -> Runtime 在动作边界执行权限、沙箱、预算和持久化
  -> 工具结果回到同一 Session，模型继续判断下一步
  -> 模型验证产物并根据结果继续、修复、提问或停止
  -> 给出结果、验证、风险/下一步
  -> 用户在同一 Session 中继续
```

Plan、Review、Debug、Accept 是用户可理解的交互动作或模式，不是默认自动串联的
多套执行控制器。任务失败首先返回同一 Session，让模型结合观察继续判断；只有真实
动作风险、不可逆操作、权限边界或资源硬停才强制打断。

## 3. 六个稳定产品原语

### 3.1 Session

Session 是用户任务连续性的主对象，包含对话、工具过程、产物变化、验证、提问、
结果和恢复信息。Session 可以继续、恢复和分叉。

Run 是一次执行尝试，属于 Session 的实现记录；不能让用户为了继续任务先理解 run
状态机。

### 3.2 Agent Loop

主循环是开放的 `model -> action -> observation -> model`。模型负责语义判断和下一步
选择；Runtime 负责让动作可执行、可审计、可中断、可恢复。

循环可以产生工具调用、委派、提问、结果或停止，但不得要求每种自然语言行为都映射到
一套穷举业务状态。

### 3.3 Action Boundary

权限、受保护路径、破坏性命令、网络、外部目录、远程推送、部署、promotion 和预算
硬停必须在动作执行前判定。动作边界使用少量稳定结果：

```text
allow | ask | deny
```

风险规则约束动作，不替模型决定任务语义。Hook、permission 和 sandbox 是动作边界的
扩展方式，不是另一个任务编排器。

### 3.4 Evidence And Verification

工具调用、文件 diff、命令输出、测试结果、模型调用和子任务结果必须保留真实证据。
验证用于回答“结果是否成立”，不能用合成成功或缺失证据补齐成功链。

Studio 主会话展示用户可理解的过程摘要；Inspector 提供原始证据、diff、route、worker
和验证细节。

### 3.5 Context

上下文服务于当前模型判断，而不是把所有持久化对象塞进 prompt。上下文来源包括：

- 当前 Session 最近交互和必要摘要。
- 仓库级、目录级和用户级指导。
- 按需读取的文件、Skill 和外部能力说明。
- 子任务隔离上下文和返回摘要。

接近上下文上限时进行压缩或交接；压缩必须保留目标、已完成工作、关键证据、开放风险
和下一步。context breakdown 属于 Inspector 和评估数据，不占据主会话。

### 3.6 Scoped Delegation

子 Agent 是模型可按需调用的受控能力，不是固定角色流水线。每次委派应有明确目标、
允许工具、上下文边界、预算和返回结果。默认串行；只读或写入范围明确且有隔离、合并
证据时才允许并行。

## 4. Runtime 的责任与非责任

Runtime 必须负责：

- Session、Run、工具结果和真实证据的持久化。
- provider 抽象、流式响应、超时和可解释的降级。
- 工具注册、动作权限、沙箱和不可逆操作审批。
- 上下文装配、压缩和恢复。
- 子任务隔离、candidate workspace、diff 和 promotion。
- 验证执行、成本记录和产品评估。

Runtime 不应负责：

- 用固定阶段替模型选择语义上的下一步。
- 默认自动串联 Review、Debug、Replan 和 Repair 控制器。
- 为每种失败文本增加 keyword 分支或特殊状态。
- 用内部完整性 gate 判断用户任务是否“语义完成”。
- 把固定 Agent 类、TaskGraph 或状态机当作产品愿景。

内部可以保存 `running`、`waiting_for_user`、`completed` 等少量恢复状态，但它们只是
持久化字段，不是用户工作流，也不是模型思考脚本。

## 5. Studio 架构

Studio 是 Runtime evidence 的第一方客户端，不是第二套 Runtime。

主窗口是一条连续 Session transcript：

- 用户目标和追问。
- 简短计划或 Todo。
- 真实工具使用、修改和验证摘要。
- 权限请求、需要用户回答的问题和恢复提示。
- 最终的结果、验证、风险/下一步。

主窗口不得展示 route blocked、gate status、capability mismatch 等维护者词汇来代替
用户任务进展。

Inspector 是按需查证区：

- 文件 diff 和产物预览。
- 工具输入输出与验证详情。
- provider route、模型调用、context breakdown。
- 子任务、candidate workspace、merge/promotion evidence。
- 原始 run files 和只读诊断解释。

主会话事件应由 Runtime 生产侧天然表达用户任务进展。Studio 不通过穷举映射或猜测
内部事件来重建故事。

## 6. 恢复与显式动作

恢复优先复用当前 Session：

```text
工具失败或验证失败
  -> observation 返回当前模型循环
  -> 模型继续尝试、改变方法、询问用户或停止
```

用户可以显式选择：

- `continue/resume`：继续当前 Session。
- `review`：查验当前改动并给出反馈。
- `debug`：聚焦诊断，但不启动第二套隐藏修复编排器。
- `accept`：确认结果或执行受控 promotion。
- `fork`：从当前上下文建立独立探索。

Checkpoint、resume 和 fork 用于恢复与探索；失败不应默认触发另一个拥有独立任务、
决策和修复状态的控制器。

## 7. 分层边界

```text
CLI / Studio
  -> Session API / Command Router
  -> Agent Loop Harness
       -> Context Builder
       -> Model Provider
       -> Tool Gateway（本地工具；MCP/Skill 适配层已就绪但未接入循环）
       -> Scoped Delegation（受控子 Agent，已接入）
  -> Action Policy / Sandbox / Promotion
  -> Evidence / Verification / Evaluation
  -> Filesystem JSON/JSONL Store
```

- CLI / Studio：表达用户意图，展示连续过程和结果。
- Session API：维护连续会话、恢复和显式用户动作。
- Agent Loop Harness：把 observation 返回模型，直到结果、提问、打断或资源硬停。
- Gateway：本地工具的发现与调用，调用前经过动作边界。**MCP** 已实现 stdio JSON-RPC 适配器（`McpAdapter`，含 initialize/tools.call/超时重试，并有 gated 官方 server smoke），但**尚未接入模型循环**——没有 policy→adapter 装配、没有 execute 路径路由、模型面只有一个静态 `mcp` 占位 token；**Skill** 当前**仅发现**（`SkillDiscovery` 扫 `SKILL.md`，默认 `SkillManifestHandler` 只回显元数据、不执行）。二者都不在模型可直接调用的工具面里（受控子 Agent/Subagent 则已接入，见 §7 委派）。
- Evidence / Verification：保存真实过程并验证结果。
- Store：当前使用 `.asteria/` 下的 JSON/JSONL；存储格式可替换，不进入产品心智。

## 8. 参考产品机制基线

实现前必须阅读当前 Slice 的 reference brief，并优先复用成熟产品已证明的机制：

| 参考 | 应吸收的机制 | Asteria 约束 |
| --- | --- | --- |
| Claude Code | 连续 session、工具过程回到模型、分层项目指导、compact/resume、按需子 Agent、Pre/Post Tool hooks、动作权限 | 不复制专有实现；恢复留在同一 Session |
| Codex | 目标驱动工作、连续线程、工具与 diff 可见、审批与沙箱、AGENTS 分层指导、验证后交付、Inspector 查证 | 主会话讲用户任务，Inspector 查证内部证据 |
| OpenCode | session/client-server、plan/build 等可选模式、按工具和模式配置 permission、Task 调用子 Agent、Skill 按需发现 | 模式是能力配置，不是固定阶段流水线 |

详细调研与来源见
[S74 竞品机制与产品收敛基线](./plans/S74_REFERENCE_PRODUCT_BASELINE.md)。

## 9. 复杂度裁决

任何现有或新增机制必须回答：

1. 它解决了哪一个真实用户摩擦或安全边界？
2. Claude Code、Codex、OpenCode 或公开 Agent Harness 如何解决同类问题？
3. 它是否与 Session Agent Loop、动作边界或证据层重复责任？
4. 是否有真实任务和可观测指标证明收益？
5. 删除或替换它会损失哪一个已验证能力？

裁决结果只有：

```text
KEEP | REPLACE_IMPLEMENTATION | MERGE | FREEZE | DELETE
```

愿景可以保留，劣质实现不能因为代码量、历史成本或“自研特色”获得保护。

## 10. 当前收敛优先级

1. 删除或替换 Review / Repair / Debug / Goal policy 的重复恢复责任。
2. 让 Session Agent Loop 成为唯一默认语义推进路径。
3. 让 Studio transcript 只展示真实用户任务进展，Inspector 承载查证。
4. 统一 context 和 capability 的生产源，删除重复投影与报告耦合。
5. 用 3-5 个真实 Beta 任务校准延迟、成功率、恢复和用户体验。
6. 只有真实 friction 证明必要时，才扩大并行、编排、角色或 Studio 功能。

## 11. 技术基线

```text
语言：Python 3.11+
CLI：Typer
Schema：Pydantic / JSON Schema
存储：文件系统 + JSON/JSONL，必要时再引入 SQLite
Studio：本地 client/server，消费 Session transcript 和 evidence
测试：pytest
模型接口：多 provider adapter
```

技术选型服务于简单、可验证、可替换和本地优先。框架、状态字段和内部对象均不是产品
目标。
