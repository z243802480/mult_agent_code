# 设计情报吸收循环

本文定义 Asteria 在长任务研发中如何吸收成熟产品、开源系统、论文和工程实践。它不是面向普通用户的产品功能，而是 runtime 在需求进入、规划、架构、实现和复盘时使用的研发能力。

## 1. 目标

长任务不能只死扣用户的原始目标。Asteria 应该像一个小型研发团队，在执行前和执行中持续回答：

- 市面上成熟产品如何解决类似问题？
- 哪些设计可以借鉴，哪些不适合照搬？
- 哪些开源实现、论文、工程模式能降低风险？
- 这些发现如何转成任务、约束、验证和记忆？

这条能力的目标是让长任务具备外部设计吸收能力，避免技术路线封闭化。

## 2. 和现有 `/research` 的关系

当前 `/research` 已具备基础能力：

- 本地文档、URL、Serper 搜索 source adapter。
- `ResearchAgent` 综合来源。
- `research_report.json` / `research_report.md`。
- 带来源的 claims、expanded requirements、risks、decision candidates。
- `research_calls` 成本记录。
- `--type` 支持 `general`、`product_research`、`architecture_research`、`implementation_research`、`competitive_research`、`paper_research`、`open_source_research`、`risk_research`、`design_pattern_research`。

后续不另起炉灶，而是在这条链路上继续强化 `research_type` 的消费侧：让 research 不只服务论文或资料摘要，也服务产品研发、架构调研、实现选型、风险分析、任务约束和验证计划。

## 3. Research 类型

| 类型 | 使用时机 | 主要产物 |
| --- | --- | --- |
| `product_research` | 需要理解成熟产品交互、用户工作流、状态表达。 | product design brief、用户路径、可借鉴交互模式。 |
| `architecture_research` | 需要决定 runtime、sandbox、agent 编排、恢复机制。 | architecture brief、架构选项、权衡和风险。 |
| `implementation_research` | 需要选择库、API、开源实现或具体技术路径。 | implementation options、集成建议、验证命令。 |
| `competitive_research` | 需要比较 Claude Code、Cursor、Codex、Copilot、OpenHands 等系统。 | comparison matrix、差异化判断。 |
| `paper_research` | 需要吸收论文、benchmark、评测方法。 | source-grounded claims、实验假设。 |
| `open_source_research` | 需要学习开源项目结构、插件机制、sandbox 或 agent loop。 | reusable patterns、license/risk notes。 |
| `risk_research` | 需要识别权限、安全、成本、隐私、发布风险。 | risk register、mitigation、gate 建议。 |
| `design_pattern_research` | 需要沉淀可复用设计模式。 | pattern library entry、适配建议。 |

## 4. 标准输出

所有 research 类型都必须继续保留来源和可验证结论。新增类型可以扩展以下字段：

```json
{
  "research_type": "product_research",
  "design_brief": {
    "problem": "要解决的问题",
    "observed_patterns": [],
    "asteria_adaptation": [],
    "do_not_copy": [],
    "open_questions": []
  },
  "pattern_candidates": [
    {
      "name": "checkpoint rollback",
      "seen_in": ["Cursor"],
      "why_it_matters": "降低长任务失败后的用户焦虑",
      "asteria_adaptation": "映射到 run checkpoint、candidate workspace 和 restore action",
      "validation": "用真实小任务验证恢复点是否可解释"
    }
  ]
}
```

## 5. 研发接入点

Research 不应该变成每个任务的无条件前置步骤。建议使用以下触发策略：

- 用户目标模糊且属于产品/工具/系统设计。
- 大功能会影响架构、权限、恢复、并行或用户体验。
- Planner 发现多个技术路线且取舍会影响长期成本。
- review/debug 发现当前路线反复失败。
- roadmap 进入新阶段，例如 Studio MVP、真实 sandbox 并行、发布 beta。
- 新需求进入时涉及用户体验、产品边界、架构方向或长期路线。

触发后，research 输出应进入：

- `research_report.json` / `research_report.md`
- task plan 的约束和验证策略
- DecisionPoint 候选项
- 项目 memory 或 pattern library
- 后续 roadmap / weekly report

## 5.1 需求进入闸门

> **现状说明（勿误读为已接线）**：本节是**设计准则 / 研发流程约定**，尚未接入默认 `RequirementPlanner`——代码里没有 `ProductAgent` 类，planner 也不消费 `design_brief` / `pattern_candidates`（研究产物经 `design_intel_research_bridge` 进上下文，但 intake gate 的自动判定属 §7「下一步」）。当前由开发者 / 智能体在 Plan 与研发流程中**手动遵循**。

当用户提出新功能、产品体验、路线规划或大范围改造时，Planner / ProductAgent（**目标形态，待接线**）应先判断是否需要外部产品参考：

- 小型修复、明确文档更新、窄范围测试补充：默认不触发联网调研，可只读取本地文档和当前 evidence。
- 产品/Studio/交互/架构/长期路线需求：优先触发 `product_research`、`competitive_research`、`architecture_research` 或等价的显式 URL / 本地资料审阅。
- 进入 task plan 前，必须把参考结论转成 Asteria 自己的 requirement、non-goal、DecisionPoint、validation task 或 doc update。
- 如果网络、成本或隐私策略不允许外部调研，应记录 DecisionPoint 或明确使用本地公开资料缓存；不能假装已经参考了公开产品。

需求进入后的最小产物：

- `design_brief.observed_patterns`：公开产品或开源系统中的稳定模式。
- `design_brief.asteria_adaptation`：Asteria 如何吸收为自己的运行时、证据、体验或验证约束。
- `design_brief.do_not_copy`：不照搬的界面、术语、商业策略或专有实现。
- `pattern_candidates[].validation`：至少一个可验证任务或验收信号。

## 6. 成熟产品参考边界

Asteria 可以学习成熟产品的设计思想，但不复制专有实现，不把对方产品术语直接暴露给用户。

公开参考入口：

- Claude Code subagents 文档：https://code.claude.com/docs/en/sub-agents
- Cursor 文档入口：https://cursor.com/docs
- OpenAI Codex 文档入口：https://developers.openai.com/codex/
- GitHub Copilot cloud agent 文档：https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent

重点参考方向：

- Claude Code：subagent 的独立 context window、工具限制、权限模式、memory 和按任务委派。
- Cursor：background agents 的异步远程执行、状态跟进、handoff，以及 checkpoint / restore 的用户可回滚状态。
- OpenAI Codex：sandboxing、subagents、workflows、permissions、worktrees、results/state 和 evals 等运行时组织方式。
- GitHub Copilot cloud agent：repository research、implementation plan、branch / pull request 边界、ephemeral environment、测试/linters 和任务时间边界。
- OpenHands / SWE-agent：开源 agent loop、任务评测和工具边界。

吸收原则：

- 学流程，不抄界面。
- 学边界，不抄品牌概念。
- 学风险控制，不降低本地优先和可审计性。
- 所有外部启发都要转成 Asteria 自己的 artifact、gate、validation 和 memory。

## 7. 下一步接入

`research --type`、schema、agent synthesis 和命令文档已具备基础实现。下一步不是继续扩展类型数量，而是把 research 结果更稳定地接入需求进入和计划执行：

1. Plan/Run 在需求进入时识别是否需要 product / competitive / architecture research。
2. Task plan 消费 `design_brief` 和 `pattern_candidates`，生成明确约束、non-goals、验证任务和 DecisionPoint。
3. final report 说明哪些需求来自用户原始目标，哪些来自公开产品参考，哪些被暂缓。
4. 文档和 memory 只沉淀可复用设计模式，不把一次性资料摘要堆入长期上下文。
