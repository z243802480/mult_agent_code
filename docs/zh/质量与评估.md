# 多智能体自主开发系统 - 质量、评估与测试

## 1. 文档目的

本文档定义系统如何判断“任务完成得好不好”，以及如何测试这套 Asteria runtime。

工程治理层的 ADR/RFC、schema 兼容、迁移、错误分类、feature flag、golden trace、发布分级和威胁模型规范见 [工程治理体系.md](./工程治理体系.md)。本文聚焦测试、验收、质量指标和评估方法。

系统不能只依赖模型自评。评估体系必须结合：

- 结构化验收条件。
- 自动测试。
- 运行结果。
- 代码和产物评审。
- 用户决策。
- 成本和轨迹评估。

## 2. 评估分层

```text
Goal Eval：目标是否被正确理解和扩展
Workspace Eval：输入、输出、session、run 和 evidence 是否落在正确 Workspace 边界内
Artifact Eval：产物是否存在、可运行、可阅读
Outcome Eval：最终结果是否满足目标
Trajectory Eval：执行过程是否健康、经济、可恢复，且用户侧能看见关键判断、工具调用和验证进展
Permission Eval：权限模式是否符合用户选择，高风险操作是否被护栏拦截或升级
Cost Eval：成本是否适度且有效
```

> 实现现状（勿把愿景当现态）：**确定性 EvalReport 实为 5 层**——Goal / Artifact / Outcome / Trajectory / Cost。**Workspace 与 Permission 不是 EvalReport 子对象**，而是在**动作边界**强制（PathGuard / 权限硬护栏 / merge gate / promotion queue，见 ADR-0013）；本节把它们并列为"评估视角"仅作概念归类。
>
> 下文各 `>=` 阈值多为**目标 / aspirational**，并非运行时强制的验收闸门。真正被确定性计算的只有少数几项（如 `requirement_coverage`、`verification_pass_rate`、`command_verification_pass_rate`、`blocked_task_count`、`run_success`、模型/工具计数与 `status`）；其余模型打分项（`goal_clarity_score`、`definition_of_done_score`、`documentation_score`、`safety_score`、usability、轨迹/决策类指标）是 **model-optional、schema 未约束**（`eval_report` 对应子对象声明为裸 `{type:object}`）、**不校验、不作硬 gate**。唯一完整落地并被强制的是 §9.1 任务计划质量（`TaskPlanEvaluator`）。

## 3. Goal Eval

指标：

- `goal_clarity_score`
- `requirement_expansion_score`
- `assumption_quality_score`
- `definition_of_done_score`
- `decision_point_quality_score`

最低验收：

```text
goal_clarity_score >= 0.75
definition_of_done_score >= 0.75
```

## 4. Artifact Eval

检查：

- 产物是否写入当前 Workspace 的目标输出范围，而不是写入安装目录、全局用户配置目录或其他项目目录。
- 是否生成目标规格。
- 是否生成任务计划。
- 是否生成任务计划质量评估。
- 是否生成运行日志。
- 是否生成代码或报告等目标产物。
- 是否生成最终报告。
- 是否记录工具调用。
- 是否记录成本摘要。

失败条件：

- 只生成聊天摘要，没有文件产物。
- 修改文件但没有记录原因。
- 把项目产物、run evidence 或 session 状态写入全局用户目录。
- 没有最终报告。

## 4.1 Workspace Eval

检查：

- `--root` / selected workspace 是否决定本次 session、run、evidence、artifact 和 Git 操作边界。
- Workspace 内的 `.asteria/` 是否保存项目级运行态，全局用户目录是否只保存 recent/current workspace、模型路由、账号引用、UI 偏好和缓存。
- 多 Workspace 切换后，任务列表、session、文件预览、Git 状态、MCP/plugin/skill 配置是否按 Workspace 隔离。

失败条件：

- 一个 Workspace 的 session、run evidence 或产物出现在另一个 Workspace。
- 为了运行项目任务读取或写入全局 route/key/account 文件。
- Studio 或 CLI 只记住产品安装目录，没有让用户选择目标 Workspace 和输出位置。

## 5. Outcome Eval

通用指标：

- `requirement_coverage`
- `verification_pass_rate`
- `usability_score`
- `documentation_score`
- `safety_score`
- `run_success`

建议最低验收：

```text
requirement_coverage >= 0.70
verification_pass_rate >= 0.80
documentation_score >= 0.60
safety_score >= 0.80
```

## 6. Trajectory Eval

指标：

- `loop_count`
- `repair_success_rate`
- `tool_relevance_score`
- `scope_drift_score`
- `decision_noise_score`
- `cost_efficiency_score`
- `rollback_correctness`
- `user_progress_visibility_score`
- `workspace_boundary_correctness`
- `permission_mode_correctness`

危险信号：

- 反复修改同一文件但没有验证改善。
- 绕过测试。
- 频繁扩大范围。
- 不断调用模型但没有产物。
- 用户侧看不到模型判断、接口调用、工具调用、文件变化、验证进度或最终整理，只能看到后台日志。
- `ask_everything` 模式下绕过询问，或 `reviewed_auto` 模式下把高风险操作静默通过。
- `auto` 模式下越过 protected paths、破坏性 shell、远程 push、生产部署、预算 hard-stop 或 Workspace 边界。
- 频繁询问用户小问题，说明默认策略没有利用低风险自动通过能力。
- 出现高风险操作但没有决策点或等价的 runtime policy evidence。

## 7. Cost Eval

指标：

- 模型调用次数。
- 估算 token。
- 工具调用次数。
- 运行时间。
- 每个任务平均成本。
- 每个成功 patch 成本。
- 无产物调用比例。

这些指标分为两类：

- **产品 SLO / 回归指标**：按任务类型比较成功率、P50/P90、调用量、repair 和成本；超过目标触发分析，不直接判定复杂任务失败。
- **资源保险丝**：由用户或运行策略配置，用于防止无限运行；触发后必须保留状态并允许 resume。

不得把统一低 model-call 或 repair 数量作为所有任务的 Runtime 完成门槛。provider retry、schema retry 和任务 repair 必须分开归因。

资源保险丝默认值：

```yaml
max_model_calls_per_goal_mvp: 60
max_tool_calls_per_goal_mvp: 120
max_repair_attempts_per_task: 2
max_no_artifact_model_call_ratio: 0.25
```

其中 `max_repair_attempts_per_task` 是旧兼容保险丝，不代表产品质量目标。后续停止判断优先使用“是否持续获得新 observation / artifact / verification evidence”的 no-progress 检测；修改该兼容值必须通过 DecisionPoint 和真实任务 eval。

> **接线现状（诚实标注）**：`max_repair_attempts_per_task` 目前只被 `run_command` 间接消费——据它派生 recovery
> inner-cycle 上限（`max_inner_cycles = max(3, min(iterations, replans+repairs+1))`）；真正生效的修复上界是这个
> 派生 cycle 上限 + 上述 no-progress 检测，而非 `BudgetController` 的逐次修复计数。`max_repair_attempts_total`
> 当前**未接线**：`BudgetController.record_repair_attempt()` 全仓库无生产调用者，该预算永不触发。唯一逻辑正确的
> 接线点是 `execute_command.py` 的 repair 派发分支（DO_NOT_TOUCH），且会改控制流（超限 `raise BudgetExceededError`），
> 属逻辑改动而非“追加 user_progress”，因此真接线须先经 DecisionPoint 解锁该文件的 DO_NOT_TOUCH 例外，不在默认范围内。

## 8. 用户决策评估

指标：

- `critical_decision_recall`
- `minor_question_rate`
- `decision_packet_quality`

一个合格决策包必须包含：

- 问题。
- 推荐。
- 选项。
- 取舍。
- 默认行为。
- 影响说明。

## 9. 自迭代评估

系统必须证明自己不是一步执行器。

指标：

- 是否发现缺失需求。
- 是否创建后续任务。
- 是否基于验证结果调整计划。
- 是否在达到可用基线后停止。

失败条件：

- 用户说“密码测试工具”，系统只做一个输入框评分。
- 没有评估“是否好用”。
- 没有基于评审创建改进任务。

## 9.1 任务拆解质量评估

`/plan` 必须产出 `task_plan_eval.json`，用于在执行前评估任务计划是否适合 agent 自动执行。

评估维度：

- 任务颗粒度：不能把多个核心需求压成一个不可验收的大任务，也不能拆成大量无意义小任务。
- 依赖关系：必须有 ready 入口，`depends_on` 只能引用存在的任务，不能自依赖。
- 验收标准：每个任务需要有可观察、可验证的 acceptance。
- 产物明确性：实现、UI、报告类任务需要明确 `expected_artifacts`。
- 工具覆盖：实现任务需要写入工具，要求验证的任务需要测试或命令工具。

门禁建议：

```text
pass: 可直接进入 execute
warn: 可以执行，但应在 review 中关注 warnings
fail: 不应直接执行，应先 replan 或创建 DecisionPoint
```

## 10. 验收分级

### Pass

- 核心需求满足。
- 验证大部分通过。
- 成本在预算内。
- 风险已说明。
- 有最终报告。

### Partial

- 主要产物存在。
- 有部分需求未覆盖。
- 有失败但已解释。
- 可以进入下一轮迭代。

### Fail

- 无可用产物。
- 目标理解错误。
- 验证完全缺失。
- 产物不可运行且未说明。
- 成本失控。

- 成功路径。
- 失败路径。
- 权限拒绝。
- 日志记录。
- 输出结构。
- 超时。

## 15. 命令工作流测试

必须覆盖：

- `/init`
- `/plan`
- `/brainstorm`
- `/compact`
- `/debug`
- `/review`
- `/handoff`

## 16. Agent Loop 测试

测试闭环：

```text
goal
  -> plan
  -> implement
  -> verify
  -> repair
  -> review
  -> report
```

必须覆盖：

- 正常完成。
- 验证失败后修复成功。
- 修复失败后停止。
- 用户决策后继续。
- 上下文压缩后继续。
- 成本接近阈值后降级。

## 17. 端到端场景

### 17.1 密码测试工具

期望：

- 自动扩展需求。
- 识别隐私和安全边界。
- 生成可运行工具。
- 有基础测试。
- 有最终报告。

### 17.2 Markdown 知识库

期望：

- 生成导入、索引、搜索、问答任务。
- 输出合适 UI 形态建议。
- 至少实现 MVP 子集。

### 17.3 批量文件重命名工具

期望：

- 形成 CLI/桌面/Web 决策点。
- 默认保护文件安全。
- 支持预览再执行。

### 17.4 修复已有项目

期望：

- 自动运行测试。
- 定位失败。
- 尝试最小修复。
- 通过后生成 diff 和报告。

### 17.5 上下文长任务续航

期望：

- 压缩后不丢失目标、任务、决策。
- 后续阶段能继续。

## 18. 回归基准集

```text
benchmarks/
  password_tool/
  markdown_kb/
  file_renamer/
  failing_tests_project/
  long_context_project/
```

每个 benchmark 包含：

- 输入目标。
- 初始文件。
- 期望产物。
- 验收脚本。
- 预算限制。
- 预期报告片段。

### 18.1 可靠基线运行方式

- 固定 provider、模型、workspace 初态、权限配置和验证命令。
- 关键 case 每种候选策略至少重复运行 3 次。
- 先判断 artifact、verification、安全和 workspace 边界，再比较效率。
- 比较成功率、P50/P90 耗时、首次有效动作、model/tool calls、provider/schema/task repair、成本和用户进展一致性。
- 保存完整 trace，用于区分模型决策、工具、provider、验证和产品展示问题。
- 新策略必须与当前默认路径做配对对比；单次成功或失败不得直接改变默认策略。
- 从真实用户和生产 friction 持续补充 Golden Tasks，避免只优化维护者自测样本。

## 19. 模型不稳定性测试策略

不比较完整自然语言输出。优先使用：

- Schema 校验。
- 关键字段检查。
- 产物存在检查。
- 命令退出码。
- 测试通过率。
- 语义评分。
- 稳定部分的快照测试。

真实模型专项检查：

- `model-check` 验证 provider 配置、端点、认证和基础 JSON 响应。
- 端到端 smoke 使用临时目录，检查目标产物、session 日志和最终报告。
- `asteria acceptance` 必须持久化 `acceptance_report.json`，让验收通过/失败都可被后续 runtime 读取。
- `asteria acceptance --promote-failures` 必须把失败场景转换为当前 session 的可执行修复任务，并避免重复生成同一场景任务。
- 新 promoted failure 必须记录为 `failure_lesson` memory，避免真实模型失败经验只存在于一次性日志里。
- `asteria acceptance --run-promoted` 必须是显式开关；默认不得自动触发真实模型执行成本。
- 必须覆盖 `acceptance` 失败、promote、memory、run-promoted、final report 的离线闭环集成测试。
- `asteria acceptance --rerun-promoted` 必须只复验本次新 promoted 的失败场景，并记录 closed/remaining 结果。
- 结构化输出测试覆盖 `<think>`、markdown code fence、近似 JSON、字段别名和少量 schema drift。
- 无法安全归一化的输出必须被阻塞或进入修复流程，不能静默当作成功。
- 验证命令归一化集中在 `verification_command_normalizer.py`；只改写已知低风险测试夹具命令，不可证明安全的命令必须保持原样交给 shell policy 拦截。
- 网络超时、TLS EOF、429/5xx 等链路抖动通过有限重试验证，不能无限重试。

## 20. MVP 测试完成定义

最低条件：

- `/init` 测试通过。
- `/plan` 测试通过。
- `/compact` 测试通过。
- 至少 2 个端到端场景通过。
- 成本阈值测试通过。
- 安全权限测试通过。
- 失败修复测试至少一个通过。
