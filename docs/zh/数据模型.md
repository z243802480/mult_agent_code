# 多智能体自主开发系统 - 数据模型

## 1. 文档目的

本文档定义系统核心数据对象、状态枚举、文件落盘位置和 schema 约定。

目标：

- 让运行时、命令、智能体、工具和评估系统共享同一套结构化语言。
- 减少靠自然语言传递状态造成的歧义。
- 支持长任务续航、上下文压缩、任务恢复和审计。
- 为后续代码实现提供直接的数据结构依据。

## 2. 通用约定

### 2.1 Schema 版本

每个持久化对象必须包含：

```json
{
  "schema_version": "0.1.0"
}
```

版本规则：

- patch：字段说明、非破坏性默认值调整。
- minor：新增可选字段。
- major：字段删除、字段含义改变或结构破坏性变更。

### 2.2 ID 约定

推荐 ID 格式：

```text
run-20260427-0001
goal-0001
task-0001
decision-0001
exp-0001
artifact-0001
event-0001
agent-0001
toolcall-0001
memory-0001
```

ID 应在单个项目内唯一。

### 2.3 时间格式

所有时间使用 ISO 8601：

```text
2026-04-27T14:30:00+08:00
```

### 2.4 状态字段

状态字段必须使用枚举，不使用自由文本。

自由文本应放到：

- `summary`
- `reason`
- `notes`
- `description`

### 2.5 文件路径

路径使用项目根目录相对路径：

```json
{
  "path": "src/main.py"
}
```

禁止在持久化对象中默认写入机器相关绝对路径，除非对象是本机运行日志。

## 6. Session 与 Run

`Session` 是面向用户的上下文单位：一个目标、一组任务、一段可恢复的工作会话。

`Run` 是内部执行记录：当前 MVP 中一个 session 映射到一个 `.asteria/runs/<run_id>/`
目录。为了兼容已有日志和 schema，内部字段仍使用 `run_id`；用户命令和文档使用
`session_id` 表达要恢复或切换的上下文。

当前 session 指针文件：

```text
.asteria/current_session.json
```

旧的 `.asteria/current_run.json` 只作为兼容读取入口；新的运行时写入
`.asteria/current_session.json`。

```json
{
  "schema_version": "0.1.0",
  "session_id": "run-20260427-0001",
  "set_at": "2026-04-27T14:30:00+08:00",
  "reason": "plan_created"
}
```

## 10. TaskPlanEval

文件：

```text
.asteria/runs/<run_id>/task_plan_eval.json
```

用途：

记录整张任务计划的确定性质量评估，避免 PlannerAgent 生成“看起来有任务、实际不可执行或不可验收”的计划。

```json
{
  "schema_version": "0.1.0",
  "run_id": "run-20260427-0001",
  "created_at": "2026-04-27T14:30:00+08:00",
  "status": "pass",
  "overall_score": 0.92,
  "scores": {
    "granularity_score": 0.9,
    "dependency_score": 1.0,
    "acceptance_score": 0.9,
    "artifact_score": 0.9,
    "tooling_score": 0.9
  },
  "summary": "Task plan quality pass with score 0.92; 0 error(s), 1 warning(s).",
  "issues": [],
  "recommendations": [],
  "task_count": 4
}
```

评估维度：

- 任务颗粒度是否适中。
- 是否有明确 ready 入口。
- `depends_on` 是否引用有效任务。
- `acceptance` 是否可观察、可验证。
- `expected_artifacts` 是否足够具体。
- `allowed_tools` 是否支持任务真实执行和验证。

枚举：

```text
task_plan_eval.status:
  pass
  warn
  fail

task_plan_eval.issues[].severity:
  warning
  error
```

`fail` 代表当前计划不应直接进入 `/execute`，应优先重规划或创建决策点。

## 11.1 RuntimeProfile

用途：

描述一次 Worker 启动时挂载的运行环境。RuntimeProfile 可以由多个子 profile 组成，让同一个 AgentSpec 在不同任务中使用不同模型、权限、账号和上下文。

```json
{
  "schema_version": "0.1.0",
  "runtime_profile_id": "runtime-profile-0001",
  "agent_id": "agent-0001",
  "model_profile_id": "model-profile-0001",
  "tool_permission_profile_id": "tool-profile-0001",
  "account_profile_id": "account-profile-0001",
  "sandbox_profile_id": "sandbox-profile-0001",
  "context_mount_id": "context-mount-0001",
  "budget": {
    "max_model_calls": 3,
    "max_tool_calls": 20,
    "max_runtime_minutes": 10
  }
}
```

原则：

- profile 保存配置和引用，不保存 secret 明文。
- 模型选择、账号权限、工具权限和沙盒策略应可独立替换。
- Coordinator 根据任务类型、风险、成本和模型能力画像选择 RuntimeProfile。

## 11.2 ModelProfile

用途：

定义 Worker 本次执行使用的模型供应商、模型名、模型层级和用途。

```json
{
  "schema_version": "0.1.0",
  "model_profile_id": "model-profile-0001",
  "purpose": "coding",
  "provider": "openai_compatible",
  "model_name": "example-coder-model",
  "model_tier": "medium",
  "fallback_profile_ids": ["model-profile-cheap-0001"],
  "limits": {
    "max_input_tokens": 24000,
    "max_output_tokens": 4000
  }
}
```

## 11.3 ToolPermissionProfile

用途：

定义 Worker 本次执行可以使用哪些工具，以及读写范围。

```json
{
  "schema_version": "0.1.0",
  "tool_permission_profile_id": "tool-profile-0001",
  "allowed_tools": ["read_file", "search_code", "apply_patch", "run_tests"],
  "read_scope": ["src/", "tests/", "docs/"],
  "write_scope": ["src/asteria_runtime/", "tests/"],
  "allow_network": false,
  "allow_shell": true,
  "allow_destructive_shell": false
}
```

设计说明：

- `ToolPermissionProfile` 是运行时硬外壳的一部分，用来约束风险、所有权和可并发调度边界。
- 它不应被滥用成业务流程脚本。profile 应回答“Worker 可以在哪里读写、能用哪些工具、哪些风险被禁止”，而不是回答“模型必须按哪些固定步骤完成任务”。
- 如果模型判断当前权限或 scope 不足，应通过结构化请求让 Coordinator 扩展 scope、补充 context 或创建 DecisionPoint，不能静默越界。
- 随着模型能力提升，profile 的目标应保持稳定：保护系统和用户，而不是替代模型推理。

## 11.4 AccountProfile

用途：

定义 Worker 可使用的账号或凭据引用。该对象只能保存引用，不能保存 secret 明文。

```json
{
  "schema_version": "0.1.0",
  "account_profile_id": "account-profile-0001",
  "provider": "openai_compatible",
  "credential_ref": "AGENT_MODEL_API_KEY",
  "permission_tier": "standard",
  "rate_limit_hint": {
    "requests_per_minute": 60
  }
}
```

## 11.6 PromptEnvelope 与 CapabilityManifest

文件：

```text
.asteria/runs/<run_id>/prompt_envelope.json
.asteria/runs/<run_id>/prompt_envelope_execute.json
.asteria/runs/<run_id>/prompt_envelope_debug.json
.asteria/runs/<run_id>/prompt_envelope_review.json
```

用途：

把模型工作循环看到的系统提示词和能力边界固化为可审计对象。`plan`、`execute`、`debug`、`review` 都必须生成同一结构的 PromptEnvelope；`plan` 保留兼容文件名 `prompt_envelope.json`，其他 mode 使用带后缀的文件名。Prompt evidence 默认只保存 section 摘要、hash、token 估算和证据引用，不保存完整 prompt body，避免 protected path 或 secret 内容被复制进运行证据。

```json
{
  "schema_version": "0.1.0",
  "run_id": "run-20260427-0001",
  "mode": "plan",
  "section_order": [
    "identity",
    "operating_contract",
    "project_guidance",
    "capability_manifest",
    "tool_policy",
    "safety_envelope",
    "failure_repair",
    "delegation_contract",
    "context_compaction",
    "user_communication"
  ],
  "sections": [
    {
      "name": "project_guidance",
      "source": "AGENTS.md",
      "priority": "project",
      "cache_scope": "workspace",
      "token_estimate": 1200,
      "content_hash": "sha256:...",
      "summary": "Project rules and boundaries...",
      "evidence_refs": ["AGENTS.md"],
      "cache_break_reasons": ["workspace_guidance_changed"]
    }
  ],
  "capability_manifest": {
    "modes": ["plan", "build", "review", "repair", "release"],
    "direct_tools": [],
    "deferred_tools": [],
    "mcp_tools": [],
    "skills": [],
    "subagents": [],
    "verification": [],
    "boundaries": {
      "protected_paths": [".env", "secrets/"],
      "shell": "deny",
      "destructive_shell": "deny",
      "budget": "runtime_enforced"
    }
  },
  "content_hash": "sha256:..."
}
```

CapabilityManifest 面向模型展示能力和边界，面向 Runtime 保留强制执行字段。每个能力项至少包含：

```text
name
kind
permission_state
sandbox_profile
read_scope
write_scope
cost_tier
observation_schema
```

分层：

```text
direct_tools       当前模型循环可直接计划使用的读、搜、改、执行类工具
deferred_tools     需要先发现或装载的延迟能力
mcp_tools          经过 runtime policy、预算、schema、日志门禁的 MCP adapter
skills             领域工作流、模板和参考资料
subagents          有 delegation brief、scope、权限和验证预期的子 worker
verification       run_tests、review_agent、merge_gate 等独立验证能力
```

## 11.8 WorkerInvocation

文件：

```text
.asteria/runs/<run_id>/workers.jsonl
```

用途：

记录 Coordinator 启动一次 Worker 的完整挂载信息。

```json
{
  "schema_version": "0.1.0",
  "worker_invocation_id": "worker-0001",
  "run_id": "run-20260427-0001",
  "task_id": "task-0001",
  "agent_id": "agent-0001",
  "runtime_profile_id": "runtime-profile-0001",
  "status": "running",
  "started_at": "2026-04-27T14:30:00+08:00",
  "ended_at": null,
  "summary": "Run CoderAgent for task-0001 with controlled patch workspace.",
  "delegation_brief": {
    "goal": "实现 task-0001 的可验证改动",
    "why": "该任务来自当前 TaskGraph 的 ready 节点",
    "known_context": {
      "task_id": "task-0001",
      "acceptance": ["目标行为可验证"],
      "read_scope": ["src/", "tests/"]
    },
    "constraints": {
      "allowed_tools": ["read_file", "apply_patch", "run_tests"],
      "parallel_safety": "serial",
      "merge_strategy": "candidate_workspace"
    },
    "allowed_writes": ["src/", "tests/"],
    "expected_output": {

    }
  },

    "status": "pass",

  }
```

枚举：

```text

  queued
  running
  succeeded
  failed
  denied
  timeout
```

- hook 必须通过 `RuntimeHookManager` 写入，不能由命令层临时拼 JSONL。
- hook handler 默认为观测型，失败只写入 `runtime_hook_handler_failed`，不应破坏主执行。
- hook 数据只记录摘要、id、状态和参数 key，不能写入 secret 或大段原始上下文。
- hook 写入前必须应用 policy 中的 `redacted_data_keys`，敏感 key 的值统一替换为 `<redacted>`。
- 插件体系后续只能在该生命周期层上扩展，并继续受 runtime policy、预算、schema 和 protected paths 约束。

## 25. PluginManifest

文件：

```text
.asteria/plugins/<plugin-id>.plugin.json
```

用途：

声明插件元数据、订阅的 hook、权限需求和入口点。当前阶段只校验和加载声明，不执行外部插件代码。这样插件体系可以先形成可审计控制面，再逐步开放 handler 执行。

```json
{
  "schema_version": "0.1.0",
  "plugin_id": "example.audit",
  "name": "Example Audit Plugin",
  "version": "0.1.0",
  "enabled": false,
  "entrypoint": "plugins/example_audit.py",
  "hook_subscriptions": ["after_tool_call", "worker_error"],
  "permissions": {
    "network": false,
    "shell": false,
    "write_workspace": false,
    "read_secrets": false
  },
  "capabilities": ["audit-log"],
  "description": "Records additional audit metadata for selected hooks."
}
```

约束：

- `plugin_id` 必须稳定，后续日志和报告以它作为审计主键。
- `hook_subscriptions` 只能包含 HookPolicy 允许的 hook name。
- `enabled=false` 或 `hooks.plugins_enabled=false` 时，manifest 可以被读取，但不得注册 executable handler。
- `entrypoint` 是声明字段，不代表当前阶段会 import 或执行该文件。
- 插件权限必须显式声明；默认没有 network、shell、workspace write、secret read。


## 25.5 ErrorTaxonomy

用途：

统一 runtime 阻塞分类。`doctor`、`package-check`、`gate-status` 和 `capability-report` 的每个 check 都会映射到 `error_type`，用户不再只看到 traceback 或模糊 blocked，而是看到结构化的错误分类、恢复策略和下一步操作。

当前分类（7 类）：

```text
candidate_workspace  候选工作区创建、隔离、promotion 失败
configuration        配置缺失、schema 不一致、版本不同步
internal             内部运行时错误、未分类异常
plugin               插件 manifest blocked、hook 订阅非法、schema missing
promotion            candidate promotion queue 阻塞、审批未决
provider             模型路由不可用、gate 报告缺失、provider 响应异常
schema               持久化对象 schema 校验失败、版本不兼容
```

每个分类包含：

```text
error_type       分类标识
user_summary     用户可读的一句话解释
auto_recovery    系统可能自动恢复的策略
next_action      建议用户执行的命令
release_gate     是否默认阻断 release
```

实现位置：`src/asteria_runtime/core/error_taxonomy.py`。

## 25.6 SchemaMigrationRegistry

实现位置：`src/asteria_runtime/core/schema_migration.py`。

用途：为 JSON/JSONL 持久化对象提供版本化迁移链。每次迁移记录审计日志。

```json
{
  "schema_name": "policy_config",
  "from_version": "0.1.0",
  "to_version": "0.2.0",
  "description": "Add feature_flags and capability_flags top-level sections."
```

## 25.7 FeatureFlag 与 CapabilityFlag

实现位置：`src/asteria_runtime/core/flag_resolver.py`。

**FeatureFlag**：控制功能是否启用，存储在 `policy_config.feature_flags`。

```json
{
  "name": "debug_export",
  "enabled": true,
  "requires": ["real_model"]
}
```

**CapabilityFlag**：描述环境能力是否具备，由 `FlagResolver` 自动推导。

```json
{
  "name": "strong_model",
  "available": true,
  "reason": "Strong model route is configured."
}
```

**FlagResolution**：解析结果，同时检查功能开关和环境能力。`active` 为 `true` 当且仅当 `enabled=true` 且所有 `requires` 能力均 `available=true`。

## 27. 状态转移约束

### 27.1 Task 状态转移

```text
backlog -> ready
ready -> in_progress
in_progress -> testing
testing -> reviewing
reviewing -> done
in_progress -> blocked
testing -> blocked
reviewing -> blocked
blocked -> ready
in_progress -> discarded
```

禁止：

- `done -> in_progress`，除非创建新任务。
- `discarded -> done`，除非恢复为新任务。

### 27.2 Run 状态转移

```text
queued -> running
running -> paused
paused -> running
running -> blocked
blocked -> running
running -> completed
running -> failed
running -> cancelled
```

## 27.3 GrayRun

文件：

```text
.asteria/gray_runs/<gray_run_id>/summary.json
```

用途：

记录真实模型小任务灰度的完整控制面证据。`GrayRun` 不是普通运行日志，而是从 gate 到实战验证之间的发布证据对象，用来回答“当前配置是否可以扩大真实任务灰度”。

核心字段：

- `gray_run_id`：本次灰度运行编号。
- `status`：`blocked`、`dry_run`、`completed` 或 `failed`。
- `preflight`：`doctor` 和 `gate-status` 的机器可读结果。
- `budgets`：灰度任务使用的迭代数、每轮任务数、research/并发策略。
- `route_expectations`：planner/coordinator 使用 strong route，worker 使用 medium route。
- `run_result`：底层 `RunCommand` 返回的运行结果。
- `evidence`：聚合 `model_calls`、`worker_results`、`task_execution_evidence`、`merge_gate_evidence` 和 `cost_report` 后得到的灰度证据。
- `next_actions`：扩大灰度、修复路由或检查阻塞点的建议。

设计约束：

- 只有 `gate-status.stage == ready_for_small_real_task_gray` 才能正式启动小任务灰度。
- dry-run 只写计划和 preflight 证据，不调用模型。
- 正式运行必须证明 strong 和 medium route 都被实际使用，否则标记为失败。
- 后续 TUI / GUI / 灰度自动化应优先读取 `GrayRun`，不要散读多个运行产物自行拼状态。

## 27.4 AgentRunGraph collaboration protocol

`agent_run_graph.json` 的 `collaboration_summary.collaboration_protocol` 用来把多 worker 协作边界落成可审计协议：

- `isolation_model`：写入 worker 使用独立 candidate workspace，防止 child worker 产物互相污染。
- `review_agent_role`：ReviewAgent 汇总 child diff、冲突和 release risk。
- `debug_agent_role`：DebugAgent 基于失败 evidence 重试或替换失败 child worker。
- `merge_gate_role`：merge gate 在 promotion 前阻断 scope 冲突和验证失败。
- `promotion_queue_role`：promotion queue 统一承接人工审批、重试、拒绝或丢弃。
