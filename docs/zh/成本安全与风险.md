# 多智能体自主开发系统 - 成本、安全与风险治理

## 1. 文档目的

本文档定义系统如何控制 API 成本、工具成本、时间成本、安全风险和工程风险。

成本控制不是简单省钱，也不是把所有工具调用次数粗暴压低，而是保证 token、风险加权工具调用和智能体迭代能转化为有效产物。默认策略应服务长期自主迭代，而不是用过早的固定次数限制压制模型充分探索。

## 2. 成本目标

系统应追求：

```text
适度调用
高产物率
低空转
可解释成本
可配置预算
超预算前可降级或停止
```

即使包年 API 调用量充足，也不能允许爆炸式占用。

## 3. 成本类型

### 3.1 模型成本

- 模型调用次数。
- 输入 token。
- 输出 token。
- 长上下文消耗。
- 强模型调用比例。

### 3.2 工具成本

- 原始 `tool_calls`：完整记录所有工具调用，用于审计和轨迹评估。
- 风险加权 `tool_budget_units`：用于预算守卫。
- 低风险探索：读取、搜索、列目录、diff，默认权重为 0。
- 低风险状态/验证：todo 状态、测试运行，默认低权重。
- 高风险动作：写入、shell、MCP、Skill、外部连接，默认高权重并继续受权限策略约束。

### 3.3 时间成本

- 单任务执行时长。
- 自动修复轮数。
- 等待用户决策时间。
- 长任务总体时长。

### 3.4 认知成本

- 用户被打扰次数。
- 用户需要阅读的决策包数量。
- 最终报告复杂度。

## 4. 默认预算策略

```yaml
goal_budget:
  active_budget_profile: autonomous_long_task
  max_model_calls: 200
  max_tool_calls: 1000  # risk-weighted emergency brake, not raw tool_calls
  max_total_minutes: 240
  max_iterations: 32
  max_repair_attempts_total: 20
  max_repair_attempts_per_task: 4
  max_replans_per_task: 3
  max_research_calls: 20
  max_user_decisions: 12
  tool_budget_weights:
    read_only: 0
    state: 1
    verification: 1
    write: 2
    shell: 2
    external: 3
    unknown: 1

budget_profiles:
  validation:
    max_model_calls: 60
    max_tool_calls: 120
    max_total_minutes: 30
  balanced:
    max_model_calls: 120
    max_tool_calls: 500
    max_total_minutes: 120
  autonomous_long_task:
    max_model_calls: 200
    max_tool_calls: 1000
    max_total_minutes: 240

context:
  model_context_window_tokens: 200000
  compaction_threshold: 0.75
  hard_stop_threshold: 0.90

model_routing:
  planning: strong
  architecture: strong
  coding: medium
  review: strong
  summarization: cheap
  classification: cheap
```

当前项目的真实模型成本策略：

- GLM coding 套餐走 `https://open.bigmodel.cn/api/coding/paas/v4`。
- 在 500 万 `glm-4.7` 免费 token 额度用完前，strong route 优先设为 `glm-4.7`。
- 免费额度耗尽、质量不足、关键 release gate 或验证发布前，切换 strong route 到 `glm-5.1` 复验。
- 即使存在免费额度，也仍然执行模型调用、token、风险加权工具预算、repair、replan、context pressure、provider health 和重复低价值循环守卫，避免低价值空转。

预算 profile 语义：

- `validation`：发布验证、CI、真实证据补齐等短闭环场景，保留严格阈值。
- `balanced`：普通开发任务，允许较充分探索，但仍较早暴露预算压力。
- `autonomous_long_task`：默认长期自主迭代场景，阈值放宽，让系统为了目标持续推进；稳定性主要依赖上下文压缩、权限边界、修复/replan 限制、provider 健康和重复低价值循环检测。

`max_tool_calls_per_goal` 只是风险加权 emergency brake。它不能被解释为智能体能力边界，也不能作为系统稳定性的主要来源。原始 `tool_calls` 只用于审计、回放和后续阈值校准。

上下文窗口治理语义：

- `estimated_input_tokens` / `estimated_output_tokens`：provider usage 或本地模型估算返回后的累计 token 成本。
- `latest_context_estimated_tokens`：最近一次模型请求在发送前按 `ChatRequest.messages` 估算的上下文占用。
- `max_context_estimated_tokens`：本 run 中观测到的最大请求上下文占用。
- `context_window_tokens`：当前策略声明的模型上下文窗口容量，默认 200000。
- `context_window_ratio`：`latest_context_estimated_tokens / context_window_tokens`。
- `context_pressure_status`：按 `compaction_threshold` 与 `hard_stop_threshold` 计算出的上下文压力状态。

这组字段让 context pressure 成为独立信号，而不是借用模型调用数、工具预算或 repair 次数。Claude Code 类产品的关键启示是：上下文窗口是运行时资源，包含指令、记忆、已读文件、工具结果、模型回复和动态挂载内容；接近上限时应 compact、隔离或裁剪，而不是用原始工具次数阻断探索。

## 5. 成本降级策略

当接近预算时，系统应按顺序执行：

1. 压缩上下文。
2. 减少 brainstorm 候选数量。
3. 停止低价值分支。
4. 降级非关键模型。
5. 合并相似任务。
6. 减少自动修复次数。
7. 请求用户批准继续。
8. 生成阶段性报告并暂停。

运行时 `/run` 在每个阶段前执行预算守卫：

- 达到 `compaction_threshold` 时自动生成一次 `ContextSnapshot`；如果压力来自 `context_window`，compact 应优先保留目标、不变量、当前任务、已修改文件、失败证据、验证结论和下一步。
- 达到 `hard_stop_threshold` 或超过预算时创建 `DecisionPoint`，暂停等待用户决定是否继续。
- replan/debug 必须受 `max_repair_attempts_per_task` 和 `max_replans_per_task` 限制，不能无限循环。
- 大量低风险 read/search 不应单独触发 hard-stop；真正触发预算压力的是模型调用、修复/replan、上下文压力、权限风险、provider 健康、重复低价值循环、写入/shell/external 等风险加权成本。

## 6. 成本异常检测

危险信号：

- 模型调用很多但没有文件产物。
- 重复读取同一大文件。
- 反复运行同一失败测试但没有修复。
- 多个 agent 做重复调研。
- 长时间 brainstorm 没有收敛。
- 上下文接近上限但未压缩。

触发后系统必须：

- 写入事件日志。
- 总结异常原因。
- 尝试压缩和收敛。
- 必要时创建 `DecisionPoint`。

## 7. 默认安全策略

```yaml
allow_network: false
allow_shell: true
allow_destructive_shell: false
allow_global_package_install: false
allow_secret_file_read: false
allow_remote_push: false
allow_deploy: false
```

需要突破默认策略时必须创建 `DecisionPoint`。

用户侧权限模式决定询问频率，但不改变 runtime 的硬护栏：

- `ask_everything`：每个操作都询问。询问卡片必须提供允许一次、允许同类或同前缀命令在本 session 内自动通过、拒绝、转为计划/只读等选项。
- `reviewed_auto`：默认模式。低风险读取、测试、格式化、受控写入可按 policy 自动通过；高风险、越界、联网、安装、预算接近上限等操作继续询问，询问选项同上。
- `auto`：完全授权的自动推进模式。模型主导工作循环可连续执行，但 runtime 仍必须拦截 protected paths、secrets、破坏性 shell、全局安装、远程 push、生产部署、预算 hard-stop、Workspace 越界和不可恢复删除；需要通过候选工作区、diff、验证、回滚或等价机制控制风险。

## 8. 安全控制

### 8.1 路径保护

默认保护：

- `.env`
- `.env.*`
- `secrets/`
- `.git/`
- 私钥文件。
- 凭证文件。
- 全局用户目录中的模型 route、账号引用、token、缓存和本机配置文件。

### 8.2 Shell 命令分级

```text
safe：读取、测试、构建、格式化
risky：安装依赖、修改大量文件、网络访问
blocked：删除大量文件、全局安装、远程推送、部署生产
```

### 8.3 网络访问

默认关闭。联网调研或外部 API 必须由策略开启，或通过用户决策点批准。

### 8.4 Secrets 检测

文件读取和报告生成前应避免泄露：

- API key。
- token。
- 私钥。
- 密码。
- cookie。

## 9. 风险分类与设计控制

### 9.1 目标偏离

风险：

智能体自主扩展需求时偏离用户真实目标。

设计控制：

- 使用 `GoalSpec`。
- 记录假设。
- 重大范围扩展进入 `DecisionPoint`。
- 评估 `scope_drift_score`。

### 9.2 成本爆炸

设计控制：

- 全局预算。
- 每命令预算。
- 每 agent 预算。
- 上下文压缩。
- 强模型路由限制。
- 超预算前暂停。
- `auto` 模式不能跳过 hard-stop；跨过 hard-stop 前必须降级、压缩、暂停或形成用户可见决策。

### 9.3 幻觉调研

设计控制：

- 来源记录。
- claim/evidence 分离。
- 无来源内容标记为推断。
- 关键结论进入验证或决策。

### 9.4 破坏代码库

设计控制：

- 当前 Project/Workspace 隔离。
- 项目产物、session、run evidence 和候选工作区默认落在当前 Workspace，不写入安装目录或全局用户目录。
- diff 审查。
- 回滚机制。
- 高风险文件保护。
- 合并前验证。

### 9.5 过度打扰用户

设计控制：

- 决策颗粒度和权限模式配置。
- 小问题自动默认。
- 只对重大分支询问。
- 记录 `minor_question_rate`。
- 允许用户在询问时把同类或同前缀低风险命令提升为本 session 自动通过。

### 9.6 不询问重大决策

设计控制：

- Decision Manager。
- 重大决策检测信号。
- 隐私/安全/预算/范围扩展默认升级。
- 即使处于 `auto` 模式，protected paths、secrets、破坏性删除、远程 push、生产部署、预算 hard-stop 和 Workspace 越界仍由 runtime 阻断或进入恢复流程。

### 9.7 自动修复循环失控

设计控制：

- 最大修复次数。
- 最大重规划次数。
- 修复前后指标对比。
- 无改善则回滚。
- 生成阻塞报告。

### 9.8 多 agent 冲突

设计控制：

- 单 agent MVP。
- 后续 Git worktree。
- 文件 ownership。
- 合并队列。
- ReviewerAgent。

### 9.9 安全和隐私

设计控制：

- 受保护路径。
- 网络权限配置。
- 外部服务决策点。
- 本地优先默认。
- secrets 检测。

## 10. 风险处理状态

每个风险应标记：

- `designed`
- `mitigated`
- `accepted`
- `blocked`
- `needs_research`

不能只写“有风险”，必须有处理状态和负责人。
