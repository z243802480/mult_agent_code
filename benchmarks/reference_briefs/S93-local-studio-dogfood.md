# S93 — 本地 Studio 主路径 dogfood

## 目的与参考

S92 已用真实 Release 运行验证摘要诚实性。下一刀回到产品主路径：从用户座位完成一项小型代码任务，记录实际卡点，再决定是否修复。承接 S74 brief 的规则：任务结果、耗时、恢复和用户叙事需用真实路径检验；不能因为某项能力存在或一次失败就扩编排。参考 Codex/Claude Code/OpenCode 的机制只用于核对「用户能看清进展、改动和验证」的目标，不复制其内部实现。

## 本刀任务

- 在隔离的本地临时工作区放一个小 CLI，使用 `benchmarks/studio_user_tasks.json#small_code_change` 的目标：增加 `--version` 并补测试。
- 从 Studio 用户入口提交 Goal，观察 Plan、执行、权限提示、文件改动、验证结果、Review/Accept。记录时间、是否需人工干预，以及 UI 文字是否与 Runtime 证据一致。
- 只使用本机已有 provider 配置；不读取或记录 key 值，不提交 key，不向 GitHub 配置 Actions Secrets。若本机模型路由无法运行，先如实记录配置卡点，再完成不依赖真模型的 UI 路径验收，不能冒充真实模型通过。
- 对第一个可复现且影响完成任务的产品卡点做最小修复；没有明确卡点则只留证据报告，不为凑切片添加功能。

## 验收与边界

- 留下脱敏的步骤记录、产物和验证结果；结论区分实跑、模拟与未运行。
- 行为改变时补针对性测试，跑该切片 smoke 与文档契约测试。
- 不扩新编排 Wave、任务批并行写、LAN 暴露或 best-of-N；G12/G13/G16/G19 仅按真实摩擦证据另行排期。
- 不碰既有未跟踪验证目录；临时任务工作区不进入提交。
