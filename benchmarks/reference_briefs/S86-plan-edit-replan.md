# S86 — G6 刀二：编辑框 → 喂模型重出计划

## 用户拍的板（2026-07-17）

G6 刀二 = **「编辑框→喂模型重出」**。**不是** harness 直改 `model_todos.json` / `task_plan.json`。

这正是路线 §G6 在 1.2.101 就给出的结论所指的形态：

> 刀二的卡点不是"不知该编哪份"（语义清楚），而是"要不要一个与 ADR-0016 张力的直编辑面"
> ——相容形态已由刀一实现。这是**产品决定**，交用户。

用户选了**相容形态的加强版**：不新增直编辑面（不写计划文件），但把**编辑手感**给到用户
——刀一只能"对第 N 步写一句意见"，刀二能**直接改计划本体**（增/删/改/重排），改完的文本
作为**意见**喂给模型，由模型自己 `todo_write` 重出计划。

## 刀一 vs 刀二：差在哪（不是重复造轮子）

| | 刀一（1.2.85·已落地） | 刀二（本刀） |
| --- | --- | --- |
| 交互 | 每步一个评论入口 | 计划本体一个编辑框（预填当前各步标题·一行一步） |
| 擅长表达 | 「第 2 步别动 schema」（**约束**） | 「删掉第 3 步、加一步、换个顺序」（**结构**） |
| 用散文表达结构改动 | 别扭（"把第 3 步删了，然后在第 1 步后面插一步…"） | 直接编辑，所见即所提 |
| 通道 | 托盘 → 既有通道 | **同一个托盘、同一条通道**（复用，不另起） |
| 谁改计划 | 模型 | 模型（**一样**） |

## 已核实的接入点（读过代码，不是猜的）

- `PlanChecklist.tsx` 渲染 `plan.items[].title`（`planModel.ts:4` `PlanItem = {id, title, state}`），
  刀一的评论入口就挂在每个 `planItem` 行上。
- `planComments.ts` = 会话作用域 store（`createSessionScopedStore`）+ `formatPlanCommentsMessage`
  合成一段散文。**刀二照这个形状写**。
- `DiffCommentTray.tsx` 已经是**多种待提交意见的共享托盘**：`buildFeedbackMessage(diff, plan)`
  按种类分节；`pickCommentChannel(isRunning, midRunSteer, hasSteer)` → `steer|send|blocked`
  （**纯函数·可单测**）；**只有通道报成功才清空**（失败不吃用户输入）。
- ⇒ **刀二 = 第三种待提交意见**。复用托盘 = 白拿通道路由 + 诚实标签 + 失败保留。
  自己另做一个提交按钮 = **把通道选择变成第二份真源**，不干。

## 诚实设计：模型不采纳时，UI 凭什么不说谎

**由构造保证，不靠自觉**：本刀**一个字节都不写计划文件**。清单永远渲染磁盘上真实的
`model_todos.json`/`task_plan.json`（`planModel.ts`）。所以：

1. 提交后编辑框关闭，**清单仍显示旧计划**——因为计划确实还没变。
2. 用户的话作为一条普通消息出现在主线程（与刀一同）。
3. 模型 `todo_write` 重排后，清单**自己**更新，`plan.updateReason`（模型自己的话）解释为什么。
4. **模型若不采纳**：清单不动，模型在回答里说原因。UI 没有任何地方声称"计划已改"。

**明确不做**：不做乐观更新（提交后先把编辑后的计划画上去）——那正是"假装计划已改"，
且模型一旦不采纳就变成永久的谎。

## 喂回去的措辞（brief 必须先定死）

```
下面是我改过的计划。请据此重新规划（用 todo_write 更新计划）后再继续；
如果其中哪一步你认为不可行或会破坏别的东西，先告诉我原因，不要默默跳过。

1. <编辑后的第 1 行>
2. <编辑后的第 2 行>
...
```

两个刻意的选择：
- **「用 todo_write 更新计划」**——点名工具，因为计划变更必须是模型的动作（ADR-0016），
  而 `todo_write` 是唯一写者（`todo_tools.py:56-58`）。
- **「不可行就先告诉我原因，不要默默跳过」**——保住模型的判断权（ADR-0016 认知归模型），
  同时挡住"静默偏离"这个最坏结局。

## 做什么

1. `studio/src/session/planRevision.ts`：会话作用域 store，**最多一份草稿**（不是列表）。
   字段 `{ text, original }`——`original` 是打开编辑框那一刻的计划文本，用于
   ①提交前判断"用户到底改没改"（没改就别提交一条废消息）②托盘里显示"改了几行"。
2. `PlanChecklist.tsx`：头部加「编辑计划」入口 → textarea 预填 `plan.items.map(i => i.title)`
   一行一步 → 保存进 store（**不是**直接提交，与刀一一致：攒进托盘）。
3. `DiffCommentTray.tsx`：第三节 + 一行摘要；`buildFeedbackMessage` 加第三段。
4. 测试：`formatPlanRevisionMessage` 措辞与边界；store 的会话隔离/上限/脏值；托盘三种意见的
   合成顺序；**Playwright** 真编辑流（编辑框是 textarea·**blur/焦点相关的东西只有真浏览器验得了**
   ——1.2.106 的教训）。

## 不做（诚实边界）

- **不写任何计划文件**（见上）。
- **不做拖拽重排**——文本行序就是顺序，拖拽是纯装饰的复杂度。
- **不做 diff 视图**（旧计划 vs 新计划）——托盘显示"改了 N 行"够了；真要看，主线程里就是用户
  自己写的文本。等真 friction 证据。
- **不动 runtime**：本刀零后端，与刀一同。

## 验收判据（DoD）

- [ ] 编辑框预填的是**当前真实计划**的各步标题（不是硬编码/占位）。
- [ ] 没改就提交 → 不产生消息（不浪费一轮）。
- [ ] 提交后**清单仍是旧计划**（UI 不说谎的核心判据）。
- [ ] 走既有通道：运行中 + steer → 标签「提交 · 下一轮生效」；运行中无 steer → blocked 且说明原因；
      空闲 → 新 turn。**这三条是复用来的，测试确认没被绕过**。
- [ ] 通道失败 → 草稿仍在（不吃用户的编辑）。
- [ ] vitest / tsc / eslint / smokes / Playwright（**新 spec 必须连跑 ≥3 遍**——1.2.106 的自产 flake 教训）。
